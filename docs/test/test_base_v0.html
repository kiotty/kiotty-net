1. 세 질문과 테스트의 층

질문 셋을 테스트의 층 셋에 대응시킨다. 한 층의 테스트는 아래 층을 신뢰한다.

질문층무엇을 두나OS / 소켓
1. 기능이 맞나 (정상, 엣지)unitcore, IoAction, TlsEngine 둘을 버퍼로 맞붙인 것, Connection 에 가짜 completion 을 넣는 것, ConnectionHost, WorkContext, config / action 조립없음. 소켓도 thread 도 시계도 안 쓴다. 같은 바이너리가 어느 OS 에서도 같은 답
1. 기능이 맞나 (흐름)integrationEventListener, Acceptor, IoLoop, Server / EventClient / StreamClient 를 loopback (127.0.0.1, Unix domain) 으로있음. 상대편은 테스트 thread 의 blocking 소켓 (라이브러리를 라이브러리로 검증하지 않는다)
2. 오용을 막나unit 과 integration 양쪽에 오용 으로 섞어 둔다잘못된 config, 닫힌 handle, 규약 위반 action, 두 번 finish, IO Thread 안의 destroy경우에 따라
3. 성능이 나오나benchmarkloopback 위의 echo, 스트리밍, broadcast, 접속 churn, TLS 오버헤드, idle CPU있음. ctest 기본 실행에서 빠지고 따로 돈다

오용 테스트의 기준은 requirement 2절 "무조건 반환값으로 알린다" 다. 오용은 (a) 코드로 돌아오거나 (b) onError(code, static message) 뒤 CLOSE 로 드러나야 하고, 어느 쪽도 아닌 "조용히 무시" 나 crash 는 실패다. C 로 막을 수 없는 것 (finish 를 영영 안 부름) 은 테스트하지 않고 사용 지침에 둔다.

  • 문장형 이름은 PascalCase 식별자로 쓴다 (3절). Catch2 의 문자열 이름이 사용자의 취향에 더 가깝지만, 그 하나로 참고 프로젝트와 다른 프레임워크를 들일 이유는 안 된다. 참고 프로젝트의 TEST(BlockPool, ReleasedBlockIsHandedOutAgain) 이 이미 그 모양이다.

  • 성능은 GoogleTest 안에 "시간을 재서 EXPECT_LT" 로 넣지 않는다. 노이즈로 깨지는 테스트는 곧 무시된다. Google Benchmark 로 수치를 내고, CI 는 기준치 (12절) 대비 회귀만 본다.
  • 내가 다른 프로젝트에서 doctest / Catch2 를 고르는 이유는 단일 헤더와 문자열 이름이다. 둘 다 여기서는 결정 요인이 아니다.

3. 이름 규칙

suite 는 모듈 (클래스) 이름 그대로, test 는 "무엇을 하면 무엇이 된다" 를 PascalCase 로 이어 쓴 문장이다. 문장은 계약을 말하고 구현을 말하지 않는다 (CallsWSARecv 가 아니라 CompletesWithLengthWhenPeerSends).

TEST(Stage, CommitAfterPrepareMakesBytesReadable)                        // unit. suite = 모듈
TEST_F(Connection, TimeoutWithPendingReadAndWriteReturnedReportsBusyAndExtends)   // fixture 이름도 모듈 그대로
TEST_P(StageCapacity, WriteOfCapacityPlusOneClosesWithBufferFull)          // 파라미터 군은 suite 에 군 이름을 붙인다
TEST(Server, ThirtyTwoClientsEchoOneThousandMessagesEach)                  // integration 도 같은 규칙
BENCHMARK(EchoRoundtrip1KiB)                                              // benchmark 는 동작 이름만
  • fixture 클래스는 테스트 namespace 안에 모듈과 같은 이름으로 둔다 (struct Connection : ::testing::Test). 실물은 kiotty::net::Connection 으로 완전 한정해 부른다. 그래야 출력이 Connection.Timeout... 으로 읽힌다.
  • 분류 (정상 / 엣지 / 오용) 는 이름에 넣지 않는다. 문장이 말해 준다. 이 문서의 표가 분류를 든다.
  • 플랫폼에 묶인 테스트는 접미어 _Iocp, _Epoll 를 suite 에 붙이고 #if 로 감싼다. 이런 테스트는 7절의 두 개뿐이어야 한다.
  • 파일 하나는 suite 하나. tests/unit/kiotty_test_stage.cpp, tests/integration/kiotty_test_server.cpp.

9. 케이스 : connection

기준은 설계 v4 9.1 ~ 9.9 와 11절이다. Connection 은 listener 를 모른다. 테스트는 Stage 에 바이트를 넣고 IoCompletion 을 손으로 만들어 dispatch 에 넣는다. 그 뒤 돌아온 IoAction, handler 기록, Stage 상태, pickWrite 가 고른 WRITE, resolve 의 payload 를 본다. step 쪽 (dispatch → apply) 과 drain 쪽 (pickWrite → resolve) 을 따로 부르므로 "어느 lane 이 거는가" 가 테스트에서 그대로 보인다.

11.1 push 의 주기와 지연 (no_delay)

push 경로 셋 (Server 의 notifyConnection, Server 의 broadcastServer, EventClient 의 notifyEventClient) 이 10 ms 간격의 작은 메시지를 모으거나 미루지 않고 바로 내보내는지 본다. 파라미터 군은 PushCadence = { 위 셋 } × transport { TCP (no_delay true, 기본), PIPE } 이다. 사이클 7 은 내부 클래스로, 사이클 8 은 C API 로 같은 케이스를 돈다.

재는 법. 보내는 쪽은 IO Thread 가 아닌 thread 하나가 64 바이트 메시지 200 개를 절대 시각 start + i × 10 ms 에 보낸다. Windows 의 기본 timer 해상도 (15.6 ms) 를 피하려고 sleep_until(deadline - 2 ms) 뒤 남은 시간은 spin 한다. 호출 직전의 steady_clock 을 t_send[i] 로 적고, 메시지 안에 i 를 넣는다. 받는 쪽은 테스트 thread 의 blocking LoopbackPeer (EventClient 의 경우 상대는 LoopbackPeer 서버) 가 64 바이트씩 recvExactly 하고, 돌아온 직후의 steady_clock 을 t_recv[i] 로 적는다. 같은 프로세스라 시계가 하나다. 첫 10 개는 warm-up 으로 버린다.

모듈테스트분류확인하는 것
PushCadenceMessagesSentEveryTenMillisecondsArriveEveryTenMilliseconds정상도착 간격 Δrecv[i] = t_recv[i] - t_recv[i-1] 의 평균이 10 ms ± 0.5 ms. 보낸 간격과의 차 |Δrecv[i] - Δsend[i]| 의 p99 가 1 ms 이하. 메시지 순서와 i 가 그대로. 둘이 한 recv 에 붙어 오거나 (Nagle, 지연 ACK) 한 바퀴 늦게 나가면 Δrecv 가 0 과 20 ms 로 갈라져 여기서 잡힌다
PushCadenceLatencyFromCallToPeerReceiveStaysBelowHumanPerception정상t_recv[i] - t_send[i] 의 p99. TCP loopback 은 1 ms 이하. PIPE 는 200 µs 이하 (Unix domain 은 TCP 스택을 거치지 않는다. 숫자는 초기 추정이고 첫 측정으로 낮춘다). 최대값은 판정하지 않고 출력만 한다 (CI runner 의 선점)
PushCadenceCadenceHoldsWhileTheSameConnectionIsWritingUserData엣지상대가 1 MiB 를 thenWrite 로 받는 중에도 push 는 그 WRITE 하나가 끝난 뒤 바로 나간다. 지연 p99 는 그 WRITE 하나의 송신 시간 이하이고 push 사이의 순서는 그대로 (설계 v4 9.6 : write lane 하나, notify 가 send 보다 먼저)
PushCadenceBroadcastToThirtyTwoClientsKeepsTheCadenceForEveryClient정상broadcast 만. 32 클라이언트 각각의 도착 간격이 위의 첫 케이스를 만족하고, 같은 i 의 클라이언트 사이 도착 차 p99 가 1 ms 이하 (TCP)

실제 망의 지연은 이 테스트의 범위 밖이다. loopback 과 Unix domain 에서 라이브러리가 더하는 지연만 본다. 두 번 연속 플래키면 plan 의 리스크 표 규칙대로 그 테스트를 고치는 commit 이 먼저다.

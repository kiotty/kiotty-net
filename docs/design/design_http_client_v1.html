HttpClient 설계 v1 (초안) : 요청 body 를 조각으로 올리기

2026-11-16 초안. v0 (design_http_client_v0.html (v0.1.0 에서 지움, git 6f3db91), C1 ~ C5 끝) 의 정할 것 8 "요청 body 를 조각으로 올리기" 를 지금 하기로 했다 (사용자 결정 2026-11-16). v0 의 요청은 body 를 앱 메모리 한 덩어리 (KiottyNetSpan) 로 받으므로 펌웨어 / 로그 파일 올리기, 만들면서 보내는 센서 데이터에 맞지 않는다. 동기 모양 (begin → write 여러 번 → finish) 을 더한다. v0 의 요청 함수는 그대로다.

v0.1.0 (2026-11-19) 에서 v0 문서 design_http_client_v0.html 를 지웠다. 이 문서의 "v0 결정 N", "v0 N절" 은 git 6f3db91 의 그 문서를 가리킨다. HttpClient 의 요청 / 응답 기본 (동기 API, 다시 연결, 응답 body 읽기, TLS) 의 지금 규칙은 docs/requirement/requirement_v0.md 11절과 docs/requirement/user_guide_http.md 2절에 있다.

0. 한눈에

/* 길이를 안다 (파일) : Content-Length */
KiottyNetHttpClientRequest upload = KiottyNet_makeHttpClientRequest(KIOTTY_NET_HTTP_METHOD_PUT, "/firmware/1.2.bin");
upload.type = KIOTTY_NET_HTTP_CONTENT_TYPE_OCTET_STREAM;
KiottyNetCode began = KiottyNet_beginHttpRequest(client, &upload, NULL, 0, file_size, 5000);   /* 머리만 보낸다 */
while (began == KIOTTY_NET_CODE_SUCCESS && has_more(file)) {
    size_t length = read_piece(file, piece, sizeof(piece));
    KiottyNetResult sent = KiottyNet_writeHttpRequestBody(client, piece, length, 5000);       /* 앱 버퍼에서 바로 */
    if (sent.code != KIOTTY_NET_CODE_SUCCESS) { break; }
}
KiottyNetHttpReply reply = KiottyNet_finishHttpRequest(client, 10000);                        /* 응답 머리까지 */
/* body 는 v0 그대로 readHttpReplyBody */

/* 길이를 모른다 (만들면서) : Transfer-Encoding: chunked */
KiottyNet_beginHttpRequest(client, &report, headers, 1, KIOTTY_NET_HTTP_BODY_LENGTH_UNKNOWN, 5000);
for (each sample batch) { KiottyNet_writeHttpRequestBody(client, batch, batch_length, 5000); }  /* write 하나 = chunk 하나 */
reply = KiottyNet_finishHttpRequest(client, 5000);                                            /* 0 chunk 를 보내고 머리까지 */
것무엇
모양동기 셋: beginHttpRequest (머리), writeHttpRequestBody (조각, 여러 번), finishHttpRequest (끝 + 응답 머리). 응답 body 는 v0 의 readHttpReplyBody
길이begin 의 body_length. 알면 Content-Length, KIOTTY_NET_HTTP_BODY_LENGTH_UNKNOWN 이면 Transfer-Encoding: chunked
메모리새 버퍼 없음. 조각은 앱 버퍼에서 바로 보내고 (TLS 는 send_capacity 씩 암호화), chunk 머리 (1a2b\r\n) 는 요청 머리 영역에 만든다
다시 보내기하지 않는다. body 는 이미 흘려보냈고 라이브러리는 그것을 갖고 있지 않다. 대신 begin 이 다시 쓰는 연결이 살아 있는지 먼저 본다
v0바뀌지 않는다. 메서드별 일곱과 sendHttpRequest 는 그대로 한 덩어리 body

1. 결정

#결정이유
1begin / write / finish 셋. 콜백 (라이브러리가 "다음 조각을 달라" 고 부르는 pull 모양) 은 두지 않는다v0 이 동기 API 하나다 (v0 결정 1). 앱은 파일 읽기 / 센서 읽기를 자기 loop 에서 하고 조각이 생길 때 write 한다. pull 콜백은 앱의 상태를 콜백 밖으로 끌어내야 해서 C 에서 쓰기 어렵다. libcurl 의 READFUNCTION 이 pull, Go 의 io.Pipe / Python http.client 의 putrequest / send / getresponse 가 push 다
2길이를 알면 Content-Length, 모를 때만 chunked. body_length 는 uint64_t, 모름은 KIOTTY_NET_HTTP_BODY_LENGTH_UNKNOWN (UINT64_MAX)chunked 요청을 받지 않는 서버와 proxy 가 아직 많다 (nginx 는 1.3.9 부터, 일부 클라우드 gateway 와 S3 의 PUT 은 길이가 있어야 한다). 파일 올리기는 길이를 안다
3write 하나 = chunk 하나 (chunked 일 때). 라이브러리는 조각을 모으거나 나누지 않는다. 길이 0 write 는 아무것도 보내지 않고 { 0, SUCCESS } (0 chunk 는 끝이므로 finish 만 보낸다)버퍼가 없어도 된다. 조각 크기는 앱이 정한다. 너무 잘게 쓰면 chunk 머리가 붙는 만큼 늘어나는 것은 앱의 선택
4Content-Length 와 실제 길이가 다르면 요청을 버린다. 선언보다 많이 쓰는 write 는 아무것도 보내지 않고 INVALID_ARGUMENT (상태는 그대로라 맞는 길이로 다시 write 할 수 있다). 선언보다 적게 쓰고 finish 하면 INVALID_ARGUMENT 이고 연결을 닫는다서버는 모자란 body 를 끝까지 기다리고 넘친 바이트는 다음 요청으로 읽는다 (요청 밀반입). 어느 쪽도 보내면 안 된다. 모자란 채로는 그 연결을 다시 쓸 수 없다
5다시 보내기는 없다. begin 은 다시 쓰는 연결이 살아 있는지 본다. 연결이 열려 있으면 peek 로 EOF / reset 을 확인하고 닫혀 있으면 머리를 보내기 전에 다시 연결한다v0 의 재시도 (멱등 메서드 한 번) 는 body 를 갖고 있어서 된다. 여기서는 갖고 있지 않다. 서버가 idle 연결을 닫은 가장 흔한 경우는 머리 전에 알 수 있다. 머리를 보낸 뒤에 끊기면 앱이 처음부터 다시 한다
6올리는 중에는 그 client 의 다른 요청이 올리기를 끝낸다. begin 뒤 finish 전에 요청 / begin 을 부르면 연결을 닫고 (올리던 요청은 버려진다) 새 요청을 보낸다. readHttpReplyBody 는 INVALID_ARGUMENTv0 결정 13 ("다 읽지 않은 body 뒤의 요청은 연결을 닫고 다시 연다") 과 같은 규칙. 서버가 반쯤 받은 요청을 끝낼 길은 연결을 닫는 것뿐이다
7timeout 은 호출마다. begin 은 (다시) 연결 + 머리 송신, write 는 그 조각 송신, finish 는 끝 표시 송신 + 응답 머리 수신v0 3절과 같다. 큰 파일은 write 마다 timeout 이 새로 시작해야 한다
8BUSY 와 close 는 v0 그대로. 셋 모두 플래그를 잡는다. closeHttpClient 는 걸린 write / finish 를 CLOSED 로 깨우고 올리기는 버려진다새 규칙이 없다
9Content-Type 과 헤더 규칙은 v0 그대로. request 의 type 으로 Content-Type, body 는 비어 있어야 한다 (아니면 INVALID_ARGUMENT). 공통 헤더와 요청 헤더 배열도 v0 과 같다. 텍스트 type 이어도 조각의 UTF-8 은 보지 않는다글자 하나가 write 둘에 나뉠 수 있다 (응답 read 와 같은 이유, v0 6절)

2. 흐름과 상태

IDLE ──begin──▶ SENDING ──write*──▶ SENDING ──finish──▶ (응답 머리) ──▶ IDLE + 응답 body 읽기 (v0)
                   │                                     │
                   └── 오류 / close / 다른 요청 ─────────┴──▶ 연결 닫음, IDLE
상태에서부른 것결과
IDLEwrite / finishINVALID_ARGUMENT (올리는 중이 아님)
SENDINGwrite조각을 보낸다. Content-Length 면 남은 길이 안이어야 한다
SENDINGfinishchunked 면 0\r\n\r\n, Content-Length 면 다 썼는지 확인. 응답 머리를 받아 v0 의 Reply 로 돌려준다
SENDING요청 / begin연결을 닫고 새 요청 (결정 6)
SENDINGreadHttpReplyBodyINVALID_ARGUMENT
SENDINGdisconnect / close / connect연결을 닫고 IDLE

begin 은 v0 의 요청처럼 남은 응답 body 를 버린다 (다 읽지 않았으면 연결을 닫고 다시 연다).

3. 보내는 바이트

길이begin 이 보내는 머리writefinish
앎 (N)v0 의 머리 + Content-Length: N (N = 0 이어도). Content-Type 은 N > 0 일 때바이트 그대로보내는 것 없음. 쓴 합이 N 이어야 한다
모름v0 의 머리 + Transfer-Encoding: chunked + Content-Type<hex 길이>\r\n + 바이트 + \r\n (조각 하나 = chunk 하나)0\r\n\r\n (trailer 없음)
  • Transfer-Encoding 은 v0 처럼 라이브러리가 쓰는 헤더다. 앱의 헤더 배열에 있으면 INVALID_ARGUMENT.
  • HTTP/1.1 만 보낸다. chunked 는 HTTP/1.0 서버가 읽지 못하지만 우리는 요청을 언제나 1.1 로 보낸다 (v0).
  • write 의 length 는 KiottyNetResult.bytes 에 들어가야 하므로 최대 INT32_MAX. 넘으면 INVALID_ARGUMENT.

4. 오류와 연결

호출code연결
beginv0 요청의 검사 code 셋 (INVALID_ARGUMENT, REQUEST_TOO_LARGE, TABLE_FULL), request.body 가 비어 있지 않음 → INVALID_ARGUMENT. (다시) 연결 실패, 머리 송신 실패검사 실패는 아무것도 바꾸지 않는다. 송신 실패는 닫는다
writeINVALID_ARGUMENT (올리는 중이 아님, NULL, 선언보다 많음), TIMEOUT, PEER_CLOSED, SOCKET_ERROR, CLOSED, TLS인자 오류는 그대로, 송신 오류는 닫고 IDLE
finishv0 Reply 의 code 들. 선언보다 적게 씀 → INVALID_ARGUMENTv0 과 같다. 적게 씀은 닫는다

서버가 body 를 다 받기 전에 응답하는 경우 (401, 413, 507 을 보내고 닫음) 는 write 가 PEER_CLOSED / SOCKET_ERROR 로 끝난다. 이때 이미 와 있는 응답을 앱에 보여줄지는 정할 것 1.

6. 장면별 흐름

6.1 펌웨어 / 로그 파일 올리기

size = 파일 크기 begin(client, { PUT, "/devices/7/logs/2026-11-16.log", OCTET_STREAM }, [], size, 5000) loop : n = fread(piece, 16384) → write(client, piece, n, 10000) (파일 끝까지) reply = finish(client, 30000) status 201 이면 끝. 응답 body 는 readBody write 가 PEER_CLOSED → finish 를 부르면 서버가 먼저 보낸 응답 (413 등) 이 보인다 (정할 것 1). 앱이 처음부터 다시 한 줄로: reply = sendHttpFile(client, { PUT, "/devices/7/logs/2026-11-16.log", OCTET_STREAM }, [], "/var/log/device.log", 30000)

6.2 측정하면서 보내기

begin(client, { POST, "/v1/samples", NDJSON }, [], UNKNOWN, 5000) 매 100 ms: write(client, 줄 하나 이상, 1000) (chunk 하나) 측정 끝 : reply = finish(client, 5000)

6.3 다른 thread 에서 취소

upload thread : begin, write ... (네트워크가 느려 걸려 있음) UI thread : closeHttpClient(client) → 걸린 write 가 CLOSED. 올리기는 버려지고 연결은 닫혔다 upload thread : 다시 하려면 begin 부터

7. 안에서

  • 상태 하나 더. HttpClient 에 올리기 상태 (IDLE / SENDING, 방식 LENGTH / CHUNKED, 남은 길이) 를 둔다. v0 의 응답 body 상태와 따로다.
  • begin 은 v0 의 writeRequestHead 를 쓴다. RequestHead 에 "body 방식" 을 더해 Content-Length 를 body_length 로 쓰거나 Transfer-Encoding: chunked 를 쓴다 (C1 의 조립기를 넓힌다).
  • chunk 머리 는 요청 머리 영역 (머리 버퍼의 뒤 반) 에 hex\r\n 를 만들어 보낸다. 데이터는 앱 버퍼에서 바로, 끝의 \r\n 은 상수. 송신 세 번을 한 번으로 묶는 일 (writev) 은 base 의 write 가 조각 목록을 받는지 보고 정한다 (notify 는 조각 목록을 받는다).
  • 살아 있는지 보기 (결정 5) 는 ConnectionStream::connected() 의 peek 를 쓴다. EOF / reset 이면 닫고 다시 연결한다. 수신 Stage 에 바이트가 남아 있으면 (서버가 요청 전에 보낸 것) 그것은 프로토콜 오류이므로 닫고 다시 연결한다.
  • finish 는 v0 의 receiveReply 를 그대로 부른다 (1xx 건너뛰기, framing, body reader).

U2 구현 (2026-11-18): 살아 있는지 보기는 connected() 대신 ConnectionStream::peek 를 1 ms 로 부른다 (ensureIdleConnected). connected() 는 소켓에 바이트가 있으면 열린 것으로 보므로 TLS 의 close_notify 를 놓치고, 서버의 work stream 이 같은 함수를 쓰므로 뜻을 바꾸지 않았다. 수신 Stage 에 바이트가 있음, peek 가 바이트를 받음, EOF / reset 이면 닫고 다시 연결한다. 시간 끝 (TIMEOUT) 만 살아 있음이다. TLS 1.3 의 NewSessionTicket 은 평문이 아니므로 살아 있음으로 남는다. 다시 쓰는 연결의 begin 은 1 ms 늦어진다.

U2 구현 (2026-11-18), 정할 것 1: write 의 송신이 PEER_CLOSED / SOCKET_ERROR 면 연결을 닫지 않고 올리기 상태를 REFUSED 로 둔다 (그 뒤 write 는 INVALID_ARGUMENT). finish 는 끝 표시를 보내지 않고 응답 머리를 읽는다. 받으면 그 응답을 돌려주고 연결은 응답 body 뒤에 닫는다 (Persistence::CLOSE). 와 있는 것이 없으면 읽기의 code 를 돌려준다 (PEER_CLOSED / SOCKET_ERROR. write 의 code 를 따로 담지 않았다). TIMEOUT / CLOSED 는 U1 처럼 연결을 닫고 IDLE. TLS 에서 송신이 깨진 뒤에는 보내지 못한 암호문이 읽기를 막을 수 있어 응답을 보이지 못할 수 있다.

U2 확인 (2026-11-18): Windows 는 RST 를 받으면 앱이 아직 읽지 않은 수신 바이트를 버리므로, 올리는 중 서버가 먼저 보낸 응답이 커널에 있는 채로 RST 가 오면 finish 가 SOCKET_ERROR 다 (Linux 는 응답을 돌려준다). 설명은 docs/learning/early-reply-and-rst.html. 고치는 길: write 가 상대 바이트를 보면 멈추고 수신 Stage 로 옮긴 뒤 KIOTTY_NET_CODE_DATA_ARRIVED_WHILE_WRITING 을 돌려준다 (base, 새 설계 문서). 올리기에서는 A3 사이클이 그 위에서 1xx 를 버리고 최종 응답이면 멈춘다.

U3 구현 (2026-11-18): sendHttpFile 은 파일을 한 번에 보내지 않고 send_capacity (0 이면 16 KiB) 조각마다 base 의 ConnectionStream::writeFile(path, offset, length) 을 부른다 (사용자 결정). writeFile 은 시작할 때만 상대 바이트를 보므로 (A1 결정) 조각의 경계가 확인 간격이 되고, 조각 사이에 1xx 는 버리고 최종 응답이면 멈춰 그 응답을 돌려준다 (Windows 에서도). 복사 버퍼는 없고 sendfile / TransmitFile 을 그대로 쓴다. 조각마다 파일을 다시 연다. 파일을 열 수 없으면 NOT_FOUND, timeout 은 (다시) 연결부터 응답 머리까지 하나다. C++ 은 5절의 begin / write / finish 와 sendFile(request[, headers], path, timeout).

8. 정할 것

  1. 서버가 먼저 응답하고 닫을 때. 닫음 (2026-11-16): 보여준다. write 가 PEER_CLOSED / SOCKET_ERROR 로 끝난 뒤 finish 를 부르면 이미 수신 쪽에 와 있는 응답 머리를 읽어 돌려준다 (401 이면 토큰, 413 이면 크기를 앱이 안다). 와 있는 것이 없으면 write 의 code.
  2. Expect: 100-continue. 닫음 (2026-11-16): 지금은 두지 않는다. 모든 올리기가 왕복 한 번 (보내지 않는 서버 / proxy 면 기다림 시간) 을 더 기다리고, begin 에 "100 기다림 / 최종 응답 먼저 / 시간 끝" 상태가 생긴다. 서버가 먼저 거절하는 경우는 정할 것 1 로 이유를 알 수 있다. 느린 회선의 큰 올리기에서 필요해지면 begin 에 선택 인자로 더한다.
  3. 파일 올리기 도우미. 닫음 (2026-11-16): 둔다. KiottyNet_sendHttpFile(client, request, headers, header_count, path, timeout): 라이브러리가 파일 크기로 Content-Length 를 쓰고 send_capacity 조각으로 읽어 보낸 뒤 응답 머리까지 받는다 (base 의 writeStreamFile). 파일을 열 수 없으면 NOT_FOUND.
  4. C++ RAII. 닫음 (2026-11-16): 두지 않는다. 다음 요청 / close 가 이미 버린다.

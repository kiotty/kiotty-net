상대에 따른 설정과 StreamClient 취소 v0

2026-11-19 확정 (정할 것 넷 닫음). kiotty-net 을 실제 DICOM 라이브러리에 적용하면서 들어온 변경 요청 둘을 다룬다. (1) 연결 시도와 송신에 관한 다섯 설정은 Endpoint 가 아니라 연결할 상대에 따라 정해진다. (2) 다른 thread 에서 막혀 있는 동기 read / write 를 취소하고 싶다. 사용자와 정한 것 (2026-11-19): 다섯 설정은 KiottyNetAddress 로 옮긴다. 취소는 StreamClient 에만 두고, 취소한 뒤에도 연결은 살려 두며, connect 도 깨운다. 서버 work stream 에는 두지 않는다. 사이클 D1 (설정), D2 (취소).

0. 한눈에

/* create: 메모리만 */
KiottyNetClientConfiguration configuration;
KiottyNet_initializeClientConfiguration(&configuration);
KiottyNet_configureClientBuffer(&configuration, 64 * 1024, 64 * 1024, 0);
KiottyNetStreamClientResult made = KiottyNet_createStreamClient(context, &configuration);

/* connect: 어디로, 어떻게 */
KiottyNetAddress pacs;
KiottyNet_initializeTcpAddress(&pacs, "10.0.0.5", 104);
KiottyNet_setAddressConnectTimeout(&pacs, 3000);
KiottyNet_setAddressRetry(&pacs, 5, 1000);                 /* 시도 횟수, 시도 간격 */
KiottyNet_setAddressSendTimeout(&pacs, 30000);
KiottyNet_connectStreamClient(made.handle, &pacs, NULL);

/* 다른 thread: 막혀 있는 read / write / connect 를 깨운다. 연결은 그대로 */
KiottyNet_cancelStreamClient(made.handle);

/* 막혀 있던 thread */
KiottyNetResult got = KiottyNet_readStreamClient(made.handle, buffer, sizeof(buffer), 0);
if (got.code == KIOTTY_NET_CODE_CANCELLED) {
    /* 같은 연결로 C-CANCEL 을 보내고 다시 read 하거나, disconnect */
}
것무엇
create 의 설정*MemorySize 가 읽는 값만: 서버는 max_clients 와 세 capacity, 클라이언트는 세 capacity
address"어디로" (transport, host, port) 에 "어떻게" (connect_timeout_milliseconds, max_trial, trial_interval_milliseconds, no_delay, send_timeout_milliseconds) 가 붙는다
취소KiottyNet_cancelStreamClient(client), code KIOTTY_NET_CODE_CANCELLED (enum 맨 끝). 연결은 닫지 않는다
바뀌지 않는 것connect / run 의 모양 (address, tls_or_null). HttpClient 의 close (지금처럼 CLOSED). 서버 / EventClient 의 close / await. 이미 있는 code 의 번호

1. 결정

#결정이유
1다섯 설정을 KiottyNetClientConfiguration / KiottyNetServerConfiguration 에서 빼서 KiottyNetAddress 에 넣는다DICOM 에서는 한 SCU 가 여러 PACS 에 붙고, PACS 마다 응답 속도, 재시도 정책, Nagle 의 득실이 다르다. 상대에 따라 정해지는 값은 상대를 정하는 자리 (connect / run) 에서 받는 것이 맞다. connect / run 은 이미 address 를 받으므로 함수 모양이 바뀌지 않는다
2create 의 설정은 메모리 크기만 남긴다. 이름은 그대로 (KiottyNetClientConfiguration, KiottyNetServerConfiguration). 세 번째 설정 구조체를 만들지 않는다"create 에 주는 것은 메모리를 정하는 값" 이라는 규칙 하나로 설명된다. 특수한 이름의 구조체가 하나 더 생기면 앱이 어느 것을 어디에 주는지 헷갈린다
3메모리 크기는 createContext 가 아니라 지금처럼 create* 에서 받는다Context 는 process 에 하나다. 한 process 에 SCP (서버) 와 SCU (클라이언트) 가 같이 있고 capacity 가 서로 다르다
4취소는 StreamClient 에만 둔다. 서버 work stream 에는 두지 않는다사용자 결정 (2026-11-19). 서버는 이미 close 가 있고, 연결마다 깨움 handle 을 두는 값을 지금 낼 필요가 없다
5취소는 연결을 닫지 않는다. read / write 는 { 그때까지 읽거나 보낸 길이, CANCELLED }DICOM 에서 오래 걸리는 C-MOVE / C-FIND 를 기다리다 취소하면 같은 association 으로 C-CANCEL 을 보내야 한다. 끊으면 상대는 association 이 비정상으로 끝난 것으로 본다
6취소는 connect (연결 시도, 시도 사이의 쉼, TLS handshake) 도 깨운다. 이때는 연결이 아직 없으므로 연결되지 않은 채 CANCELLED사용자 결정. 꺼진 PACS 에 5 회 × 3 초를 기다리는 동안 앱이 멈출 수 있어야 한다. 반쯤 된 TLS handshake 는 이어 쓸 수 없다
7새 code KIOTTY_NET_CODE_CANCELLED 는 KiottyNetCode 의 맨 끝 (DATA_ARRIVED_WHILE_WRITING 뒤) 에 붙인다이미 있는 번호를 바꾸지 않는다. CLOSED 는 "닫혀서 끝남" 이므로 "연결은 그대로, 이 호출만 끝남" 과 갈라야 앱이 다음 동작을 고를 수 있다
8깨움은 이미 있는 StopSignal 을 쓴다. 새 운영체제 자원이 없다StreamClient 는 _stop 을 가지고 있고, 소켓 backend 의 기다림 (Windows waitReady, POSIX waitFor) 은 소켓과 stop handle 을 한 번에 기다린다. A1 에서 write 의 기다림도 IN | OUT | stop 이 되었다. Windows / Linux 의 차이는 이미 backend 가 푼다 (Windows 는 자기에게 bind 한 UDP 소켓, POSIX 는 pipe)

2. D1 상대에 따른 설정

2.1 두 묶음

2.2 헤더 초안 (C)

  • initialize*Address 가 지금의 설정 기본값을 그대로 채운다 (연결 시간, 시도 횟수, 간격, NO_DELAY_ON, 송신 시간). 앱이 기본값만 쓰고 있었다면 동작은 같다.
  • 지금의 KiottyNet_configureClientConnectTimeout / configureClientRetry / configureClientNoDelay / configureClientSendTimeout, configureServerNoDelay / configureServerSendTimeout 은 없앤다. 같은 값의 setter 가 address 쪽에 생긴다. 검사 (max_trial == 0 이면 INVALID_ARGUMENT 등) 는 그대로 옮긴다.
  • setter 이름은 지금의 configure* 와 갈라 setAddress* 로 한다. address 는 "설정 구조체" 가 아니라 상대를 나타내는 값이라는 것을 이름이 보이게 한다. (정할 것 4)

2.3 address 의 initialization_mark

지금 address 에는 표시가 없어서 KiottyNetAddress address{} 뒤에 필드를 직접 채울 수 있다. 새 필드가 0 이면 뜻이 바뀐다: connect_timeout 0 과 send_timeout 0 은 "끝없이" (timeout 0 규칙), no_delay 0 은 OFF. 직접 채운 address 가 조용히 끝없이 기다리는 것을 막으려고, 설정 구조체처럼 initialization_mark 를 두고 connect / run 은 initialize*Address 를 거치지 않은 address 를 INVALID_ARGUMENT 로 거절한다. (정할 것 2)

직접 채우는 곳은 지금 테스트 다섯 파일이다 (kiotty_test_acceptor, kiotty_test_active_socket, kiotty_test_connection_stream, kiotty_test_connect_with_retry, kiotty_test_endpoint). D1 에서 initializeTcpAddress 로 바꾼다.

2.4 서버의 address

필드서버 run 에서
no_delay듣는 소켓과 받아들인 모든 연결에 (지금 Server::listen 이 설정에서 읽던 것)
send_timeout_milliseconds받아들인 연결마다 ConnectionConfiguration 으로 넘겨 Connection::initialize 가 송신 흐름에 건다 (지금도 연결마다 limits 를 넘기므로 자리만 바뀐다). ConnectionLimits 는 메모리 셋만 남는다
connect_timeout_milliseconds, max_trial, trial_interval_milliseconds읽지 않는다

D1 구현 (2026-11-19): 송신 시간은 ConnectionConfiguration 의 새 칸이 아니라 run 마다 만드는 LoopParts 의 send_timeout_milliseconds 로 넘긴다. IoLoop 가 받아들인 연결의 ConnectionLimits 에 그 값을 넣고, ConnectionHost::acquire 는 메모리 셋만 create 때의 값으로 채운다. ConnectionLimits 의 모양은 그대로이고 ConnectionHost 에 공개 메서드를 더하지 않는다 (수칙의 PUBLIC). EventClient 도 같은 길이다. Server / EventClient 의 _configuration 멤버는 읽는 곳이 없어져 뺐다.

2026-11-19 의 대화에서는 "서버 address 의 connect 값이 0 이 아니면 INVALID_ARGUMENT" 로 적었다. 그런데 initializeTcpAddress 가 클라이언트 기본값 (0 이 아님) 을 채우므로, 그 규칙이면 기본 address 로 서버를 run 할 수 없다. 이 문서는 "서버는 그 셋을 읽지 않는다" 로 고쳐 제안한다. (정할 것 1)

2.5 위 층

  • HttpClient 는 이미 HttpClientTarget::address 에 address 를 통째로 가지고 다시 연결할 때 쓴다. 새 필드도 함께 따라간다. 바꿀 것 없음.
  • HTTP 서버, WebSocket 서버 / 클라이언트, statemachine 의 run / connect 는 address 를 base 에 그대로 넘긴다. 함수 모양은 바뀌지 않는다.
  • connectWithRetry 는 (configuration, address, …) 에서 (address, …) 로. 다섯 값 중 연결에 쓰는 넷을 address 에서 읽는다.
  • EventClient 의 limitsOf 와 StreamClient 의 handshake 시간 (지금 _configuration.connect_timeout_milliseconds) 도 address 에서 읽는다. StreamClient 는 address 를 새 멤버로 두지 않는다. 다시 연결 (reconnect) 은 지금처럼 address 를 인자로 받는다.

2.6 C++

KiottyNetClientConfiguration configuration;
KiottyNet_ClientConfigurationBuilder(configuration).bufferCapacity(64 * 1024, 64 * 1024, 0);

KiottyNetAddress pacs;
KiottyNet_AddressBuilder(pacs, "10.0.0.5", 104).connectTimeout(3000).retry(5, 1000).sendTimeout(30000);

ClientConfigurationBuilder 는 bufferCapacity 만, ServerConfigurationBuilder 는 maxClients / bufferCapacity 만 남는다. connectTimeout / retry / noDelay / sendTimeout 은 address builder 로 옮긴다. 이름은 지금 builder 들과 같은 꼴로 KiottyNet_AddressBuilder, 파이프는 KiottyNet_AddressBuilder::pipe(address, name). (정할 것 4)

2.7 호환

설정 구조체와 address 의 배치가 바뀌므로 ABI 가 깨진다. 앱은 다시 컴파일해야 하고, 없어진 configure* 함수를 부르던 코드는 컴파일 오류로 드러난다 (조용히 다르게 동작하지 않는다). 단일 헤더를 다시 만든다.

3. D2 StreamClient 취소

3.1 헤더 초안

KIOTTY_NET_API KiottyNetCode KiottyNet_cancelStreamClient(KiottyNetStreamClientHandle client);
/* KiottyNetCode 맨 끝 */ KIOTTY_NET_CODE_CANCELLED

/* C++ */
KiottyNetCode KiottyNet_StreamClient::cancel();

돌려주는 값: SUCCESS. client 가 NULL 이면 INVALID_ARGUMENT. 연결되어 있지 않아도 SUCCESS (다음 connect 가 받는다, 3.3).

3.2 막혀 있던 호출이 받는 것

막혀 있던 호출돌려받는 것연결
read{ 0, CANCELLED }. read 는 바이트를 하나라도 받으면 바로 돌아오므로, 기다리는 중에는 받은 것이 없다. TLS 의 반쯤 온 레코드는 TLS 수신 Stage 에 남아 다음 read 가 잇는다그대로
write (평문){ 보낸 길이, CANCELLED }. 앱은 data + bytes 부터 이어 보낼 수 있다그대로
write (TLS){ 받아들인 길이, CANCELLED }. 레코드로 만들어진 조각은 받아들인 것으로 센다 (A1 의 DATA_ARRIVED_WHILE_WRITING 과 같은 셈). 그 조각의 보내지 못한 암호문은 송신 쪽 Stage 에 남고, 다음 read / write 가 먼저 보낸다. 레코드를 반만 보낸 채 다른 레코드를 보내면 TLS 가 깨지기 때문이다그대로
connect (시도, 시도 사이 쉼, TLS handshake)CANCELLED없음. connect 는 시작할 때 이전 연결을 이미 닫는다. 반쯤 된 시도와 handshake 는 닫는다

write 가 CANCELLED 로 끝나면 앱 프로토콜의 메시지가 중간에서 끊겨 있을 수 있다. 같은 연결을 계속 쓰려면 앱이 메시지 경계를 지킨다: 남은 바이트를 보내 메시지를 끝내거나, 끊는다 (4.2).

3.3 막혀 있지 않을 때의 취소

cancel 은 다른 thread 에서 오므로 "막히기 직전" 과 "막힌 뒤" 를 앱이 가를 수 없다. 그래서 cancel 은 받아질 때까지 남는다.

때동작
호출이 막혀 있음그 호출이 깨어 CANCELLED 를 돌려주고 cancel 을 받는다 (지운다)
호출이 없음다음 read / write / connect 가 시작하자마자 { 0, CANCELLED } 를 돌려주고 cancel 을 받는다. 수신 Stage 에 바이트가 있어도 cancel 이 먼저다 (바이트는 남아 그 다음 read 가 준다)
cancel 이 여러 번받을 때 한 번으로 친다 (StopSignal 의 raised / accepted 셈 그대로)
호출이 cancel 과 거의 같이 성공으로 끝남그 호출은 성공을 돌려주고, cancel 은 남아 다음 호출이 받는다
disconnect남은 cancel 을 지운다 (정할 것 3). 연결을 버리는 앱은 그 cancel 이 다음 연결에 걸리기를 바라지 않는다

3.4 thread 규칙

  • KiottyNet_cancelStreamClient 는 create 뒤, destroy 전이면 어느 thread 에서나 부를 수 있다. destroy 와 겹치면 안 된다 (앱의 몫, 다른 handle 함수와 같다).
  • read / write / connect / disconnect 는 지금처럼 한 번에 한 thread 에서만. cancel 은 그 thread 를 깨우기만 한다.
  • cancel 은 막히지 않는다 (stop handle 에 1 바이트를 보낼 뿐이다).

3.5 HttpClient 와의 관계

HttpClient 의 close 도 같은 StopSignal 로 걸린 write 를 깨운다 (U2). HttpClient 는 base 의 StreamClient 를 안에서 쓰지만 readStreamClient / writeStreamClient usecases 를 거치지 않고, 깨어나면 stop 을 받아 연결을 닫고 CLOSED 를 돌려준다 (settleStop). D2 는 base 의 StreamClient usecases 에서만 CLOSED 를 CANCELLED 로 바꾸므로 HttpClient 의 공개 동작은 바뀌지 않는다. HttpClient 에는 "연결을 살리는 취소" 를 두지 않는다 (요청 중간에 끊긴 HTTP/1.1 연결은 다시 쓸 수 없다).

4. 장면

4.1 오래 걸리는 C-MOVE 를 취소 (read)

SCU thread : write(C-MOVE-RQ) → read(..., 0) (PACS 가 수천 장을 옮기는 동안 막힘) UI thread : cancelStreamClient(client) SCU thread : read → { 0, CANCELLED } write(C-CANCEL-RQ) → read(C-MOVE-RSP, status Cancel) → 다음 작업 (association 그대로)

4.2 큰 C-STORE 를 보내는 중 취소 (write)

SCU thread : write(P-DATA-TF, 16 MiB, 60000) (느린 회선에서 막힘) UI thread : cancelStreamClient(client) SCU thread : write → { 5 242 880, CANCELLED } PDU 가 반만 나갔다. 둘 중 하나: a. 나머지 (data + 5 242 880 부터) 를 보내 PDU 를 끝낸 뒤 A-ABORT b. disconnect (상대는 연결 끊김으로 본다)

4.3 꺼진 PACS 에 연결 시도 중 취소 (connect)

address : setAddressConnectTimeout(&pacs, 3000), setAddressRetry(&pacs, 5, 1000) (최대 약 19 초) SCU thread : connectStreamClient(client, &pacs, NULL) (두 번째 시도 중) UI thread : cancelStreamClient(client) SCU thread : connect → CANCELLED (연결 없음). 다른 PACS 로 connect 하면 바로 시작한다 (cancel 은 받아졌다)

5. 안에서

  • 깨움. 이미 된다. 소켓 backend 의 기다림은 시작할 때 isStopped(stop) 를 보고, 기다리는 동안 stop handle 을 같이 본다. 둘 다 SocketCode::CANCELLED 를 돌려주고 toNetCode 가 KIOTTY_NET_CODE_CLOSED 로 바꾼다. connectWithRetry 의 쉼도 stop 을 보고 CLOSED 를 돌려준다. StreamClient 의 소켓은 ActiveSocket::open(transport, &_stop) 로 만들어져 이미 stop 을 가진다.
  • code 바꾸기. toNetCode 는 바꾸지 않는다 (HttpClient 와 서버의 이벤트 경로가 CLOSED 에 기댄다). 대신 base 의 StreamClient usecases (readStreamClient, writeStreamClient, connect) 가 결과 code 가 CLOSED 이고 _stop.accept() 가 참이면 CANCELLED 로 돌려준다. StreamClient 의 ConnectionStream 이 CLOSED 를 내는 길은 stop 뿐이므로 다른 뜻을 덮지 않는다.
  • 시작 확인. 세 usecases 는 시작할 때 _stop.accept() 가 참이면 기다리지 않고 { 0, CANCELLED } (3.3). 확인 뒤, 기다림에 들어가기 전에 온 cancel 은 backend 의 시작 검사 (isStopped) 가 잡고, 기다리는 동안 온 cancel 은 stop handle 이 깨운다.
  • 연결 유지. read / write 의 CANCELLED 에서는 disconnect 를 부르지 않는다. connect 의 CANCELLED 는 지금의 실패 경로대로 disconnect.
  • disconnect. StreamClient::disconnect 가 끝에 _stop.accept() 로 남은 cancel 을 지운다. reset (destroy) 의 raise → disconnect 순서는 그대로 둔다.
  • 새 메모리 / 운영체제 자원 없음. StopSignal 은 StreamClient 마다 이미 하나 있다.

6. 정할 것

모두 닫음 (2026-11-19, 사용자).

  1. 서버 address 의 connect 값. 닫음: 읽지 않는다 (2.4).
  2. address 의 initialization_mark. 닫음: 둔다 (2.3). initialize*Address 는 host / port (파이프는 이름) 를 반드시 받고, 연결 시간 / 재시도 / 송신 시간 / no_delay 는 기본값으로 채운다. 바꾸려면 setAddress*.
  3. disconnect 가 남은 cancel 을 지우는가. 닫음: 지운다 (3.3).
  4. 이름. 닫음: setter KiottyNet_setAddress*, C++ KiottyNet_AddressBuilder, code KIOTTY_NET_CODE_CANCELLED, 이 문서 design_peer_settings_and_cancel_v0.html, 사이클 D1 / D2.

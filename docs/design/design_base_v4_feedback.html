1. IoAction 은 submit 의 단위다 동의

v3 의 IoAction 은 "콜백이 돌려준 뜻" 이었고, OS 에 무엇을 걸지는 SUBMIT 이 Connection 상태를 읽어 따로 정했다. 그래서 두 가지 길이 생겼다 (action 과 상태). 지적대로 IoAction 하나가 submit 까지 가고, 그 결과가 IoCompletion 으로 돌아오는 한 길로 고친다. 콜백의 return 은 그 action 의 "handler 가 준 절반" 이고, dispatch 가 "listener 에 줄 절반" 을 채운다.

IoCompletion ──▶ on* hook ──▶ IoAction (handler 절반) ──▶ resolve (listener 절반 채움) ──▶ submit ──▶ OS ──▶ IoCompletion ▲ └── 다음 바퀴

1.1 IoAction

enum class IoActionKind : uint8_t { NONE, HOLD, READ, READ_UNTIL, WRITE, START_WORK, CLOSE };
enum class IoPurpose    : uint8_t { USER, HANDSHAKE, NOTIFY, CONTROL };     // 완료를 누구에게 돌려주나. CONTROL 은 TLS 의 KeyUpdate 답장 (2.1)

struct IoAction
{
    IoActionKind kind;
    IoPurpose    purpose;
    uint32_t     timeout_ms;                                                // 0 이면 deadline 없음

    union                                                                   // handler 가 준 절반. KiottyNetConnectionAction 과 같은 모양
    {
        struct { size_t exact; }                                      read;
        struct { char delimiter[4]; uint8_t length; size_t max; }     read_until;
        struct { KiottyNetSpan data; }                                write;   // 사용자 메모리. resolve 가 Stage 로 복사한 뒤에는 보지 않는다
        struct { KiottyNetCode reason; }                              close;
    } as;

    void*  io_buffer;                                                       // listener 에 줄 절반. resolve 가 채운다
    size_t io_length;                                                       //   READ  : 받을 자리 (Stage::Provider::prepare 의 포인터와 writable)
                                                                            //   WRITE : 보낼 구간 (Stage 안의 포인터와 길이). Segment 타입은 없다
    static IoAction from(const KiottyNetConnectionAction& action);         // base.cpp 의 번역. purpose = USER, io_* = 0
};
  • Segment 는 없다. 보낼 구간은 io_buffer / io_length 다. KiottyNetSpan 을 안 쓴 이유는 그 struct 의 data 가 const 라 READ 의 받을 자리에 못 쓰기 때문이다. 필드 둘로 둔다.
  • listener 가 보는 것은 kind, io_buffer, io_length 셋이다. EventListener::submit(Holder<IoEvent>&, SocketHandle, const IoAction&) 하나로 줄어든다 (v1 2.4 의 "셋 또는 하나" 가 여기서 하나로 답이 난다). READ / READ_UNTIL 은 receive, WRITE 는 send, 나머지 kind 는 listener 에 가지 않는다.
  • IoEvent 가 action 을 기억한다. submit 할 때 kind 와 purpose 를 event 에 적어 두고, 완료가 그것을 싣고 돌아온다. 그래서 IoCompletion 에 purpose 가 있다.

1.2 IoCompletion : OS 가 만드는 넷 + IoLoop 가 만드는 둘

"completion 을 받아 처리하는 것은 모두 on*" 으로 가면, v3 의 SCAN 이 보던 세 가지 (deadline, Work 끝, written) 도 completion 이어야 한다. written 은 SEND 완료가 그 자리에서 처리하면 되므로 (1.4) 사라지고, 나머지 둘은 IoLoop 가 만드는 completion 이 된다.

enum class IoKind : uint8_t { WAKE, ACCEPT, RECEIVE, SEND,        // EventListener::wait 가 돌려준다
                              TIMEOUT, WORK_DONE };                // IoLoop::collect 가 만든다 (5절 Phase 1)

struct IoCompletion
{
    IoKind     kind;
    IoPurpose  purpose;                         // RECEIVE / SEND. 걸었던 action 의 것
    int32_t    slot;                            // ACCEPT / WAKE 는 -1
    SocketCode code;
    size_t     length;
};

이렇게 하면 dispatch 의 input 은 언제나 IoCompletion 이고, 시계와 다른 thread 의 CAS 는 completion 을 만드는 쪽 (collect) 에만 보인다.

1.3 recv 는 늘 걸려 있지 않다

전제를 바꾸면 따라오는 것이다. 구현 가이드 1.3 은 "IO Thread 는 read 요청이 있든 없든 계속 recv" 였는데, action 이 submit 의 단위면 READ action 이 있을 때만 recv 가 걸린다. 얻는 것과 잃는 것:

얻는 것잃는 것
Work 중과 HOLD 중에 Stage 가 차는 일이 없다. 흐름 제어가 kernel 버퍼로 내려간다 (peer 가 보내도 우리가 안 읽으면 TCP 창이 닫힌다)HOLD 와 Work 중에는 peer 의 FIN 을 모른다. 다음 READ 를 걸어야 안다. isWorkConnected 는 "마지막으로 본 상태" 다
submit 이 action 의 kind 만 본다. "받을 자리가 있으면" 같은 상태 판단이 없다TLS 의 KeyUpdate / NewSessionTicket 도 다음 READ 때 들어온다. 문제는 없다. OpenSSL 이 그때 소화한다

잃는 것 하나가 걸리면 길이 있다. IOCP 는 길이 0 인 WSARecv 가 "읽을 것이 생기면 알려 주되 버퍼는 안 쓴다" 이고 epoll 은 EPOLLRDHUP 이다. HOLD 를 "capacity 0 인 READ" 로 submit 하면 HOLD 중에도 끊김을 안다. backend 가 조금 더 커지므로 지금은 넣지 않고 선택 으로 둔다.

1.4 IoEvent 는 연결당 둘

event싣는 action동시에 걸릴 수 있나
_io_eventREAD / READ_UNTIL / WRITE (purpose USER, HANDSHAKE, CONTROL)하나만. 모델이 read ↔ write 교대라서 둘이 같이 걸릴 일이 없다
_notify_eventWRITE (purpose NOTIFY)_io_event 와 같이 걸린다. notify 는 read / write 와 무관하게 온다

같은 socket 에 send 둘이 걸리는 것 (사용자 write 와 notify) 은 stream socket 에서 건 순서대로 나간다. IOCP 는 overlapped WSASend 를 건 순서로 보내고, epoll 흉내는 listener 가 순서대로 send 한다. TLS 에서 이 순서가 중요하다 (4.2).

onWritten 이 SEND 완료 자리에서 바로 나가도 되는 이유도 여기 있다. 구현 가이드 1.6 이 onWritten 을 loop 끝으로 미룬 것은 epoll 에서 write() 안의 send() 가 바로 성공해 콜백이 콜백 안에서 나오는 재진입 때문이었다. 이제 send 는 SUBMIT phase 에서만 걸리고 그 결과는 다음 바퀴의 completion 이다. 재진입이 구조적으로 없으므로 onSent(USER) 가 다 보냈으면 그 자리에서 onWritten 을 낸다.

1.5 START_WORK 와 CLOSE 도 submit 에 간다

"submit 은 listener 와 연관된 일을 하는데 START_WORK 도 거기서" 라는 지적을 이렇게 받았다. kind 일곱 개 모두 submit 의 switch 에 한 줄씩 있다. 콜백은 dispatch 에서 끝내고, submit 은 listener 와 socket 만 만진다.

2. handshake 다시 : onHandshake 가 SEND / RECEIVE 를 돌려준다 동의

맞다. v3 의 "MORE 면 HOLD" 는 "recv 는 늘 걸려 있고 cipherSend 는 SUBMIT 이 알아서 보낸다" 는 전제 위에서만 말이 됐다. 1.3 으로 그 전제가 없어졌으니 handshake 도 무엇을 걸어야 하는지를 action 으로 말해야 한다. 보낼 것이 있으면 WRITE, 받아야 하면 READ 다. HOLD 는 handshake 에서 사라진다.

2.1 TlsPipe::handshake 의 답은 넷

"더 보내야 할 때도 있고 더 받아야 할 때도 있다" 를 답에 그대로 드러낸다. 보낼 것이 있으면 그것이 먼저다. SSL_do_handshake 가 WANT_READ 를 돌려줘도 wbio 에 보낼 것이 쌓여 있으면 그것을 보내야 peer 가 답을 준다.

enum class TlsStep : uint8_t { SEND, RECEIVE, DONE, FAILED };

TlsStep TlsPipe::handshake()                    // cipherReceive → rbio, SSL_do_handshake, wbio → cipherSend
{
    int result = SSL_do_handshake(_ssl);
    moveWbioToCipherSend();
    if (cipherSend().consumer().readable() > 0) return TlsStep::SEND;     // 보낼 것이 있으면 먼저 보낸다. DONE 직후의 NewSessionTicket 도 여기 걸린다
    if (result == 1)                             return TlsStep::DONE;
    int error = SSL_get_error(_ssl, result);
    if (error == SSL_ERROR_WANT_READ)            return TlsStep::RECEIVE;
    recordError(error);                                                    // 3절. code 와 static message 를 _last_* 에
    return TlsStep::FAILED;
}

이 함수는 몇 번을 불러도 안전하다. 끝난 뒤 다시 부르면 1 이 돌아오고 (DONE), 보낼 것이 있으면 SEND 다. 그래서 Connection 은 HANDSHAKING 동안 들어오는 모든 completion (RECEIVE 든 SEND 든) 에 같은 함수 하나를 부른다.

2.2 Connection::onHandshake

IoAction Connection::onHandshake(const Handler& handler)           // HANDSHAKING 의 모든 completion 뒤, 그리고 open 직후 한 번
{
    switch (_tls.handshake())
    {
    case TlsStep::SEND:    return IoAction::write(_tls.cipherSend(), IoPurpose::HANDSHAKE, _handshake_timeout_ms);   // io_* = cipherSend 의 읽을 구간
    case TlsStep::RECEIVE: return IoAction::read (_tls.cipherReceive(), IoPurpose::HANDSHAKE, _handshake_timeout_ms); // io_* = cipherReceive 의 빈 자리. exact 0 = 오는 만큼
    case TlsStep::DONE:    _phase = Phase::READY;
                           return handler.onReady(_context, handle());                                                // 첫 사용자 action
    case TlsStep::FAILED:  handler.onError(_app_context, handle(), _tls.lastCode(), _tls.lastMessage());               // 3절
                           return IoAction::close(_tls.lastCode());
    }
}
시점TLS 서버TLS 클라이언트
open 직후 onOpenedonHandshake → RECEIVE (ClientHello 를 기다린다) → READ(HANDSHAKE)onHandshake → ClientHello 가 cipherSend 에 → SEND → WRITE(HANDSHAKE)
RECEIVE 완료 (HANDSHAKE)cipherReceive.commit → onHandshake → SEND 면 WRITE, RECEIVE 면 READ, DONE 이면 onReady 의 action, FAILED 면 onError + CLOSE
SEND 완료 (HANDSHAKE)cipherSend.consume → onHandshake (같은 함수). 1.3 서버는 client Finished 뒤 DONE 이 되면서 NewSessionTicket 이 cipherSend 에 남으므로 SEND 한 번 더, 그 완료에서 DONE → onReady
TIMEOUT 완료onTimeout hook 이 HANDSHAKING 이면 onError(KIOTTY_TLS_HANDSHAKE_TIMEOUT) + CLOSE

HOLD 가 없어지면서 v3 2.2 의 "handshake 전용 deadline 변수가 없다" 는 그대로다. READ / WRITE 의 timeout_ms 가 그 자리다.

2.3 READY 에서 받는 길

1.2 의 네 줄이 자리를 바꿔 들어가는 곳이다. READ action 의 받을 자리는 receiveStage() 가 고르고 (TLS 면 cipherReceive), 완료 뒤 평문을 만드는 것은 onReceived 가 한다.

IoAction Connection::onReceived(IoPurpose purpose, SocketCode code, size_t length, const Handler& handler)
{
    _io_pending = false;
    if (_phase == Phase::CLOSING) return IoAction::none();
    if (code != SocketCode::SUCCESS || length == 0) return onPeerGone(code);
    receiveStage().provider().commit(length);                               // 평문: _receive_stage, TLS: _tls.cipherReceive()

    if (purpose == IoPurpose::HANDSHAKE) return onHandshake(handler);       // 2.2. phase 가 HANDSHAKING 인 동안만 이 purpose 가 온다

    if (_tls.active())
    {
        KiottyNetCode decoded = _tls.decode(_receive_stage);                // cipher → plain. 레코드가 덜 찼으면 0 바이트
        if (decoded != KIOTTY_SUCCESS) { handler.onError(_app_context, handle(), decoded, _tls.lastMessage()); return IoAction::close(decoded); }
        if (_tls.cipherSend().consumer().readable() > 0)                    // KeyUpdate 답장 (v3 2.1). 먼저 보내고 READ 로 돌아온다
            return IoAction::write(_tls.cipherSend(), IoPurpose::CONTROL, 0);
    }
    return _read;                                                           // 등록된 READ 조건을 다시 돌려준다. resolve 가 pump 해서 찼으면 onRead, 아니면 다시 받는다
}

_read 는 "등록된 조건" 이고 _pending 은 "다음에 submit 할 action" 이다. 조건은 여러 번의 receive 에 걸쳐 살아 있고, pending 은 바퀴마다 새로 정해진다. 둘을 따로 두는 이유가 CONTROL 이다. KeyUpdate 답장을 보내는 동안에도 사용자의 READ 조건은 남아 있어야 한다.

3. TLS 오류를 세밀하게 동의

"어디서 났는지" 는 code 가, "왜" 는 message 가 말하게 한다. message 는 v1 의 규칙 (static literal) 을 지키면서도 OpenSSL 의 이유 문자열을 그대로 쓸 수 있다. ERR_reason_error_string 과 X509_verify_cert_error_string 은 둘 다 OpenSSL 안의 static 문자열 포인터 를 돌려주므로 버퍼가 필요 없다.

  • onError 에 handle 을 더한다 (선택). 지금은 onError(app_context, code, message) 라 어느 연결인지 모른다. onError(app_context, connection, code, message) 로 바꾸고 연결이 없는 오류 (accept 실패) 는 0 을 넘기면, 사용자가 getConnectionInfo(connection) 로 peer 주소까지 안다.
  • TlsPipe 가 마지막 오류를 든다. lastCode(), lastMessage(). recordError 가 SSL_get_error 와 SSL_get_verify_result 를 보고 위 표의 code 를 고른다. 분류는 tls/ 안에만 있다.
  • 서버 / 클라이언트 어느 쪽인지 는 handler 를 등록한 쪽이 이미 안다. message 에 넣지 않는다.

4. notify / broadcast : NotificationContext 부분 동의

구조에 동의한다. PushSlot (4 칸, 호출자 대기) 을 지우고 호출자가 직접 연결의 Notification Stage 에 쓴다. 바꾸고 싶은 것은 둘이다. 암호화를 lock 안에서 하지 않는 것 (4.2) 과 instant (4.4).

4.1 구조

struct NotificationContext                       // host 에 하나. 모든 연결의 Notification Stage 를 한 mutex 가 지킨다
{
    std::mutex     mutex;
    EventListener* listener;                     // wake 하기 위해. IO Thread 바깥에서 부르는 것은 wake 하나뿐이다
    bool           isIoThread() const;
};

class Connection
{
    NotificationContext& _notification;          // host 의 것
    Stage                _notification_stage;    // push_capacity. [u32 길이][바이트] 가 아니라 바이트 그대로. 경계가 필요 없다 (4.3)
    size_t               _notify_in_flight;      // 지금 걸린 WRITE(NOTIFY) 가 보내는 길이. 0 이면 안 걸림

public:
    KiottyNetCode notify(KiottyNetSpan data);    // 아무 thread
};

KiottyNetCode Connection::notify(KiottyNetSpan data)
{
    {
        std::lock_guard<std::mutex> lock(_notification.mutex);
        if (!alive())                                                   return KIOTTY_PEER_CLOSED;
        if (_notification_stage.provider().writable() < data.length)    return KIOTTY_BUFFER_FULL;
        memcpy(_notification_stage.provider().prepare(data.length), data.data, data.length);
        _notification_stage.provider().commit(data.length);             // 평문 그대로. TLS 라도 여기서 암호화하지 않는다 (4.2)
    }
    if (!_notification.isIoThread()) _notification.listener->wake();   // IO Thread 안이면 이 바퀴의 SUBMIT 이 본다
    return KIOTTY_SUCCESS;
}

KiottyNetCode ConnectionHost::broadcast(KiottyNetSpan data)             // Server.notify
{
    std::lock_guard<std::mutex> lock(_notification.mutex);
    for (Connection& c : alive connections) if (c.notificationWritable() < data.length) return KIOTTY_BUFFER_FULL;   // 하나라도 모자라면 아무 데도 안 쓴다
    for (Connection& c : alive connections) c.appendNotification(data);                                                // 검사 없이 복사
    if (!_notification.isIoThread()) _notification.listener->wake();
    return KIOTTY_SUCCESS;
}

broadcast 의 "하나라도 모자라면 전부 거절" 에 동의한다. v2 의 "가득 찬 연결은 건너뛴다" 보다 계약이 분명하다. 호출자는 SUCCESS 면 모두에게 들어갔음을, BUFFER_FULL 이면 아무에게도 안 들어갔음을 안다.

4.2 암호화는 IO Thread 가 submit 할 때

"TLS 일 경우 lock 안에서 암호문으로 변환" 은 두 가지에 걸린다.

  1. SSL* 은 thread-safe 가 아니다. notify 가 다른 thread 에서 SSL_write 를 부르면, IO Thread 의 decode / encode 전부가 같은 mutex 를 잡아야 한다. 받는 길의 모든 바이트가 notify 의 lock 을 지나게 된다.
  2. TLS 레코드는 순서가 있다. 레코드마다 sequence number 가 들어가고 peer 는 그 순서로 MAC 을 검사한다. thread A 가 notify 를 SSL_write 해서 레코드 N 을 만들고, IO Thread 가 사용자 write 를 SSL_write 해서 N+1 을 만든 뒤 N+1 을 먼저 submit 하면 peer 는 bad record mac 으로 끊는다. 암호화 순서와 submit 순서가 같아야 하고, 그것은 한 thread 에서만 보장된다.

그래서 notify 는 평문을 Stage 에 넣고 깨우기만 한다. 암호화는 SUBMIT 이 그 연결의 notify 를 걸 때 IO Thread 가 한다. 평문 연결은 Stage 의 구간을 그대로 submit 한다. TLS 연결은 _tls.cipherNotify() 로 encode 한 뒤 그 구간을 submit 한다. 사용자 write 의 cipherSend 와 다른 Stage 를 쓰는 이유는 둘이 동시에 걸려 있기 때문이다 (1.4). 메모리는 TLS 연결당 cipher Stage 셋 (receive 는 레코드 하나 16 KiB + 헤더, send 와 notify 는 각각 send_capacity / push_capacity + 레코드 오버헤드) 이다.

이 규칙이면 1.4 의 "같은 socket 의 send 둘은 건 순서로 나간다" 와 합쳐져 TLS 순서가 지켜진다: SSL_write 는 IO Thread 의 SUBMIT 안에서만, submit 한 순서대로 불린다.

4.3 Stage 하나로 메시지 경계 없이

Notification Stage 에 [u32 길이] 헤더를 두지 않는다. notify 는 "바이트를 순서대로 보낸다" 이고 완료 콜백이 없으므로 경계가 필요 없다. 걸린 WRITE(NOTIFY) 가 보내는 구간은 Stage 의 [begin, begin + in_flight) 이고, 그 사이 들어온 notify 는 뒤에 붙는다. 완료가 오면 lock 안에서 consumer.commit(in_flight) 하고, 남은 것이 있으면 SUBMIT 이 다음 구간을 건다.

compact 규칙 하나. Stage 의 compact 는 포인터를 옮기므로 걸린 send 가 있는 동안 하면 안 된다. Notification Stage 의 compact 는 lock 안에서, _notify_in_flight == 0 일 때만 한다. 그 자리는 SEND(NOTIFY) 완료 처리 끝이다.

4.4 instant 우려

"다른 Connection 을 지연시키더라도 동기로 보낸다" 는 지연 전송이 안 되는 곳을 위한 것으로 읽었다. 걸리는 것:

  • 순서. 그 socket 에 overlapped send 가 걸려 있는 상태에서 다른 thread 가 동기 send 를 하면 둘의 바이트 순서가 보장되지 않는다. TLS 면 4.2 의 2 번이 그대로 터진다.
  • 지연의 실체. notify 가 wake 하면 IO Thread 는 지금 바퀴를 마치고 (남은 completion 의 콜백) 바로 SUBMIT 으로 간다. 추가 지연은 "지금 돌고 있는 사용자 콜백 하나" 다. 콜백이 짧다는 모델의 전제 (긴 일은 Work) 가 지켜지면 수십 µs 다.
  • IO Thread 안에서 부른 notify 는 이미 같은 바퀴의 SUBMIT 에 걸린다. instant 와 차이가 없다.

추천: 지금은 넣지 않는다. 지연이 측정으로 문제가 되면 그때 "IO Thread 가 아니면 wake 뒤 submit 완료까지 기다린다" (동기 송신이 아니라 동기 제출) 로 넣는 것이 순서를 깨지 않는 모양이다 (선택).

5. StreamClient 의 TLS 동의

TlsProfile 과 TlsPipe 로 충분하다. StreamClient 는 loop 가 없으므로 Connection 의 onHandshake 가 completion 마다 한 걸음 가는 것을 while 로 돈다. TlsPipe::handshake 의 답 넷이 그대로 분기다.

KiottyNetCode StreamClient::connect()
{
    Result<KiottyNetCode, ActiveSocket> connected = connectWithRetry(_config, _stop);
    if (!connected) return connected.code();
    _socket = std::move(connected.value());
    if (!_profile) return KIOTTY_SUCCESS;

    KiottyNetCode opened = _tls.open(*_profile, _config.endpoint.host);
    if (opened != KIOTTY_SUCCESS) return opened;
    for (;;)
    {
        switch (_tls.handshake())
        {
        case TlsStep::SEND:    { KiottyNetCode code = sendAll(_tls.cipherSend(), _config.connect_timeout_ms);        if (code != KIOTTY_SUCCESS) return code; break; }
        case TlsStep::RECEIVE: { KiottyNetCode code = receiveSome(_tls.cipherReceive(), _config.connect_timeout_ms); if (code != KIOTTY_SUCCESS) return code; break; }
        case TlsStep::DONE:    return KIOTTY_SUCCESS;
        case TlsStep::FAILED:  return _tls.lastCode();                     // 3절의 code. lastMessage 는 로그로
        }
    }
}

KiottyNetResult StreamClient::read(void* buffer, size_t length, uint32_t timeout_ms)
{
    while (_receive_stage.consumer().readable() == 0)                      // 평문이 남아 있으면 그것부터
    {
        Stage& target = _tls.active() ? _tls.cipherReceive() : _receive_stage;
        KiottyNetCode code = receiveSome(target, timeout_ms);              // poll 한 번 + recv 한 번
        if (code != KIOTTY_SUCCESS) return failure(code);
        if (_tls.active()) { code = _tls.decode(_receive_stage); if (code != KIOTTY_SUCCESS) return failure(code); }   // 0 바이트면 다시 돈다
    }
    return copyOut(buffer, length);
}

KiottyNetResult StreamClient::write(KiottyNetSpan data, uint32_t timeout_ms)
{
    if (!_tls.active()) return sendAll(data, timeout_ms);
    _tls.encode(data);                                                     // send_capacity 단위로 나눠 encode + sendAll 을 반복한다
    return sendAll(_tls.cipherSend(), timeout_ms);
}

Connection 과 다른 점은 sendAll / receiveSome 이 동기 (non-blocking + poll, v0 15-5) 라는 것뿐이다. decode 가 0 바이트를 돌려줄 수 있다는 것 (레코드가 덜 찼다, NewSessionTicket 을 소화했다) 을 while 이 받는다. sendAll 이 cipherSend 를 다 비우고 돌아오므로 StreamClient 에는 cipherNotify 가 없다. TlsPipe 생성자가 notify 용 capacity 0 을 받는다.

6. IoLoop 다시 : COLLECT → DISPATCH → SUBMIT → SETTLE

v3 의 여섯 phase 가 넷이 된다. SCAN 은 COLLECT 로 들어가고 (completion 을 만드는 쪽), APPLY 는 DISPATCH 의 마지막 작은 동작 resolve 가 된다 (action 의 listener 절반을 채우는 쪽). 큰 동작 넷의 input 과 output 은 서로 다른 타입이라 phase 끼리 섞일 수 없다.

void IoLoop::runOnce()
{
    Span<const IoCompletion> completions = collect();                       // 1
    for (const IoCompletion& completion : completions) dispatch(completion); // 2
    submit();                                                               // 3
    settle();                                                               // 4

Phase 1. COLLECT : 세 출처 → IoCompletion 하나의 배열

Span<const IoCompletion> IoLoop::collect()
{
    size_t count = _listener.wait(nearestDeadline(monotonicMs()), _completions, OS_CAPACITY);   // 1a. TIMEOUT 이면 0. WAKE 도 여기 섞여 온다
    uint64_t now = monotonicMs();
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& c = _host.at(i);
        if (!c.alive()) continue;
        if (c.expireDeadline(now)) _completions[count++] = IoCompletion{ IoKind::TIMEOUT,   IoPurpose::USER, (int32_t)i, SocketCode::SUCCESS, 0 };   // 1b. deadline 을 0 으로 돌리며 true
        if (c.workFinished())      _completions[count++] = IoCompletion{ IoKind::WORK_DONE, IoPurpose::USER, (int32_t)i, SocketCode::SUCCESS, 0 };   // 1c. _work 가 DONE
    }
    return Span<const IoCompletion>(_completions, count);                   // 배열은 IoLoop 의 것. OS_CAPACITY + 2 × capacity
}

시계와 다른 thread 의 CAS 를 보는 자리는 이 함수가 유일하다. 뒤의 phase 는 completion 의 kind 만 본다.

Phase 2. DISPATCH : completion → hook → action → resolve

void IoLoop::dispatch(const IoCompletion& completion)
{
    if (completion.kind == IoKind::WAKE)   return;                           // 2a. 깨우기만. notify 는 3c 가, close 는 run 의 while 이 본다
    if (completion.kind == IoKind::ACCEPT) { admit(); return; }              // 2b

    Connection& c = _host.at(completion.slot);
    IoAction action;
    switch (completion.kind)
    {
    case IoKind::RECEIVE:   action = c.onReceived(completion.purpose, completion.code, completion.length, handler()); break;   // 2c. 2.3 절
    case IoKind::SEND:      action = completion.purpose == IoPurpose::NOTIFY
                                   ? c.onNotified(completion.code, completion.length)                                        // 2d. NONE. _pending 을 건드리지 않는다
                                   : c.onSent(completion.purpose, completion.code, completion.length, handler());   break;
    case IoKind::TIMEOUT:   action = c.onTimeout(handler());                                                        break;   // 2e
    case IoKind::WORK_DONE: action = c.onWorkFinished();                                                            break;   // 2f
    }
    resolve(c, action);                                                      // 2g
}

2b. admit : ACCEPT → Connection 하나

void IoLoop::admit()
{
    Result<SocketCode, ActiveSocket> accepted = _acceptor->accept();
    if (!accepted) { handler().onError(_app_context, 0, toNetCode(accepted.code()), "accept failed"); return; }

    Connection& c = *_host.acquire();                                        // accept 는 빈 slot 이 있을 때만 걸었다 (3d)
    KiottyNetConnectionDecision decision = handler().onConnected(_app_context, c.handle(), accepted.value().peer());
    if (!decision.accepted) { accepted.value().close(); _host.release(c); return; }

    c.open(std::move(accepted.value()), decision.connection_context, _tls_profile);   // phase = TLS ? HANDSHAKING : READY. attach 는 3a 가
    resolve(c, c.onOpened(handler()));                                       // 평문: onReady 의 action. TLS: onHandshake 의 READ / WRITE (HANDSHAKE)
}

EventClient 는 동기 connect 뒤 run 안에서 같은 네 줄을 한 번 한다 (admit(ActiveSocket&&) 로 두고 같이 쓴다).

2c ~ 2f. hook 넷

onReceived 는 2.3 절에 있다. 나머지 셋:

IoAction Connection::onSent(IoPurpose purpose, SocketCode code, size_t length, const Handler& handler)
{
    _io_pending = false;
    if (_phase == Phase::CLOSING) return IoAction::none();
    if (code != SocketCode::SUCCESS) return onPeerGone(code);
    sendStage(purpose).consumer().commit(length);                            // HANDSHAKE / CONTROL / TLS 의 USER : cipherSend. 평문 USER : _send_stage
    switch (purpose)
    {
    case IoPurpose::HANDSHAKE: return onHandshake(handler);                  // 2.2 절. 같은 함수가 다음 걸음을 정한다
    case IoPurpose::CONTROL:   return _read;                                 // KeyUpdate 답장이 나갔다. 사용자의 READ 조건으로 돌아간다 (io 없음 → resolve 가 pump)
    case IoPurpose::USER:      if (hasMoreToSend()) return nextWriteChunk(); // 송신 Stage 에 남은 것 (TLS 는 encode 더). io 채운 WRITE(USER)
                               return handler.onWritten(_context, handle(), _write_length);   // 1.4. 이 자리에서 바로
    }
}

IoAction Connection::onTimeout(const Handler& handler)                       // 2e
{
    if (_phase == Phase::HANDSHAKING) { handler.onError(_app_context, handle(), KIOTTY_TLS_HANDSHAKE_TIMEOUT, "tls: handshake timeout"); return IoAction::close(KIOTTY_TLS_HANDSHAKE_TIMEOUT); }
    return handler.onTimeout(_context, handle());
}

IoAction Connection::onWorkFinished()                                         // 2f
{
    IoAction outcome = _work.onFinished();                                   // DONE → IDLE
    return _peer_closed.load() ? IoAction::close(KIOTTY_PEER_CLOSED) : outcome;
}

IoAction Connection::onPeerGone(SocketCode code)                             // RECEIVE 의 0 바이트 / 오류, SEND 의 오류
{
    if (_work.working()) { _peer_closed.store(true); return IoAction::none(); }   // Work 중엔 기록만
    return IoAction::close(code == SocketCode::CLOSED ? KIOTTY_PEER_CLOSED : KIOTTY_SOCKET_ERROR);
}

2g. resolve : handler 절반 → listener 절반

규칙 하나로 돈다. READ / WRITE 는 io_buffer 가 채워져 있으면 끝난 action 이다 (onHandshake 의 READ / WRITE, pump 가 돌려준 READ, write 가 돌려준 WRITE). 비어 있으면 handler 가 준 것이므로 Connection 이 채운다. 채우는 중에 콜백이 또 action 을 내면 (READ 가 바로 충족돼 onRead) 그것을 같은 loop 의 다음 회차로 돈다. 재귀가 아니다.

void IoLoop::resolve(Connection& c, IoAction action)
{
    for (;;)
    {
        switch (action.kind)
        {
        case IoActionKind::NONE:        return;                                                      // _pending 그대로 (NOTIFY 완료, CLOSING 의 늦은 완료, Work 중 끊김)
        case IoActionKind::HOLD:        c.hold(action.timeout_ms);                      c.setPending(action); return;   // deadline 만
        case IoActionKind::START_WORK:  c.startWork();                                                                   // _work.start(generation)
                                        handler().onWorkStarted(c.context(), c.workHandle()); c.setPending(action); return;
        case IoActionKind::CLOSE:       c.shutdown();                                                                    // FIN. socket.close 는 3b 가
                                        handler().onDisconnected(_app_context, c.context(), c.handle(), action.as.close.reason);
                                        c.setPending(action); return;
        case IoActionKind::READ:
        case IoActionKind::READ_UNTIL:  if (action.io_buffer) { c.setPending(action); return; }     // 끝난 action
                                        c.setRead(action);                                           // 조건 등록 + deadline. exact > capacity 면 CLOSE 가 돌아온다
                                        action = c.pump(handler());                                  // 찼으면 onRead 의 return (io 없음 → 다음 회차). 안 찼으면 io 채운 READ
                                        continue;
        case IoActionKind::WRITE:       if (action.io_buffer) { c.setPending(action); return; }     // 끝난 action
                                        action = c.write(action);                                    // 사용자 span → 송신 Stage (+encode) → io 채운 WRITE. BUSY / BUFFER_FULL 이면 CLOSE
                                        continue;
        }
    }
}

IoAction Connection::pump(const Handler& handler)                            // _read 조건을 _receive_stage 에 대 본다
{
    if (_read.kind == IoActionKind::NONE) return IoAction::none();
    KiottyNetSpan data;
    if (satisfied(_read, _receive_stage, data))                              // EXACT : readable ≥ exact. UNTIL : delimiter 가 _scanned 뒤에 있다 (없고 max 넘으면 CLOSE)
    {
        _read = IoAction::none();                                            // 조건 소진. onRead 가 다음 조건을 return 한다
        IoAction next = handler.onRead(_context, handle(), data);
        _receive_stage.consumer().commit(data.length);                       // 콜백이 돌아온 뒤 소비. data 는 콜백 동안만 유효하다
        return next;
    }
    IoAction armed   = _read;                                                // 안 찼다. 받을 자리를 채워 돌려준다
    armed.io_length  = receiveStage().provider().writable();                 // 평문 : _receive_stage, TLS : cipherReceive
    armed.io_buffer  = receiveStage().provider().prepare(armed.io_length);
    return armed;
}

Phase 3. SUBMIT : pending → listener

void IoLoop::submit()
{
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        if (!_host.occupied(i)) continue;
        Connection& c = _host.at(i);
        if (c.phase() == Phase::CLOSING) continue;                           // 닫는 중. SETTLE 이 본다
        if (!c.attached()) { _listener.attach(c.socket(), (int32_t)i); c.markAttached(); }           // 3a. 열린 뒤 첫 바퀴 한 번

        if (!c.ioPending())                                                                          // 3b. pending action 하나
        {
            const IoAction& action = c.pending();
            switch (action.kind)
            {
            case IoActionKind::NONE:
            case IoActionKind::HOLD:        break;                                                   // 걸 것 없음. deadline 은 COLLECT 가 본다
            case IoActionKind::READ:
            case IoActionKind::READ_UNTIL:
            case IoActionKind::WRITE:       _listener.submit(c.ioEvent(), c.socket(), action); c.markIoPending(); break;   // receive 또는 send. 즉시 실패는 다음 wait 의 오류 완료로
            case IoActionKind::START_WORK:  break;                                                   // Work 중엔 socket 에 아무것도 걸지 않는다
            case IoActionKind::CLOSE:       _listener.detach(c.socket()); c.closeSocket(); break;   // phase = CLOSING
            }
        }

        IoAction notification = c.takeNotification();                                                // 3c. lock 안에서 Stage 의 구간을 WRITE(NOTIFY) 로. TLS 면 여기서 encode. 없거나 걸려 있으면 NONE
        if (notification.kind == IoActionKind::WRITE) _listener.submit(c.notifyEvent(), c.socket(), notification);
    }
    if (_acceptor && !_acceptor->pending() && _host.hasFreeSlot()) _acceptor->submit(_listener);     // 3d
}

IoAction Connection::takeNotification()                                      // IO Thread. 4절
{
    std::lock_guard<std::mutex> lock(_notification.mutex);
    if (_notify_pending) return IoAction::none();
    Stage& out = _tls.active() ? _tls.encodeNotification(_notification_stage) : _notification_stage;   // TLS : 평문 → cipherNotify 로 옮기고 cipherNotify 를 돌려준다
    size_t length = out.consumer().readable();
    if (length == 0) return IoAction::none();
    _notify_pending = true;
    return IoAction::write(out.consumer().prepare(length), length, IoPurpose::NOTIFY);
}

3b 의 switch 는 kind 일곱 개가 한 줄씩이다. 상태를 읽어 판단하는 줄이 없다. "받을 자리가 있으면", "보낼 것이 있으면" 이 모두 action 을 만든 쪽 (resolve) 의 일이 됐기 때문이다. 3c 만 Stage 를 본다. notify 는 action 을 거치지 않고 다른 thread 가 Stage 에 쓰기 때문이다.

Phase 4. SETTLE

void IoLoop::settle()
{
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& c = _host.at(i);
        if (_host.occupied(i) && c.phase() == Phase::CLOSING && !c.ioPending() && !c.notifyPending())
            _host.release(c);                                                // 늦은 완료가 다 돌아온 뒤 slot 반납 (IOCP 의 ERROR_OPERATION_ABORTED)
    }
    if (_stop_when_empty && _host.empty()) _stopped = true;
}

골라 주실 것

  1. 1.3 HOLD / Work 중의 끊김 감지: 지금은 포기 (추천) 또는 HOLD 를 capacity 0 인 READ 로 submit (IOCP 0 바이트 WSARecv, epoll EPOLLRDHUP)
  2. 3절 onError 에 connection handle 추가: 추가 (추천) 또는 그대로
  3. 4.2 TLS notify 의 암호화 자리: IO Thread 의 SUBMIT (추천) 또는 notify 의 lock 안 (SSL 에 mutex 가 필요해진다)
  4. 4.4 instant: 지금은 넣지 않음 (추천), 동기 제출 (wake 뒤 submit 까지 대기), 또는 동기 송신
  5. 1.1 EventListener::submit(event, socket, IoAction) 하나: v1 2.4 의 답으로 이대로 (추천) 또는 셋 유지
  6. 남은 것: Span (collect 가 돌려주는 타입으로 쓰고 있다. 이대로면 확정), 15-1 (handle 비트와 Context 찾기), 15-4 (TLS Pool 크기)

kiotty_net_base.h 구현 설계 v5

2026-11-07. 개발 수칙 v2 리팩터링 (docs/plan/plan_refactor_v0.md 단계 0 ~ 7, commit ff717ac 까지) 의 결과를 design_base_v4.md 위에 다시 쓴 판이다. 절 번호는 v4 와 같게 두어 나란히 볼 수 있게 했다. 17절이 수칙 v2 와 v4 가 달라진 곳, 18절이 편차 요약이다.

우선순위: 두 문서가 다르면 docs/requirement/requirement_v0.md, 흐름이 다르면 implementation_guide_v0.md, 코드 모양이 다르면 development_rule.md (수칙 v2) 가 이긴다. 수칙에서 벗어난 곳은 docs/deviations.md 에 있다. 이 문서의 코드 블록 안 주석은 설명용이다 (결정 D4). 소스에는 주석을 두지 않는다 (수칙 4.9).

표기: 코드 는 지금 저장소에 있고 테스트가 도는 것, 설계 는 아직 코드가 없고 plan_base_v2.md 의 5b 이후 사이클이 만들 것이다.

설계 방침 (v4 그대로)

  1. 맥락은 맥락끼리. 받는 맥락 (receive), 보내는 맥락 셋 (user send, notify, TLS 의 cipher 출력), Work 맥락, 수명 맥락 (phase) 은 각자 자기 Stage 와 자기 완료 처리를 가진다. 맥락 사이를 잇는 것은 IoAction 과 IoCompletion 두 값 타입뿐이다. v5 에서는 이 방침이 클래스 경계가 됐다: ReceiveFlow, SendFlow, WorkFlow (9절). 수칙 6.3 / 6.5 와 같은 말이다.
  2. 엣지 케이스는 프로세스가 삼킨다. socket 당 WRITE 는 하나이므로 "동시에 끝남" 이 없고, 송신은 Stage 에 넣는 것과 Stage 에서 꺼내 거는 것이 다른 프로세스다. 늦은 완료와 닫힌 뒤의 local completion 은 dispatch 의 첫 줄 하나가 받는다. 수칙 6.4 와 같은 말이다.
  3. 프로세스는 input → output 이다. 한 바퀴는 다섯 프로세스 (drain, settle, collectIoEvents, step, stepLocalEvents) 이고 각 프로세스의 input 과 output 은 값이다. 다른 thread 가 쓰는 것은 세 자리 (notify Stage, WorkContext 의 CAS, listener.wake) 뿐이고 전부 "적고 깨운다" 다.

원칙

  1. src/kiotty_net_base.cpp 는 번역만 한다 (15절). 수칙 7.1 의 "얇은 어댑터".
  2. 클래스는 최소 함수와 최소 변수만 가진다. public 메서드는 7 개 이하다 (수칙 4.1, 세는 법은 DV9 / DV11).
  3. 의존은 아래로만 간다: context → domain/usecases → data/repository → data/infra, data/datasource → domain/entity → core. OS 가 다른 부분은 그 폴더의 backend/ 안에만, OpenSSL 은 data/infra/tls/backend/ 안에만 있다.
  4. 한 줄에 한 동작. 호출 결과는 const 지역 변수로 받은 뒤 검사한다. cancel 은 없다. 요청은 completion 으로만 비워진다.

READ 는 RECV, ACCEPT 는 POLL_ADD (readable 이 오면 Acceptor 가 accept, epoll 과 같은 계약). RECV / SEND 가 -EAGAIN 이면 POLL_ADD 로 기다렸다 다시 건다. 부분 SEND 는 남은 길이로 다시 건다. detach 는 fd 를 닫는 것으로 취소되지 않으므로 (ring 이 file 참조를 쥔다) ASYNC_CANCEL 을 걸고 event 는 pending 인 채 둔다. 그 완료가 오면 (detach 된 event 는 fd 가 -1) CANCELLED 다. IoEvent 가 ring 에 걸린 채 소멸하면 ASYNC_CANCEL 을 걸고 CQ 에서 그 완료를 찾아 user_data 를 무시 표시로 덮는다 (끝난 event 의 주소를 나중에 읽지 않게). close 는 ASYNC_CANCEL_ANY 로 전부 취소하고 완료를 거둔 뒤 munmap. wake 는 같은 eventfd 에 쓰고, ring 은 그 eventfd 에 READ 를 걸어 둔다. thread 가 끝나면 커널이 그 thread 가 건 요청을 취소하므로 wait 가 막히기 전마다 wake READ 가 걸려 있는지 본다 (같은 Server 를 다른 thread 로 다시 run 하는 경우).

  • OS 가 주소를 들고 있는 raw pointer (IocpRequest::owner, epoll data.ptr, kqueue udata, next, listener) 는 DV3 다.

9.4 step 쪽 : dispatch → react → apply

IoAction Connection::dispatch(const IoCompletion& completion, const Handler& handler, std::mutex& notification)
{
    const bool alive = isAlive(_phase.load());
    if (!alive) { return IoAction::none(); }    // 늦은 완료 (CANCELLED) 와 CLOSE 뒤의 local completion
    return apply(react(completion, handler, notification), handler);
}

IoAction Connection::react(...)                 // kind 라우팅만
{
    switch (completion.kind)
    {
    case IoKind::RECEIVE:    return onReceived(completion, handler);
    case IoKind::SEND:       return onSent(completion, handler, notification);
    case IoKind::TIMEOUT:    return onTimeout(handler);
    case IoKind::WORK_READY: return onWorkReady(handler);
    case IoKind::WORK_DONE:  return _receive_flow.drive(completion.action, callerFor(handler));
    case IoKind::ACCEPT:
    case IoKind::WAKE:       return IoAction::none();
    }
    return IoAction::none();
}

IoAction Connection::apply(IoAction action, const Handler& handler)
{
    switch (action.kind)
    {
    case IoActionKind::HOLD: case IoActionKind::READ: case IoActionKind::READ_UNTIL:
        setDeadline(action.timeout_milliseconds); return action;
    case IoActionKind::START_WORK:
        _deadline.store(0); _work.request(); return action;          // REQUESTED. WORKING 은 stepLocalEvents 의 WORK_READY
    case IoActionKind::CLOSE:
        enterClosing(action.as.close.reason, handler); return action; // deadline 0, CLOSING, _work.abandon(), onDisconnected
    case IoActionKind::NONE: case IoActionKind::WRITE: case IoActionKind::ACCEPT:
        return action;
    }
    return action;
}

IoAction Connection::onReceived(completion, handler)
{
    if (completion.code != SocketCode::SUCCESS) { return closedBy(completion.code); }   // CLOSED → PEER_CLOSED, 그 외 SOCKET_ERROR
    _receive_flow.commit(completion.action.purpose, completion.length);
    if (completion.action.purpose == IoPurpose::HANDSHAKE) { return onHandshake(handler); }
    return _receive_flow.drive(completion.action, callerFor(handler));
}

IoAction Connection::onSent(completion, handler, notification)
{
    if (completion.code != SocketCode::SUCCESS) { return closedBy(completion.code); }
    _send_flow.release(completion, notification);       // 암호문은 길이로, 평문은 purpose 의 Stage 에서 as.write.length (NOTIFY 는 lock 안)
    switch (completion.action.purpose)
    {
    case IoPurpose::HANDSHAKE: return onHandshake(handler);
    case IoPurpose::CONTROL:
    case IoPurpose::NOTIFY:    return IoAction::none();
    case IoPurpose::USER:      return onWritten(completion.action.as.write.length, handler);
    }
    return IoAction::none();
}

IoAction ReceiveFlow::drive(IoAction action, const Caller& caller)   // 재귀 없음. 반복 상한은 receive_capacity
{
    while (isRead(action))
    {
        const ReadyResult ready = satisfied(action, _receive);   // 초과: REQUEST_TOO_LARGE, max 안에 delimiter 없음: PROTOCOL_ERROR
        if (!ready) { return IoAction::close(ready.code); }
        if (ready.value.length > 0) { action = deliver(ready.value, caller); continue; }   // onRead → commit → caller.admit
        const RefillResult more = refill();                      // compact, TLS 면 decode
        if (!more) { return refuse(more.code, caller); }         // onError 뒤 CLOSE
        if (more.value == 0) { return action; }                  // 정말 더 받아야 한다
    }
    return settled(action);                                      // HOLD / START_WORK / CLOSE 는 그대로, 나머지는 NONE
}
  • v4 9.5 의 성질은 그대로다: decode 는 refill 한 자리, call stack 은 dispatch → on* → drive → 콜백의 상수 깊이, step 의 output 에 WRITE 가 없다 (adoptAction 이 HOLD 로 바꾼다).
  • v4 의 drive 는 for (;;) 안의 switch 였다. v5 는 while (isRead(action)) 과 보조 함수 (satisfied / exactly / until / findDelimiter / settled, 익명 namespace) 다. 중첩 2 단과 30 줄 안에 들어간다.
  • Phase × kind 표는 v4 9.5 의 표 그대로다.

KiottyNetCode WorkFlow::closeStream(int32_t generation, const KiottyNetConnectionAction& then)   // worker
{
    const KiottyNetCode verified = _reporter.verify(generation);
    if (verified != KIOTTY_NET_CODE_SUCCESS) { return verified; }
    const bool starts_work = then.type == KIOTTY_NET_ACTION_TYPE_START_WORK;
    if (starts_work) { return KIOTTY_NET_CODE_INVALID_ARGUMENT; }
    const AdoptResult outcome = adoptAction(then, _send);       // WORKING 동안 send Stage 는 worker 의 것
    if (!outcome) { return outcome.code; }
    _reporter.finish(outcome.value);
    const Phase phase = _phase.load();
    if (phase == Phase::CLOSING) { return KIOTTY_NET_CODE_CLOSED; }
    return KIOTTY_NET_CODE_SUCCESS;
}

19. 메모리 할당

v4 19절의 원칙 (객체는 한 번 만들고 켜고 끈다, 메모리가 보장되는 시점은 create*, 은퇴한 Owner 는 OS 에 돌려주지 않는다, 잡아 둔 메모리는 쓰기 전까지 RAM 에 올라가지 않는다, Pool 은 소비의 상한이고 손상의 방어가 아니다, 멤버는 run 보다 오래 사는 상태뿐이다) 은 그대로다. 바뀐 것만 적는다.

19.1 원칙에서 바뀐 것

  • #2, #3: v4 는 "Context 는 타입별 포인터 표만 가진다. 메모리는 실제로 만든 Owner 에 비례한다" 였다. LazyReusablePool 이 std::vector<T> 위로 바뀌어 (commit ada2830) initialize 가 상한 개수의 Owner 를 한 번에 만든다. 메모리가 보장되는 시점이 create* 에서 initializeContext 로 당겨지고, 그 양은 MemoryLimits::OWNERS 와 Owner 의 sizeof 의 곱이다. 큰 배열은 default-init 이라 쓰기 전까지 RAM 에 올라가지 않는 것 (#5) 은 같다. Context 를 만들 때 이 양을 다시 재고, create* 의 KIOTTY_NET_CODE_OUT_OF_MEMORY 가 initializeContext 로 옮겨 가는지 정한다.
  • #7 (MISRA): 코드는 C++17 이다. 소유하지 않는 raw 포인터를 "쓴다" 에서 "쓰지 않는다 (수칙 1.10), 예외는 DV3 / DV12" 로 좁혔다.

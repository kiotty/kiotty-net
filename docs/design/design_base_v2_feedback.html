1. TLS hook 의 자리 (1.4) 부분 동의

제안: Stage 가 void* cipher_context 와 encode / decode 함수를 받고, context 가 있으면 알아서 암호화한다. 목표에 동의한다. 목표는 "Connection 이 TLS 인지 아닌지를 모른다" 이고, 그것이 v1 의 B 보다 낫다. 다만 hook 을 Stage 안에 두면 세 가지가 걸린다.

  1. TLS 는 바이트 → 바이트 변환이 아니다. cipher 바이트 100 을 넣으면 평문 0 (레코드가 아직 안 찼다) 이 나올 수도, 평문 80 이 나올 수도 있다. 그래서 cipher 버퍼와 plain 버퍼가 따로 있어야 하고, hook 을 가진 Stage 는 안에 Stage 를 하나 더 가진 "두 버퍼짜리" 가 된다.
  2. handshake 는 받는 쪽에서 보내는 쪽으로 넘어간다. recv Stage 의 decode 가 handshake 바이트를 소화하면 그 답 (ServerHello 등) 은 send 쪽으로 나가야 한다. recv Stage 와 send Stage 가 같은 context 를 공유하고 둘 사이에 길이 있어야 한다. Stage 둘이 서로를 알게 된다.
  3. core 의 Stage 가 TLS 를 알게 된다. Stage 는 push ring, HTTP 응답 버퍼, StreamClient 에도 쓰이는데 그 모두가 cipher 포인터 셋을 들게 된다.

그래서 hook 을 Stage 가 아니라 Connection 의 "받는 길 / 보내는 길" 에 둔다. 제안하신 cipher_context + encode + decode 를 인터페이스 하나로 묶고, 평문은 아무것도 안 하는 구현을 꽂는다. 그러면 Connection 에 if (tls) 가 한 줄도 없다.

class Codec                                     // connection/kiotty_codec.h. Connection 의 받는 길과 보내는 길

2. timeout 은 action 의 필드 (2.1, 7) 동의

맞다. action 이 timeout 을 가지면 timeout 을 거는 별도 인터페이스가 없다. KiottyNet_setConnectionTimeout 은 지운다. 모든 action 생성 함수가 timeout_ms 를 받고 0 은 "없음" 이다. 의미는 "이 action 이 시작한 기다림의 한도" 하나다.

actiontimeout_ms 가 재는 것지나면
READ, READ_UNTIL조건이 찰 때까지onTimeout. 그 return 이 다음 action
WRITEonWritten 까지onTimeout. 느린 peer 를 끊을지 사용자가 정한다
HOLD아무 일도 없이 기다리는 한도 (push 나 timeout 만 기다린다)onTimeout
START_WORK없음 (0 만 허용). 다음 action 은 worker 의 finishWork 가 가져오고 그것이 자기 timeout 을 가진다—

HOLD 에 timeout 이 있으므로 "timeout 만 기다리는" 경우도 KiottyNet_holdConnection(timeout_ms) 하나로 된다. 7번의 혼란은 여기서 끝난다: setTimeout 은 없다.

3. 제출은 IO Thread 만, 다른 thread 는 wake 만 (2.2) 부분 동의

고민의 뿌리는 "finishWork 와 notify 는 다른 thread 인데, 거기서 EventListener 에 제출하려면 Connection 이 EventListener 를 알아야 한다" 이다. 답은 다른 thread 는 제출하지 않는다 이다. 다른 thread 가 하는 일은 "할 것을 Connection 에 적어 두고 IO Thread 를 깨우는 것" 뿐이고, 제출은 깨어난 IO Thread 가 평소와 같은 길로 한다. 그러면 Connection 은 EventListener 를 영영 모른다.

3.1 왜 IOCP 에서도 다른 thread 가 WSASend 하면 안 되는가

  • thread 가 끝나면 그 thread 가 건 overlapped IO 는 취소된다. worker 가 WSASend 를 걸고 return 한 뒤 그 thread 가 종료되면 (thread pool 이 줄어들 때) 보내던 것이 ERROR_OPERATION_ABORTED 로 끝난다. IOCP 에 붙은 소켓도 같다.
  • lane 과 Stage 는 thread-safe 가 아니다. worker 가 write lane 에 쓰는 동안 IO Thread 가 같은 lane 을 drain 하면 안 된다. 구현 가이드 1.5 가 WORKING 동안 IO Thread 가 write lane 을 안 만지기로 한 이유가 이것이다. 그 약속은 "제출은 한 thread" 일 때만 지킬 수 있다.
  • onWritten 은 어차피 IO Thread 가 낸다. 완료는 IOCP 큐로 오므로 worker 가 걸어도 콜백은 IO Thread 다. 걸기만 다른 thread 에서 하면 얻는 것이 없다.

그래서 IOCP 도 epoll 과 같은 길을 간다. backend 분기가 없다.

3.2 epoll 에서 "감시해 달라고 부탁" 은 한 번뿐이다

epoll 의 등록 (epoll_ctl ADD) 은 연결이 열릴 때 IoLoop 가 한 번 한다 (_listener.attach(socket.handle(), slot)). IoLoop 는 listener 와 host 를 둘 다 들고 있으므로 여기서 Connection 이 listener 를 알 필요가 없다. 그 뒤의 receive 는 늘 걸려 있고 (readable 이 오면 listener 가 recv 해서 provider 에 쓴다), send 는 IO Thread 가 submitSend 할 때 바로 send 해 보고 EAGAIN 이면 EPOLLOUT 을 켠다. 전부 IO Thread 다.

3.3 세 길이 같은 모양이 된다

다른 thread 의 호출Connection 에 적는 것깨우기IO Thread 가 하는 것
콜백의 return (IO Thread 자신)——apply(connection, action)
finishWork(work, action)_work_outcome = action 뒤 CAS WORKING → DONE_listener.wake()scan 에서 DONE 을 보면 apply(connection, takeWorkOutcome()). 콜백의 return 과 같은 함수다

close() (소유자)_stopped = true_listener.wake()loop 를 끝낸다

finishWork 는 "미뤄진 return" 이다. worker 가 return 할 action 을 Connection 에 맡겨 두면 IO Thread 가 대신 return 한 것처럼 적용한다. 그래서 EventListener 에 다른 thread 가 들어갈 길은 wake() 하나다 (PostQueuedCompletionStatus / eventfd / kqueue EVFILT_USER / io_uring msg ring). 이것이 v0 의 5번에서 startWork / finishWork / notify 를 IoLoop 의 메서드로 둔 이유였는데, 그때는 "왜 다른 thread 가 직접 제출하면 안 되는가" 를 적지 않았다.

3.4 주입은 필요 없다

"Connection 을 만들 때 submit 인터페이스를 주입" 은 위 표에서 필요한 곳이 없다. 다른 thread 는 Connection 의 atomic 둘 (_work_state, _work_outcome) 과 IoLoop 의 PushSlot 에만 쓴다. 제출하는 코드는 IoLoop 안의 두 줄 (submitReceive, submitSend) 과 Acceptor 의 한 줄뿐이다. 의존은 ioloop → event_listener, ioloop → connection 로 그대로고 역방향 선이 없다.

4. create 가 Result 를 돌려준다 동의

create 시점에 아는 것이 낫다. C 에서 struct 반환은 값이므로 할당이 없다.

typedef struct KiottyNetServerResult
{
    KiottyNetCode         code;                 // SUCCESS 가 아니면 handle 은 NULL. TLS stub 이면 KIOTTY_TLS_NOT_SUPPORTED, slot 이 없으면 KIOTTY_TABLE_FULL
    KiottyNetServerHandle handle;
} KiottyNetServerResult;

KIOTTY_NET_API KiottyNetServerResult KiottyNet_createServer(KiottyNetContext context, const KiottyNetServerConfig* config, const KiottyNetTlsServerConfig* tls);

EventClient, StreamClient 도 같은 모양의 struct 를 각각 가진다 (타입이 달라 서로 섞이지 않는다). C++ 의 KiottyNet_Server 생성자는 code 를 _code 에 보관하고 valid() 와 code() 를 둘 다 둔다. 같은 이유로 KiottyNet_createContext 도 KiottyNetContextResult 로 바꾸면 "왜 NULL 인가" 가 모든 create 에서 사라진다.

5. 콜백 이름 (5) 부분 동의

"accept 는 서버만 하는 일이니 양쪽에 다 오는 콜백은 onConnected" 에 동의한다. 전송 계층이 이어진 시점이고 서버와 클라이언트가 같은 뜻이다. 그 다음 콜백 (첫 action 을 return 하는 것) 을 onHandshake 로 하자는 데는 하나 걸린다. 평문 연결에는 handshake 가 없어서 onHandshake 가 "아무 일도 없이" 바로 온다.

전송 계층 연결 (accept / connect 직후, handshake 전)onConnectedKiottyNetConnectionDecision (accept / ignore + context)info 로 거른다context 만 준다
데이터를 주고받을 수 있게 됨 (handshake 뒤. 평문은 바로)onHandshake (제안) 또는 onReady (추천)첫 action같다같다

추천: onReady. "handshake 가 끝났다" 는 TLS 의 사정이고 사용자에게 보이는 사실은 "이제 read / write 를 걸 수 있다" 다. onHandshake 로 가도 문제는 없다 (선택). struct 와 함수는 KiottyNetConnectionDecision, KiottyNet_acceptConnection(context), KiottyNet_ignoreConnection() 그대로다.

6. hold 와 Work (8) 우려

"hold 가 있고 다른 thread 가 IoCommand 를 제출할 수 있으면 Work 가 필요 없다" 는 절반이 맞다. 3절대로 다른 thread 는 제출하지 않고 적어 두기만 하므로, Work 가 하는 일을 다시 세어 보면 Work 는 hold + 소유권 표시 다.

Work 가 주는 것hold 만으로는
WORKING 동안 IO Thread 가 그 연결의 콜백을 하나도 내지 않는다 (onTimeout, onWritten, onDisconnected 까지). Session 을 worker 가 혼자 쓴다hold 중에도 peer 가 끊으면 onDisconnected 가 나간다. worker 가 Session 을 쓰는 중에 onDisconnected 가 그 Session 을 release 하면 use-after-release 다 (v0 15-7 의 문제가 이것이다)
write lane 을 worker 가 직접 쓴다 (finishWithWrite 는 복사 없이 lane 에 들어간다). IO Thread 는 안 만진다다른 thread 는 write lane 을 만질 수 없다. notify (push lane, 복사) 만 된다. 큰 응답은 push_capacity 에 묶인다
finishWork 는 한 번, generation 이 맞을 때만 받는다. 늦게 온 worker 의 결과가 재사용된 연결에 들어가지 않는다"다른 thread 가 아무 때나 action 을 적는다" 를 허용하면 그 action 이 IO Thread 의 pump 와 경쟁한다. CAS 상태가 결국 필요하다 = Work

그래서 Work 는 남긴다. 대신 return-action 모델이 Work 를 한 단계 줄여 준다. DRAINING 이 필요했던 이유는 "startWork 가 불릴 때 write lane 에 보내는 중인 메시지가 있을 수 있다" 였다. 콜백이 action 을 하나만 return 하면 WRITE 를 return 한 뒤 다음 콜백은 onWritten (또는 onTimeout, onDisconnected) 이고, onRead 는 READ 를 return 한 뒤에만 온다. 즉 START_WORK 가 return 되는 시점에 write lane 은 항상 비어 있다. 단 하나의 예외는 "WRITE 의 timeout 이 지나 onTimeout 이 START_WORK 를 return" 인데, 이것은 onTimeout 이 WRITE 중이면 START_WORK 를 거부 (KIOTTY_BUSY 로 close) 하면 된다.

v0 : RUNNING ──startWork──▶ DRAINING ──(write lane 비면, 다음 바퀴)──▶ WORKING ──finishWork──▶ DONE ──(scan 에서 apply)──▶ RUNNING
v2 : RUNNING ──START_WORK return──▶ WORKING (onWorkStarted 는 apply 안에서 바로) ──finishWork──▶ DONE ──(scan 에서 apply)──▶ RUNNING

지워지는 것: DRAINING, tryStartWork, _saved_read / _saved_deadline (START_WORK 가 return 된 콜백의 read 조건은 이미 소진됐다), scan 의 한 줄. 그리고 KiottyNet_startWork 는 "아무 thread 에서 부르는 함수" 가 아니라 다른 action 과 같은 return 값 이 된다 (v1 6.2 의 목록에 이미 그렇게 썼다). Work 를 std::move 로 다른 thread 에 넘기고 거기서 finishWork 하는 모양은 그대로다.

남는 논의 하나 (선택): finishWithWrite 가 write lane 에 직접 쓰는 특권을 유지할지, 아니면 Work 중의 쓰기도 모두 notify (push lane) 로 통일하고 finishWork 는 READ / HOLD / CLOSE 만 받을지. 후자는 lane 규칙이 "write lane 은 IO Thread 만" 으로 단순해지지만, 큰 응답 (HTTP body) 이 push_capacity 에 묶인다. 전자 (유지) 를 추천 한다.

7. 한 바퀴가 따를 규칙 (11) 동의

v1 의 runOnce 가 case by case 로 보인 이유는 Connection 의 hook 중 어떤 것은 action 을 돌려주고 (onReceived) 어떤 것은 안 돌려줘서 (onSent, tryStartWork) 호출 모양이 셋이었기 때문이다. 1 ~ 6 이 정해진 뒤 다시 쓰되, 그때 지킬 규칙을 먼저 적어 둔다. 코드는 설계 문서에서.

  1. Connection 의 모든 hook 은 IoAction 을 돌려준다. 콜백이 안 나간 hook 은 NONE 을 돌려준다. 그래서 loop 의 모든 줄이 apply(connection, connection.hook(...)) 한 모양이다.
  2. action 이 Connection 에 들어가는 길은 apply 하나다. 콜백의 return, finishWork 의 outcome, onTimeout 의 return 이 전부 같은 함수를 지난다. apply 는 재귀 없이 loop 다 (READ 가 바로 충족되어 onRead 가 또 action 을 내는 경우).
  3. 한 바퀴는 세 단계다. (a) wait, (b) 완료마다 hook 하나, (c) 연결마다 scan 하나 (DONE, deadline, written). 단계 안에서 분기는 completion.kind 와 scan 의 세 조건뿐이다.
  4. EventListener 에 들어가는 호출은 IoLoop 의 세 줄이다. submitReceive (receive 가 안 걸려 있고 provider 에 자리가 있으면), submitSend (send 가 안 걸려 있고 sendSegment 가 비어 있지 않으면), wake (다른 thread). 셋 다 Connection 의 상태를 읽고 IoLoop 가 결정한다.
  5. 다른 thread 는 적고 깨운다. 3절.

이 규칙으로 쓰면 (b) 는 kind 별 한 줄, (c) 는 조건 별 한 줄, apply 는 kind 별 한 줄이 되고 그 밖의 줄이 없어야 한다. 그렇게 안 되는 자리가 나오면 그것이 설계가 덜 된 곳이다.

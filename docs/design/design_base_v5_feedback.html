2026-10-29. design_base_v4_feedback.html 에 대한 12개 답변에 대한 답이다. 가장 큰 지적은 10번 ("proactor 인데 왜 상태를 계속 검사하나") 과 9번 (dispatch / resolve / submit 의 역할) 이다. 둘을 받아들이면 v4 의 _pending, _io_pending, markAttached, setRead 가 전부 사라지고, 한 completion 이 dispatch → resolve → submit 을 한 줄로 지나간다. 그래서 1절에서 그 구조를 먼저 고치고 (5, 9, 10, 11, 12), 2절이 "이벤트 관심을 끄는 일" (2, 12), 3절이 Connection 의 상태와 onReceived (4), 4절이 실시간 push (7, 8) 다.

  5. 실시간 push : 왜 40 ms 로 묶이는가 (7, 8)

1. dispatch → resolve → submit : 한 completion 이 한 줄로 (5, 9, 10, 11) 동의

10번이 맞다. v4 가 상태를 계속 검사한 이유는 DISPATCH 와 SUBMIT 을 다른 phase 로 떼어 놓아서 다. 떼어 놓으니 둘 사이에 action 을 보관할 자리 (_pending), "이미 걸렸나" 를 기억할 자리 (_io_pending), "이미 등록했나" 를 기억할 자리 (markAttached) 가 생겼다. completion 하나를 받으면 그 자리에서 dispatch → resolve → submit 을 끝내면 그 셋이 전부 없어진다. proactor 는 원래 그렇게 돈다: completion 하나 → 다음 요청 하나.

IoCompletion ──▶ dispatch ──▶ IoAction ──▶ resolve ──▶ IoPayload ──▶ submit ──▶ OS ──▶ IoCompletion (OS 가 준 것) Stage 갱신 (뜻) Stage 를 (자리) listener 에 + handler 보고 계산 action + payload (pump 반복)

1.1 세 동작의 타입 (9)

제안하신 역할 분담 그대로다. 셋이 서로 다른 타입을 주고받으므로 섞일 수 없다.

1.2 IoAction 과 IoPayload 를 나눈다 (5)

맞다. v4 는 "사용자의 뜻" 과 "실제 버퍼" 를 한 struct 에 넣고 io_buffer 가 비었는지로 둘을 구분했다. 그것이 또 하나의 상태 검사였다. 나눈다.

enum class IoActionKind : uint8_t { NONE, HOLD, READ, READ_UNTIL, WRITE, START_WORK, CLOSE, ACCEPT };   // ACCEPT 는 1.4
enum class IoPurpose    : uint8_t { USER, HANDSHAKE, CONTROL, NOTIFY };

struct IoAction                                 // 뜻. handler 가 준 것 + Connection 이 덧붙인 purpose. KiottyNetConnectionAction 과 같은 모양 + purpose
{
    IoActionKind kind;
    IoPurpose    purpose;
    uint32_t     timeout_ms;
    union
    {
        struct { size_t exact; }                                      read;
        struct { char delimiter[4]; uint8_t length; size_t max; }     read_until;
        struct { KiottyNetSpan data; }                                write;       // 사용자 메모리. dispatch 가 Stage 로 복사한 뒤에는 보지 않는다
        struct { KiottyNetCode reason; }                              close;
    } as;
};

struct IoPayload                                // 자리. resolve 가 만든다. listener 는 이것만 OS 에 넘긴다
{
    void*  buffer;
    size_t length;
};

void EventListener::submit(Holder<IoEvent>& event, SocketHandle socket, const IoAction& action, IoPayload payload);
//   READ / READ_UNTIL → receive(payload),  WRITE → send(payload),  ACCEPT → accept(payload = IOCP 의 주소 버퍼),  그 밖의 kind 는 오지 않는다
//   event 가 action 을 기억한다. 완료가 그 action 을 싣고 돌아온다 (1.3)

Segment 는 없다 (v3 의 뜻 그대로). KiottyNetSpan 을 안 쓰는 이유도 그대로다 (const 라 받을 자리에 못 쓴다).

1.3 completion 이 action 을 싣고 돌아온다

event 가 "무슨 action 으로 걸렸나" 를 들고 있으면 completion 이 그것을 돌려줄 수 있다. 그러면 Connection 이 "지금 걸린 read 조건" 을 따로 기억할 필요가 없다 (v4 의 _read). 조건은 action 안에 있고, 완료가 그 action 을 가져온다. READ_UNTIL 의 진행 위치 (_scanned) 도 action 안에 두면 Connection 에서 사라진다.

struct IoCompletion
{
    IoKind     kind;                            // ACCEPT, RECEIVE, SEND, WAKE (OS)  +  TIMEOUT, WORK_DONE (IoLoop 가 만든다)
    int32_t    slot;                            // ACCEPT / WAKE 는 -1
    SocketCode code;                            // SUCCESS, CLOSED (0 바이트), CANCELLED (2절), 그 밖의 오류
    size_t     length;
    IoAction   action;                          // RECEIVE / SEND / ACCEPT : 걸었던 action 그대로. TIMEOUT / WORK_DONE / WAKE : NONE
};

dispatch 는 completion.action.purpose 로 switch 한다 (3절). "이 completion 이 무엇에 대한 답인가" 를 Connection 의 상태가 아니라 completion 이 말한다.

1.4 ACCEPT 도 action 이다 (11)

맞다. Acceptor 가 혼자 특별 취급을 받은 이유는 ACCEPT 가 action 이 아니어서 같은 pipeline 을 못 탔기 때문이다. kind 에 ACCEPT 를 넣으면 Acceptor 는 "slot 이 -1 인 연결" 처럼 같은 세 동작을 지난다.

dispatchresolvesubmit
ACCEPT 완료admit(): acceptor.accept() → host.acquire() → onConnected → open + attach → onOpened 의 action 을 그 연결에 대해 resolve / submit. 그 다음 Acceptor 의 action: host.hasFreeSlot() ? ACCEPT : NONEIOCP: 미리 만든 소켓 + 주소 버퍼. epoll: 빈 payload_listener.submit(acceptor.event(), acceptor.socket(), action, payload)

남는 특별 취급 하나: slot 이 꽉 차서 NONE 을 냈다가 나중에 slot 이 비면 누가 다시 ACCEPT 를 거는가. 그것은 slot 을 비우는 자리 (CLOSE 의 마지막, 5절 settle) 에서 "Acceptor 의 event 가 비어 있으면 ACCEPT" 한 줄이다. 상태 검사가 하나 남지만 Connection 이 아니라 IoEvent 의 것 이고 (2.1), Acceptor 에만 있다. 이것보다 줄이려면 "꽉 차도 accept 하고 바로 닫기" (v0) 로 돌아가야 하는데 v1 6.1 에서 backlog 에 두기로 했으므로 한 줄을 받아들인다.

공개 KiottyNetConnectionAction 에는 ACCEPT 가 없다. 사용자가 return 할 수 없는 kind 는 IoAction::from() 이 만들 수 없다.

2. 관심을 끄는 일은 없다 : attach, submit, cancel, detach (2, 12) 부분 동의

질문: "proactor 는 받으려면 매번 다시 걸어야 하고 reactor 는 안 받으려면 명시적으로 끊어야 하는데, 왜 START_WORK 의 submit 이 아무것도 안 하나." 답은 우리 흉내에서는 "관심" 이 곧 "걸려 있는 요청" 이라서 다. 요청이 없으면 관심도 없다. 다만 하나 빠진 것이 있었다. 요청이 걸려 있는 채로 START_WORK 가 오는 경우다 (2.2).

2.1 epoll 흉내의 규칙 하나 : one-shot

epoll backend 는 fd 를 EPOLLONESHOT 으로 다룬다. submit(READ) 가 epoll_ctl(MOD, EPOLLIN | EPOLLONESHOT) 이고, readable 이 한 번 오면 kernel 이 관심을 스스로 끈다. listener 는 그때 recv 해서 payload 에 쓰고 completion 을 만든다. 다음 submit 이 와야 다시 켜진다. 그래서:

안 걸면아무것도 안 온다아무것도 안 온다 (레벨 트리거였다면 여기서 돌았을 것이다)START_WORK 의 submit 에 할 일이 없는 이유

reactor 의 "명시적으로 끊어야 한다" 는 레벨 트리거 + 영구 등록일 때의 일이다. 우리는 그 모드를 쓰지 않는다. 그래서 "안 받고 싶으면 안 건다" 가 양쪽에서 같다. IoEvent 가 armed() 하나를 든다 (submit 이 true, wait 가 completion 을 꺼낼 때 false). Connection 의 _io_pending 은 이것으로 대체된다 (3절).

2.2 빠진 것 : 걸려 있는 채로 다른 action 이 올 때 → cancel

completion 을 받아 dispatch 한 뒤 submit 하면 그 event 는 비어 있다. 그런데 TIMEOUT 과 WORK_DONE 은 OS completion 이 아니라 IoLoop 가 만든 것이라, 그 시점에 _stream_event 에 READ 가 걸려 있을 수 있다. 거기서 handler 가 START_WORK / CLOSE / HOLD / WRITE 를 return 하면 걸린 READ 를 끊어야 한다. 이것이 질문하신 "명시적으로 끊는" 자리이고 v4 에 없었다.

SocketCode EventListener::cancel(Holder<IoEvent>& event);   // IOCP: CancelIoEx → ERROR_OPERATION_ABORTED 완료가 온다
                                                            // epoll: epoll_ctl MOD 0 + event 에 cancelled 표시 → listener 가 다음 wait 에서 CANCELLED 완료를 만든다

양쪽 모두 completion 하나 (code CANCELLED) 가 돌아온다. dispatch 는 CANCELLED 를 "아무것도 안 하고 NONE" 으로 처리한다. 그래서 cancel 뒤에도 "event 는 completion 으로만 비워진다" 는 규칙이 지켜지고, settle 의 slot 반납 조건 (두 event 가 다 비었다) 도 그대로다.

WORK_DONE 에 READ 가 걸려 있을 수 있나: Work 중에는 걸지 않으므로 (1.3 의 "recv 는 늘 걸려 있지 않다") 없다. 그래서 cancel 이 실제로 일어나는 자리는 TIMEOUT 뒤의 START_WORK / CLOSE / HOLD / WRITE 넷이다.

3.1 onReceived : IoCompletion 이 첫 인자, purpose 로 switch

규칙 셋을 그대로 적용했다. on* 은 첫 인자가 const IoCompletion&, Phase 로 먼저 자르고, purpose 로 switch, TLS 분기는 그 안의 한 줄.

IoAction Connection::onReceived(const IoCompletion& completion, const Handler& handler)
{
    if (_phase == Phase::CLOSING)                       return IoAction::none();           // 늦은 완료. settle 이 event 가 비었는지만 본다
    if (completion.code == SocketCode::CANCELLED)       return IoAction::none();           // 2.2. 끊은 쪽이 이미 다음 action 을 냈다
    if (completion.code != SocketCode::SUCCESS)         return onPeerGone(completion.code);  // CLOSED (0 바이트) 포함

    switch (completion.action.purpose)                                                        // 어느 Stage 에 들어왔나
    {
    case IoPurpose::HANDSHAKE:                                                                // _phase == HANDSHAKING 일 때만 이 purpose 가 온다
        _tls.cipherReceive().provider().commit(completion.length);
        return onHandshake(handler);                                                          // SEND / RECEIVE / DONE(onReady) / FAILED(onError + CLOSE)

    case IoPurpose::USER:                                                                     // _phase == READY
        if (_tls.active())
        {
            _tls.cipherReceive().provider().commit(completion.length);
            KiottyNetCode decoded = _tls.decode(_receive_stage);                             // cipher → plain. 레코드가 덜 찼으면 0 바이트
            if (decoded != KIOTTY_SUCCESS) { handler.onError(_app_context, handle(), decoded, _tls.lastMessage()); return IoAction::close(decoded); }
            if (_tls.hasControlOutput())  return IoAction::write(IoPurpose::CONTROL);         // KeyUpdate 답장. 보낸 뒤 completion.action (READ) 으로 돌아온다
        }
        else
        {
            _receive_stage.provider().commit(completion.length);
        }
        return pump(completion.action, handler);                                              // 걸었던 READ 조건을 Stage 에 대 본다. 찼으면 onRead 의 return, 안 찼으면 같은 READ

    case IoPurpose::CONTROL:
    case IoPurpose::NOTIFY:
        return IoAction::none();                                                              // RECEIVE 에는 오지 않는 purpose. 방어
    }
}

4. 실시간 push : 왜 40 ms 로 묶이는가 (7, 8) 우려

7번을 다시 읽으면 걱정은 "IO Thread 가 Notification Stage 가 찰 때까지 모았다가 보내서, 20 ms 마다 받아야 할 클라이언트가 한 번을 못 받고 다음에 둘을 받는다" 이고, 8번이 그 실측이다 (SecuritSocket 에서 동기 write 로 풀었다). 둘로 나눠 답한다. 하나는 "이 설계는 모으지 않는다", 다른 하나는 "40 ms 는 context switch 가 아닐 가능성이 크다".

4.1 이 설계는 모으지 않는다

  • notify 가 Stage 에 넣고 wake() 하면 IO Thread 는 지금 바퀴를 마치고 바로 그 연결의 WRITE(NOTIFY) 를 submit 한다. "찰 때까지" 기다리는 코드는 없다. 기다리는 유일한 경우는 앞의 notify send 가 아직 안 끝났을 때 이고 (한 event 에 하나), 그 완료가 오면 그 사이 쌓인 것을 한 번에 건다. 그것은 "모으기" 가 아니라 "따라잡기" 다. 두 번째 메시지는 어차피 그 시점이 자기 차례다.
  • IO Thread 를 깨우는 비용은 idle 한 thread 를 깨우는 비용이다. PostQueuedCompletionStatus → GetQueuedCompletionStatus 복귀, eventfd write → epoll_wait 복귀. 수십 µs 다. 20 ms 의 1 / 500 이다.
  • 그 수십 µs 가 수 ms 가 되는 조건은 하나다: IO Thread 가 사용자 콜백 안에서 오래 머무를 때. "콜백은 짧고 긴 일은 Work" 가 이 모델의 전제이고, push 의 실시간성은 그 전제에 달려 있다.

4.2 40 ms 는 Nagle + delayed ACK 의 숫자다

"20 ms 간격 같은 길이의 buffer 가 2 ~ 3 개 묶여 40 ms 간격으로" 는 TCP 의 고전 증상과 숫자가 같다. Nagle (앞 조각의 ACK 가 오기 전에는 작은 조각을 보내지 않는다) 과 수신측 delayed ACK (Linux 40 ms, Windows 200 ms 를 두 세그먼트마다) 가 맞물리면 작은 메시지가 정확히 40 ms 단위로 묶여 나간다. 송신 thread 가 동기 write 를 해도 이 묶임은 그대로다. 동기 write 가 SecuritSocket 에서 효과가 있었다면, 그 서버가 TCP_NODELAY 를 켰거나 메시지가 MSS 보다 컸을 가능성이 있다.

4.3 그래도 "보내는 쪽이 직접" 이 필요하면

SecuritSocket 의 모양 (producer thread 가 active client 들에 동기 write) 을 그대로 두는 것은 v4 4.4 의 이유로 안 된다: 걸려 있는 overlapped send 와 순서가 섞이고, TLS 면 레코드 순서가 깨져 peer 가 끊는다. 대신 thread hop 자체를 없애는 길이 하나 있다. 데이터를 만드는 주기를 IO Thread 안에 두는 것이다.

// Server 에 주기 콜백 하나. IoLoop 의 deadline 하나가 더 늘 뿐이다 (연결의 deadline 과 같은 collect 가 본다)
KIOTTY_NET_API KiottyNetCode KiottyNet_setServerTick(KiottyNetServerHandle server, uint32_t interval_ms);

void (*onTick)(KiottyNetAppContext app_context);        // IO Thread. 안에서 KiottyNet_broadcastServer / notifyConnection 을 부른다
                                                        // IO Thread 안이므로 lock 뒤 바로 같은 바퀴의 submit 이다. wake 도 context switch 도 없다

producer thread 는 최신 샘플을 double buffer 에 두고, onTick 이 20 ms 마다 그것을 broadcast 한다. 송신 시점의 jitter 는 IoLoop 의 deadline 정밀도 (ms) 다. 이것이 "active client 들에 동기 write" 와 같은 시간표를 thread 하나로 만든다. 선택: 지금 넣을지, 4.2 를 측정한 뒤 넣을지. 추천: TCP_NODELAY 기본 + onTick 은 설계 문서에 자리만 잡아 두고, 실측에서 wake 지연이 보이면 넣는다.

그래서 "지금 서버가 SecuritSocket 의 broadcast 서버를 대체할 수 있는가" 에 대한 답: 20 ms 주기는 할 수 있다. 조건은 TCP_NODELAY 와 짧은 콜백이다. 그 둘이 지켜지면 wake 경로의 지연은 주기의 1 % 아래다.

5. 다시 짠 한 바퀴

1 ~ 3 절을 반영하면 phase 는 셋이고 (collect, completion 마다 한 줄, settle), 상태를 읽어 판단하는 줄은 armed() 세 번 (2.2 의 cancel, settle 의 반납, Acceptor 의 재무장) 뿐이다.

void IoLoop::runOnce()
{
    Span<const IoCompletion> completions = collect();                                    // OS 완료 + TIMEOUT + WORK_DONE. 바뀐 것 없다 (v4 Phase 1)
    for (const IoCompletion& completion : completions) step(completion);                // completion 하나 → dispatch → resolve → submit
    flushNotifications();                                                                // notify event 가 비어 있고 Stage 에 바이트가 있는 연결 → WRITE(NOTIFY) 한 줄
    settle();                                                                            // CLOSING 이고 두 event 가 비면 slot 반납. Acceptor 재무장. stop_when_empty
}

void IoLoop::step(const IoCompletion& completion)
{
    if (completion.kind == IoKind::WAKE)   return;                                      // 깨우기만. flushNotifications 와 run 의 while 이 본다
    if (completion.kind == IoKind::ACCEPT) { admit(); arm(_acceptor, _host.hasFreeSlot() ? IoAction::accept() : IoAction::none()); return; }

    Connection& c = _host.at(completion.slot);
    IoAction action = dispatch(c, completion);                                           // 3절의 on* 중 kind 에 맞는 하나. handler 는 여기서만
    if (c.streamEvent().armed() && needsCancel(action))                                  // 2.2. TIMEOUT 뒤의 START_WORK / CLOSE / HOLD / WRITE
    {
        _listener.cancel(c.streamEvent());                                               // CANCELLED 완료가 돌아온 뒤 WRITE 는 그때 건다 (dispatch 가 action 을 들고 있다)
        return;
    }
    arm(c, action);
}

void IoLoop::arm(Connection& c, IoAction action)                                         // resolve → submit. Acceptor 도 같은 함수 (overload)
{
    switch (action.kind)
    {
    case IoActionKind::NONE:
    case IoActionKind::HOLD:        c.setDeadline(action.timeout_ms);                                              return;
    case IoActionKind::START_WORK:  c.startWork(); handler().onWorkStarted(c.context(), c.workHandle());            return;
    case IoActionKind::CLOSE:       handler().onDisconnected(_app_context, c.context(), c.handle(), action.as.close.reason);
                                    _listener.detach(c.socket()); c.closeSocket();                                  return;   // phase = CLOSING
    case IoActionKind::READ:
    case IoActionKind::READ_UNTIL:
    case IoActionKind::WRITE:       c.setDeadline(action.timeout_ms);
                                    _listener.submit(c.eventFor(action.purpose), c.socket(), action, c.resolve(action));   return;
    }
}

IoAction Connection::dispatch(const IoCompletion& completion, const Handler& handler)   // kind 별 on* 하나. 전부 (completion, handler) 를 받는다
{
    switch (completion.kind)
    {
    case IoKind::RECEIVE:   return onReceived(completion, handler);                     // 3.1
    case IoKind::SEND:      return onSent(completion, handler);
    case IoKind::TIMEOUT:   return onTimeout(completion, handler);
    case IoKind::WORK_DONE: return onWorkFinished(completion, handler);
    }
}

IoPayload Connection::resolve(const IoAction& action)                                     // 뜻 → 자리. 콜백 없음, listener 없음
{
    switch (action.kind)
    {
    case IoActionKind::READ:
    case IoActionKind::READ_UNTIL: { Stage& in  = receiveStage(action.purpose);           // HANDSHAKE / TLS USER : cipherReceive, 평문 USER : _receive_stage
                                     size_t n   = in.provider().writable();
                                     return IoPayload{ in.provider().prepare(n), n }; }
    case IoActionKind::WRITE:      { Stage& out = sendStage(action.purpose);              // HANDSHAKE / CONTROL / TLS USER : cipherSend, NOTIFY : cipherNotify 또는 _notification_stage, 평문 USER : _send_stage
                                     size_t n   = out.consumer().readable();
                                     return IoPayload{ out.consumer().peek(), n }; }
    }
}

dispatch 의 WRITE(USER) 가 사용자 span 을 _send_stage 에 복사하고 (TLS 면 encode 까지) 돌아오므로 resolve 는 Stage 만 본다. dispatch 의 READ 가 pump 로 "이미 찼으면 onRead" 를 끝내고 돌아오므로 resolve 는 "받을 자리" 만 본다. resolve 에 분기가 kind 둘, purpose 가 고르는 Stage 하나 뿐인 것이 9번의 역할 분담이 맞았다는 증거다.

골라 주실 것

  1. 1.3 completion 이 action 을 값으로 싣는다 (추천. ~48 바이트 복사) 또는 event 안의 action 을 포인터로 가리킨다
  2. 2.2 cancel 을 넣는다 (추천) 또는 TIMEOUT 뒤의 START_WORK / CLOSE 는 걸린 READ 의 완료를 기다렸다가 적용한다 (cancel 없음. 늦어진다)
  3. 4.2 TCP_NODELAY 를 기본으로 켠다 (추천) 또는 config 옵션으로 끈 채 시작
  4. 4.3 onTick: 설계 문서에 자리만 (추천) 또는 지금 넣는다
  5. 남은 것: v4 1.3 (HOLD 중 끊김 감지), Span, 15-1, 15-4

1. Stream : Work 동안 쥐는 동기 통로 (2, 6) 동의

맞다. KiottyNet_readConnection(handle, ...) 이 onRead 에서 받은 handle 로 불리면 "되는 줄 알고" 부른다. runtime 에서 BUSY 를 돌려주더라도 API 가 그 실수를 유도하면 안 된다. 동기 IO 는 다른 타입으로 분리한다. 그러면 v6 의 "handle 은 하나" 는 이렇게 다듬어진다: 비동기 쪽 handle 은 KiottyNetConnectionHandle 하나 (notify, getInfo), 동기 쪽은 KiottyNetConnectionStream 하나 (read, write, writeFile). 둘은 할 수 있는 일이 겹치지 않는다. 그래서 타입이 둘이어도 "같은 값에 타입 둘" 이 아니다.

1.1 누가 만드나

"Connection 에서 만드는데 IO Thread 에서는 생성 불가" 보다 한 단계 더 단순하게 할 수 있다. 라이브러리가 만들어서 onWorkStarted 로 준다. 사용자는 만들지 않는다. 그러면 open 함수도, "지금 만들 수 있나" 검사도 없다. Stream 이 손에 있다는 것이 곧 "지금 이 연결은 네 것" 이라는 뜻이다.

2. 송신은 tx 하나 (5) 동의

"notification 과 write 는 모아서 나가는 게 맞다" 가 결론이고, 거기서 한 걸음 더 간다. v6 은 평문 Stage 둘 (send, notify) 과 암호문 Stage 하나를 두고 "고르는 순간에 encode" 라고 했다. 그 "고르기" 가 WriteLane 이 되어 머리를 복잡하게 했다. 고르지 않으면 고르는 것이 없다.

보낼 것은 들어오는 즉시 tx 에 들어간다 (평문이면 복사, TLS 면 encode). 한 번의 WRITE 는 그 순간 tx 에 있는 바이트 전부다. WRITE 는 그것을 다 보내야 완료된다 (3b 계약). 완료가 오면 tx 를 그만큼 비운다.
Stage누가 쓰나누가 읽나들어가는 것
receiveIO Thread (완료 commit, TLS 면 decode 의 출력)onRead 의 span, Stream 의 readpeer 가 보낸 평문
txIO Thread 만socket (WRITE 의 payload)USER 메시지, handshake, control, 그리고 notify Stage 에서 옮겨 온 notify. 평문 모드면 평문, TLS 모드면 전부 암호문
notify아무 thread (mutex)IO Thread (tx 로 옮길 때)notify / broadcast 의 평문. 다른 thread 가 encode 할 수 없고 (SSL 은 IO Thread 만), tx 에 섣불리 끼면 순서가 깨지므로 대기실이 필요하다. 이것이 notify Stage 가 따로 있는 유일한 이유다

v2 와 비교하면 TLS 의 Stage 가 여섯 (plain receive / send / notify + cipher receive / send / notify) 에서 넷 (receive, tx, notify + cipher receive) 로 준다. cipher receive 는 decode 의 입력이라 TlsEngine 안에 그대로 둔다. "암호화 순서 = 송신 순서" 는 규칙으로 지키는 것이 아니라 tx 가 하나라서 저절로 지켜진다.

2.1 notify 는 언제 tx 로 옮기나

write event 가 비어 있을 때만. 그 자리는 두 곳이다 (IoLoop 의 broadcast 가 slot 마다 한 번, 그리고 SEND 완료 직후). 옮기는 순간 notify Stage 에서는 바로 consume 한다. tx 에 복사되었으니 notify Stage 의 할 일은 끝이다. 그래서 완료 때 notify 쪽에서 치울 것이 없다. 이것이 질문 4 ("Notification 자원은 어떻게 정리하지") 의 답이다.

옮기지 않는 때: HANDSHAKING (평문으로 나가 버린다), WORKING (worker 의 것), write event 가 pending (지금 커널이 tx 앞부분을 읽고 있다. 뒤에 붙이는 것은 되지만 굳이 지금 옮길 이유가 없다. 다음 완료 때 옮긴다).

2.2 완료 때 무엇을 아나 : _write_length 하나

tx 안에 USER 메시지와 notify 가 섞여 있어도 완료 때 구분할 것은 하나다. "이 WRITE 에 사용자의 메시지가 들어 있었나, 몇 바이트였나" — onWritten 을 부르기 위해서다. notify 는 이미 정리되었고 handshake / control 은 완료 뒤 할 일이 Phase 로 정해진다. 그래서 v2 9.2 의 _write_length 가 그대로 그 일을 한다. 둘로 나눌 뿐이다.

size_t _user_staged;     // tx 에 들어갔지만 아직 submit 되지 않은 사용자 메시지의 평문 길이. adopt(thenWrite) 가 채운다
size_t _user_sending;    // 지금 걸린 WRITE 에 실린 사용자 메시지의 평문 길이. submit 때 _user_staged 를 옮겨 받고 _user_staged = 0. 0 이면 onWritten 없음

왜 둘인가: notify 가 나가는 중에 onRead 가 thenWrite 를 돌려주면 그 메시지는 tx 뒤에 붙지만 지금 걸린 WRITE 에는 들어 있지 않다 (4.3 의 경우). 그 WRITE 의 완료에서 onWritten 을 부르면 안 된다. 그래서 "tx 에 있다" 와 "지금 나가고 있다" 를 나눈다.

IoAction 의 purpose 는 이제 쓸 자리가 없다. WRITE 의 완료는 _user_sending 과 Phase 로, READ 의 Stage 는 _tls.active() 로 정해진다. IoPurpose 를 지운다 (choices 2). IoAction 이 작아진다.

2.3 dispatch 와 resolve 는 그대로다

"dispatch 와 resolve 를 reduce 해서 합쳐진 WRITE 요청을 만드는 작업이 필요하다" — 그 작업이 resolve(WRITE) 다. 새 단계가 아니다. v2 의 resolve(WRITE) 는 "send Stage 의 readable 전체" 였고, v3 의 resolve(WRITE) 는 "notify 를 tx 로 옮긴 뒤 tx 의 readable 전체" 다. 한 줄이 늘었다. IoSubmission 은 이름의 문제다. listener 가 받는 (action, payload) 를 struct 하나로 묶어 그렇게 부르든 둘로 넘기든 뜻은 같다. 유지해도 좋다.

IoPayload Connection::resolve(const IoAction& action)
{
    if (action.kind == IoActionKind::WRITE)
    {
        moveNotifyIntoTx();                                 // READY 일 때만. lock 안에서 notify → tx (복사 또는 encode), notify consume
        _user_sending = _user_staged;
        _user_staged = 0;
        size_t ready = _tx.consumer().readable();
        return IoPayload{ _tx.consumer().peek(), ready };
    }
    Stage& in = _tls.active() ? _tls.cipherReceive() : _receive;
    size_t room = in.provider().writable();
    return IoPayload{ in.provider().prepare(room), room };
}

  • 늘어나는 것은 평문 notify 한 번 뿐이다. notify 는 push_capacity 로 묶인 작은 바이트고 뜨거운 길이 아니다. 대신 평문과 TLS 가 같은 그림이 되고 WSASend / writev 의 scatter 버퍼가 필요 없다 (listener 는 그대로다). 줄어드는 것은 TLS USER write 의 평문 복사 한 번이다.
  • libuv 의 0 복사는 공짜가 아니다. uv_write 는 사용자 버퍼의 포인터만 큐에 넣고 (uv_write_t 연결 리스트), 콜백이 올 때까지 사용자가 버퍼를 살려 두어야 한다. 우리는 "return 하면 끝" 을 택했다 (v2 5절 "IoAction 은 사용자 메모리를 가리키지 않는다"). 의료기기 소프트웨어에서 dangling 을 사용자에게 맡기는 것보다 복사 한 번이 낫다. 큰 것은 Stream 의 writeFile 로 0 복사다.
  • libuv 도 lane 은 하나다. Unix 에서 uv_write 는 큐의 머리 요청만 writev 하고, 일부만 나가면 그 요청의 offset 을 전진시켜 다음 POLLOUT 에 이어 보낸다. 머리가 끝나기 전에 다음 요청을 시작하지 않는다. 우리가 5번에서 도달한 결론과 같다. Windows 에서는 libuv 가 WSASend 를 요청마다 바로 걸지만, Windows 는 한 socket 의 overlapped send 를 커널 (AFD) 이 건 순서대로 줄 세우므로 섞이지 않는다. epoll 에서만 사용자 공간이 줄을 세워야 한다. "IOCP 는 되는데 epoll 은 안 된다" 가 바로 그것이다.

4. 네 가지 경우의 flow (5)

기호: tx[..] 는 tx 의 내용 (앞이 먼저 나간다), W 는 write event 의 pending 여부, us 는 _user_sending, st 는 _user_staged. 연결은 READY 이고 사용자 action 은 READ(USER) 가 걸려 있다 (read event pending). TLS 면 "복사" 를 "encode" 로 읽으면 된다. 그 밖에 다른 점은 없다.

TLS 면 바퀴 3 의 tx 는 [레코드(AAAA) | 레코드(MM)] 이고 완료 length 는 암호문 길이다. _user_sending 은 평문 4 를 따로 들고 있으므로 onWritten 은 여전히 4 다. 레코드 둘이 한 WSASend 로 나가는 것은 TLS 에서 정상이다.

5. START_WORK 가 write 와 겹칠 때 : DRAINING 이 필요한 유일한 자리 (4) 부분 동의

"notification 용 event 를 따로 떼어 내면 DRAINING 은 신경 쓸 필요가 없는데" — 5번에서 그 길이 막혔으므로 (notify 도 같은 lane), 남는 질문은 "그래도 DRAINING 이 정말 필요한가" 다. 답: 한 경우에만 필요하고, 그 경우는 피할 수 없다. 그러나 상태 enum 이나 바퀴마다의 검사가 아니라 bool 하나다.

그 경우: notify 가 나가는 중 (W=1) 에 onRead 가 thenWork 를 돌려준다. 이 순간 커널이 tx 앞부분을 읽고 있다. worker 에게 지금 Stream 을 주면 worker 의 send 가 그 뒤에 끼어든다 (epoll 은 섞이고, IOCP 는 overlapped 와 동기 send 를 섞는 것이다). 걸린 send 를 취소하는 것은 메시지를 반 토막 내는 일이라 더 나쁘다 (v2 원칙 4 "cancel 은 없다"). 그러니 그 send 가 끝나기를 기다리는 것 외에 길이 없다. 그것을 무엇이라 부르든.

W == 0 일 때 (대부분) adopt(START_WORK): W == 0 → WORKING, onWorkStarted(ctx, stream) 같은 step 안에서. 기다림 없음 W == 1 일 때 adopt(START_WORK): W == 1 → _work_requested = true, return NONE ... SEND 완료 ... onSent: tx.consume ; us == 0 (사용자 메시지는 없다. 사용자는 READ 중이었다) _work_requested → WORKING, onWorkStarted(ctx, stream) ◀── 다음 WRITE 를 걸지 않는다. tx 는 비어 있다
  • START_WORK 가 return 되는 자리에서 read event 는 늘 비어 있다: onRead 는 RECEIVE 완료를 소비한 뒤이고, onReady 는 아직 아무것도 안 걸었고, onWritten 때는 사용자 READ 가 없고 (사용자 action 은 한 번에 하나), onTimeout 에 read 가 걸려 있으면 v2 11절대로 BUSY 다. 그래서 기다릴 것은 write event 하나다.
  • tx 에 사용자 메시지가 staged 된 채 START_WORK 가 올 수는 없다 (thenWrite 뒤에는 onWritten 이 와야 다음 action 을 낸다). handshake / control 바이트는 READY 에서 control 답장이 나가는 중일 수 있는데, 그것도 W=1 에 포함되어 같은 길로 기다린다.
  • WorkContext 에 DRAINING 상태를 두는 것과 _work_requested bool 하나는 같은 것이다. 구현 가이드 1.5 처럼 WorkContext 의 State 에 넣는 쪽이 한 곳에 모여 읽기 쉽다. 이름은 중요하지 않다. 중요한 것은 "바퀴마다 모든 slot 을 보며 DRAINING 인가 묻지 않는다" 는 것이다. 전이는 SEND 완료 한 자리에서만 일어난다.
  • Work 중 notify: notify Stage 에 쌓인다. 옮기는 자리 (resolve, broadcast) 가 WORKING 을 건너뛰므로 저절로 그렇다. WORK_DONE 의 첫 일이 그 바퀴의 broadcast 에서 옮겨지는 것이다. 특별한 코드가 없다.

6. Connection 이 드는 것 (v3)

v2 9.2 의 표를 다시 쓴다. 줄어든 것이 보이도록 v2 와 나란히 둔다.

v2v3왜
_stream_event, _notify_event_read_event, _write_event방향으로 나눈다 (v6 5절)
_plain StageSet { receive, send, notify } + _tls.cipher() { receive, send, notify }_receive, _tx, _notify + _tls.cipherReceive()송신은 tx 하나 (2절)
_resume_read없음control 답장이 나가는 중에도 READ 는 read event 에 바로 걸 수 있다. 미룰 것이 없다
_write_length, _notify_plain_length_user_staged, _user_sending2.2. notify 의 평문 길이는 옮길 때 바로 consume 하므로 들 필요가 없다
_peer_closed없음Work 중 IO Thread 는 socket 을 보지 않는다. worker 의 Stream 이 끊김을 직접 본다

_phase, _deadline, _socket, _slot, _generation, _context, _info, _state, _handshake_timeout_ms, _app_context그대로

IoAction 에서 purpose 가 빠지고, IoKind 는 그대로 여섯, listener 는 3b 코드 그대로다 (WRITE 완료 = payload 전부 계약 한 줄만).

onSent 는 이렇게 짧아진다.

IoAction Connection::onSent(const IoCompletion& completion, const Handler& handler)
{
    if (_phase == Phase::CLOSING)
    {
        return IoAction::none();
    }
    if (completion.code != SocketCode::SUCCESS)
    {
        return onPeerGone(completion.code);
    }
    _tx.consumer().commit(completion.length);
    if (_phase == Phase::HANDSHAKING)
    {
        return onHandshake(handler);
    }
    if (_work.requested())
    {
        return IoAction::startWork();                       // apply 가 WORKING 으로 올리고 onWorkStarted
    }
    if (_user_sending > 0)
    {
        size_t written = _user_sending;
        _user_sending = 0;
        KiottyNetConnectionAction returned = handler.onWritten(_context, handle(), written);
        return adopt(returned, handler);                    // WRITE 면 tx 에 붙이고 W 를 본다. 아니면 그 action
    }
    return nextWrite();                                     // tx 또는 notify 에 남은 것이 있으면 WRITE, 없으면 NONE
}

nextWrite() 는 "tx 에 바이트가 있거나 notify Stage 에 바이트가 있으면 IoAction::write(), 아니면 none" 한 줄이다. broadcast 가 slot 마다 부르는 것도 이것이다 (v2 의 onNotified 자리). adopt(WRITE) 뒤에 onWritten 의 return 이 READ 이면 그 READ 는 read event 로 가고, tx 에 남은 notify 는 다음 broadcast 가 건다. 두 lane 이 독립이라 둘 다 같은 step 에서 submit 해도 된다. IoLoop::step 이 "action 하나만 submit" 이던 v2 10절은 "read lane 의 action 하나 + write lane 의 nextWrite" 로 넓어진다. 그것이 v3 10절의 유일한 변화다.

7. 골라 주실 것 선택

  1. Work / Stream 이름: (a) action 과 콜백은 Work (thenWork, onWorkStarted), 객체는 Stream (KiottyNetConnectionStream, closeConnectionStream) — 추천. HTTP 가이드의 Work 용어가 그대로 산다. (b) 전부 Stream (thenStream, onStreamOpened, KIOTTY_ACTION_OPEN_STREAM).
  2. IoPurpose 삭제: 2.2 대로 지우는가. 3b 코드에서 IoAction::read(purpose, ...) / write(purpose, ...) 의 인자가 빠진다. 추천: 지운다.
  3. DRAINING 의 자리: WorkContext 의 State 에 REQUESTED 로 (추천) / Connection 의 bool 로. 동작은 같다.
  4. max_clients 128, 상한 1024, TLS Pool 8 MiB 인자 (v6 6절): 이 수치로 확정하는가.

이 넷이 정해지면 design_base_v3.md 를 쓴다. 3절의 Stage 셋, 4절의 flow 넷, 6절의 표가 v3 의 9절 (connection) 이 되고, 나머지 절은 v6 8절의 변경 목록을 따른다.

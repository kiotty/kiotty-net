0. 규칙 셋 (요약 1, 2, 3) 동의

요약하신 세 줄을 19.3 의 규칙으로 올린다. 아래 항목들은 전부 이 셋의 적용이다.

1. 멤버는 run 보다 오래 사는 것만. 한 함수가 쓰고 마는 것은 그 함수의 인자다.
2. 풀 안의 객체 (Connection, Owner) 는 자기 바깥을 가리키지 않는다. 필요한 것은 부르는 쪽이 그때 참조로 준다.
3. OpenSSL 의 메모리는 TlsMemory 하나가 맡는다. 전역은 static, thread 는 private 함수 하나, Owner 는 멤버.

규칙 2 의 알려진 예외 하나: IoEvent 가 드는 listener 포인터 (IocpEvent::listener, epoll 의 ListenerState*). backend 안의 것이고, attach 가 적고 detach 가 지우며, listener 가 완료의 주인을 확인하는 데 (belongsTo) 쓴다. listener 는 같은 Owner 의 형제라 Connection 보다 오래 산다. 이것은 "바깥" 이 아니라 "자기를 등록한 곳" 이라 둔다. 19.3 에 예외로 적는다.

"주석으로 이 함수 호출 때 이 인자들이 필요하다 정도는 명시" 는 코드 주석 대신 19.3 의 표 (9절의 "함수가 받는 것" 열) 로 한다. 코드는 무주석 원칙 그대로다.

1. NotificationContext 없는 Connection : IoLoop 경로 검토 (1) 동의

된다. v4 에서 Connection 이 _notification 으로 하던 일은 여섯이다. 하나씩 어디로 가는지 적는다.

v4 에서 _notification 을 쓰던 자리무엇을 썼나어디로 가나
Connection::notify (아무 thread)mutex, listenerConnectionHost::notify(handle, data) 가 자기 mutex 안에서 find → c.stageNotification(data). wake 는 Owner 가 _listener.wake()
select (drain, IO Thread)mutexpickWrite(std::mutex& notification). IoLoop::drain 이 host.notificationMutex() 를 넘긴다
onSent(NOTIFY) 의 release (step)mutexdispatch(completion, handler, std::mutex& notification)
release 의 notify clear (settle)mutexConnectionHost::release(c) 가 mutex 를 잡고 c.reset(). reset 은 noexcept 무인자 (풀 계약) 라 lock 을 모른다
closeStream 의 wake (worker)listenerOwner 가 _host.closeStream(h, then) 뒤 _listener.wake()
isIoThread (Stream 의 BUSY)io_threadIoLoop::isIoThread(). run 이 _io_thread 에 적는다 (atomic). Owner 의 stream 함수가 먼저 본다

그래서 NotificationContext 는 struct 로 남지 않는다. mutex 는 ConnectionHost 의 멤버, listener 는 Owner 의 멤버 (이미 있다), io_thread 는 IoLoop 의 멤버다. 셋 다 "참조" 가 아니라 "자기 것" 이다.

2. 풀의 이름과 자리 (2, 3, 4, 5) 부분 동의

둘로 나누는 것, Owner 라는 말을 이름에서 빼는 것, core/pool/ 로 모으는 것 전부 동의다. 이름 하나만 다시 보자고 한다.

두 풀의 차이는 저장 공간 하나다. 객체가 풀 안의 배열에 있어 풀과 같이 태어나는가 (지금 ObjectPool), 처음 acquire 때 heap 에 한 번 만들고 그 뒤로 은퇴 상태로 두는가 (지금 OwnerPool). acquire → initialize, release → reset, find, generation 은 똑같다. 그래서 공통 단어는 계약 이름 그대로 Reusable 이고, 앞에 붙는 단어가 저장 공간을 말하면 된다.

제안하신 이름대안저장 공간상태쓰는 곳
지금 ObjectPoolStaticReusablePool<T, N>ReusablePool<T, N>std::array<T, N>. 풀과 같이 생성EMPTY / ACTIVEConnection
지금 OwnerPoolReusablePool<T, N>LazyReusablePool<T, N>std::array<std::unique_ptr<T>, N>. 첫 acquire 때 new (nothrow), 그 뒤 RETIRED 로 재사용, reserve(n)EMPTY / ACTIVE / RETIREDServer, StreamClient, EventClient

대안을 권하는 이유: core/pool/ 에는 이미 StaticPool 이 있고 거기서 Static 은 "멤버가 전부 static, .bss" 라는 뜻이다. 같은 폴더에서 StaticReusablePool 의 Static 이 "객체가 멤버 배열 안" 을 뜻하면 한 단어가 두 뜻이 된다. 멤버 배열 쪽을 기본 이름 (ReusablePool) 으로 두고, 다른 쪽에만 유일한 차이 (늦게 만든다) 를 붙이는 것이 "역할에 집중한 이름" 이다. 둘 다 static_assert(is_reusable<T>::value) 다. choices 1.

폴더는 이렇게 된다. core 의 다른 파일 (stage, span, result, clock) 은 그대로다.

3. Context 는 하나 (6) 동의

11.1 로 바뀜: static 객체는 그대로이나 instance() 는 없다. Context::open() 을 initializeContext 만 부르고, handle 만 받던 C 함수 일곱은 context 를 첫 인자로 받는다.

맞다. 같은 process 에서 Context 를 둘 만들 이유가 없고, 둘을 지원하느라 든 것 (handle 의 context 4 bit, MAX_TLS_CONTEXTS, g_contexts 와 그 lock, TLS 등록표의 Context 탐색) 이 전부 빠진다. 다만 그 static 을 base.cpp 가 아니라 context/ 에 둔다. base.cpp 는 번역만 하기 때문이다.

// context/kiotty_context.h
class Context                                   // process 에 하나. 복사 / 이동 없음
{
public:
    static Context& instance();                 // 함수 안의 static 객체 하나. 첫 호출에 생성된다 (C++11 의 thread-safe static init). heap 없음

    KiottyNetCode initialize(const KiottyNetContextConfig& config);   // OpenSSL 초기화 (process 첫 번째만), TlsMemory 설치, 예열, reserve. 두 번째 호출은 choices 2
    void          release();                    // 남은 Owner destroy → 세 풀 비움 → TlsMemory 등록표 지움. OPENSSL_cleanup 은 부르지 않는다
    bool          initialized() const;

    Result<KiottyNetCode, Server&>       createServer(const KiottyNetServerConfig&, const KiottyNetTlsServerConfig*);
    Result<KiottyNetCode, StreamClient&> createStreamClient(...);
    Result<KiottyNetCode, EventClient&>  createEventClient(...);
    void destroy(Server&);  void destroy(StreamClient&);  void destroy(EventClient&);

    Owner* owner(int64_t handle);               // handle 의 type · owner · owner_generation 비트로. 7절. 없으면 nullptr

private:
    Context();
    LazyReusablePool<Server,       MAX_SERVERS>        _servers;
    LazyReusablePool<StreamClient, MAX_STREAM_CLIENTS> _stream_clients;
    LazyReusablePool<EventClient,  MAX_EVENT_CLIENTS>  _event_clients;
    std::mutex                                         _mutex;        // initialize / release / create / destroy
    bool                                               _initialized;
};

base.cpp: KiottyNet_initializeContext() 는 Context::instance().initialize(config) 뒤 &Context::instance() 를 handle 로 돌려주고, KiottyNet_releaseContext(ctx) 는 ctx->release() 다. KiottyNetContext 타입과 create 함수의 첫 인자는 그대로 둔다 (API 가 바뀌지 않는다). 사이클 4 노트의 R4 ("handle 함수가 전부 Context 를 첫 인자로 받는다") 는 필요 없어진다. 하나뿐이라 handle 만으로 찾는다 (7절).

static std::unique_ptr<Context> 대신 static 객체를 권하는 이유 하나: Context 자체는 수 KB 라 heap 이 필요 없고 (19.1 #2), 어느 쪽이든 process 종료 때 소멸자가 돈다는 점은 같다. releaseContext 를 불렀으면 그 소멸자는 빈 풀을 지우고 끝난다. 부르지 않았으면 Owner 들이 그때 지워진다 (run 중인 thread 가 있으면 사용자 오류다. 19.9 의 "releaseContext 없이 종료" 테스트가 보는 것이 이것이다).

지워지는 것:

  • g_contexts, g_contexts_lock, MAX_CONTEXTS, Context::_id, ObjectPool<Context, 16>. Context 는 풀 계약 (is_reusable) 을 따르지 않아도 된다.
  • handle 의 context 4 bit. index 는 type (2) · owner (4) · owner_generation (6) · connection (16) 28 bit 가 되어 int32 양수에 들어간다 (7절).
  • KIOTTY_NET_MAX_TLS_CONTEXTS, CONTEXT_SLOT_BITS, tlsBlocks 의 TLS_CONTEXTS 곱.
  • Context 의 _tls_ranges. 등록표는 TlsMemory 의 static 이 된다 (4절).
  • _tls_pooled. TlsMemory::installed() 가 답한다.

4. TlsMemory (7) 동의

19.5 의 free 함수 셋 + thread_local 셋 + Context 의 등록표를 클래스 하나로 모은다. 요청하신 세 층이 그대로 세 구역이다: 전역은 static, thread 는 thread() 하나, Owner 는 멤버.

// tls/kiotty_tls_memory.h. OpenSSL 헤더를 모른다. 함수 포인터의 시그니처만 OpenSSL 의 것 (size, file, line) 이다
struct TlsMemoryFunctions                       // CRYPTO_set_mem_functions 에 그대로 넘기는 셋. backend 의 installTlsMemory() 가 받는다
{
    void* (*allocate)(size_t bytes, const char* file, int line);
    void* (*reallocate)(void* block, size_t bytes, const char* file, int line);
    void  (*release)(void* block, const char* file, int line);
};

class TlsMemory
{
public:
    // 전역 (process 에 하나). 전부 static
    static TlsMemoryFunctions functions();      // Context::initialize → backend 가 CRYPTO_set_mem_functions(f.allocate, f.reallocate, f.release)
    static bool               installed();      // hook 이 걸렸는가 (정적 링크 build). 지금의 Context::tlsPooled()
    static void               warmThread();     // 이 thread 의 OpenSSL 상태를 전역 arena 에. thread().warmed 가 false 일 때만 backend 의 ERR_clear_error + RAND_bytes
    static void               leaveThread();    // IO thread 끝. 전역으로 되돌리고 backend 의 OPENSSL_thread_stop
    static size_t             lateFrees();      // 어느 arena 에도 없는 주소의 free. 역참조하지 않고 센다
    static StaticPoolUsage    globalUsage(size_t index);

    // Owner 별
    class Scope                                 // RAII. 이 thread 의 할당을 이 Owner 의 서브풀로. 소멸자가 이전 값을 복원한다
    {
    public:
        explicit Scope(TlsMemory& owner);
        ~Scope();
    private:
        PoolBase* _previous;
    };
    size_t failures() const;                    // 서브풀이 못 준 횟수. 그 handshake 만 실패했다

protected:
    TlsMemory();
    void publish(PoolBase& pool);               // 파생이 자기 서브풀을 만든 뒤 등록표에 (begin, end, &pool). release 순서로 발행

private:
    struct Thread { PoolBase* current; PoolBase* last_hit; bool warmed; };
    struct Range  { const unsigned char* begin; const unsigned char* end; std::atomic<PoolBase*> pool; };

    static Thread&  thread();                   // thread_local 을 돌려주는 유일한 자리. nullptr current 는 전역
    static void*    allocate(size_t bytes, const char* file, int line);        // thread().current 또는 전역 arena. 못 주면 nullptr
    static void*    reallocate(void* block, size_t bytes, const char* file, int line);   // block 의 arena 안에서 새로 꺼내 복사
    static void     release(void* block, const char* file, int line);          // arenaOf → release. 없으면 lateFrees++
    static PoolBase* arenaOf(const void* block); // last_hit → 등록표 → 전역. 비교는 std::less<const unsigned char*>

    typedef StaticPool<GlobalTlsTag, GlobalTlsLayout> Global;   // 전역 arena. .bss
    static Range            s_ranges[MAX_SERVERS + MAX_STREAM_CLIENTS + MAX_EVENT_CLIENTS];   // 등록표. Context::release 가 지운다
    static std::atomic_flag s_ranges_lock;
};

template <class Layout>
class OwnerTlsMemory : public TlsMemory         // Server 는 ServerTlsLayout, client 둘은 ClientTlsLayout. TLS OFF 면 Layout 의 ARENA_BYTES 가 0
{
public:
    OwnerTlsMemory() { publish(_pool); }
private:
    Pool<Layout> _pool;
};

클래스가 둘인 이유 하나: class template 의 static 멤버는 instantiation 마다 따로 생긴다. Server 와 client 의 Layout 이 다르므로 서브풀은 template 이어야 하고, 전역 arena 와 thread_local 은 하나여야 한다. 그래서 static 전부를 template 이 아닌 TlsMemory 에 두고, 서브풀 멤버만 OwnerTlsMemory<Layout> 이 든다. 사용자 (Server) 가 보는 이름은 OwnerTlsMemory<ServerTlsLayout> _tls_memory 하나다.

guard 자리는 19.5 의 표 그대로이고, 전부 Owner 의 코드에 있다. IoLoop 는 TLS 를 모른다.

KiottyNetCode Server::run(const KiottyNetConnectionHandler* callbacks, KiottyNetAppContext app_context)
{
    Handler handler = { callbacks, app_context };
    TlsMemory::warmThread();
    KiottyNetCode code = KIOTTY_SUCCESS;
    {
        TlsMemory::Scope scope(_tls_memory);
        code = _loop.run(_host, _listener, &_acceptor, &_profile, handler, false);
    }
    TlsMemory::leaveThread();
    _parker.unpark(...);                        // 8절
    return code;
}

StreamClient 의 connect / read / write / close 는 함수마다 warmThread() + Scope 다. Owner 의 initialize (TlsProfile 생성) 와 reset (SSL_CTX_free) 도 Scope 안이다. kiotty_tls_memory.h 의 지금 함수 셋 (useTlsStaticPool, tlsPoolClassCount, tlsPoolUsage) 은 이 클래스의 static 이 된다.

5. IoLoop 가 드는 것 (8, 9, 10, 11) 부분 동의

9, 10, 11 은 그대로 동의다. 8 은 목적 (멤버에서 뺀다) 은 같고 "run 의 지역 변수" 대신 배열 자체를 없앤다.

5.1 run 이 전부 받는다 (9, 10, 11)

struct Handler                                  // 콜백 여덟과 app_context. 늘 같이 다니므로 하나로. run 의 stack 에 있고 아래로 참조로 내려간다
{
    const KiottyNetConnectionHandler* callbacks;
    KiottyNetAppContext               app_context;
};

class IoLoop                                    // 멤버 둘. 둘 다 다른 thread 가 읽거나 쓴다
{
public:
    KiottyNetCode run(ConnectionHost& host, EventListener& listener, Acceptor* acceptor, TlsProfile* profile, const Handler& handler, bool stop_when_empty);
    void          stop();                       // 아무 thread. _stopped. 부른 쪽이 listener.wake()
    bool          isIoThread() const;           // 아무 thread. Stream 의 BUSY

Server 는 _loop.run(_host, _listener, &_acceptor, &_profile, handler, false), EventClient 는 _loop.admit(...) 뒤 _loop.run(_host, _listener, nullptr, &_profile, handler, true) 다. _stop_when_empty 는 멤버가 아니라 인자다. step 의 인자가 여섯인 것은 그 함수가 그만큼 필요하다는 뜻이고, 그것을 보이는 것이 10번의 취지라 그대로 둔다. 네 참조 (host, listener, acceptor, profile) 를 struct 하나로 묶는 것은 지금 하지 않는다. 묶으면 "무엇이 필요한가" 가 다시 안 보인다.

app_context 를 Handler 안에 넣은 이유: 콜백 셋 (onConnected, onDisconnected, onError) 에만 들어가고 콜백 없이 쓰이는 자리가 없다. 따로 넘기면 모든 step / dispatch / on* 에 인자가 하나씩 더 붙는다. Handler 는 v4 에 이미 있는 이름 (typedef) 이라 새 개념이 아니다. choices 3.

5.2 local completion 배열은 없앤다 (8)

run 의 지역 변수로 두면 멤버는 아니지만 stack 이다. sizeof(IoCompletion) 은 약 88 바이트 (IoAction 64 미만 + kind, slot, code, length) 라 3 × 128 이면 약 33 KB, 상한 1024 면 약 270 KB 가 IO thread 의 stack 에 run 내내 있다. cpp-developer 규약의 "큰 struct 를 stack 에 두지 않는다" 와 19.1 #1 ("stack 이 아닌 것은 Owner 의 멤버") 둘 다와 부딪힌다.

그런데 모아 둘 이유가 없다. v4 가 모으는 이유는 "OS 완료를 다 step 한 뒤의 상태에서 만든다" 였고, 그것은 OS 완료 loop 가 끝난 뒤에 scan 하면 그대로 성립한다. scan 하면서 slot 마다 만들어 바로 step 하면 배열이 없다. slot i 의 step 이 slot j 의 deadline 이나 Work 를 바꾸는 길이 없으므로 (콜백이 다른 연결에 할 수 있는 것은 notify 뿐이고 그것은 Stage 에 넣는 것이다) 순서도 같다.

void IoLoop::runOnce(...)
{
    drain(host, listener);
    settle(host, listener, acceptor, stop_when_empty);
    Span<const IoCompletion> arrived = collectIoEvents(host, listener);
    for (const IoCompletion& completion : arrived)
    {
        step(completion, host, listener, acceptor, profile, handler);
    }
    bool stepped = true;
    while (stepped)
    {
        stepped = stepLocalEvents(host, listener, handler);   // 아무것도 만들지 않을 때까지. 상한은 slot 당 셋 (아래)
    }
}

bool IoLoop::stepLocalEvents(ConnectionHost& host, EventListener& listener, const Handler& handler)
{
    bool stepped = false;
    uint64_t now = monotonicMs();
    for (int32_t i = 0; i < host.capacity(); ++i)
    {
        Connection& c = host.at(i);
        if (c.expireDeadline(now))
        {
            step(IoCompletion::timeout(i), host, listener, nullptr, nullptr, handler);
            stepped = true;
        }
        if (c.workReady())
        {
            step(IoCompletion::workReady(i), host, listener, nullptr, nullptr, handler);
            stepped = true;
        }
        if (c.workFinished())
        {
            IoAction outcome = c.takeWorkOutcome();
            step(IoCompletion::workDone(i, outcome), host, listener, nullptr, nullptr, handler);
            stepped = true;
        }
    }
    return stepped;
}
while 이 붙은 이유는 v4 의 구멍 하나다. v4 는 collectLocalEvents 를 한 번만 돈다. local completion 의 step (TIMEOUT 의 onTimeout, WORK_DONE 뒤의 drive) 이 thenWork 를 돌려주면 REQUESTED 가 되지만 그것을 WORK_READY 로 만드는 scan 은 이미 지나갔고, 다음 바퀴의 wait 는 deadline 만 보므로 (REQUESTED 는 deadline 0) 다른 OS 완료가 올 때까지 Work 가 시작되지 않는다. 배열 버전도 같은 구멍이 있다. "아무것도 만들지 않을 때까지" 가 그것을 막는다. 끝나는 근거: 한 바퀴 안에서 slot 의 상태는 한 방향으로만 간다 (deadline 만료 → 0, REQUESTED → WORKING, DONE → IDLE). WORK_DONE → drive → START_WORK → REQUESTED → WORK_READY → WORKING 이 가장 긴 사슬이고, WORKING 에서 나가는 것은 worker thread 다. 그래서 slot 당 step 은 최대 셋, 전체 3 × N 이다. v4 10절의 "같은 slot 에서 local completion 셋이 함께 나오는 일은 없다" 는 "한 scan 에서" 로 읽으면 그대로 맞다.

step 의 acceptor / profile 에 nullptr 를 넘기는 것은 connection 완료가 그 둘을 쓰지 않기 때문이다. ACCEPT 완료는 collectIoEvents 에서만 온다. v4 의 "여섯 프로세스" 는 "drain, settle, collectIoEvents, step, stepLocalEvents" 다섯으로 적는다. 설계 방침 3 의 "input → output 은 값" 은 stepLocalEvents 의 input 이 연결 상태, output 이 bool 이라 그대로다.

7. handle 만으로 찾기, MISRA, int64 (15) 동의

7.1 handle 만으로 찾을 수 있나

11.1 로 바뀜: 아래의 Context::instance() 는 인자로 받은 context 가 되고, Context::owner 는 Result<KiottyNetCode, Owner&> 를 돌려준다 (11.2).

있다. 단, 길은 하나뿐이다. notifyConnection(h, data) 에는 Context 인자가 없으므로 static 저장소에서 닿는 표를 거쳐야 한다. 6번으로 그 표는 Context::instance() 하나다. 비트를 푸는 함수도 하나 (Context::owner) 고, 그 밖의 코드는 비트를 모른다.

int64 handle ├ 상위 32 : connection generation ── Connection 의 PoolHandle.generation 과 비교 (ReusablePool::find) └ 하위 32 : index bit 31 : 0 (int32 양수) bit 30 ~ 29 : type (SERVER, EVENT_CLIENT) ── Context 가 어느 LazyReusablePool 을 볼지 bit 28 ~ 25 : owner slot ── 그 풀의 칸 bit 24 ~ 19 : owner generation ── destroy 뒤의 handle 을 거른다 bit 18 ~ 16 : (비움) bit 15 ~ 0 : connection slot ── ConnectionHost 의 칸 Stream handle 은 같은 값에 bit 63 (generation 의 부호 비트. generation 은 int32 양수라 늘 0 이다) 을 세운다 Context::owner(h) : type → 풀 → slot 의 Owner → owner generation 비교 → Owner* 또는 nullptr. _mutex 는 잡지 않는다 (아래) Owner::notify(h, d) : _host.notify(h, d) → ReusablePool::find(PoolHandle{generation, slot}) → Connection 또는 nullptr

lock 없이 찾아도 되는 이유: Owner 는 destroy 로 지워지지 않고 은퇴한다 (19.1 #4). 그래서 Owner* 는 releaseContext 전까지 늘 유효하고, 틀린 handle 은 두 generation (owner, connection) 중 하나가 걸러 빈 값 / INVALID_ARGUMENT 로 돌아온다. 사용자가 handle 을 받은 뒤에 그 Owner 가 만들어졌을 수는 없으므로 (handle 은 그 Owner 가 만든 것이다) 풀의 unique_ptr 을 읽는 쪽과 쓰는 쪽의 경합도 없다.

8. Parker (16) 부분 동의

mutex + condition_variable 을 "재우고 깨운다" 하나로 묶는 것은 맞다. 모양 하나만 바꾼다. 생성자가 lock 을 잡으면 멤버로 둔 Parker 는 영원히 잠긴 채이고, 함수 안에서 만들면 mutex 와 cv 가 밖에 따로 있어야 해서 묶은 의미가 없다. lock 의 범위는 객체의 수명이 아니라 park 와 unpark 의 본문이다. 그래서:

class Parker                                    // core/kiotty_parker.h. mutex 와 condition_variable 이 있는 유일한 자리
{
public:
    template <class Ready>
    bool park(Ready ready, uint64_t timeout_ms);        // lock → ready() 가 참이 될 때까지 wait (0 이면 무한) → unlock. 돌아올 때의 ready()
    template <class Change>
    void unpark(Change change);                         // lock → change() → unlock → notify_all. ready() 가 읽는 것은 change() 가 적는다
private:
    std::mutex              _mutex;
    std::condition_variable _cv;
};

// Server
KiottyNetCode Server::await(uint64_t timeout_ms)
{
    bool finished = _parker.park([this]() { return _finished; }, timeout_ms);
    if (!finished)
    {
        return KIOTTY_TIMEOUT;
    }
    return _code;
}
// run 의 끝
_parker.unpark([this, code]() { _code = code; _finished = true; });

Server 와 EventClient 의 _mutex + _cv + _code 가 _parker + _code + _finished 가 된다. Context 의 create / destroy mutex 와 host 의 notification mutex 는 기다리는 것이 아니라 잠그는 것이라 std::mutex 그대로다. Parker 는 await 자리 둘에만 있다.

{

    {

11.5 attach 는 Scope 의 생성자로, detach 는 한 줄 남긴다 (6) 부분 동의

attach 는 합친다. 두 번째부터는 thread().attached 가 참이라 bool 하나 보고 끝이고, Scope 가 있는 곳은 늘 attach 가 먼저 필요한 곳이다. detach 는 합치지 않는다. 이유는 Server::run 이 아니라 StreamClient 다.

detach 를 소멸자에 넣으면 StreamClient::read → Scope 생성 (attach) → SSL_read → Scope 소멸 (detach = OPENSSL_thread_stop: 이 thread 의 오류 큐와 DRBG 를 지운다) StreamClient::read → Scope 생성 (attach = ERR_clear_error + RAND_bytes: DRBG 를 다시 만든다. OS 의 entropy 를 다시 읽는다) ... 호출마다 지우고 다시 만든다 IO thread 안에서 콜백이 StreamClient 를 부르면 (Scope 가 겹친다) Server::run 의 Scope ─┬ 콜백 → StreamClient::read 의 Scope 소멸 → detach → Server 쪽 SSL 이 쓰던 thread 상태가 사라진다 └ 이어지는 SSL_read 는 다시 만들어 쓰므로 틀리지는 않지만 매번 낸다

그래서 detach 는 "이 thread 의 OpenSSL 이 끝났다" 를 아는 자리, IO thread 가 끝나는 둘 (Server::run, EventClient::run 의 끝) 에만 한 줄로 남긴다. StreamClient 가 쓰는 사용자 thread 는 언제 끝나는지 라이브러리가 모르므로 detach 할 자리가 없다 (사이클 4 노트의 "Windows 정적 링크에서는 남는다" 가 그 경우다).

KiottyNetCode Server::run(const KiottyNetConnectionHandler& callbacks, KiottyNetAppContext app_context)
{
    Handler handler(callbacks, app_context);
    KiottyNetCode code = KIOTTY_SUCCESS;
    {
        TlsMemory::Scope scope(_tls_memory);                    // attachThread 포함
        code = _loop.run(_host, _listener, _acceptor, _profile, handler, false);
    }
    TlsMemory::detachThread();
    _parker.unpark([this, code]() { _code = code; _finished = true; });
    return code;
}

typedef struct KiottyNetConnectionOwner KiottyNetConnectionOwner;      // 불투명. C++ 에서는 Owner (가상 함수 일곱)

    int64_t                   id;               // 상위 32 generation, 하위 16 slot
} KiottyNetConnectionHandle;
typedef struct KiottyNetConnectionStream { KiottyNetConnectionOwner* owner; int64_t id; } KiottyNetConnectionStream;   // 같은 값. 타입만 다르다

// base.cpp
KiottyNetCode KiottyNet_notifyConnection(KiottyNetConnectionHandle handle, KiottyNetSpan data)
{
    if (handle.owner == nullptr)
    {
        return KIOTTY_INVALID_ARGUMENT;
    }
    return handle.owner->notify(handle.id, data);                       // Owner::notify → _host.notify(PoolHandle{generation, slot}, data)
}

write 중 도착 설계 v0 : 보내는 동안 상대 바이트가 오면 멈춘다

2026-11-18 확정 (정할 것 넷 닫음). 배경은 docs/learning/early-reply-and-rst.html: HttpClient 가 올리는 중에 서버가 413 / 401 을 먼저 보내고 RST 로 닫으면, 응답 바이트는 커널 수신 버퍼에 있지만 kiotty 는 보내는 동안 읽지 않는다. 그 사이 RST 가 오면 Windows 는 그 바이트를 버린다. 그 문서 10절의 길 1 ("write 의 기다림이 읽을 것도 본다") 을 고르고, 사용자와 정한 것 (2026-11-18) 을 base 의 송신 규칙으로 적는다. 사이클 A1 (base), A2 (HTTP 서버 work), A3 (HttpClient 올리기).

0. 한눈에

KiottyNetResult sent = KiottyNet_writeStreamClient(client, data, length, 5000);
if (sent.code == KIOTTY_NET_CODE_DATA_ARRIVED_WHILE_WRITING) {
    /* sent.bytes 만큼은 보냈다. 상대 바이트는 이미 kiotty 의 수신 Stage 에 있다 */
    KiottyNetResult got = KiottyNet_readStreamClient(client, buffer, sizeof(buffer), 5000);   /* Stage 에서 바로 */
    /* 읽은 것을 보고 이어 보낼지 (data + sent.bytes 부터) 그만둘지 앱이 정한다 */
}
것무엇
규칙송신이 기다릴 때 쓰기와 읽기를 함께 기다린다 (poll / select 의 IN | OUT | stop). 상대 바이트가 오면 보내기를 멈추고 그 바이트를 수신 Stage 로 옮긴 뒤 { 보낸 만큼, KIOTTY_NET_CODE_DATA_ARRIVED_WHILE_WRITING }
확인 시점write 를 시작할 때 한 번 (기다리지 않음) 과 송신이 막힐 때마다
닫힘EOF 는 PEER_CLOSED, RST 는 SOCKET_ERROR. 그 전에 온 바이트는 Stage 에 남는다
앱에 새로 보이는 것code 하나 (enum 맨 끝). poll 이나 기다리지 않는 read 는 공개하지 않는다
바뀌지 않는 것이벤트 루프가 보내는 것 (서버의 보통 응답, WebSocket). read 의 모양. 이미 있는 code 의 번호

1. 결정

#결정이유
1송신의 기다림은 읽기 또는 쓰기 를 기다린다. 읽을 것이 오면 recv 로 수신 Stage 에 옮기고 write 를 멈춘다413 은 거의 언제나 write 가 송신 버퍼에 자리가 나기를 기다리는 동안 온다 (learning 9절). 그 기다림이 읽기도 봐야 RST 전에 바이트를 kiotty 의 메모리로 옮긴다. Stage 에 들어온 바이트는 운영체제가 지울 수 없다
2확인 시점은 write 를 시작할 때 한 번 (기다리지 않는 recv) 과 막힐 때마다. 보내기가 막히지 않는 동안은 확인하지 않는다write 와 write 사이에 온 바이트도 잡는다. 막히지 않는 송신 중간에 시스템 호출을 더하지 않는다. 막히지 않으면 상대가 읽고 있다는 뜻이고 RST 와의 경주는 다음 write 의 시작이 잡는다
3EOF 는 PEER_CLOSED, RST 는 SOCKET_ERROR. 둘 다 그 전에 옮긴 바이트는 Stage 에 두고 연결을 닫지 않는다 (닫는 것은 위 층이 정한다)FIN 과 RST 를 지금처럼 구별한다 (learning 3절). "닫혔지만 응답은 와 있다" 를 위 층이 읽을 수 있어야 한다
4Stage 에 바이트를 실제로 옮겼을 때만 알린다. Stage 가 차 있으면 읽기를 보지 않고 쓰기만 기다린다Stage 가 차 있으면 옮길 수 없다. 그때 읽기를 계속 보면 poll 이 바로 돌아와 헛돈다. 차 있는 Stage 는 앱이 아직 읽지 않았다는 뜻이고 알림은 이미 한 번 갔다
5TLS 는 평문이 나올 때만 멈춘다. 암호문은 TLS 수신 Stage 로 옮겨 풀어 보고, 평문이 없으면 (NewSessionTicket, key update 같은 제어 레코드) 계속 보낸다TLS 1.3 서버는 handshake 뒤 ticket 을 보낸다. 그때마다 write 가 멈추면 앱이 읽을 것 없는 read 를 부르게 된다. close_notify 는 EOF 와 같게 PEER_CLOSED
6새 code KIOTTY_NET_CODE_DATA_ARRIVED_WHILE_WRITING 는 KiottyNetCode 의 맨 끝 (PEER_NOT_READING 뒤) 에 붙인다이미 있는 번호를 바꾸지 않는다 (ABI)
7poll 이나 기다리지 않는 read 는 앱에 공개하지 않는다. 앱은 code 를 보고 보통의 read 를 부르면 된다. read 는 Stage 에서 먼저 준다 (지금 그대로)API 를 늘리지 않는다. Stage 에 이미 있으므로 read 는 기다리지 않고 돌아온다
8적용: StreamClient (writeStreamClient) 와 서버의 work stream (writeConnectionStream, http 의 writeHttpWorkChunk). 이벤트 루프가 보내는 것과 WebSocket 은 바뀌지 않는다work stream 은 WorkFlow::isReady 가 읽기 / 쓰기 이벤트가 쉴 때만 시작하므로 IoLoop 와 같은 소켓의 바이트를 다투지 않는다. 이벤트 루프는 이미 읽기와 쓰기를 함께 본다

2. 송신의 흐름

write(data, timeout) ├─ 시작 확인 : Stage 에 자리가 있으면 기다리지 않는 recv 한 번 │ ├─ 바이트를 옮김 (TLS 는 평문이 나옴) → { 0, DATA_ARRIVED_WHILE_WRITING } │ ├─ EOF / close_notify → { 0, PEER_CLOSED } │ ├─ RST → { 0, SOCKET_ERROR } │ └─ 없음 (WOULD_BLOCK, TLS 제어 레코드뿐) → 보내기로 └─ 보내기 : send 를 되풀이 └─ WOULD_BLOCK → 기다림 (Stage 에 자리가 있으면 IN | OUT | stop, 없으면 OUT | stop) ├─ OUT → send 를 이어 함 ├─ IN → recv 로 Stage 에 옮김. 결과는 시작 확인과 같은 갈래 (bytes = 그때까지 보낸 만큼) ├─ IN 과 OUT 함께 → recv 먼저 (RST 와의 경주에서 앞서려고) ├─ stop → { 보낸 만큼, CLOSED } (지금 그대로) └─ 시간 끝 → { 보낸 만큼, TIMEOUT } (지금 그대로)

read 는 바뀌지 않는다. 시작할 때 송신 Stage 를 비우는 flush 가 있는데, 연결이 이미 끊겨 flush 가 실패하면 지금은 read 가 그 code 로 끝난다. A1 에서 수신 Stage 에 바이트가 있으면 flush 실패보다 그 바이트를 먼저 준다 로 고친다 (learning 11절의 TLS 걸림). Stage 가 비면 그때 flush 의 code (또는 recv 의 code) 를 준다.

4. 어디에 적용되나

호출쓰는 곳도착이 뜻하는 것사이클
KiottyNet_writeStreamClient앱의 클라이언트 프로토콜앱이 정한다 (code 그대로 앱에)A1
KiottyNet_writeConnectionStreambase 서버의 work (앱이 직접 보냄)앱이 정한다 (code 그대로 앱에)A1
KiottyNet_writeHttpWorkChunkhttp 서버의 긴 응답 (SSE, chunked)클라이언트의 다음 요청 (pipelining) 이나 떠남. work 층이 받아 계속 쓴다. 앱에는 보이지 않는다A2
HttpClient 의 writeHttpRequestBody올리기서버의 먼저 온 응답. 1xx 면 버리고 이어 보냄, 최종 응답이면 올리기를 REFUSED 로 하고 finish 가 그 응답A3

A2 에서 볼 것: 서버 work 뒤의 Stage

work stream 은 연결의 수신 Stage (WorkFlow 의 parts.receive) 를 IoLoop 와 함께 쓴다. worker thread 가 옮긴 다음 요청 바이트는 Stage 에 있고 소켓에는 없으므로, edge-triggered 이벤트 (epoll ET, io_uring, IOCP) 는 다시 오지 않는다. work 가 끝나 연결이 읽기로 돌아갈 때 Stage 에 이미 있는 바이트를 먼저 다음 요청으로 처리 해야 한다. pipelining 의 지금 처리 (응답 뒤 남은 바이트) 가 이것을 하는지 A2 에서 확인하고, 아니면 고친다.

A2 는 또 failureOf 의 짐작 (isStreamOpen 으로 PEER_CLOSED / SOCKET_ERROR 를 다시 고름) 을 없앤다. 송신이 EOF 와 RST 를 직접 구별하므로 필요 없다. isHttpWorkConnected 는 남기고 "다음 write 전에 떠났는지 미리 볼 때" 로 문서를 고친다.

5. TLS

  • 소켓에서 오는 것은 암호문 레코드다. 시작 확인과 IN 은 암호문을 TLS 수신 Stage (TlsEngine::stages().receive) 로 옮기고 바로 풀어 평문 수신 Stage 로 보낸다.
  • 평문이 나오면 멈춤. 평문이 없으면 (ticket, key update, 레코드 조각) 계속 보낸다. 조각은 TLS 수신 Stage 에 남아 다음에 이어진다.
  • close_notify 는 PEER_CLOSED. TLS alert (오류) 는 지금의 TLS code.
  • 풀기가 TLS 응답 (key update 의 답 등) 을 만들면 그것은 송신 Stage 에 쌓이고 보내기가 이어서 보낸다 (지금의 readCipher 가 flush 하는 것과 같다).
  • 평문 수신 Stage 가 차 있으면 IN 을 보지 않는다 (결정 4). TLS 수신 Stage 만 차 있고 평문 Stage 에 자리가 있으면 먼저 풀어서 자리를 만든다.

6. 쓰지 않는 방법

방법되는 것쓰지 않는 이유
FIONREAD / MSG_PEEK 로 길이만 보고 알리기 (옮기지 않음)데이터가 왔는지, 닫혔는지 구별바이트가 커널 버퍼에 남아 있으므로 Windows 의 RST 가 여전히 지운다 (풀려는 문제 그대로). TLS 는 암호문 길이만 보여서 ticket 과 평문을 구별하지 못한다
write 를 부를 때만 한 번 확인 (learning 길 2)write 사이의 도착막혀 있는 동안의 도착 (가장 흔한 경우) 을 놓친다
앱에 poll / 기다리지 않는 read 공개앱이 원하는 때 확인모든 앱이 같은 규칙을 다시 짜야 하고, 막힌 write 안의 도착은 여전히 놓친다
서버 lingering close 만우리 HttpServer 를 상대로는 해결클라이언트는 서버를 고를 수 없다 (learning 8절). 서버 쪽은 따로 할 수 있는 일로 남긴다

7. 안에서

  • 소켓 backend: POSIX waitFor 는 poll 의 events 를 받으므로 POLLIN | POLLOUT 과 어느 쪽이 왔는지를 돌려주는 함수 하나 (waitReadableOrWritable, 결과 Readiness { readable, writable }). Windows waitReady 는 select 의 readable / writable 집합 둘 다에 넣는다 (WaitDirection::EITHER). stop 은 지금처럼 함께 본다.
  • ConnectionStream: sendAll 의 awaitWritable 자리를 "기다림 + 도착이면 옮김" 으로. 시작 확인은 write 와 send 의 첫 줄. 옮기기는 지금의 fillStage / receiveCipher 를 기다림 없이 한 번 부르는 것. 공개 메서드는 그대로 7 (read, peek, consume, write, writeFile, connected, handshake).
  • Sent 의 code 는 SocketCode 그대로 두고 SocketCode::READABLE 을 더했다 (A1). 기다림이 읽을 것을 보면 READABLE 로 돌아오고, 부른 쪽이 지금 보내던 구간을 commit 한 뒤에 옮긴다 (TLS 의 BIO / cipher Stage 를 쥔 채 decode 하지 않으려고).
  • TLS 레코드와 BIO pair (A1, 사용자 결정 2026-11-18): BIO pair 가 4 KiB 이면 16 KiB 레코드 하나를 내보내는 데 SSL_write 를 여러 번 다시 불러야 하고, OpenSSL 은 끝날 때까지 같은 데이터로 다시 부르기를 기대하므로 레코드 중간에서 멈출 수 없다. BIO pair 를 레코드 하나가 통째로 들어가는 크기 (평문 16384 + 레코드 여유 64 + 제어 여유 512 = 16960 바이트, 양쪽) 로 키우고, 레코드마다 먼저 BIO 를 비운 뒤 넣는다. 그래서 멈춤은 언제나 레코드 사이다. TLS 연결 하나의 OpenSSL 메모리가 늘어 TlsMemory 상한을 128 KiB 에서 160 KiB 로 올렸다 (DV2).
  • read 는 수신 Stage 에 바이트가 있으면 flush 없이 먼저 준다 (A1). 2절의 "flush 실패보다 Stage 먼저" 를 이렇게 했다.
  • A1 의 다리: http 의 writeHttpWorkChunk (sendSpan) 와 HttpClient 의 writeAll 은 code 만 보고 길이를 버리므로, A1 에서 도착이면 보낸 만큼 넘기고 이어 보내게 했다 (뜻은 지금 그대로). A2 / A3 가 각자의 규칙으로 바꾼다.
  • writeFile (sendfile / TransmitFile): 운영체제 안에서 기다리므로 그 안의 도착은 보지 못한다. 시작 확인만 하고, TLS 의 writeFile (조각마다 send) 은 보통의 송신 규칙을 따른다 (정할 것 2, 닫음).
  • handshake 와 flush 만 하는 경로 (read 의 시작): 바뀌지 않는다. 도착 알림은 앱 데이터를 보내는 write 에서만.
  • 새 메모리 없음. 옮기는 곳은 이미 있는 수신 Stage 다.

8. 정할 것

모두 닫음 (2026-11-18, 사용자).

  1. HttpClient 올리기 write 의 code. 닫음: base 와 같은 DATA_ARRIVED_WHILE_WRITING 을 쓴다. 새 code 를 만들지 않는다. 올리기에서는 1xx 를 내부에서 넘기고 최종 응답일 때만 앱에 돌려주며, HttpClient 문서에 "최종 응답이 와 있다, finish 를 불러 본다" 로 적는다.
  2. writeFile 의 도착. 닫음: 시작 확인만 한다 (zero-copy 를 지킴). 보내는 중의 도착을 보고 싶은 앱은 파일을 읽어 조각 write 로 보내면 된다 (그 write 가 이 규칙을 따른다).
  3. 전이중 프로토콜의 알림. 닫음: 결정 4 그대로. 바이트를 Stage 로 옮길 때마다 멈추고 알린다.
  4. 이름. 닫음: 이 문서 design_write_arrival_v0.html, 사이클 A1 ~ A3.

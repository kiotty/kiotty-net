설계 방침

  1. 새 개념은 없다. 스트리밍 응답은 base 에 이미 있는 두 모양 (Work 로 동기 write, Hold 뒤 notify 로 push) 을 HTTP 의 이름으로 드러낸 것이다. 새 객체, 새 thread, 새 버퍼 클래스는 두지 않는다.
  2. HTTP 는 Session 하나와 표 하나다. design_statemachine_v0.md 11절 그대로. 라이브러리의 표가 Connection 을 밟고, 사용자 콜백은 transition action 안에서 불린다. 사용자는 표를 보지 않는다.
  3. 응답은 "body 의 종류" 로 나뉜다. 복사, 참조, 파일, 스트림 넷 중 하나이고 setter 하나가 종류를 정한다. 스트림이면 chunk 를 누가 쓰느냐 (worker 가 동기로, 아무 thread 가 push 로) 가 2절의 두 모양이다.
  4. 메모리는 create 때 끝난다. 라우트 표와 Session 배열 (max_clients 개) 을 createHttpServer 가 잡는다. run 중 할당 0 (수칙 1.1, DV1).

1. 목표와 범위 : Streamable HTTP

MCP 의 Streamable HTTP transport 는 HTTP/1.1 위의 두 가지다. 하나는 보통의 요청 - 응답 (JSON 하나), 다른 하나는 Server-Sent Events 다. SSE 는 Content-Type: text/event-stream 인 응답 body 를 끝내지 않고 이벤트 (event:, data:, id: 줄과 빈 줄) 를 계속 보내는 것이다. HTTP/1.1 에서 길이를 모르는 body 는 Transfer-Encoding: chunked 로 보낸다. 그래서 라이브러리가 할 일은 하나다. 응답 body 를 chunk 단위로, 끝을 정하지 않고, 나중에 보낼 수 있게 한다. SSE 의 줄 형식은 앱이 chunk 안에 쓴다.

지금 헤더 (v1) 로는 되지 않는 이유는 둘이다. 응답은 body 하나뿐이고 Content-Length 를 라이브러리가 채운다. Work 에는 finishWithResponse / finishWithClose 만 있고 중간에 쓰는 함수가 없다. 이 판은 그 둘을 더하고 나머지는 그대로 둔다.

범위 밖: HTTP/2, 요청 body 스트리밍 (요청은 max_body_bytes 안에 다 받는다), 압축, Range, 파라미터 파싱, CORS 자동 처리. 전부 user_guide 1.11 그대로다.

2.1 완성 응답 유지

user_guide 1.4, 1.5 그대로다. onRequest 안에서 setter 를 부르고 return 하면 보내지고, startHttpWork 를 불렀으면 worker 가 setter 로 채운 뒤 finishHttpWorkWithResponse 가 보낸다. 라이브러리가 Content-Length, Connection, Date, Content-Type (body setter 의 인자) 을 채운다.

IO thread : READ(요청 끝) → onRequest(request, response) { setHttpStatus, setHttpBody, ... } → return → [Sending] write 조각들 → WRITTEN ... → keep-alive 면 다음 요청, 아니면 close

2.2 Work 스트림 추가

base 의 Work 모양이다. onRequest 가 startHttpWork 를 부르고, onWorkStarted 가 work 를 worker 에게 넘긴다. worker 는 setHttpBodyStream(response, "text/event-stream") 으로 body 종류를 스트림으로 놓고 (status 와 다른 헤더도 이때), writeHttpWorkChunk(work, data, timeout) 를 부른다. 첫 번째 write 가 상태줄 + 헤더 (Transfer-Encoding: chunked) 와 첫 chunk 를 보낸다. 그 뒤의 write 는 chunk 하나씩이다. finishHttpWorkWithResponse(work) 가 끝 chunk (0\r\n\r\n) 를 보내고 keep-alive 면 다음 요청으로 돌아간다. finishHttpWorkWithClose 는 끝 chunk 없이 끊는다.

IO thread : READ(요청 끝) → onRequest { startHttpWork } → return → [Working] thenWork → WORK_STARTED → onWorkStarted(request, response, work) → thenWork worker : setHttpBodyStream(response, "text/event-stream") writeHttpWorkChunk(work, "event: message\ndata: {...progress...}\n\n", 5000) ← 첫 write 가 헤더 + chunk writeHttpWorkChunk(work, "...", 5000) ← chunk ... setHttpStatus 는 더 못 바꾼다 (이미 나갔다) finishHttpWorkWithResponse(work) ← 끝 chunk "0\r\n\r\n". closeConnectionStream(thenWrite(끝 chunk)) IO thread : WRITTEN → keep-alive 면 [ReadingRequestLine], 아니면 close
  • write 는 KiottyNet_writeConnectionStream 그대로다 (동기, 전부 보내거나 실패, timeout 0 은 무한). 돌아온 뒤 data 는 버려도 된다. 코드는 Stream 의 것 (PEER_CLOSED, TIMEOUT, CLOSED = 서버 close, BUSY = 이미 finish 함).
  • chunk 하나의 길이에 상한은 없다. 라이브러리가 chunk 머리 (길이 hex + CRLF) 와 꼬리 (CRLF) 를 붙여 Stream 에 세 번 write 하거나, send_capacity 안이면 Session 의 응답 버퍼에 모아 한 번 write 한다 (7절). 사용자는 모른다.
  • 헤더가 나간 뒤의 setter (setHttpStatus, setHttpHeader, body setter) 는 BUSY 다.
  • 스트림이 아닌 응답 (body 복사 / 참조 / 파일) 에 writeHttpWorkChunk 를 부르면 INVALID_ARGUMENT. body setter 를 하나도 부르지 않고 writeHttpWorkChunk 를 부르면 그것도 INVALID_ARGUMENT 다. 스트림은 명시적으로 고른다.
  • 진행 알림을 다 보내고 "최종 응답" 을 같은 스트림에 보내는 것 (MCP 의 POST SSE) 은 마지막 chunk 에 그 이벤트를 쓰고 finish 하는 것이다. 라이브러리에 "최종" 이라는 개념은 없다.
  • 끝 chunk 를 보내는 것은 closeConnectionStream(stream, thenWrite(끝 chunk)) 다. 끝 chunk 는 상수 문자열이라 수명 문제가 없다.

2.3 push 스트림 추가

base 의 Hold + notify 모양이다. onRequest 가 setHttpBodyStream 을 부르고 Work 없이 return 한다. 라이브러리가 상태줄 + 헤더 (Transfer-Encoding: chunked, Connection: close) 를 write lane 으로 보내고 그 연결을 스트림 상태로 둔다. 그 뒤 아무 thread 가 pushHttpChunk(response, data) 로 chunk 를 push lane (notify) 에 넣는다. endHttpStream(response) 이 끝 chunk 를 push lane 에 넣고 연결을 닫는다. 상대가 끊거나 서버가 close 하면 라우트의 onStreamClosed(app_context, response, reason) 가 온다. 앱의 end 에도 온다 (reason = SUCCESS).

IO thread : READ(요청 끝) → onRequest { setHttpStatus(200), setHttpHeader(...), setHttpBodyStream(response, "text/event-stream"), 앱이 response 를 보관 } → return → [SendingStreamHeader] thenWrite(상태줄 + 헤더) → WRITTEN → [Streaming] thenRead(1, 0) ← 상대가 끊으면 바로 안다. 데이터가 오면 400 close 아무 thread : pushHttpChunk(response, "event: message\ndata: {...}\n\n") ← chunk 머리 / 꼬리를 붙여 KiottyNet_notifyConnection. IO thread 의 drain 이 보낸다 pushHttpChunk(response, ": ping\n\n") ← 주기적 ping 은 앱이 ... endHttpStream(response) ← 끝 chunk 를 notify 로, 닫힘 플래그 IO thread : (끝 chunk 가 나간 뒤) close(SUCCESS) → CLOSED → onStreamClosed(app_context, response, SUCCESS) → 다음 요청 없음 또는 : READ 가 PEER_CLOSED → onStreamClosed(app_context, response, PEER_CLOSED). 그 뒤 pushHttpChunk 는 PEER_CLOSED 또는 : 서버 close → onStreamClosed(app_context, response, CLOSED)
  • pushHttpChunk 의 규칙과 코드는 KiottyNet_notifyConnection 과 같다. push lane 에 복사하고 돌아온다. 돌아온 뒤 data 는 버려도 된다. 완료 콜백은 없다. chunk 머리와 꼬리를 더한 길이가 push_capacity 보다 크면 INVALID_ARGUMENT, 자리가 없으면 BUFFER_FULL (그 chunk 는 버려진다. 끊을지는 앱이 정한다). 빈 chunk 는 INVALID_ARGUMENT (HTTP 에서 길이 0 chunk 는 끝이다).
  • 스트림 동안 라이브러리는 1 바이트 read 를 걸어 둔다. 상대가 FIN 을 보내면 PEER_CLOSED 로 바로 닫히고 onStreamClosed 가 온다. 데이터가 오면 (pipelining 은 지원하지 않는다) 400 없이 PROTOCOL_ERROR 로 닫는다. 그래서 끊김을 알기 위한 ping 은 필요 없다. 앱이 ping 을 보내는 것은 proxy 를 지나기 위해서다 (MCP 권고).
  • push 스트림은 Connection: close 다. 끝 chunk 뒤에 다음 요청을 기다리지 않고 닫는다. notify 에는 완료 이벤트가 없어 "끝 chunk 가 나갔다" 를 표가 보지 못하므로, 닫힘 플래그를 세우고 push lane 이 빈 뒤 close 하는 것이 가장 단순하다 (7절). keep-alive 를 유지하며 스트림을 끝내려면 Work 스트림을 쓴다. MCP 의 GET 스트림은 서버가 언제든 끊어도 되고 클라이언트가 다시 연다. 9절의 정할 것 2.
  • onStreamClosed 는 IO thread 에서, 그 연결의 마지막 콜백이다. 그 뒤 response handle 은 무효다 (generation). onStreamClosed 가 NULL 인 라우트에서 setHttpBodyStream 을 Work 없이 부르면 INVALID_ARGUMENT 다. 끝을 모르는 채 handle 을 들고 있게 하지 않는다.
  • 스트림 상태의 연결에는 deadline 이 없다 (thenRead(1, 0)). keep-alive timeout 은 스트림에 적용되지 않는다. 오래 조용한 스트림을 끊는 것은 앱이 endHttpStream 으로 한다.
  • HEAD 로 스트림 라우트에 오면 (GET 라우트의 자동 처리) 헤더만 보내고 끝낸다. onStreamClosed 는 오지 않는다. setHttpBodyStream 이 HEAD 요청에서는 SUCCESS 를 돌려주되 스트림 상태로 가지 않는다.

3. 공개 API (C)

include/kiotty_net_http.h 판 v2 의 C 부분 전체다. 추가 와 제거 만 표시했고 나머지는 v1 그대로다. 이름은 수칙 5.2 (KIOTTY_NET_<TYPE>_<MEMBER>, 약어 없음) 를 따른다. "SSE" 는 약어라 API 이름에 쓰지 않고 "stream" 과 "chunk" 를 쓴다.

3.1 상수, 메서드, limits 유지

#define KIOTTY_NET_MAX_URL_LENGTH          256
#define KIOTTY_NET_MAX_CONTENT_TYPE_LENGTH 64

typedef enum KiottyNetHttpMethod { GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS, COUNT } KiottyNetHttpMethod;   /* KIOTTY_NET_HTTP_METHOD_ 접두 */
#define KIOTTY_NET_HTTP_METHOD_BIT(method) (1u << (method))

typedef struct KiottyNetHttpLimits {
    uint32_t initialization_mark;
    size_t   max_routes;                          /* 64.  라우트 + 정적 경로 + Upgrade 경로 */
    size_t   max_header_bytes;                    /* 8 KiB. request line + 헤더. 넘으면 431 */
    size_t   max_headers;                         /* 32 */
    size_t   max_body_bytes;                      /* 64 KiB. 요청 body. 넘으면 413. Upgrade 뒤 WebSocket 메시지 버퍼도 이 크기 */
    size_t   response_bytes;                      /* 64 KiB. 응답 버퍼 (상태줄 + 헤더 + 복사된 body). 스트림은 chunk 하나를 여기서 조립한다 */
    uint32_t header_timeout_milliseconds;         /* 10000 */
    uint32_t keep_alive_timeout_milliseconds;     /* 15000. 스트림 상태에는 적용되지 않는다 */
} KiottyNetHttpLimits;

KiottyNetCode KiottyNet_initializeHttpLimits(KiottyNetHttpLimits* limits);
KiottyNetCode KiottyNet_configureHttpMaxRoutes(KiottyNetHttpLimits* limits, size_t max_routes);
KiottyNetCode KiottyNet_configureHttpHeaderCapacity(KiottyNetHttpLimits* limits, size_t max_header_bytes, size_t max_headers);
KiottyNetCode KiottyNet_configureHttpBodyCapacity(KiottyNetHttpLimits* limits, size_t max_body_bytes);
KiottyNetCode KiottyNet_configureHttpResponseCapacity(KiottyNetHttpLimits* limits, size_t response_bytes);
KiottyNetCode KiottyNet_configureHttpTimeouts(KiottyNetHttpLimits* limits, uint32_t header_timeout_milliseconds, uint32_t keep_alive_timeout_milliseconds);

스트림을 위한 limit 은 더하지 않는다. Work 스트림의 timeout 은 write 마다 인자로 받고 (base 의 Stream 과 같다), push 스트림의 chunk 상한은 base 의 push_capacity 다.

request 가 가리키는 것은 Session 의 요청 버퍼다. onRequest 가 return 하면 무효이고, Work 면 finish 까지, push 스트림이면 onRequest 가 return 할 때까지다 (스트림 동안 요청은 더 이상 필요 없고 Session 의 요청 버퍼는 chunk 조립에 쓰인다). MCP 의 Mcp-Session-Id 처럼 스트림 동안 필요한 값은 onRequest 안에서 복사한다.

3.6 push 스트림 추가

KiottyNetCode KiottyNet_pushHttpChunk(KiottyNetHttpResponseHandle response, KiottyNetSpan data);   /* 아무 thread. push lane 에 복사 */
KiottyNetCode KiottyNet_endHttpStream(KiottyNetHttpResponseHandle response);                       /* 아무 thread. 끝 chunk 뒤 닫는다 */
함수코드
pushHttpChunkSUCCESS 들어갔다. BUFFER_FULL 자리 없음, 아무것도 넣지 않았고 연결은 그대로. INVALID_ARGUMENT 빈 data, 머리 / 꼬리를 더해 push_capacity 초과. PEER_CLOSED 닫힌 handle (스트림이 끝났거나 상대가 끊음). BUSY 스트림이 아닌 응답, 헤더가 아직 나가기 전은 아니다 (아래), 또는 endHttpStream 뒤. CLOSED 서버 close 뒤
endHttpStreamSUCCESS, PEER_CLOSED, BUSY 두 번째 호출. 돌아온 뒤 handle 은 곧 무효가 된다. onStreamClosed(SUCCESS) 가 IO thread 에서 온다

onRequest 안에서 (헤더가 나가기 전에) push 한 chunk 가 헤더보다 먼저 나가지 않는 것은 base 의 lane 규칙 (write lane 이 먼저, 메시지 경계에서만 lane 을 바꾼다) 에 기댄다. 그래서 "헤더가 나갔다" 를 앱에 알리는 콜백을 두지 않는다. 9절의 정할 것 3 에서 테스트로 확인한다.

5. 예제 : MCP 서버

엔드포인트 /mcp 하나에 POST (JSON-RPC 요청. 응답은 JSON 하나이거나 SSE), GET (서버 → 클라이언트 스트림), DELETE (세션 종료) 다. JSON 과 세션 표는 앱의 것이다. 여기서는 라이브러리 호출만 보인다.

5.1 C++

#include "kiotty_net_http.h"

struct McpApp
{
    WorkerPool                  pool;
    SessionTable                sessions;      // Mcp-Session-Id → { 상태, GET 스트림의 response handle (없으면 { nullptr, 0 }) }. 앱이 잠근다
};

// POST /mcp : JSON-RPC. 알림 / 응답만이면 202. 요청이면 Work 로
static void onPost(KiottyNetAppContext app_context, const KiottyNetHttpRequest* request, KiottyNetHttpResponseHandle r)
{
    McpApp*       app     = static_cast<McpApp*>(app_context);
    KiottyNet_HttpResponse response(r);
    KiottyNetSpan accept  = KiottyNet_findHttpHeader(request, "Accept");
    KiottyNetSpan session = KiottyNet_findHttpHeader(request, "Mcp-Session-Id");
    if (!acceptsJsonAndEventStream(accept))            { response.status(406); return; }
    if (!isInitialize(request->body) && !app->sessions.has(session)) { response.status(404); return; }
    if (isNotificationOrResponseOnly(request->body))   { response.status(202); return; }      // body 없음. Content-Length: 0
    response.startWork();                                                                       // onWorkStarted 로
}

static void onPostWork(KiottyNetAppContext app_context, const KiottyNetHttpRequest* request, KiottyNetHttpResponseHandle r, KiottyNetHttpWorkHandle w)
{
    McpApp*            app = static_cast<McpApp*>(app_context);
    std::string        body(request->body.data, request->body.length);                          // request 는 finish 까지 유효하지만 worker 로 넘기므로 복사
    std::string        session = textOf(KiottyNet_findHttpHeader(request, "Mcp-Session-Id"));
    KiottyNet_HttpWork work(w);
    app->pool.post([app, body, session, r, work = std::move(work)]() mutable
    {
        KiottyNet_HttpResponse response(r);
        JsonRpcRequest         rpc = parse(body);
        if (rpc.isInitialize())
        {
            std::string id = app->sessions.create();
            response.header("Mcp-Session-Id", id.c_str());
            response.body(span(initializeResult(rpc)), "application/json");
            work.finishWithResponse();
            return;
        }
        if (!rpc.isLong())                                                                       // 빠른 요청 : JSON 하나
        {
            response.body(span(handle(rpc)), "application/json");
            work.finishWithResponse();
            return;
        }
        response.bodyStream("text/event-stream");                                                // 긴 요청 : SSE. 진행 알림 여러 개 뒤 최종 응답
        for (Progress p : run(rpc))
        {
            std::string event = "event: message\ndata: " + progressNotification(p) + "\n\n";
            if (work.write(span(event), 5000).code != KIOTTY_NET_CODE_SUCCESS)                   // 상대가 끊었거나 timeout
            {
                work.finishWithClose();
                return;
            }
        }
        std::string last = "event: message\ndata: " + finalResponse(rpc) + "\n\n";
        work.write(span(last), 5000);
        work.finishWithResponse();                                                               // 끝 chunk. keep-alive 로 다음 요청
    });
}

// GET /mcp : 서버 → 클라이언트 스트림. 연결을 붙잡지 않고 아무 thread 가 push
static void onGet(KiottyNetAppContext app_context, const KiottyNetHttpRequest* request, KiottyNetHttpResponseHandle r)
{
    McpApp*       app     = static_cast<McpApp*>(app_context);
    KiottyNet_HttpResponse response(r);
    KiottyNetSpan session = KiottyNet_findHttpHeader(request, "Mcp-Session-Id");
    if (!acceptsEventStream(KiottyNet_findHttpHeader(request, "Accept"))) { response.status(405); return; }
    if (!app->sessions.has(session))                                        { response.status(404); return; }
    if (!app->sessions.attachStream(session, r))                            { response.status(409); return; }   // 세션당 스트림 하나
    response.status(200);
    response.header("Cache-Control", "no-cache");
    response.bodyStream("text/event-stream");                                                    // return 하면 헤더가 나가고 Streaming
    // Last-Event-ID 가 있으면 여기서 밀린 이벤트를 push 해 둔다. 헤더보다 먼저 나가지 않는다 (3.6)
}

static void onGetClosed(KiottyNetAppContext app_context, KiottyNetHttpResponseHandle r, KiottyNetCode)
{
    static_cast<McpApp*>(app_context)->sessions.detachStream(r);                                   // 이 뒤 r 은 무효
}

// DELETE /mcp : 세션 종료
static void onDelete(KiottyNetAppContext app_context, const KiottyNetHttpRequest* request, KiottyNetHttpResponseHandle r)
{
    McpApp* app = static_cast<McpApp*>(app_context);
    KiottyNetHttpResponseHandle stream = app->sessions.remove(KiottyNet_findHttpHeader(request, "Mcp-Session-Id"));
    if (stream.server != nullptr) { KiottyNet_endHttpStream(stream); }                           // 열린 GET 스트림이 있으면 닫는다. onGetClosed(SUCCESS) 가 온다
    KiottyNet_HttpResponse(r).status(204);
}

    // PEER_CLOSED 면 onGetClosed 가 이미 왔거나 곧 온다

6. 규칙 : thread, 수명, 코드

어디서든IO thread (onRequest 안) 또는 Work 를 든 workerIO thread 만
pushHttpChunk, endHttpStream, finishHttpWork*, isHttpWorkConnected, closeHttpServer, awaitHttpServersetter 일곱 (setHttpStatus ~ setHttpBodyStream, startHttpWork 은 onRequest 안만), writeHttpWorkChunk (worker 만)findHttpHeader (request 가 유효한 동안), 라우트 등록 (run 전)
  • 같은 응답을 두 thread 가 동시에 만지는 순간은 없다. 완성 응답과 Work 는 v1 그대로 (RUNNING 이면 IO thread, WORKING 이면 worker). push 스트림은 onRequest 가 return 한 뒤 Session 의 응답 버퍼를 IO thread 가 헤더 송신에 쓰고, 그 뒤로는 push lane 만 쓴다. pushHttpChunk 는 응답 버퍼를 보지 않는다 (chunk 머리는 stack 의 작은 버퍼에서 만든다).
  • handle 의 수명. response handle 은 요청 하나의 것이다. 완성 응답은 onRequest return 까지 (Work 면 finish 까지), push 스트림은 onStreamClosed 까지. 그 뒤는 generation 이 올라 PEER_CLOSED. 소유자 destroy 뒤에도 PEER_CLOSED 만 돌아온다 (Owner 는 은퇴할 뿐 사라지지 않는다. base 19.1).
  • 서버의 close. Work 중인 연결에는 FIN 만 보내고 finish 를 기다린다 (v1). push 스트림 연결은 바로 닫히고 onStreamClosed(CLOSED) 가 온다. run 은 모든 Work 가 finish 된 뒤 CLOSED 로 돌아온다.
  • timeout. 헤더 수신 header_timeout, 다음 요청 대기 keep_alive_timeout, Work 와 스트림 상태에는 없음. Work 스트림의 write 는 호출마다 인자. 응답 송신 (write lane 조각) 에도 timeout 이 없다 (v1 과 같다. 느린 클라이언트는 close 로 끊는다. 9절의 정할 것 5).

9. 정할 것

  1. onStreamClosed 를 라우트의 넷째 필드로 둘지. 대안은 콜백 없이 pushHttpChunk 의 PEER_CLOSED 로만 아는 것이다. 그러면 push 할 것이 없는 동안 끊긴 클라이언트를 모르고 앱의 세션 표가 낡는다. MCP 는 세션 ↔ 스트림 대응을 들고 있어야 해서 콜백을 두는 쪽을 추천한다. base 의 onDisconnected 와 같은 자리다.
  2. push 스트림의 끝이 연결을 닫는 것. keep-alive 로 돌아가려면 "끝 chunk 가 나갔다" 를 표가 알아야 하는데 notify 에는 완료 이벤트가 없다. 닫는 쪽을 추천한다 (MCP 의 GET 스트림은 끊어도 되고, 헤더에 Connection: close 를 넣어 클라이언트가 안다). keep-alive 가 필요하면 Work 스트림.
  3. onRequest 안의 push 가 헤더보다 먼저 나가지 않는 것. base 의 lane 규칙에 기댄다. 사이클 H5 의 테스트 (PushFromInsideOnRequestGoesOutAfterTheHeader) 가 확인한다. 깨지면 "헤더가 나가기 전의 push 는 BUSY" 로 바꾸고 onStreamOpened 를 더해야 한다. 그러고 싶지 않다.
  4. notify 의 gather. chunk 머리 + data + 꼬리를 한 번에 push lane 에 넣으려면 내부의 Connection::push 가 Span 둘 또는 셋을 받아야 한다. 공개 KiottyNet_notifyConnection 은 그대로 둔다. WebSocket 의 frame 머리 + payload 도 같은 길이다. base 의 작은 변경 (사이클 H5 에서 같이).
  5. 송신 timeout. 응답 조각 (write lane) 과 push lane 의 drain 에는 timeout 이 없다. 느린 클라이언트가 Session 을 붙잡는다. v1 과 같은 상태라 이 판에서는 두지 않고, 필요하면 KiottyNetHttpLimits 에 send_timeout_milliseconds 를 더한다.
  6. 정적 파일. base 에 KiottyNet_writeConnectionStreamFile (sendfile / TransmitFile) 이 생겼다. 파일 응답을 Work 모양으로 (IO thread 가 아닌 worker 가 writeConnectionStreamFile) 보낼지, 구현 가이드 4.7 대로 응답 버퍼 조각으로 보낼지. 조각 송신은 thread 를 붙잡지 않고, sendfile 은 복사가 없다. 임베디드 타깃에서는 조각 송신을 추천한다 (worker 가 없어도 된다). 사이클 H6.
  7. Work 스트림의 chunk 를 응답 버퍼에서 조립하는 것. 머리 + data + 꼬리가 send_capacity 안이면 한 번의 write, 아니면 세 번. 세 번일 때 base 의 Stream write 가 조각 사이에 다른 것을 끼우지 않는 것은 WORKING 의 규칙 (push lane 은 쌓이기만) 으로 보장된다. 확인만.
  8. HttpClient. MCP 클라이언트를 만들 때만 필요하다. requirement 11절의 동기 API (StreamClient 위) 에 SSE 를 읽는 함수 하나 (KiottyNet_readHttpReplyChunk(client, buffer, length, timeout): chunked 응답을 chunk 단위로 돌려준다) 를 더하면 Streamable HTTP 클라이언트가 된다. 이 판에는 넣지 않고 다음 판 (design_http_v1) 에서 서버가 돈 뒤에 정한다.
  9. Content-Type 을 setHttpHeader 로 넣는 것을 막을지. 막는 쪽을 적었다 (body setter 의 인자로만). 열어 두면 중복 헤더가 나갈 수 있다.

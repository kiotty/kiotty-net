HttpClient 설계 v0 (초안)

2026-11-13 초안. requirement_v0.md 11절의 HttpClient 초안 (2026-11-09 전후) 을 지금의 규약에 맞춰 다시 세운다: create 는 자원만 잡고 주소와 TLS 는 connect 가 받는다 (base B2), 결과는 { code, ... } 값, 설정은 새 struct 대신 KiottyNetHttpLimits, body 종류는 서버와 같은 KiottyNetHttpContentType. 그리고 design_http_v0.html 결정 10 이 다음 판으로 미룬 것, 곧 끝나지 않는 body (SSE) 를 받은 만큼 꺼내는 read 를 넣는다. 공개 인터페이스가 중심이고 10절에 정할 것을 모았다.

2026-11-15 고침 (설계 피드백). 응답 body 를 읽는 길을 하나로: 모든 요청은 상태줄과 헤더까지 돌려주고 body 는 언제나 readHttpReplyBody 로 받은 만큼 꺼낸다 (Reply 의 body, max_body_bytes 의 body 버퍼, openHttpStream / closeHttpStream 을 없앰). 요청 인자는 struct KiottyNetHttpClientRequest 하나 (requestHttp 의 인자 여덟 대신 sendHttpRequest). 헤더 배열을 만드는 makeHttpHeader 와 C++ KiottyNet_HttpHeaders<N>. 다른 thread 에서 걸린 호출을 깨우는 closeHttpClient. 정할 것 2, 3, 5, 6, 7, 9 를 닫았다.

2026-11-15 고침 2 (사용 순서). 쓰는 순서를 공통 헤더 등록 → 요청마다의 헤더 만들기 → 요청 (헤더를 인자로) → readBody → (close) → 공통 헤더 지우기 로 맞췄다: 헤더 배열을 요청 struct 에서 빼서 모든 요청 함수의 인자 headers, header_count 로 (path 바로 뒤), 공통 헤더를 모두 지우는 clearHttpClientHeaders 를 더했다 (하나만 지우면 setHttpClientHeader(client, name, NULL)). 결정 7, 14.

0. 한눈에

/* 1. 만들고 연결 */
KiottyNetHttpClientResult created = KiottyNet_createHttpClient(context, &configuration, &limits);   /* 자원만 */
KiottyNetHttpClientHandle client  = created.handle;
KiottyNet_connectHttpClient(client, &address, &tls);                                               /* 대상과 첫 연결. tls NULL 이면 http */

/* 2. 공통 헤더 : 이 client 의 모든 요청에 붙는다 */
KiottyNet_setHttpClientHeader(client, "Authorization", "Bearer abc");
KiottyNet_setHttpClientHeader(client, "User-Agent", "device/1.0");

/* 3. 요청마다의 헤더 : 앱의 stack 배열 */
KiottyNetHttpHeader headers[2];
headers[0] = KiottyNet_makeHttpHeader("Accept", "application/json");
headers[1] = KiottyNet_makeHttpHeader("X-Request-Id", request_id);

/* 4. 요청 : 헤더는 path 바로 뒤의 인자. 없으면 NULL, 0. 모두 상태줄 + 헤더까지 받고 돌아온다 */
KiottyNetHttpReply reply = KiottyNet_getHttp(client, "/api/status", headers, 2, 3000);
reply = KiottyNet_postHttp(client, "/api/report", NULL, 0, KIOTTY_NET_HTTP_CONTENT_TYPE_JSON, report, 3000);

KiottyNetHttpClientRequest request = KiottyNet_makeHttpClientRequest(KIOTTY_NET_HTTP_METHOD_PUT, "/api/config");
request.type = KIOTTY_NET_HTTP_CONTENT_TYPE_JSON;
request.body = config;
reply = KiottyNet_sendHttpRequest(client, &request, headers, 2, 3000);                             /* 메서드별 함수와 같은 일 */

/* 5. body : 언제나 readHttpReplyBody. 받은 만큼, { 0, SUCCESS } 가 끝 */
for (;;) {
    KiottyNetResult got = KiottyNet_readHttpReplyBody(client, buffer, sizeof(buffer), 3000);
    if (got.code != KIOTTY_NET_CODE_SUCCESS || got.bytes == 0) { break; }
    consume(buffer, got.bytes);
}
/* SSE 처럼 끝이 없는 body 는 TIMEOUT 이면 다시 read 한다 (스트림은 그대로) */

/* 6. (필요하면) 다른 thread 에서 걸린 호출 깨우기 */
KiottyNet_closeHttpClient(client);                                                                 /* 걸린 호출이 CLOSED */

/* 7. 공통 헤더 지우기 : 하나는 value NULL, 전부는 clear */
KiottyNet_setHttpClientHeader(client, "Authorization", NULL);
KiottyNet_clearHttpClientHeaders(client);

KiottyNet_destroyHttpClient(context, client);
// C++ : 같은 순서
KiottyNet_HttpClient client(context, configuration, &limits);
client.connect(address, tls);
client.header("Authorization", "Bearer abc");                               // 공통 헤더

KiottyNet_HttpHeaders<> headers;                                            // 요청마다의 헤더. stack, heap 없음
headers.add("Accept", "application/json").add("X-Request-Id", request_id);

KiottyNetHttpReply reply = client.get("/api/status", headers, 3000);
reply = client.post("/api/report", KIOTTY_NET_HTTP_CONTENT_TYPE_JSON, report, 3000);   // 헤더 없는 판
KiottyNetResult got = client.readBody(buffer, sizeof(buffer), 3000);

client.header("Authorization", nullptr);                                    // 하나 지우기
client.clearHeaders();                                                      // 전부 지우기
것무엇
모양동기. base 6절 StreamClient 위. IO Thread 가 없고 호출한 thread 가 보내고 기다린다. 콜백 없음
연결client 하나 = 연결 하나 = keep-alive. 서버가 닫은 keep-alive 는 다음 요청이 조용히 다시 연다 (3절)
설정KiottyNetClientConfiguration (버퍼, 재시도) + KiottyNetHttpLimits (머리 상한). 새 설정 struct 는 없다
헤더공통 헤더는 client 에 등록 (setHttpClientHeader, 지우기는 value NULL 또는 clearHttpClientHeaders). 요청마다의 헤더는 앱의 stack 배열을 요청 함수의 인자로
요청메서드별 일곱 (getHttp ...) 과 struct 를 받는 sendHttpRequest. 모두 (client, path 또는 request, headers, header_count, ...) 순서이고 상태줄과 헤더까지 받고 돌아온다
응답KiottyNetHttpReply { code, status, headers, header_count }. body 는 readHttpReplyBody 로 앱 버퍼에 받은 만큼. 작은 JSON 도 SSE 도 같은 길
threadclient 하나는 한 번에 한 thread. 동시 호출은 BUSY. 다른 thread 는 closeHttpClient 로 걸린 호출을 깨운다. MCP 처럼 스트림과 요청을 같이 하면 client 둘

1. 결정

#결정이유
1동기 API 하나로 시작한다. StreamClient 위에 얹고 IO Thread 를 두지 않는다. 비동기 판 (EventClient 위, 콜백으로 응답) 은 두지 않는다장비가 클라우드 REST 를 부르는 장면은 "보내고 답을 기다린다" 가 전부다. 동시에 여러 요청이 필요하면 client 를 여럿 만들고 thread 를 나눈다. 비동기가 필요한 곳은 동시 요청이 수백인 crawler, gateway 다. 이벤트 기반 양방향은 WebSocketClient 가 있다
2create 는 자원만, 대상은 connect. createHttpClient(context, configuration, limits), connectHttpClient(client, address, tls). Host 헤더와 SNI 는 address 의 hostbase B2 의 규약 (StreamClient connect, WebSocketClient run) 과 같다. 11절 초안은 create 가 tls 를 받았다
3설정은 KiottyNetHttpLimits. 쓰는 필드는 max_header_bytes / max_headers (응답 머리, 그리고 보내는 머리 전체) 둘뿐이다. 11절 초안의 KiottyNetHttpClientLimits 는 두지 않는다WebSocketClient 도 같은 struct 를 쓴다. 새 개념을 늘리지 않는다. max_body_bytes 는 결정 6 으로 쓸 곳이 없다 (body 버퍼가 없다). 서버 전용 필드 (max_routes, response_bytes, keep-alive, WebSocket 타이머) 는 읽지 않는다
4body 종류는 KiottyNetHttpContentType. 11절 초안의 const char* content_type 대신. CUSTOM 이면 앱이 헤더 배열에 Content-Type 을 넣는다서버의 setHttpBody(response, type, data) 와 같은 모양. 문자열 오타가 없다. 텍스트 계열이면 서버처럼 요청 body 의 UTF-8 을 본다
5응답은 값 + code, 머리만. KiottyNetHttpReply { code, status, headers, header_count }. headers 는 client 의 머리 버퍼를 가리키고 다음 요청 / disconnect / close 까지 유효하다. body 를 읽어도 무효가 되지 않는다11절 초안의 "다음 호출까지 유효" 를 유지하되 body 는 뺐다 (결정 6). SSE 를 읽는 동안에도 Content-Type 을 볼 수 있다
6응답 body 를 읽는 길은 하나. 모든 요청은 상태줄과 헤더까지 받고 돌아온다. body 는 readHttpReplyBody(client, buffer, length, timeout) 로 chunk 를 벗긴 바이트를 받은 만큼 꺼낸다. 한 번에 받는 요청, openHttpStream / closeHttpStream 은 두지 않는다. SSE 이벤트를 나누는 일은 앱앱은 body 크기를 미리 모른다. body 를 통째로 돌려주면 max_body_bytes 초과가 실패가 되고 라이브러리가 body 버퍼를 잡아야 한다. 길이 하나면 큰 body 는 read 를 여러 번 부르면 되고 body 버퍼가 없어진다. SSE 와 다운로드는 어차피 이 길이 필요하다 (http 설계 결정 10). libcurl, Go 도 "통째로" 를 두지 않는다
7요청은 struct 하나 + 메서드별 일곱, 헤더는 인자. KiottyNetHttpClientRequest { method, path, type, body } 와 헤더 배열을 sendHttpRequest(client, request, headers, header_count, timeout) 에 넘긴다. GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS 는 C 와 C++ 둘 다 메서드별 함수가 있고 안에서 sendHttpRequest 를 부른다. 헤더 배열은 모든 요청 함수에서 path (request) 바로 뒤의 headers, header_count 이고 없으면 NULL, 0. C++ 은 헤더 없는 판과 KiottyNet_HttpHeaders 를 받는 판 둘11절 초안의 requestHttp 는 인자가 여덟이었다. struct 면 쓰지 않는 필드 (GET 의 body) 를 0 으로 두면 되고 필드가 늘어도 함수 모양이 그대로다. 헤더를 struct 에 넣으면 메서드별 함수로는 헤더를 보낼 수 없고 sse.headers = ... 처럼 따로 채워야 했다. 인자로 두면 "헤더를 만들고 요청에 넘긴다" 가 한 줄에 보이고 메서드별 함수와 sendHttpRequest 가 같은 모양이다. 메서드별 함수는 HTTP 서버의 get / post ... 와 짝이다
8요청 body 는 복사하지 않는다. 머리는 client 의 머리 버퍼에 만들고 (max_header_bytes 안), body 는 사용자 버퍼에서 바로 보낸다. 언제나 Content-LengthStreamClient 의 write 는 사용자 버퍼에서 바로 보낸다 (TLS 는 send_capacity 씩 암호화). 요청을 chunked 로 올리는 일은 장비에 드물다
9하지 않는 것. redirect 따라가기, 쿠키, 압축 (gzip), 인증 흐름, 프록시, HTTP/2. 3xx 는 그대로 돌려준다11절 초안 그대로. 필요한 헤더는 앱이 넣는다
10선언은 kiotty_net_http.h 에 둔다 (서버와 같은 헤더)Method, Header, Limits, ContentType 을 같이 쓴다. 정할 것 1
11헤더 배열은 앱의 stack. C 는 KiottyNet_makeHttpHeader(name, value) 로 원소를 만들고 (strlen 으로 Span 둘), C++ 은 고정 배열을 가진 KiottyNet_HttpHeaders<N> 에 add(name, value) 로 쌓는다. 넘치면 TABLE_FULL 을 기록한다. thread_local 저장소는 두지 않는다요청은 호출 동안만 읽으므로 stack 으로 충분하고 heap 이 없다. KiottyNetHttpHeader 는 서버의 KiottyNetHttpRequest.headers 와 같은 타입이라 바꾸지 않는다. thread_local 은 숨은 전역 상태이고 일부 임베디드 toolchain 이 지원하지 않는다
12closeHttpClient 를 둔다. 다른 thread 에서 불러 걸린 호출 (요청, read, 다시 연결) 을 CLOSED 로 돌아오게 하고 연결을 닫는다. 대상은 남는다MCP 의 알림 thread 는 끝없이 read 한다. 앱을 끝낼 때 timeout 을 기다리지 않고 깨울 길이 필요하다. base 의 "close 는 멈추기" 와 같은 이름 (구 정할 것 3 의 (b))
13body 를 다 읽기 전에 다음 요청을 보내면 그 연결을 닫고 다시 연다. readHttpReplyBody 의 TIMEOUT 은 연결을 닫지 않는다closeHttpStream 이 없으므로 "다음 요청" 이 스트림을 끝내는 길이다. 남은 body 를 읽어 버리면 끝이 없는 SSE 에서 돌아오지 않는다. SSE 는 조용한 시간이 길어 짧은 timeout 으로 돌며 다시 read 한다
14공통 헤더는 client 에 등록하고 지울 수 있다. setHttpClientHeader(client, name, value) 는 더하거나 같은 이름을 바꾸고, value NULL 이면 그 이름을 지운다. clearHttpClientHeaders(client) 는 전부 지운다. 요청의 헤더 배열에 같은 이름이 있으면 그 요청에서는 요청 쪽만 보낸다Authorization, User-Agent, Mcp-Session-Id 처럼 모든 요청에 같은 것은 한 번만 넣는다. 토큰이 바뀌거나 세션이 끝나면 지운다 (connect 를 다시 해도 등록은 남는다). 같은 이름이 둘 나가면 서버마다 다르게 읽으므로 하나만 보낸다

3. 연결과 수명

  • connect 가 대상 (address, tls) 을 기억하고 연결한다 (StreamClient 의 재시도 설정을 따른다). 실패하면 그 code 이고 대상은 남는다. 다시 connect 하면 대상을 바꾼다.
  • 요청 은 기억한 대상으로 간다. 연결이 없으면 (처음, 끊긴 뒤) 그 자리에서 연결한다. connect 를 한 번도 하지 않았으면 INVALID_ARGUMENT.
  • keep-alive 가 서버에서 닫혀 있었으면 다시 연결해 한 번 더 보낸다. 조건은 셋 다: 다시 쓴 (재사용한) 연결이었고, 응답 바이트를 하나도 받지 못했고, 메서드가 멱등 (GET, HEAD, PUT, DELETE, OPTIONS). POST / PATCH 는 다시 보내지 않고 PEER_CLOSED (서버가 이미 처리했을 수 있다. RFC 9110 9.2.2).
  • 응답이 Connection: close 거나 HTTP/1.0 이거나 body 의 끝이 연결 닫힘이면 body 를 다 읽은 뒤 닫는다. 다음 요청이 다시 연다.
  • body 를 다 읽지 않고 다음 요청을 보내면 그 연결을 닫고 다시 연다 (결정 13). 요청 / read 가 오류로 끝나면 (read 의 TIMEOUT 빼고) 연결을 닫는다.
  • disconnect 는 연결만 닫는다. 대상은 남아 다음 요청이 다시 연다.
  • close (closeHttpClient) 는 아무 thread 에서나 부른다. 걸린 호출은 CLOSED 로 돌아오고 연결은 닫힌다. 그 뒤의 요청은 다시 연다 (close 는 그때 걸린 호출만 멈춘다).
  • timeout 은 호출마다 하나다. 요청은 (다시) 연결 + 송신 + 머리 수신, read 는 한 번의 read 마다 (한 바이트 이상 올 때까지).
  • client 하나는 한 번에 한 thread 가 쓴다. 다른 thread 가 동시에 부르면 BUSY (atomic 플래그). closeHttpClient 만 예외다.

4. 요청

} KiottyNetHttpClientRequest;

  • 보내는 머리. METHOD path HTTP/1.1, Host (address 의 host, 기본 포트가 아니면 :port, IPv6 literal 은 [...]), setHttpClientHeader 로 등록한 헤더 (요청의 헤더 배열에 같은 이름이 있는 것은 빼고), 요청의 헤더 배열, body 가 있으면 Content-Type 과 Content-Length (POST / PUT / PATCH 는 body 가 없어도 Content-Length: 0). 전부 max_header_bytes 안이어야 하고 넘으면 REQUEST_TOO_LARGE. 헤더 수가 max_headers 를 넘으면 TABLE_FULL. 둘 다 아무것도 보내지 않는다.
  • Host, Content-Length, Transfer-Encoding, Connection 은 라이브러리가 쓴다. 헤더 배열이나 등록에 있으면 INVALID_ARGUMENT.
  • 헤더의 글자 (RFC 9110 5.1, 5.5. 서버의 parseHeaderLine 과 같은 규칙):

  • 공통 (등록) 헤더. setHttpClientHeader(client, name, value). 같은 name (대소문자 무시) 은 바꾸고 value NULL 은 그 name 을 지운다 (없으면 SUCCESS). clearHttpClientHeaders(client) 는 전부 지운다. 등록은 connect / disconnect / close 를 지나도 남고 destroy 까지 간다. 저장은 client 의 머리 버퍼 앞쪽이고 등록 헤더의 합도 max_header_bytes 에 든다 (넘으면 BUFFER_FULL). 요청이 걸려 있는 동안 부르면 BUSY.
  • 요청이 SUCCESS 로 돌아오면 상태줄과 헤더를 받은 것이다. body 는 5절.

5. 응답 body 읽기

KiottyNetResult KiottyNet_readHttpReplyBody(KiottyNetHttpClientHandle client, void* buffer, size_t length, uint32_t timeout_milliseconds);
  • read 는 마지막 요청의 body 를 chunk 를 벗긴 바이트로, 받은 만큼 (최대 length) 준다. 수신 Stage 에 남은 것 (머리와 같이 온 body 앞부분) 을 먼저 주고 비면 socket 에서 기다린다 (StreamClient 의 read 와 같다).
  • body 가 끝나면 { 0, SUCCESS } 이고 그 뒤로도 같다. body 가 없는 응답 (HEAD, 204, 304), 요청을 보낸 적이 없을 때도 { 0, SUCCESS }.
  • TIMEOUT 은 연결을 닫지 않는다 (SSE 는 조용한 시간이 길다). 다시 read 하면 이어서 받는다. 그 밖의 오류 (PROTOCOL_ERROR 깨진 chunk, PEER_CLOSED 끝나기 전에 끊김, CLOSED) 는 연결을 닫는다.
  • body 에는 상한이 없다. 앱 버퍼보다 큰 body 는 여러 번 읽는다.
  • 텍스트 계열이어도 UTF-8 을 보지 않는다 (글자 하나가 read 둘에 나뉠 수 있다).
  • body 의 끝을 정하는 규칙은 6절. 끝이 연결 닫힘인 응답 (length 도 chunked 도 없음) 은 서버가 닫으면 { 0, SUCCESS }.

SSE 를 이벤트로 나누는 일 (data: 줄, 빈 줄, id:, retry:) 은 앱이다. JSON 이 라이브러리 밖인 것과 같은 선이다 (http 설계 결정 5). 줄 단위 분해 도우미를 둘지는 정할 것 4.

8.1 장비가 상태를 보고한다

시작 : client = create(context, configuration, NULL); connect(client, cloud, &tls); header(client, "Authorization", token) 1 분마다: reply = post(client, "/v1/devices/7/status", NULL, 0, JSON, status, 3000) code SUCCESS, status 204 → body 없음. 끝 code SUCCESS, status 200 → readBody 로 응답 JSON 을 꺼낸다 ({ 0, SUCCESS } 까지) code PEER_CLOSED (keep-alive 가 닫혀 있었음) → POST 라 다시 보내지 않는다. 앱이 다음 주기에 다시 code TIMEOUT → 연결은 닫혔다. 다음 요청이 다시 연다 토큰 갱신: header(client, "Authorization", new_token) (같은 name 은 바꾼다) 로그아웃 : clearHttpClientHeaders(client); destroy

8.2 MCP 클라이언트

client 둘 : requests, events. 같은 address, 같은 tls 초기화 : reply = post(requests, "/mcp", NULL, 0, JSON, initialize, 5000); readBody 로 JSON session = findHttpReplyHeader(&reply, "Mcp-Session-Id") 를 복사 (readBody 전에, 또는 read 중에도 유효) header(requests, "Mcp-Session-Id", session); header(events, ...) 알림 thread: get(events, "/mcp", [Accept: text/event-stream], 5000) loop: readBody(events, buffer, 4096, 30000) → SSE 파서 → 앱 큐 (TIMEOUT 이면 다시 read, { 0, SUCCESS } 면 다시 send) 요청 : reply = post(requests, "/mcp", [Accept: application/json, text/event-stream], JSON, call, 5000) Content-Type 이 application/json 이면 readBody 로 body 를 다 모은다 text/event-stream 이면 응답 이벤트가 올 때까지 readBody. 다음 요청이 남은 스트림을 닫는다 (결정 13) 세션 끝 : setHttpClientHeader(requests, "Mcp-Session-Id", NULL); 같은 것을 events 에도 끝 : closeHttpClient(events) → 알림 thread 의 read 가 CLOSED 로 돌아온다. join, destroy 둘

9. 안에서

  • HttpClient = StreamClient + 버퍼 둘. 머리 버퍼 (max_header_bytes: 앞쪽은 등록 헤더, 뒤쪽은 요청마다 만드는 머리), 응답 머리 저장소 (서버의 요청 저장소와 같은 것: max_header_bytes / max_headers), 대상 (address, tls 를 가리키는 값 — tls 는 connect 가 프로파일로 만든다). 모두 create 때 잡는다. body 버퍼는 없다 (결정 6). 응답 body 는 수신 Stage 에서 앱 버퍼로 바로 간다 (chunked 는 벗기면서).
  • 파서는 서버 것을 쓴다. 헤더 줄 (takeHeader), body 의 끝 (selectBodyFraming), chunk 크기 (parseChunkSize), keep-alive (decidePersistence). WebSocketClient 가 101 을 읽을 때 요청 저장소를 다시 쓰는 것과 같다. 상태줄 파서만 새로 (WebSocketClient 의 isSwitchingLine 을 넓힌다).
  • StateMachine 은 쓰지 않는다. 동기 호출 하나가 "보내기 → 상태줄 → 헤더" 를, read 가 "body 조각" 을 순서대로 부르는 함수다. IO Thread 가 없으므로 표를 둘 이유가 없다. 호출 사이에 남는 것은 body 의 진행 (남은 길이 / chunk 상태 / 닫힘까지) 하나다.
  • 줄 읽기. StreamClient 의 read 는 받은 만큼 주므로 줄은 HttpClient 가 수신 Stage 위에서 자른다 (StreamClient 에 "Stage 를 보고 줄까지" 를 더할지, HttpClient 가 자기 버퍼로 할지는 C1 에서).
  • keep-alive 재사용의 재시도 는 "이 연결로 응답을 받은 적이 있다" 플래그 하나와 "이번 응답 바이트 수" 로 판단한다 (3절).
  • BUSY 와 close. 호출마다 atomic 플래그를 잡고 놓는다. closeHttpClient 는 플래그를 보지 않고 StreamClient 의 멈춤 플래그를 세운 뒤 socket 을 깨운다. StreamClient 의 socket 을 다른 thread 에서 닫아도 되는지 (걸린 read / connect 가 바로 돌아오는지) 는 C4 에서 base 와 같이 확인한다.

10. 정할 것

  1. 헤더 파일. kiotty_net_http.h 에 같이 (제안) / kiotty_net_http_client.h 를 따로 (websocket.h 처럼 http.h 를 include). 서버만 쓰는 장비가 클라이언트 선언까지 보게 되는 것이 싫으면 따로.
  2. keep-alive 가 닫혀 있을 때 다시 보내기. 닫음: 멱등 메서드만 한 번 (3절).
  3. 다른 thread 에서 걸린 호출 깨우기. 닫음: closeHttpClient (결정 12).
  4. SSE 도우미. 두지 않는다 (제안. 앱의 몫) / 줄 하나씩 주는 read 를 둔다 (SSE 는 줄 단위라 앱 코드가 많이 준다).
  5. 응답 body 의 UTF-8 검사. 닫음: 보지 않는다 (6절).
  6. C++ 스트림 RAII. 닫음: 스트림 타입이 없다 (결정 6, 13).
  7. 스트림의 body 를 한 번에 모으는 함수. 닫음: 두지 않는다 (결정 6). 필요하면 C++ 에 readAll(buffer, length, timeout) (다 들어오면 길이, 넘치면 BUFFER_FULL) 을 나중에 더한다.
  8. 요청 body 를 조각으로 올리기 (chunked 요청, 파일 업로드). 두지 않는다 (제안).
  9. 응답 이름. 닫음: HttpReply (앱이 읽는 것). 요청은 HttpClientRequest (서버의 KiottyNetHttpRequest 는 서버가 받은 요청).

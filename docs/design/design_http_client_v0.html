HttpClient 설계 v0 (초안)

2026-11-13 초안. requirement_v0.md 11절의 HttpClient 초안 (2026-11-09 전후) 을 지금의 규약에 맞춰 다시 세운다: create 는 자원만 잡고 주소와 TLS 는 connect 가 받는다 (base B2), 결과는 { code, ... } 값, 설정은 새 struct 대신 KiottyNetHttpLimits, body 종류는 서버와 같은 KiottyNetHttpContentType. 그리고 design_http_v0.html 결정 10 이 다음 판으로 미룬 것, 곧 끝나지 않는 body (SSE) 를 받은 만큼 꺼내는 read 를 넣는다. 공개 인터페이스가 중심이고 10절에 정할 것을 모았다.

0. 한눈에

KiottyNetHttpClientResult created = KiottyNet_createHttpClient(context, &configuration, &limits);   /* 자원만 */
KiottyNetHttpClientHandle client  = created.handle;
KiottyNet_setHttpClientHeader(client, "Authorization", "Bearer abc");                              /* 모든 요청에 */
KiottyNet_connectHttpClient(client, &address, &tls);                                               /* 대상과 첫 연결. tls NULL 이면 http */

KiottyNetHttpReply reply = KiottyNet_getHttp(client, "/api/status", 3000);                         /* 호출한 thread 에서 보내고 기다린다 */
if (reply.code == KIOTTY_NET_CODE_SUCCESS && reply.status == 200) { parse(reply.body); }          /* 다음 호출까지 유효 */

reply = KiottyNet_postHttp(client, "/mcp", KIOTTY_NET_HTTP_CONTENT_TYPE_JSON, request, 3000);

/* SSE : 머리만 받고 body 는 받은 만큼 */
reply = KiottyNet_openHttpStream(client, KIOTTY_NET_HTTP_METHOD_GET, "/mcp", NULL, 0, KIOTTY_NET_HTTP_CONTENT_TYPE_OCTET_STREAM, NO_BODY, 3000);
for (;;) {
    KiottyNetResult got = KiottyNet_readHttpStream(client, buffer, sizeof(buffer), 30000);   /* chunk 를 벗긴 바이트 */
    if (got.code != KIOTTY_NET_CODE_SUCCESS || got.bytes == 0) { break; }                   /* 0 바이트 SUCCESS = body 끝 */
    feed_sse_parser(buffer, got.bytes);
}
KiottyNet_closeHttpStream(client);
것무엇
모양동기. base 6절 StreamClient 위. IO Thread 가 없고 호출한 thread 가 보내고 기다린다. 콜백 없음
연결client 하나 = 연결 하나 = keep-alive. 서버가 닫은 keep-alive 는 다음 요청이 조용히 다시 연다 (3절)
설정KiottyNetClientConfiguration (버퍼, 재시도) + KiottyNetHttpLimits (응답 헤더 / body 상한). 새 설정 struct 는 없다
응답KiottyNetHttpReply { code, status, headers, header_count, body }. client 안의 버퍼를 가리키고 다음 호출까지 유효
스트림openHttpStream → readHttpStream 여러 번 → closeHttpStream. MCP 의 GET / POST 의 SSE 응답
threadclient 하나는 한 번에 한 thread. 동시 호출은 BUSY. MCP 처럼 스트림과 요청을 같이 하면 client 둘 (결정 10 의 전제)

1. 결정 (제안)

#제안이유
1동기 API 하나로 시작한다. StreamClient 위에 얹고 IO Thread 를 두지 않는다. 비동기 판 (EventClient 위, 콜백으로 응답) 은 두지 않는다장비가 클라우드 REST 를 부르는 장면은 "보내고 답을 기다린다" 가 전부다. 동시에 여러 요청이 필요하면 client 를 여럿 만들고 thread 를 나눈다. requirement 11절 열린 질문 3 의 제안 그대로
2create 는 자원만, 대상은 connect. createHttpClient(context, configuration, limits), connectHttpClient(client, address, tls). Host 헤더와 SNI 는 address 의 hostbase B2 의 규약 (StreamClient connect, WebSocketClient run) 과 같다. 11절 초안은 create 가 tls 를 받았다
3설정은 KiottyNetHttpLimits. 쓰는 필드는 max_header_bytes / max_headers (응답 머리, 그리고 보내는 머리 전체), max_body_bytes (한 번에 받는 응답 body). 11절 초안의 KiottyNetHttpClientLimits 는 두지 않는다WebSocketClient 도 같은 struct 를 쓴다. 새 개념을 늘리지 않는다 (설계 피드백). 서버 전용 필드 (max_routes, response_bytes, keep-alive, WebSocket 타이머) 는 읽지 않는다
4body 종류는 KiottyNetHttpContentType. 11절 초안의 const char* content_type 대신. CUSTOM 이면 앱이 헤더 배열에 Content-Type 을 넣는다서버의 setHttpBody(response, type, data) 와 같은 모양. 문자열 오타가 없다. 텍스트 계열이면 서버처럼 UTF-8 을 본다
5응답은 값 + code, 다음 호출까지 유효. KiottyNetHttpReply 는 client 안의 버퍼를 가리킨다11절 초안 그대로. 할당 없이 버퍼 하나로 끝난다 (메모리 원칙)
6받은 만큼 꺼내는 read 를 넣는다. openHttpStream 이 머리만 받아 돌려주고, readHttpStream 이 chunk 를 벗긴 body 를 받은 만큼 준다. SSE 이벤트를 나누는 일은 앱 (JSON 이 라이브러리 밖인 것과 같다)http 설계 결정 10. SSE 응답은 끝나지 않는 body 하나라 통째로 돌려주는 API 로는 받을 수 없다. max_body_bytes 보다 큰 다운로드도 이 길이다
7메서드별 함수 일곱 + 일반 하나. GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS 와 requestHttp (헤더 배열을 받는 것)11절 초안 그대로. HTTP 서버의 get / post ... 와 짝이다
8요청 body 는 복사하지 않는다. 머리는 client 버퍼에 만들고, body 는 사용자 버퍼에서 바로 보낸다. 언제나 Content-LengthStreamClient 의 write 는 사용자 버퍼에서 바로 보낸다 (TLS 는 send_capacity 씩 암호화). 요청을 chunked 로 올리는 일은 장비에 드물다
9하지 않는 것. redirect 따라가기, 쿠키, 압축 (gzip), 인증 흐름, 프록시, HTTP/2. 3xx 는 그대로 돌려준다11절 초안 그대로. 필요한 헤더는 앱이 넣는다
10선언은 kiotty_net_http.h 에 둔다 (서버와 같은 헤더)Method, Header, Limits, ContentType 을 같이 쓴다. 정할 것 1

3. 연결과 수명

  • connect 가 대상 (address, tls) 을 기억하고 연결한다 (StreamClient 의 재시도 설정을 따른다). 실패하면 그 code 이고 대상은 남는다. 다시 connect 하면 대상을 바꾼다.
  • 요청 은 기억한 대상으로 간다. 연결이 없으면 (처음, 끊긴 뒤) 그 자리에서 연결한다. connect 를 한 번도 하지 않았으면 INVALID_ARGUMENT.
  • keep-alive 가 서버에서 닫혀 있었으면 다시 연결해 한 번 더 보낸다. 조건은 셋 다: 다시 쓴 (재사용한) 연결이었고, 응답 바이트를 하나도 받지 못했고, 메서드가 멱등 (GET, HEAD, PUT, DELETE, OPTIONS). POST / PATCH 는 다시 보내지 않고 PEER_CLOSED (서버가 이미 처리했을 수 있다). 정할 것 2.
  • 응답이 Connection: close 거나 HTTP/1.0 이면 응답을 다 읽은 뒤 닫는다. 다음 요청이 다시 연다.
  • disconnect 는 연결만 닫는다. 대상은 남아 다음 요청이 다시 연다.
  • timeout 은 호출마다 하나다. 한 번에 받는 요청은 (다시) 연결 + 송신 + 응답 전체, 스트림은 open 이 머리까지, read 는 한 번의 read 마다.
  • client 하나는 한 번에 한 thread 가 쓴다. 다른 thread 가 동시에 부르면 BUSY (atomic 플래그). 다른 thread 가 걸린 호출을 깨우는 길은 정할 것 3.

4. 한 번에 받는 요청

KiottyNetHttpReply KiottyNet_requestHttp(KiottyNetHttpClientHandle client, KiottyNetHttpMethod method, const char* path,
                                         const KiottyNetHttpHeader* headers, size_t header_count,
                                         KiottyNetHttpContentType type, KiottyNetSpan body, uint32_t timeout_milliseconds);
KiottyNetHttpReply KiottyNet_getHttp(client, path, timeout);                 /* body 없음 */

KiottyNetHttpReply KiottyNet_putHttp(client, path, type, body, timeout);
KiottyNetHttpReply KiottyNet_deleteHttp(client, path, timeout);
KiottyNetHttpReply KiottyNet_patchHttp(client, path, type, body, timeout);
KiottyNetHttpReply KiottyNet_headHttp(client, path, timeout);                /* body 는 언제나 길이 0 */
KiottyNetHttpReply KiottyNet_optionsHttp(client, path, timeout);             /* path "*" 는 서버 전체 */
  • 보내는 머리. METHOD path HTTP/1.1, Host (address 의 host, 기본 포트가 아니면 :port, IPv6 literal 은 [...]), setHttpClientHeader 로 등록한 헤더, 호출의 헤더 배열, body 가 있으면 Content-Type 과 Content-Length. 전부 max_header_bytes 안이어야 하고 넘으면 REQUEST_TOO_LARGE (아무것도 보내지 않는다).
  • Host, Content-Length, Transfer-Encoding, Connection 은 라이브러리가 쓴다. 헤더 배열이나 등록에 있으면 INVALID_ARGUMENT.
  • path 는 / 로 시작하는 보이는 ASCII (query 포함) 이거나 OPTIONS 의 *.
  • 등록 헤더. setHttpClientHeader(client, name, value). 같은 name 은 바꾸고 value NULL 은 지운다. 저장은 client 의 머리 버퍼 앞쪽이고 등록 헤더의 합도 max_header_bytes 에 든다 (넘으면 BUFFER_FULL).
  • 응답 body 는 max_body_bytes 까지 client 버퍼에 모은다. 넘으면 BUFFER_FULL 이고 연결을 닫는다 (남은 body 를 버릴 수 없어서). 큰 body 는 5절.

5. 받은 만큼 꺼내는 요청 (스트림)

KiottyNetHttpReply KiottyNet_openHttpStream(KiottyNetHttpClientHandle client, KiottyNetHttpMethod method, const char* path,
                                            const KiottyNetHttpHeader* headers, size_t header_count,
                                            KiottyNetHttpContentType type, KiottyNetSpan body, uint32_t timeout_milliseconds);   /* 머리까지. body 는 길이 0 */
KiottyNetResult    KiottyNet_readHttpStream(KiottyNetHttpClientHandle client, void* buffer, size_t length, uint32_t timeout_milliseconds);
void               KiottyNet_closeHttpStream(KiottyNetHttpClientHandle client);
  • open 은 4절과 같이 보내고 응답의 머리 (상태줄, 헤더) 까지만 받는다. Reply 의 headers 는 스트림이 닫힐 때까지 유효하다. 2xx 가 아니어도 스트림은 열린다 (오류 body 를 읽을 수 있게).
  • read 는 body 를 chunk 를 벗긴 바이트로, 받은 만큼 (최대 length) 준다. 수신 Stage 에 남은 것을 먼저 주고 비면 socket 에서 기다린다 (StreamClient 의 read 와 같다). body 가 끝나면 { 0, SUCCESS } 이고 그 뒤로도 같다. 텍스트 계열이어도 UTF-8 을 보지 않는다 (글자 하나가 read 둘에 나뉠 수 있다).
  • close 는 스트림을 끝낸다. body 를 끝까지 읽었고 keep-alive 면 연결을 남기고, 아니면 연결을 닫는다 (남은 body 를 버릴 길이 없다). 열린 스트림이 없으면 아무것도 하지 않는다.
  • 스트림이 열려 있는 동안 같은 client 의 다른 요청은 BUSY. read timeout 은 연결을 닫지 않는다 (SSE 는 조용한 시간이 길다). 다시 read 하면 된다.
  • body 의 끝을 정하는 규칙은 6절과 같다. 끝이 연결 닫힘인 응답 (length 도 chunked 도 없음) 은 서버가 닫으면 { 0, SUCCESS }.

SSE 를 이벤트로 나누는 일 (data: 줄, 빈 줄, id:, retry:) 은 앱이다. JSON 이 라이브러리 밖인 것과 같은 선이다 (http 설계 결정 5). 줄 단위 분해 도우미를 둘지는 정할 것 4.

8. 장면별 흐름

8.1 장비가 상태를 보고한다

시작 : client = create(context, configuration, NULL); header(client, "Authorization", token); connect(client, cloud, &tls) 1 분마다: reply = post(client, "/v1/devices/7/status", JSON, status, 3000) code SUCCESS, status 204 → 끝 code PEER_CLOSED (keep-alive 가 닫혀 있었음) → POST 라 다시 보내지 않는다. 앱이 다음 주기에 다시 code TIMEOUT → 연결은 닫혔다. 다음 요청이 다시 연다

8.2 MCP 클라이언트

client 둘 : requests, events. 같은 address, 같은 tls 초기화 : reply = post(requests, "/mcp", JSON, initialize, 5000) session = findHttpReplyHeader(&reply, "Mcp-Session-Id") 를 복사; header(requests, "Mcp-Session-Id", session); header(events, ...) 알림 thread: openStream(events, GET, "/mcp", [Accept: text/event-stream], ..., 5000) loop: readStream(events, buffer, 4096, 30000) → SSE 파서 → 앱 큐 (TIMEOUT 이면 다시 read, { 0, SUCCESS } 면 다시 open) 요청 : reply = openStream(requests, POST, "/mcp", [Accept: application/json, text/event-stream], JSON, call, 5000) Content-Type 이 application/json 이면 readStream 으로 body 를 다 모은다 (또는 정할 것 7) text/event-stream 이면 응답 이벤트가 올 때까지 readStream closeStream(requests) 끝 : events 를 깨우는 길 (정할 것 3), destroy 둘

8.3 큰 파일 받기

reply = openStream(client, GET, "/firmware/1.2.bin", NULL, 0, OCTET_STREAM, {NULL,0}, 5000) length = findHttpReplyHeader(&reply, "Content-Length") loop : got = readStream(client, chunk, 16384, 10000) → file.write(chunk, got.bytes) 까지 { 0, SUCCESS } closeStream(client)

9. 안에서

  • HttpClient = StreamClient + 버퍼 셋. 머리 버퍼 (max_header_bytes: 앞쪽은 등록 헤더, 뒤쪽은 요청마다 만드는 머리), 응답 저장소 (서버의 요청 저장소와 같은 것: 응답 머리 max_header_bytes / max_headers, body Stage max_body_bytes), 대상 (address, tls 를 가리키는 값 — tls 는 connect 가 프로파일로 만든다). 모두 create 때 잡는다.
  • 파서는 서버 것을 쓴다. 헤더 줄 (takeHeader), body 의 끝 (selectBodyFraming), chunk 크기 (parseChunkSize), keep-alive (decidePersistence). WebSocketClient 가 101 을 읽을 때 요청 저장소를 다시 쓰는 것과 같다. 상태줄 파서만 새로 (WebSocketClient 의 isSwitchingLine 을 넓힌다).
  • StateMachine 은 쓰지 않는다. 동기 호출 하나가 "보내기 → 상태줄 → 헤더 → body" 를 순서대로 부르는 함수다. IO Thread 가 없으므로 표를 둘 이유가 없다.
  • 줄 읽기. StreamClient 의 read 는 받은 만큼 주므로 줄은 HttpClient 가 수신 Stage 위에서 자른다 (StreamClient 에 "Stage 를 보고 줄까지" 를 더할지, HttpClient 가 자기 버퍼로 할지는 C1 에서).
  • keep-alive 재사용의 재시도 는 "이 연결로 응답을 받은 적이 있다" 플래그 하나와 "이번 응답 바이트 수" 로 판단한다 (3절).

10. 정할 것

  1. 헤더 파일. kiotty_net_http.h 에 같이 (제안) / kiotty_net_http_client.h 를 따로 (websocket.h 처럼 http.h 를 include). 서버만 쓰는 장비가 클라이언트 선언까지 보게 되는 것이 싫으면 따로.
  2. keep-alive 가 닫혀 있을 때 다시 보내기. 멱등 메서드만 한 번 (제안) / 모두 한 번 (curl 과 같음. POST 가 두 번 처리될 수 있다) / 다시 보내지 않음 (앱이 매번 PEER_CLOSED 를 처리).
  3. 다른 thread 에서 걸린 호출 깨우기. MCP 의 알림 thread 는 끝없이 read 한다. 끝낼 때 (a) read timeout 을 짧게 잡고 앱이 플래그를 본다 (라이브러리 변경 없음) / (b) KiottyNet_closeHttpClient(client) 를 두어 걸린 호출이 CLOSED 로 돌아오게 한다 (base 의 "close 는 멈추기" 와 같은 이름. StreamClient 의 socket 을 다른 thread 에서 닫아도 되는지 base 에서 확인이 필요하다). (b) 를 제안한다.
  4. SSE 도우미. 두지 않는다 (제안. 앱의 몫) / readHttpStreamLine 처럼 줄 하나씩 주는 read 를 둔다 (SSE 는 줄 단위라 앱 코드가 많이 준다).
  5. 응답 body 의 UTF-8 검사. 하지 않는다 (제안. 받은 것을 그대로 주고 판단은 앱) / 서버처럼 텍스트 계열이면 본다.
  6. C++ 스트림 RAII. closeStream 을 부르게 둔다 (제안) / KiottyNet_HttpStream 이동 전용 타입이 소멸자에서 닫는다 (HttpWork, ConnectionStream 과 같은 모양).
  7. 스트림의 body 를 한 번에 모으는 함수. MCP 의 POST 는 응답이 JSON 일지 SSE 일지 머리를 봐야 안다. readHttpStreamAll(client, timeout) (남은 body 를 max_body_bytes 까지 모아 Reply 로) 를 둘지.
  8. 요청 body 를 조각으로 올리기 (chunked 요청, 파일 업로드). 두지 않는다 (제안).
  9. 응답 이름. 서버의 HttpResponse (앱이 채우는 것) 와 구분하는 HttpReply (앱이 읽는 것) 그대로 (11절 열린 질문 2).

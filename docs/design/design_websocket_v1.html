kiotty_net_websocket.h 설계 v1

2026-11-13 첫 판, 같은 날 고침 (정할 것 전부 답: 후보 없는 101 은 통과, broadcast 는 판 v2 그대로, 클라이언트 close handshake 는 shutdownWebSocketClient, HTTP 라우트는 그대로, C++ 경로 등록은 생성자라 http.h 는 손대지 않음). design_websocket_v0.html 의 판 v2 (W1 ~ W5 로 구현) 를 쓰기 쉽게 고친 판 v3 를 정한다. 사용자 피드백: user guide 에서 받기가 어디 있는지 보이지 않고, handler struct 를 넘기는 모양이 HTTP 와 달라 보인다. JavaScript WebSocket API 와 libwebsockets 를 견주어 보고, 서버와 클라이언트 모두 kiotty HTTP 의 등록 모양을 따른다 로 정했다. 같이 HTTP 의 app_context 를 run 한 번으로 모은다 (design_http_v0.html 결정 19 를 고친다). 공개 인터페이스가 중심이다. frame 행, Session, 송신의 두 길, 타이머는 v0 6, 7절과 구현 가이드 5절 그대로다.

표기: 유지 지금 헤더 그대로, 추가 이 판이 더하거나 바꾸는 것, 제거 이 판이 빼는 것.

설계 방침

  1. 등록은 HTTP 와 같은 모양이다. 이벤트 하나에 등록 함수 하나 (KiottyNet_on<Layer><Event>), run 전에만, 같은 이벤트를 다시 등록하면 바꾼다. handler struct 는 없다.
  2. app_context 는 run 에 한 번이다. base 의 runServer / runEventClient 와 같다. 등록 함수는 app_context 를 받지 않는다. HTTP 도 그렇게 바꾼다.
  3. 등록 때 경로는 한 번만 쓴다. addWebSocket(server, "/chat") 이 돌려준 KiottyNetWebSocketRoute 에 이벤트를 이어 붙인다. broadcast 는 판 v2 그대로 경로 문자열을 받는다.
  4. 받기는 콜백이다. JavaScript 의 onmessage, libwebsockets 의 RECEIVE 와 같다. receive 함수는 두지 않는다. user guide 에 "받기" 절을 따로 둔다.
  5. 안은 그대로다. frame 행, HttpSession, 송신의 두 길, 타이머, handle { owner, id } 는 v0 그대로다. 바뀌는 것은 콜백이 어디서 와서 어디에 묶이는가뿐이다.

1. 결정 기록

#결정이유
1서버와 클라이언트 모두 HTTP 의 등록 모양을 따른다. handler struct (KiottyNetWebSocketHandler) 를 없앤다 (2026-11-13)사용자가 HTTP 는 다른 HTTP API 와 비슷해 쓰기 쉽다고 봤고 WebSocket 은 달라 보였다. 등록 규약 (KiottyNet_on<Layer><Event>) 은 http 결정 19 에서 정한 것이다
2상대 주소는 KiottyNetAddress 그대로. URL 문자열은 받지 않는다 (2026-11-13)base 의 모든 run / connect 와 같다
3서버에는 WebSocket 전용 onError / onDisconnected 가 없다. HttpServer 의 onHttpError / onHttpDisconnected 가 받고 KiottyNetCode 가 이유를 싣는다. WebSocket 의 onClose 는 남긴다 (2026-11-13)연결은 HttpServer 의 것이다. onClose 는 소켓마다의 websocket_context 를 풀 자리이고 상대의 close status / reason 을 받는 곳이라 HTTP 의 끊김 action 으로 대신할 수 없다
4경로는 한 번만 쓴다. KiottyNet_addWebSocket(server, path) 이 KiottyNetWebSocketRoute 를 돌려주고, KiottyNet_onWebSocket*(route, cb) 가 그 값을 받아 다시 돌려준다. 처음 실패한 코드가 route.code 에 남고 실패한 뒤의 호출은 아무것도 하지 않는다 (2026-11-13)사용자 제안. 마지막에 code 하나만 보면 된다. C++ builder 가 처음 실패를 기억하는 것과 같다
5app_context 는 run 에 한 번. KiottyNet_runHttpServer(server, address, tls, app_context), KiottyNet_runWebSocketClient(client, address, path, tls, app_context). HTTP 라우트의 app_context 필드와 action 등록의 app_context 인자를 없앤다 (2026-11-13)사용자 결정. 앱의 context 는 보통 하나다. base 의 runServer / runEventClient 와 같은 자리다. 규모가 크지만 (HTTP 헤더, 구현, H3 ~ H6 테스트) 모양이 하나로 모인다
6클라이언트 등록은 KiottyNet_onWebSocketClientOpen / Message / Close / Error(client, cb) (2026-11-13)사용자 결정. 클라이언트에는 경로가 없으므로 route 값 없이 client 에 바로 붙인다
7클라이언트 path 는 run 이 받는다 (2026-11-13)주소, TLS, 경로가 한 곳에 모인다. 한 클라이언트로 다른 경로에 차례로 붙을 수 있다
8클라이언트 콜백에는 소켓 handle 이 없다 (2026-11-13)소켓이 하나이고 보내기도 client 로 한다. JavaScript 의 ws.onmessage 와 같은 모양이 된다
9클라이언트도 subprotocol 후보를 보낼 수 있다. KiottyNet_setWebSocketClientProtocols(client, "ocpp1.6, ocpp2.0.1"). 101 의 Sec-WebSocket-Protocol 이 후보 중 하나면 통과, 후보 밖이거나 후보를 보내지 않았는데 오면 PROTOCOL_ERROR, 후보를 보냈는데 101 에 없으면 통과하고 고른 값은 빈 문자열 (JavaScript 와 같다). v0 결정 12 를 고친다 (2026-11-13)OCPP (충전기), MQTT over WebSocket, STOMP 서버는 후보가 없으면 연결을 거절한다. JavaScript 도 new WebSocket(url, protocols) 로 받는다
10C++ 서버는 KiottyNet_WebSocketRoute(server, "/chat").onUpgrade(..).onOpen(..).onMessage(..).onClose(..).build(). 생성자는 websocket.h 에 있고 KiottyNet_HttpServer& 를 받는다. kiotty_net_http.h 는 바뀌지 않는다 (2026-11-13)server.websocket("/chat") 멤버로 두려면 http.h 가 KiottyNet_WebSocketRoute 이름을 알아야 한다. C ABI 에는 그 이름이 들어갈 곳이 없으므로 C++ 모양 하나 때문에 의존을 늘리지 않는다
11broadcast 는 판 v2 그대로 KiottyNet_broadcastWebSocket(server, path, opcode, data). path 가 NULL 이면 서버의 모든 WebSocket 소켓 (2026-11-13)다른 라이브러리 (Node ws, websocketpp, Beast) 는 함수 이름은 없어도 연결 전부를 돌며 보내는 길을 연다. 경로 하나와 서버 전체 둘 다 쓴다
12클라이언트의 close handshake 는 KiottyNet_shutdownWebSocketClient(client, status, reason). KiottyNet_closeWebSocketClient(client) 는 base 의 run / close / await 규칙대로 멈추기 (handshake 없음). 소켓 handle 쪽은 KiottyNet_closeWebSocket(websocket, status, reason) 그대로 (2026-11-13)close 는 모든 소유자에서 "멈추기" 로 같은 뜻이어야 한다. 클라이언트 콜백에서 handle 을 뺐으므로 handshake 도 client 로 바로 한다 (send 와 sendWebSocketClient 의 짝과 같다)
13HTTP 라우트 등록 (addHttpRoute, C++ get / post ...) 은 바꾸지 않는다 (2026-11-13)사용자 결정. 지금 모양이 다른 HTTP 라이브러리와 비슷하다

2. 왜 바꾸나 : JavaScript, libwebsockets 와 견주기

JavaScriptlibwebsockets판 v2이 판
받기ws.onmessage콜백의 LWS_CALLBACK_*_RECEIVEhandler 의 onMessageonWebSocketMessage(route, cb), onWebSocketClientMessage(client, cb)
보내기아무 때나 sendWRITEABLE 콜백 안에서만 lws_write아무 thread 에서나같다

3. HTTP 에서 바뀌는 것 : app_context 는 run 에 한 번

typedef struct KiottyNetHttpRoute { KiottyNetHttpRequestAction onRequest; KiottyNetHttpWorkAction onWorkStarted; } KiottyNetHttpRoute;
KiottyNetHttpRoute KiottyNet_makeHttpRoute(KiottyNetHttpRequestAction onRequest, KiottyNetHttpWorkAction onWorkStarted);

KiottyNetCode KiottyNet_runHttpServer(KiottyNetHttpServerHandle server, const KiottyNetAddress* address, const KiottyNetTlsServerConfiguration* tls, KiottyNetAppContext app_context);
  • 콜백 typedef 넷 (RequestAction, WorkAction, DisconnectedAction, ErrorAction) 의 첫 인자 app_context 는 그대로다. 값이 run 의 것으로 바뀔 뿐이다.
  • C++: route(method, path, on_request) 와 get / post ... 는 그대로, onDisconnected(action), onError(action), run(address, app_context), run(address, tls, app_context).
  • 안: HttpSite 가 run 동안 app_context 하나를 든다. 라우트 표의 항목은 app_context 를 들지 않는다.
  • 라우트마다 다른 앱 데이터가 필요하던 앱은 app_context 안에 두고 request->path 로 가른다. MCP 예제 (H6) 는 이미 app 하나다.
  • worker 의 onWorkStarted 도 run 의 app_context 를 받는다. worker 가 run 뒤까지 남을 수 있는 것 (base 7절) 은 그대로라, worker 에 넘긴 app_context 의 수명은 앱이 지킨다.

4. 서버 : WebSocketRoute

KiottyNetWebSocketRoute chat = KiottyNet_addWebSocket(server, "/chat");
chat = KiottyNet_onWebSocketUpgrade(chat, on_upgrade);     /* 선택. 없으면 모두 허용 */
chat = KiottyNet_onWebSocketOpen(chat, on_open);           /* 선택. 없으면 websocket_context 는 NULL */

if (chat.code != KIOTTY_NET_CODE_SUCCESS) { /* 마지막에 한 번 */ }

KiottyNet_onHttpError(server, on_error);                   /* 오류와 끊김은 HttpServer 의 것 (결정 3) */
KiottyNet_runHttpServer(server, &address, tls, &app);     /* app_context 는 여기 한 번 */

/* 아무 thread */
KiottyNet_broadcastWebSocket(server, "/chat", KIOTTY_NET_WEB_SOCKET_OPCODE_TEXT, data);   /* 그 경로의 열린 소켓 전부 */
KiottyNet_broadcastWebSocket(server, NULL, KIOTTY_NET_WEB_SOCKET_OPCODE_TEXT, data);      /* 서버의 모든 WebSocket 소켓 */

route.codeaddWebSocket 의 실패 (DUPLICATE_RULE, TABLE_FULL, BUSY, INVALID_ARGUMENT) 또는 on* 의 실패 (BUSY: run 뒤, INVALID_ARGUMENT: 콜백 NULL) 중 처음 것. 실패한 route 를 받은 on* 는 아무것도 하지 않고 그대로 돌려준다

route 값{ code, server, index }. 등록에만 쓰는 값이다. run 뒤에는 쓸 곳이 없다

5. 클라이언트 : 이벤트 등록과 run

KiottyNetWebSocketClientResult created = KiottyNet_createWebSocketClient(context, &configuration, &limits);   /* path 가 빠졌다 */
KiottyNetWebSocketClientHandle client = created.handle;
KiottyNet_setWebSocketClientProtocols(client, "ocpp1.6");      /* 선택 (결정 9) */
KiottyNet_onWebSocketClientOpen(client, on_open);
KiottyNet_onWebSocketClientMessage(client, on_message);        /* 필수 */
KiottyNet_onWebSocketClientClose(client, on_close);
KiottyNet_onWebSocketClientError(client, on_error);
KiottyNet_runWebSocketClient(client, &address, "/ocpp/CP001", tls, &app);   /* IO thread. 연결 + Upgrade + loop */

/* 아무 thread */
KiottyNet_sendWebSocketClient(client, KIOTTY_NET_WEB_SOCKET_OPCODE_TEXT, data);
이벤트콜백언제
Openvoid (*)(KiottyNetAppContext app_context)101 을 받고 검사를 지났을 때. 이때부터 await 가 SUCCESS
Messagevoid (*)(KiottyNetAppContext app_context, KiottyNetWebSocketMessage message)메시지 하나
Closevoid (*)(KiottyNetAppContext app_context, KiottyNetWebSocketClose close)Open 이 나간 뒤 끝날 때 한 번. 표는 판 v2 user guide 4절 그대로
Errorvoid (*)(KiottyNetAppContext app_context, KiottyNetConnectionInfo info, KiottyNetCode code, const char* message)Open 전에 실패했을 때 한 번: 연결 재시도 실패, TLS 실패, 101 아님, Accept 틀림, subprotocol 이 후보 밖, 101 timeout. 모양은 KiottyNetHttpErrorAction 과 같다. Open 뒤의 실패는 Close 의 code 로 온다 (JavaScript 는 onerror 뒤 onclose 가 오지만 여기서는 둘 중 하나만 온다)
  • 등록은 run 전에만 (run 중이면 BUSY). 같은 이벤트는 다시 등록하면 바꾼다. 등록은 다음 run 에도 남는다. Message 가 없으면 run 이 INVALID_ARGUMENT.
  • run 의 반환값, await, close (handshake 없는 끊기) 는 판 v2 그대로다 (requirement 11절).
  • 닫기 둘 (결정 12, 흐름은 8.4). KiottyNet_shutdownWebSocketClient(client, status, reason) 은 close handshake 를 시작한다 (JavaScript 의 ws.close(code, reason)). 규칙과 코드는 KiottyNet_closeWebSocket 과 같고 열린 소켓이 없으면 PEER_CLOSED. KiottyNet_closeWebSocketClient(client) 는 base 규칙대로 멈추기다: 연결 중 재시도도 멈추고, 열린 소켓은 handshake 없이 끊는다 (onClose(CLOSED, 1001), run 은 CLOSED).
  • KiottyNet_getWebSocketClientSocket 은 남는다. 서버 코드와 같은 함수 (getWebSocketInfo 등) 를 쓰고 싶을 때 쓴다.
  • 고른 subprotocol 은 KiottyNet_getWebSocketInfo(KiottyNet_getWebSocketClientSocket(client)).protocol.

7. C++ wrapper

KiottyNet_HttpServer server(context.handle(), configuration, limits);
KiottyNetCode chat = KiottyNet_WebSocketRoute(server, "/chat")
    .onUpgrade(on_upgrade)
    .onOpen(on_open)
    .onMessage(on_message)
    .onClose(on_close)
    .build();                                           // route.code
server.onError(on_error);
std::thread io([&] { server.run(address, &app); });
KiottyNet_broadcastWebSocket(server.handle(), "/chat", KIOTTY_NET_WEB_SOCKET_OPCODE_TEXT, data);   // 아무 thread

KiottyNet_WebSocketClient client(context.handle(), configuration, &limits);
client.protocols("ocpp1.6");
client.onOpen(on_open);
client.onMessage(on_message);
client.onClose(on_close);
client.onError(on_error);
std::thread io([&] { client.run(address, "/ocpp/CP001", tls, &app); });
client.send(KIOTTY_NET_WEB_SOCKET_OPCODE_TEXT, hello);
client.shutdown(1000, "bye");                           // close handshake. 기본값 1000, nullptr
client.close();                                         // 멈추기

KiottyNet_WebSocketRoute 는 KiottyNetWebSocketRoute 값을 든 비소유 값 타입이다. onX 는 C 함수를 불러 값을 바꾸고 *this 를 돌려준다. build() 는 code, route() 는 C 값이다. 생성자 KiottyNet_WebSocketRoute(KiottyNet_HttpServer& server, const char* path) 와 KiottyNet_WebSocketRoute(KiottyNetHttpServerHandle server, const char* path) 둘을 websocket.h 에 둔다. http.h 는 바뀌지 않는다 (결정 10).

8. 장면별 흐름

8.1 장비의 웹 UI + 채팅 (서버)

run 전 : server.serveDirectory("/", "./www/") KiottyNet_WebSocketRoute(server, "/chat").onOpen(chatOpen).onMessage(chatMessage).onClose(chatClose).build() server.run(address, &app) ← app 이 모든 콜백의 app_context 연결 하나 : GET /chat + Upgrade → (Upgrade 콜백 없음 = 허용) → 101 → chatOpen(&app, ws) chatOpen : session = app.sessions.acquire(); session.ws = ws; app.clients.insert(ws); return session 메시지 : chatMessage(session, ws, { TEXT, "hi" }) → KiottyNet_WebSocket(ws).send(...) 끝 : chatClose(&app, session, { SUCCESS, 1000 }) → app.clients.erase(session.ws); release(session) 그 뒤 HttpServer 의 onHttpDisconnected(&app, info, SUCCESS)

8.2 요청을 보내고 답을 기다리는 클라이언트

run 전 : client.onMessage(onReply) onReply : app.inbox 에 복사하고 condition_variable 을 깨운다 io thread : client.run(address, "/api", nullptr, &app) 앱 thread : client.await(5000) == SUCCESS client.send(TEXT, request) → app.arrived.wait_for(3 s) → inbox 에서 꺼낸다

receive 함수가 없으므로 이 다리는 앱이 놓는다. user guide 의 "받기" 절에 이 예제를 싣는다.

8.3 OCPP 충전기 (subprotocol 이 필요한 서버에 붙기)

client.protocols("ocpp1.6") client.run(address, "/ocpp/CP001", tls, &app) → Upgrade 요청에 Sec-WebSocket-Protocol: ocpp1.6 → 101 에 Sec-WebSocket-Protocol: ocpp1.6 → onOpen(&app) → 101 에 다른 값 → onError(&app, info, PROTOCOL_ERROR, "..."), run 은 PROTOCOL_ERROR → 101 에 그 헤더가 없음 → onOpen(&app). 고른 값은 빈 문자열 (결정 9)

8.4 닫기

라이브러리가 알아서 닫는 경우 (상대의 close frame, 1002 / 1007 / 1009, pong 없음, TCP 끊김) 에 앱은 아무것도 부르지 않고 onClose 만 받는다. 앱이 닫기를 부르는 것은 스스로 끝내기로 정했을 때다.

언제어느 thread예
받은 내용을 보고IO thread (onMessage / onOpen 안)규칙에 안 맞는 메시지 (1003), 토큰이 틀림 (4001), 자리가 없음 (onOpen 에서 1013), 클라이언트가 마지막 응답을 받음
바깥 사건으로다른 thread관리자가 내보냄, 토큰 만료, 다른 기기의 로그아웃, 사용자의 "연결 끊기"
정상 종료다른 thread서버: 소켓마다 1001 을 보내고 onClose 를 기다린 뒤 closeHttpServer. 클라이언트: shutdown(1000) 뒤 run 이 돌아오기를 기다림
클라이언트의 정상 종료 앱 thread : KiottyNet_shutdownWebSocketClient(client, 1000, "bye") → 닫힘 플래그, close frame 을 push lane 에. 바로 돌아온다. 이후 send 는 CLOSED, 받은 데이터는 버린다 IO thread : 서버의 close frame → onClose(&app, { SUCCESS, 1000, 서버의 reason }) → run 이 PEER_CLOSED 로 돌아온다 서버가 답하지 않으면 → 걸린 read 가 끝날 때 (최대 ping_interval) onClose(&app, { TIMEOUT, 1000 }) 앱 thread : io.join(). 다시 붙으려면 run 을 다시 급히 멈추기 앱 thread : KiottyNet_closeWebSocketClient(client) → 열려 있으면 onClose(&app, { CLOSED, 1001 }), 연결 중이면 재시도를 멈춘다. run 은 CLOSED

9. 안에서 바뀌는 것

  • HttpRegistry 의 WebSocket 항목. 지금 WebSocketTarget { handler, app_context, path } 를 { on_upgrade, on_open, on_message, on_close, path } 로. addRoute(path) 가 index 를 돌려주고 on* 가 그 index 의 칸을 채운다. 표는 지금처럼 run 전에만 바뀐다.
  • HttpSite 가 run 의 app_context 하나를 든다. HTTP 라우트와 WebSocket 콜백이 모두 그것을 받는다.
  • WebSocketClient 는 콜백 넷을 칸에 두고 (등록은 run 전, run 중 BUSY) run 이 내부의 target 에 옮긴다. 클라이언트 콜백 모양이 서버와 달라서 frame 행이 부르는 자리 (deliver, openSocket, endSocket) 는 역할 값으로 갈라 부른다.
  • Upgrade 요청 은 run 마다 path 와 후보를 넣어 만든다. 101 검사 (isUpgradeResponse) 가 후보 목록을 받는다 (없으면 통과, 후보 밖이면 실패).
  • shutdownWebSocketClient 는 소켓 handle 을 찾아 지금의 closeSocket 을 부른다. 새 길은 없다.
  • onError 는 열리기 전 실패 (upgrade.failure, base 의 오류 action) 에서 한 번 부른다.
  • frame 행, Session, push lane / write lane, 타이머, handle 은 바뀌지 않는다.

1. action 함수의 이름 (1) 동의 선택

지적이 맞다. KiottyNet_readConnection(1024, 5000) 은 "지금 1024 바이트를 읽는다" 로 읽힌다. 실제로는 "return 한 뒤 IO Thread 가 1024 바이트가 찰 때까지 받아서 다음 onRead 를 부른다" 는 값 이다. 함수가 하는 일은 struct 하나를 채우는 것뿐이다. 이름에 "다음에 일어날 일" 이 들어가야 한다.

2. handle 은 하나, Work 는 상태 (2) 부분 동의

"Work 와 Connection 의 handle 을 따로 두지 않는다" 에 동의한다. 구현 가이드 1.5 에도 "WorkHandle 은 그 연결의 handle 과 같은 값이다. 타입만 다르다" 라고 적혀 있다. 같은 값에 타입을 둘 두는 것은 결국 "이 함수는 Work 중에만 부를 수 있다" 를 타입으로 말하려던 것이다. 그런데 그 보장은 컴파일 때 못 지킨다. Work 가 finish 된 뒤의 handle 로 부르는 것을 타입이 막지 못하기 때문에, 어차피 runtime 검사 (KIOTTY_BUSY / PEER_CLOSED) 가 필요하다. runtime 검사가 있다면 타입 둘은 중복이다.

2.1 그러나 콜백에서 handle 을 전부 없앨 수는 없다

제안은 "onReady / onRead / onWritten / onTimeout 은 동기 read / write 를 못 하니 handle 인자가 필요 없다" 인데, handle 로 할 수 있는 일이 동기 IO 만이 아니다. v2 14절: "콜백 안에서 handle 로 할 수 있는 것은 getConnectionInfo 와 notifyConnection 둘". 더 중요한 것은 콜백 밖 이다. 채팅 서버처럼 "HOLD 로 쉬고 있는 연결 X 에 다른 thread 가 push" 하려면 앱이 X 의 handle 을 어딘가에 들고 있어야 하고, 그 handle 을 받을 자리는 콜백뿐이다. Work 를 시작해야만 handle 을 얻는다면 push 하려고 매번 Work 를 열어야 한다. 그건 배보다 배꼽이다.

그래서 모양은 이렇게 된다. handle 은 하나의 타입, 모든 콜백에 그대로 있고, 함수마다 "어느 상태에서 부를 수 있나" 가 정해진다.

typedef int64_t KiottyNetConnectionHandle;                 /* KiottyNetWorkHandle 은 없다 */

typedef struct KiottyNetConnectionHandler
{
    KiottyNetConnectionDecision (*onConnected)   (KiottyNetAppContext app, KiottyNetConnectionInfo info);
    KiottyNetConnectionAction   (*onReady)       (KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection);
    KiottyNetConnectionAction   (*onRead)        (KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection, KiottyNetSpan data);
    KiottyNetConnectionAction   (*onWritten)     (KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection, size_t length);
    KiottyNetConnectionAction   (*onTimeout)     (KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection);
    void                        (*onWorkStarted) (KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection);   /* 이 순간부터 finishWork 까지 연결은 worker 의 것 */
    void                        (*onDisconnected)(KiottyNetAppContext app, KiottyNetConnectionContext ctx, KiottyNetConnectionHandle connection, KiottyNetCode reason);
    void                        (*onError)       (KiottyNetAppContext app, KiottyNetConnectionInfo info, KiottyNetCode code, const char* message);   /* 3절 */
} KiottyNetConnectionHandler;

C++ 의 KiottyNet_Work (finish 의무를 소유하는 move-only 래퍼) 는 그대로 둔다. 감싸는 값이 KiottyNetConnectionHandle 로 바뀔 뿐이다. 소멸자가 finish 하지 않은 Work 를 닫는 규칙 (requirement 108줄) 도 그대로다.

2.2 handle 을 onReady 에만 줄 수도 있다

"콜백 인자를 줄이자" 는 뜻을 살리려면 handle 을 onReady (처음), onWorkStarted, onDisconnected 에만 주고 onRead / onWritten / onTimeout 에서는 빼는 길도 있다. 앱은 onReady 에서 handle 을 connection_context 에 넣어 두면 된다. 다만 "어떤 콜백은 handle 이 있고 어떤 것은 없다" 는 규칙을 외워야 하고, 콜백 안에서 notifyConnection 을 부를 때 매번 context 에서 꺼내야 한다. 저는 모든 콜백에 그대로 두는 쪽을 권한다 (choices 2).

3. onError 는 ConnectionInfo 만 (3) 동의

동의한다. onError 는 "어디서 무엇이" 를 알리는 것이고, 연결에서 난 오류는 바로 뒤에 onDisconnected(app, ctx, connection, reason) 이 handle 과 context 를 함께 준다 (v2 8절 표). onError 에서 handle 로 할 일이 없다.

4. Work 안의 동기 IO 와 파일 전송 (4) 부분 동의 우려

4.1 전제 검증 : "Work 중에는 다른 작업이 없다" 가 v2 에서 성립하나

제안의 전제는 "action 은 transaction 이라 동시에 둘일 수 없다. Work 가 시작해서 finishWork 로 반납할 때까지 다른 작업은 수행되지 않는다" 다. action 에 대해서는 맞다. 그러나 v2 에는 action 이 아닌 길이 하나 있다. notify 다.

v2 9.6 / 10절: Work 중에도 IO Thread 는 broadcast() 에서 onNotified() 를 부르고 WRITE(NOTIFY) 를 socket 에 건다. requirement 435줄도 "push lane 은 Work 상태와 무관하게 Work 중인 연결에도 들어간다" 라고 적고 있다. 그리고 v2 는 Work 중 peer 끊김을 그 notify 송신의 실패로만 알아챈다 (onPeerGone 의 주석 "notify 완료로만 올 수 있다").

worker 가 같은 socket 에 동기 send 를 하면 IO Thread 의 notify 송신과 두 개의 송신이 한 socket 에 동시에 걸린다. 3b 에서 찾은 "메시지 경계가 섞이는" 문제가 그대로다. TLS 면 더 나쁘다. worker 가 encode 하는 동안 IO Thread 도 notify 를 encode 하므로 SSL* 을 두 thread 가 만진다. OpenSSL 의 SSL 객체는 read 와 write 조차 다른 thread 에서 동시에 할 수 없다.

lock 으로 풀 수 있나? 평문이라면 "write lane 소유 token" (FREE / IO_THREAD / WORKER 의 atomic) 으로 번갈아 쓸 수 있다. 그러나 TLS 에서는 worker 의 동기 read (decode) 와 IO Thread 의 notify write (encode) 가 같은 SSL* 이라 token 하나로는 안 되고, IO Thread 가 notify 를 보내려면 worker 의 read 까지 멈춰야 한다. 그러면 Work 의 동기 read 에 IO Thread 가 끼어드는 셈이고 "Work 중 다른 작업 없음" 이 깨진다.

결론: 제안을 받아들이려면 전제를 구조로 참이 되게 만들어야 한다. 즉 WORKING 인 동안 IO Thread 는 그 연결의 socket 과 SSL 을 전혀 건드리지 않는다. notify 는 Stage 에 쌓이기만 하고 finishWork 뒤 첫 바퀴에 나간다. 이것은 requirement 435줄과 v2 9.6 / 10절의 변경이다. 받아들이시면 v3 에 그렇게 적는다. worker 가 Work 중에 push 할 것이 있으면 writeConnection 으로 직접 보내면 되므로 잃는 것은 "다른 thread 의 broadcast 가 Work 중인 연결에 즉시 도착" 하나다.

4.2 두 번째 전제 : socket 이 worker 손에 있는 동안 닫히면 안 된다

v2 9.5: "Owner 의 close 는 WORKING 인 연결도 바로 닫고 generation 을 올린다." worker 가 그 socket 으로 동기 recv 중이면 use-after-close 다. POSIX 는 fd 번호가 바로 재사용되므로 다른 파일에 쓰는 사고 가 된다. 의료기기 소프트웨어 수준에서는 허용할 수 없다.

바꿀 규칙: WORKING 인 연결에 대한 close (Owner close, IoLoop shutdown) 는 shutdown(SD_BOTH) 만 한다. shutdown 은 다른 thread 가 쓰고 있어도 안전하고, worker 가 기다리는 poll 을 바로 깨워 read 는 0 (CLOSED), write 는 오류를 돌려준다. worker 는 그것을 보고 finishWork 한다. 실제 closesocket 은 WORK_DONE 뒤 settle 에서만 한다. IoLoop::shutdown 의 "host 가 빌 때까지 runOnce" 가 이것을 자연스럽게 기다린다. worker 가 IO 없이 계산만 오래 하면 그만큼 shutdown 이 늦어지는데, 그것은 Work 의 본질이고 isConnected 로 확인하라는 지금 규칙과 같다.

4.3 Work 의 생애 (v3)

RUNNING ──START_WORK──▶ DRAINING ──(write event 가 비면, 다음 바퀴)──▶ WORKING ──finishWork──▶ DONE ──(WORK_DONE, IO Thread)──▶ RUNNING read / write event 모두 pending 아님 IO Thread 는 socket / SSL 을 만지지 않는다 notify Stage 를 먼저 비우고 deadline 0 notify 는 Stage 에 쌓이기만 outcome 적용 close 요청은 shutdown 만
  • DRAINING: START_WORK 가 return 되는 자리 (onRead / onWritten / onReady) 에는 read event 가 걸려 있지 않다 (completion 을 소비한 뒤다). onTimeout 에서의 START_WORK 는 v2 11절대로 BUSY 다. 그러나 write event 는 notify 로 걸려 있을 수 있다. 그래서 구현 가이드 1.5 의 DRAINING 을 되살린다. write event 의 완료가 돌아오면 다음 바퀴 collect 가 WORKING 으로 올리고 onWorkStarted 를 낸다. 이 때 socket 에 걸린 overlapped 요청은 0 개다. IOCP 에서 동기 recv 와 overlapped WSARecv 를 섞지 않기 위한 조건이기도 하다.
  • WORKING: collect 는 이 연결의 deadline 을 보지 않고, broadcast 는 onNotified 를 건너뛰고, 어떤 submit 도 하지 않는다. 연결 객체에서 worker 가 만지는 것은 socket, TlsEngine, _plain.receive (이미 받아 둔 바이트가 있으면 먼저 소비), send Stage 다. IO Thread 가 만지는 것은 notify Stage (lock 안) 와 _phase (shutdown 요청) 뿐이다.
  • peer 끊김: worker 의 동기 read 가 0 을 받거나 write 가 RESET 을 받으면 그 결과로 안다. IO 없이 오래 계산하는 worker 를 위한 KiottyNet_isConnected(h) 는 non-blocking recv(MSG_PEEK) 한 번으로 구현한다 (0 이면 끊김, WOULD_BLOCK 이면 살아 있음). WORKING 이 아닐 때는 alive() 를 돌려준다. 그래서 v2 의 _peer_closed 와 onPeerGone 의 Work 분기가 없어진다.
  • DONE → RUNNING: onWorkFinished 는 먼저 notify Stage 에 쌓인 것을 write lane 으로 내보내고 (7절의 pick), 그 다음 outcome 을 적용한다. outcome 이 WRITE 면 worker 가 이미 평문을 send Stage 에 넣어 두었다 (v2 와 같다).

4.4 동기 함수의 구현 : StreamClient 가 이미 가지고 있다

v2 12절의 StreamClient 는 non-blocking socket + poll 반복 (sendAll / receiveSome) + TlsEngine 으로 동기 read / write 를 한다. Work 의 동기 함수는 같은 코드 다. 대상이 StreamClient 의 socket 이 아니라 Connection 의 socket 일 뿐이다. 그래서 둘을 하나의 클래스로 뽑는다.

class SyncChannel                               // base/connection/kiotty_sync_channel.h. StreamClient 와 Connection(WORKING) 이 같이 쓴다
{
public:
    SyncChannel(ActiveSocket& socket, TlsEngine& tls, Stage& receive, Stage& send);
    KiottyNetResult read(void* buffer, size_t length, uint32_t timeout_ms);      // receive Stage 에 남은 것 먼저. 비면 poll + recv (+ decode) 반복
    KiottyNetResult write(KiottyNetSpan data, uint32_t timeout_ms);              // 평문 sendAll. TLS 는 send_capacity 씩 encode → sendAll
    KiottyNetCode   writeFile(const char* path, uint64_t offset, uint64_t length, uint32_t timeout_ms);   // 4.5
    bool            connected() const;                                           // recv(MSG_PEEK)
};
  • Connection 은 WORKING 일 때만 SyncChannel 을 만들어 (멤버로 값 하나) 쓴다. 생성에 할당은 없다. 네 참조만 든다.
  • timeout_ms 는 필수다. 제안의 서명에는 없었지만, 끊긴 peer 에게 쓰는 worker 가 영원히 멈추면 worker pool 이 하나씩 죽는다. StreamClient 와 같은 모양 (timeout_ms, 0 은 한도 없음) 으로 둔다.
  • Windows: 소켓이 IOCP 에 붙어 있어도 lpOverlapped == NULL 인 send / recv 는 동기로 동작하고 completion packet 을 만들지 않는다 (Winsock 이 내부 event 의 하위 비트로 port 전달을 막는다). 단, 그 socket 에 overlapped 요청이 걸려 있지 않아야 한다. 4.3 의 DRAINING 이 이것을 보장한다.
  • KiottyNetResult.bytes 는 int32_t 다. read / write 한 번의 길이로는 충분하다 (send_capacity 단위). 파일은 2 GiB 를 넘을 수 있으므로 writeFile 은 code 만 돌려주고, 길이는 호출자가 이미 안다 (HTTP 의 Content-Length).

5. IoEvent 는 둘이다 : read 와 write (5) 우려

인용하신 코드 (한 socket 에 WSARecv 하나와 WSASend 둘을 각자의 OVERLAPPED 로 동시에) 는 동작한다. 3b 의 TwoSendsSubmittedInOrderArriveAtPeerInThatOrder 가 그것을 확인했다. 그러나 "동작한다" 와 "써도 된다" 는 다르다. 3b 피드백 질문 2 가 찾은 것이 바로 그 차이다.

USER 메시지 [AAAAAAAA] 를 send 1 로, NOTIFY [NN] 을 send 2 로 동시에 걸었을 때 IOCP (대개) peer 가 받는 것 : AAAAAAAA NN ← 잘 드러나지 않는다 epoll (흔히) send 1 이 AAAA 만 나가고 EAGAIN 그 사이 send 2 가 NN 을 보냄 peer 가 받는 것 : AAAA NN AAAA ← TLS 레코드 / WebSocket frame 이 깨진다

그래서 3b 의 결론은 "같은 socket 에 동시에 걸리는 write 는 항상 1 개" 였고, 그 결론이 event 를 _read_event + _write_event 로 나누게 했다. NOTIFY 전용 event 를 셋째로 두면 write 가 다시 둘이 되어 같은 버그가 돌아온다.

5.1 "READ 와 WRITE 는 절대 동시에 안 벌어진다" 는 v2 의 stream event 이야기다

헷갈림의 뿌리가 여기다. v2 의 _stream_event 는 "사용자 read 또는 write 중 하나" 를 걸었고, 그래서 "read 와 write 는 동시에 없다" 가 참처럼 보였다. 그러나 v2 에서도 이미 동시에 걸리는 조합이 있었다.

동시에 걸리는 조합v2v3허용?
read (USER) + write (NOTIFY)_stream_event + _notify_event_read_event + _write_event된다. 방향이 다르다
HOLD (아무것도 없음) + write (NOTIFY)_notify_event 만_write_event 만된다
write (USER) + write (NOTIFY)_stream_event + _notify_event. 섞인다write lane 하나에 번갈아. 동시에 없다안 된다. 메시지 경계

즉 겹쳐도 되는 것은 방향이 다른 둘 뿐이고, 그래서 event 의 수는 방향의 수와 같다. 둘이다. "READ / WRITE 는 동시에 벌어지지 않고 NOTIFY 는 따로" 가 아니라 "READ 와 WRITE 는 동시에 벌어질 수 있고, 모든 송신 (USER / HANDSHAKE / CONTROL / NOTIFY) 은 WRITE 하나를 나눠 쓴다" 가 정확한 문장이다.

5.2 3b 피드백 문서가 헷갈리게 한 자리

그 문서는 "event 를 둘 두는 생각 자체는 맞지만 나누는 기준을 용도 (stream / notify) 에서 방향 (read / write) 으로" 라고 적고, 바로 아래 "이어진 질문" 에서 "notify Stage 와 Tx Stage 는 따로 둬도 되나 → 된다" 라고 답했다. Stage 가 둘 인 것과 event 가 둘 인 것이 같은 단락에 있어 "notify 도 자기 event 를 갖는다" 로 읽힌 것 같다. 정리하면:

  • 평문 Stage: 셋 (receive, send, notify). 쓰는 thread 와 lock 규칙이 달라서 따로 둔다.
  • 암호문 Stage: 둘 (cipher receive, cipher tx). 송신 암호문은 하나다. 암호화 순서 = 송신 순서를 구조로 지키기 위해서다.
  • IoEvent: 둘 (read, write). 방향의 수다.
  • IoPurpose: 넷 (USER, HANDSHAKE, CONTROL, NOTIFY). 완료가 돌아왔을 때 어느 Stage 를 consume 할지 말해 주는 꼬리표다. event 의 수와 무관하다.

v3 에서는 3b 피드백의 질문 2 를 이 네 줄로 바꿔 적고 혼동을 없앤다.

7. notify 는 별도 submit 이 아니라 write lane 의 용도 (7) 부분 동의

"notify 의 흐름 (쌓기 → 깨우기 → 보내기 → 비우기) 을 한 덩어리로 보이게 하자" 는 데 동의한다. v2 는 그것이 notify (9.6), onNotified (9.6), broadcast (10절), onSent 의 NOTIFY case (9.4), consumeNotification (9.4) 다섯 자리에 흩어져 있다.

그러나 listener 에 submit(event, IoNotification) 을 따로 두는 것은 5번과 같은 이유로 반대한다.

  • 그 submit 이 _write_event 를 쓰면 USER write 와 겹치지 않도록 "지금 write lane 이 비었나" 를 누군가 봐야 한다. 그 판단은 Connection 의 것이고, 결국 지금의 onNotified 와 같은 일이다. 이름만 바뀐다.
  • 그 submit 이 자기 event 를 쓰면 write 가 둘이 되어 섞인다 (5절).
  • listener 는 바이트와 방향만 알아야 한다 (v2 원칙 3, 의존은 아래로만). IoNotification 과 IoKind::NOTIFIED 를 알면 listener 가 Connection 의 Stage 종류를 아는 셈이다. epoll / kqueue / io_uring backend 넷에 그 분기가 복제된다.

7.1 대신 : Connection 안의 WriteLane

흩어진 다섯 자리를 Connection 안의 클래스 하나로 모은다. listener 는 그대로다. 3b 피드백 "이어진 질문" 의 "write lane 이 다음에 보낼 평문 Stage 를 고르는 순간에 암호화" 를 그대로 코드 모양으로 옮긴 것이다.

class WriteLane                                 // base/connection/kiotty_write_lane.h. socket 하나의 송신 전부
{
public:
    WriteLane(Stage& send, Stage& notify, TlsEngine& tls, NotificationContext& notification);

    IoAction  pick();                           // 걸린 것이 없을 때. notify 에 바이트가 있으면 WRITE(NOTIFY), 아니면 send 에 있으면 WRITE(send 의 purpose), 아니면 NONE
                                                // TLS 면 고른 평문을 이 자리에서 encode → cipher tx. 암호화 순서 = 송신 순서
    IoPayload resolve(const IoAction& action);  // cipher tx 또는 고른 평문 Stage 의 readable 전체
    void      onSent(const IoCompletion& completion);   // purpose 로 어느 평문 Stage 를 consume 할지. NOTIFY 는 lock 안에서. compact
    bool      hasUserWrite() const;             // onWritten 을 낼 차례인가 (send Stage 의 USER 메시지가 다 나갔다)

    KiottyNetCode stage(IoPurpose purpose, KiottyNetSpan plain);   // USER / HANDSHAKE / CONTROL 의 평문을 send 에. 넘치면 BUFFER_FULL
    KiottyNetCode notify(KiottyNetSpan plain);                     // 아무 thread. lock. 넘치면 BUFFER_FULL
};
IO Thread 한 바퀴 (v3) collect ──▶ broadcast ──▶ step ──▶ settle │ │ │ └─ dispatch: onReceived / onSent / onTimeout / onWorkFinished │ onSent ─▶ lane.onSent(completion) ─▶ USER 가 끝났으면 handler.onWritten ─▶ adopt │ ─▶ 아니면 lane.pick() (다음 메시지) └─ 연결마다: write event 가 비어 있고 WORKING 이 아니면 lane.pick() → submit ← v2 의 onNotified 자리
  • IoKind::NOTIFIED 는 필요 없다. SEND 완료의 action.purpose == NOTIFY 가 그 역할이다. IoKind 는 그대로 여섯이다.
  • pick 의 우선순위는 "notify 먼저" 로 한다 (v2 의 "broadcast 우선"). USER WRITE 의 timeout 은 notify 뒤에서 기다리는 시간을 포함한다. notify 는 push_capacity 로 묶여 있으므로 그 시간은 한 Stage 분량으로 유계다. 번갈아 보내는 것은 공정하지만 상태 (마지막에 누구를 보냈나) 가 하나 더 생겨서 택하지 않는다.
  • v2 9.2 의 _resume_read, _write_length, _notify_plain_length 는 WriteLane 안으로 들어간다. Connection 의 표가 그만큼 짧아진다.
  • WORKING 중에는 pick 을 부르지 않는다 (4.3). notify 는 lane.notify 로 쌓이기만 한다. WORK_DONE 의 첫 일이 pick 이다.
  • 제안의 "notifying stage 꽉 차면 BUFFER_FULL" 은 지금과 같다. "broadcast 는 하나라도 모자라면 아무 데도 안 쓴다" 도 그대로다.

9. 골라 주실 것 선택

  1. action 함수 접두어: trigger* / then* / next*. 제안은 trigger, 제 추천은 then (1절).
  2. 콜백의 handle 인자: (a) 모든 콜백에 그대로 (추천) / (b) onReady, onWorkStarted, onDisconnected 에만 (2.2).
  3. Work 중 notify: "쌓기만 하고 finishWork 뒤에 나간다" 를 받아들이는가. 받아들이지 않으면 4번 전체가 성립하지 않으므로 사실상 4번의 가부다. requirement 435줄이 바뀐다 (4.1).
  4. Windows 의 writeFile 평문 경로: TransmitFile 동기 호출 / ReadFile + send 반복. worker 가 셋 이상이면 후자를 추천 (4.5).
  5. max_clients 기본 128, 상한 1024, TLS Pool 8 MiB 인자: 이 수치로 확정하는가 (6절).

이 다섯이 정해지면 design_base_v3.md 를 v2 와 같은 형식 (인터페이스 + 한 바퀴의 순서) 으로 쓴다. 8절의 표가 그 목차다.

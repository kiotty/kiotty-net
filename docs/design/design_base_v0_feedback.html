1. Socket, ListenSocket → ActiveSocket, PassiveSocket 동의

reference 와 같은 이름이고 "연결된 쪽 / 기다리는 쪽" 이 이름에 드러난다. 그대로 바꾼다. SocketHandle, INVALID_SOCKET_HANDLE 도 reference 와 같다.

2. TlsSession 의 이름 선택

이 클래스가 하는 일은 "평문 바이트를 넣으면 암호문 바이트가 나오고, 암호문을 넣으면 평문이 나온다" 다. socket 도 연결도 모른다. 상태 (handshake 진행, 세션 키) 는 있지만 사용자에게 보이는 것은 변환뿐이다. 후보:

이름어감짝이 되는 메서드
TlsCodecencode = encrypt, decode = decrypt. reference 의 PacketCodec 과 같은 어휘라 "바이트를 다른 모양으로 바꾸는 계층" 이 바로 읽힌다encode(plain, cipher_out), decode(cipher_in, plain_out), handshake()
TlsFilterNetty / ACE 의 filter. "바이트가 통과하면서 바뀐다"filterOut, filterIn
TlsTranslator말 그대로 번역 계층. 길다translateOut, translateIn
TlsPipe양쪽 BIO 를 잇는 관. Pipe 가 transport 이름 (KIOTTY_PIPE) 과 겹친다
TlsLayerrequirement 가 쓰는 말 ("선택 계층"). 다만 Layer 는 클래스 이름으로는 하는 일이 안 보인다

추천: TlsCodec. 같은 이유로 TlsContext 도 KiottyNetContext 와 Context 가 겹치므로 TlsProfile 로 바꾸는 것을 제안한다. SSL_CTX 가 담는 것이 "인증서 + 허용 버전 + cipher + 검증 방식" 이라 profile 이 맞다. TlsCodec::open(TlsProfile&, Pool&, hostname).

3. ReadRequest, FinishRequest 의 이름 선택

ReadRequest 는 "수신 Stage 가 이 조건이 되면 onRead 한 번" 이라는 등록된 조건 이다 (구현 가이드 1.3 도 "조건 등록" 이라고 부른다). 요청보다 조건에 가깝다.

이름어감
ReadCondition"exact 바이트가 모이면 / delimiter 가 나오면". 구현 가이드의 말과 같다. _read_condition.kind == NONE 이 "조건 없음" 으로 읽힌다
ReadTrigger조건이 차면 onRead 가 발사된다는 뜻. 짧다
ReadWatchStage 를 지켜본다. 조금 약하다
ReadCriteria복수형이라 어색하다

FinishRequest 는 worker 가 Work 를 끝내면서 IO Thread 에 남기는 "다음에 할 IO 하나" 다. 읽어라 / 써라 / 닫아라 중 하나이고, IO Thread 가 DONE → RUNNING 에서 그것을 적용한다.

이름어감
WorkOutcomeWork 가 끝난 결과물. finishWork(generation, WorkOutcome) 이 "이 결과로 Work 를 끝낸다" 로 읽힌다. Work 와 짝이 되는 유일한 후보
NextIo하는 일 그대로. 짧지만 Work 와의 관계가 이름에 없다
Resumption연결을 다시 IO Thread 로 돌리는 방법. 지워진 resume 이 떠오른다
WorkVerdict어감은 맞는데 흔치 않은 단어다

추천: ReadCondition 과 WorkOutcome. 같은 기준으로 IoEvent 는 그대로 두고 (event 는 "완료 통지" 의 OS 어휘), IoCompletion 도 그대로 둔다.

4. ConnectionHost 에서 IoLoop 빼기 동의

ConnectionHost 를 Connection 의 저장소 로만 줄인다. 남는 것은 셋이다.

class ConnectionHost
{
public:
    ConnectionHost(size_t capacity, size_t recv_capacity, size_t send_capacity, size_t push_capacity, TlsProfile* tls, Pool* tls_pool);

    bool        valid() const;
    size_t      capacity() const;
    Connection* at(size_t index);                              // loop 가 훑는다 (deadline, DONE, written)
    Connection* acquire();                                     // 빈 slot. 없으면 nullptr
    void        release(Connection& connection);              // generation 을 올리고 slot 을 비운다
    Connection* find(PoolHandle handle);                       // generation 이 맞는 살아 있는 연결

    KiottyNetCode deliver(PoolHandle target, KiottyNetSpan data);   // IO Thread. index 0 이면 모든 연결의 push lane 에
};

지워지는 것: EventListener, IoLoop, DoneRing, PushSlot, handler / app_context, run 상태, process* 다섯 개, wake, enqueueDone, 가상 함수 셋. deliver 가 "값을 밀어넣는 용도" 고, 다른 thread 에서 오는 notify 의 대기 (PushSlot) 는 IO Thread 를 깨워야 하므로 5번의 IoLoop 로 간다.

5. IoLoop 가 EventListener 와 ConnectionHost 를 가짐 동의

IoLoop 가 "돌아가는 것" 전부의 주인이 된다. 다른 thread 에서 IO Thread 로 들어오는 세 길 (startWork, finishWork, notify / broadcast) 이 모두 깨우기가 필요하므로 전부 IoLoop 의 메서드다.

class IoLoop
{
public:
    IoLoop(ConnectionHost& host, Acceptor* acceptor);          // acceptor 는 11번. EventClient 는 nullptr

    bool valid() const;

    KiottyNetCode run(const KiottyNetConnectionHandler& handler, KiottyNetAppContext app_context);   // stop 까지 blocking
    void          stop();                                      // 아무 thread
    bool          isIoThread() const;

    void open(Connection& connection, ActiveSocket&& socket);  // IO Thread (accept 완료) 또는 run 직전 (EventClient 의 동기 connect 뒤)

    KiottyNetCode startWork (PoolHandle handle);               // 아무 thread. CAS 뒤 wake
    KiottyNetCode finishWork(PoolHandle handle, const WorkOutcome& outcome);
    KiottyNetCode post(PoolHandle target, KiottyNetSpan data); // 아무 thread. IO Thread 면 host.deliver 바로, 아니면 slot 에 넣고 wake 뒤 대기

private:
    void runOnce();                                            // a ~ e

    ConnectionHost&                   _host;
    Acceptor*                         _acceptor;
    EventListener                     _listener;
    Holder<IoEvent>*                  _events;                 // 연결당 receive / send 둘. host.capacity() × 2
    PushSlot                          _slots[4];
    const KiottyNetConnectionHandler* _handler;
    KiottyNetAppContext               _app_context;
    std::atomic<bool>                 _stopped;
    std::thread::id                   _io_thread;
};

Connection 은 EventListener 도 IoEvent 도 모르게 된다 (6번의 순서). 그래서 Connection 은 "받을 자리를 내주고, 보낼 구간을 내주고, 완료를 받아 상태를 바꾸는" 수동 객체가 되고, OS 에 거는 쪽은 IoLoop 다.

// Connection 이 IoLoop 에게 내주는 것 (IO Thread)
void*   receiveSpace(size_t& length);  →  Stage::Provider& receiveProvider();      // 받을 자리 (output 인자 없이 Provider 를 준다)
Segment sendSegment();                                                            // 보낼 구간. 구현 가이드의 pickSegment
void    onReceived(SocketCode code, size_t length, const KiottyNetConnectionHandler& handler);   // commit + pump
void    onSent(SocketCode code, size_t length);                                   // 구현 가이드의 advance
bool    hasSendPending() const;  bool hasReceivePending() const;  void markReceivePending(bool);  void markSendPending(bool);

handler 는 Connection 이 들지 않고 IoLoop 가 매 호출에 넘긴다. run 마다 바뀔 수 있는 값을 32 개 연결이 복사해 두지 않기 위해서다.

6. 의존은 무조건 일방향 부분 동의

방향은 그대로 가져간다. 두 군데만 다르게 그린다.

  • TLS 는 socket 을 모른다. TlsCodec 은 Stage 와 Stage 사이의 바이트 변환이라 socket 아래가 아니라 옆이다. Connection 이 둘 다 쓴다. "connection ← tls ← socket" 으로 그리면 TlsCodec 이 socket 헤더를 포함해야 하는데 그럴 일이 없다.
  • EventListener 는 socket 을 안다. SocketHandle 타입과 PassiveSocket::accept 를 쓴다 (AcceptEx 의 뒤처리, epoll 의 accept). 그래서 event_listener → socket 선이 하나 있다. 순환은 아니다.
context
  └── server ─────────── ioloop ── connection_host ── connection ─┬── tls (codec, profile)
      event_client ─────┘   │                                     └── socket (active, passive)
      stream_client ────────┼───────────────────────────────────────┘
                            ├── acceptor ── socket (passive)
                            └── event_listener ── event
                                      └──────────── socket (handle 타입, accept)
core : stage, pool_handle, holder, result, clock, pool      (모두가 쓴다. 아무도 모르지 않는다)
error: socket_code                                          (socket 이상 모두가 쓴다)

StreamClient 는 loop 가 없어서 connection 을 거치지 않고 socket + tls 를 바로 쓴다. 이것도 위에서 아래로만 간다.

7. 동기 connect 동의

맞다. 비동기 connect 가 필요한 쪽은 "연결을 수십 개 동시에 거는 클라이언트" 인데 kiotty 의 클라이언트는 연결이 하나다. run 이 어차피 blocking 이므로 그 thread 가 connect 에서 기다려도 된다. 바뀌는 것:

  • ActiveSocket::connect(const KiottyNetEndpoint&, uint32_t timeout_ms) 하나. 안에서는 non-blocking + poll (15-5 번) 로 timeout 을 재지만 밖에서는 동기다. finishConnect, EventListener::submitConnect, IoKind::CONNECT, EventClient 의 _connect_event 와 _trial 이 지워진다.
  • 재시도 (max_trial, trial_interval_ms) 는 EventClient::run 의 for 문이다. StreamClient 의 connect 도 같은 for 문이라 둘이 같은 자유 함수 connectWithRetry(config) 를 쓰면 된다.
  • 하나 알아 둘 것: connect 중에 close() 가 오면 지금 시도의 timeout (기본 5 초) 까지는 기다린다. 시도 사이 interval 은 stop 플래그를 보고 바로 끊는다. 이 정도면 충분하다고 본다.

8. submit 이 무엇인가 선택

연결과는 무관하다. "OS 에 비동기 IO 요청 하나를 걸어 두는 것" 이다.

  • submitReceive(event, handle, buffer, length) : "이 소켓에서 받는 대로 이 버퍼에 써 두고, 끝나면 완료로 알려 달라". IOCP 는 WSARecv + OVERLAPPED, io_uring 은 SQE 를 제출 (submit) 하는 것, epoll 은 "readable 이 오면 listener 가 대신 recv 해서 버퍼에 쓴다" 는 약속 (15-3 번의 proactor 흉내).
  • submitSend : "이 구간을 보내고 끝나면 알려 달라".
  • submitAccept : "다음 연결이 오면 받아 두고 알려 달라" (AcceptEx / listen fd readable).

그러니까 "이거 받으라고 연결하는 것" 은 attach (소켓을 IOCP / epoll 에 등록) 이고, submit 은 등록된 소켓에 요청 하나를 거는 것이다. 이름 후보:

동사출처예
submitio_uring (submission queue), 구현 가이드 1.3 의 "recv 를 다시 건다"submitReceive, 완료는 IoCompletion
begin.NET BeginReceive / EndReceive. "시작 → 완료" 짝이 분명하다beginReceive, beginSend, beginAccept
postIOCP 문서 (post an overlapped operation). notify 의 post 와 겹친다
armepoll 의 one-shot 재등록 (re-arm). reactor 어감이 강하다

추천: submit 유지. "걸어 둔다" 와 가장 가깝고 완료 (completion) 와 짝이 된다. 짝이 더 드러나는 쪽이 좋으면 begin.

9. applyFinish, completeWritten 선택

둘 다 "언제 누가 왜" 가 이름에 없었다.

지금하는 일후보
applyFinish()worker 가 남긴 WorkOutcome 을 IO Thread 가 적용해 DONE → RUNNING. 다음 read 를 걸거나 write lane 을 보내거나 닫는다resumeFromWork()
takeWorkOutcome(), returnFromWork()
completeWritten()loop 끝 (e) 에서, 이번 바퀴에 다 나간 write 가 있으면 onWritten 을 내고 pump 한 번reportWritten()
flushWrittenEvent(), emitWritten()

추천: resumeFromWork, reportWritten. 같은 규칙으로 onDeadline() 은 expireDeadline() 으로, beginDraining() 은 tryEnterWork() 로 바꾸면 "loop 가 Connection 에 시키는 일" 네 개가 모두 동사 + 목적어가 된다.

10. DoneRing 부분 동의

용도. worker 가 아무 thread 에서 finishWork 를 부르면 그 연결은 DONE 이 된다. IO Thread 는 깨어난 뒤 "어느 연결이 DONE 인가" 를 알아야 한다. DoneRing 은 worker 가 연결 index 를 넣고 IO Thread 가 꺼내는 lock-free 큐라서, IO Thread 가 32 개를 훑지 않고 DONE 인 것만 바로 찾게 하려는 것이었다 (구현 가이드 1.5).

그런데 필요 없다. 15-6 번에서 deadline 을 매 바퀴 scan 하기로 했다. 같은 scan 에서 _work_state == DONE 도 보면 된다. 32 개 atomic load 는 ring 의 CAS 보다 싸다. 그래서 DoneRing 을 지운다. finishWork 는 CAS 로 DONE 을 만들고 wake() 만 한다. IoLoop 의 (b) 는 "깨어났으면 host.at(i) 를 훑어 DONE 인 것을 resumeFromWork" 가 된다. output 인자 문제도 같이 사라진다.

혹시 남겨야 할 때의 모양만 적어 두면: int32_t pop() 이 비었을 때 -1 을 돌려주거나 Result<SocketCode, int32_t> 다. 하지만 지우는 쪽을 권한다.

11. EventClient 용 loop 와 Server 용 loop 를 따로 부분 동의

둘이 다른 점을 세어 보면:

Server 의 loopEventClient 의 loop
accept 완료 처리있다없다 (7번으로 connect 는 run 전에 동기로 끝난다)
recv / send 완료, pump, drain, deadline, DONE, written같다같다
push slot (b)broadcast 와 notify 가 같은 delivernotify 뿐. deliver(target) 의 target 이 늘 그 하나
마지막 연결이 닫히면계속 돈다loop 를 끝낸다 (run 이 return)

다른 것은 accept 한 줄과 "마지막 연결이 닫히면 멈춤" 한 줄 이다. loop 를 두 클래스로 나누면 공통 80 % 가 두 벌이 되므로 그쪽은 권하지 않는다. 대신 다른 두 줄을 밖으로 뺀다.

  • accept 는 io_loop/kiotty_acceptor.h 의 작은 클래스 Acceptor { PassiveSocket, Holder<IoEvent> } 로 빼고 IoLoop 는 Acceptor* 를 받는다. nullptr 이면 ACCEPT 완료가 올 일이 없다. Server 만 Acceptor 를 만든다.
  • 멈춤 조건 은 IoLoop 생성 인자 stop_when_empty (bool) 하나다. EventClient 가 true 다.

그러면 "EventClient 용 loop" 는 IoLoop(host, nullptr, true), "Server 용 loop" 는 IoLoop(host, &acceptor, false) 다. 객체는 둘이지만 클래스는 하나다. 그래도 두 클래스가 낫다고 보면 ClientLoop = 공통 본체, ServerLoop = ClientLoop + Acceptor 로 두는 상속이 차선이다.

11. Server 가 ConnectionHost 를 상속하지 않음, await 는 mutex + cv 동의

4, 5 번으로 상속할 ConnectionHost 가 이미 없다. Server 는 네 부품을 값으로 가진 조립 객체가 된다. onOpenCompletion 은 Acceptor 가 accept 완료를 IoLoop 안에서 처리하므로 없어진다.

class Server
{
public:
    Server(const KiottyNetServerConfig& config, const KiottyNetTlsServerConfig* tls, Pool& tls_pool);

    bool valid() const;

    KiottyNetCode run(const KiottyNetConnectionHandler& handler, KiottyNetAppContext app_context);
    void          close();
    KiottyNetCode await(uint64_t timeout_ms);
    KiottyNetCode broadcast(KiottyNetSpan data);              // _loop.post({0, 0}, data)
    IoLoop&       loop();                                      // base.cpp 의 Connection / Work 함수가 쓴다

private:
    KiottyNetServerConfig   _config;
    TlsProfile              _tls;
    ConnectionHost          _host;
    Acceptor                _acceptor;
    IoLoop                  _loop;
    std::mutex              _mutex;
    std::condition_variable _cv;
    KiottyNetCode           _code;                             // OPENING 동안은 KIOTTY_BUSY, 열리면 SUCCESS, run 이 끝나면 그 반환값
};

KiottyNetCode Server::run(handler, app_context)
{
    KiottyNetCode code = _acceptor.open(_config.endpoint, backlog);   // bind + listen. run 을 부른 thread 에서
    { lock; _code = code; } _cv.notify_all();                 // await 중인 thread 를 깨운다
    if (code != KIOTTY_SUCCESS) return code;
    code = _loop.run(handler, app_context);                   // close 까지
    { lock; _code = code; } _cv.notify_all();                 // run 이 끝난 뒤의 await 는 이 값을 본다
    return code;
}

await 는 _cv.wait_for(timeout, [] { return _code != KIOTTY_BUSY; }) 한 줄이고, 7절의 표 (돌고 있으면 SUCCESS, 끝났으면 run 의 값, 시간이 지나면 TIMEOUT) 가 그대로 나온다. "다시 run" 은 run 의 첫 줄에서 _code = KIOTTY_BUSY 로 되돌리면 된다.

13. OpenSSL 이 없을 때 빈 껍데기 우려

빌드가 깨지지 않게 하는 것은 동의한다. 구조는 간단하다. tls/backend/kiotty_openssl_tls.cpp 와 tls/backend/kiotty_stub_tls.cpp 가 같은 TlsProfile / TlsCodec 선언을 구현하고 CMake 옵션 KIOTTY_NET_WITH_OPENSSL 이 하나를 고른다. OpenSSL 헤더는 전자만 포함한다.

우려는 stub 이 무엇을 하느냐 다. "TLS 설정을 넘겼는데 평문으로 나간다" 는 cpp-developer 규칙의 "기본값이 안전해야 한다" 와 정면으로 부딪친다. 의료기기에서 wss:// 라고 믿고 띄운 서버가 사실 평문이면 그것이 가장 나쁜 실패다. 사용자는 로그를 보기 전까지 모른다.

stub 의 동작장점단점
A. 거절. TlsProfile::open 이 KIOTTY_NOT_SUPPORTED 를 돌려주고 create*(…, tls != NULL) 은 NULL평문이 몰래 나가지 않는다. 코드 한 줄로 이유가 드러난다 (KIOTTY_NOT_SUPPORTED 를 KiottyNetCode 에 추가)TLS 없이 빌드한 사용자가 TLS 설정을 넘기면 서버가 안 뜬다. 이것은 장점이기도 하다
B. 평문 통과. encode / decode 가 그대로 복사하고 handshake 는 바로 SUCCESSTLS 유무와 무관하게 같은 코드가 돈다. 테스트가 편하다위의 위험. 제품 빌드에서 OpenSSL 링크가 빠지는 실수가 조용히 통과한다
C. A 가 기본, B 는 KIOTTY_NET_TLS_PASSTHROUGH 를 정의한 테스트 빌드에서만둘 다옵션이 하나 는다

추천: C. 제안하신 "평문 제출" 은 테스트 빌드의 옵션으로 두고, 제품 빌드의 기본은 거절로 두고 싶다. B 로 가자고 하시면 그대로 하되, 그 경우 KiottyNet_createServer 가 TLS 설정을 받았는데 stub 인 것을 최소한 KiottyNetConnectionInfo 같은 값으로 알 수 있는 길을 하나 두자.

14. 소유자 (Server, EventClient, StreamClient) 의 메모리 선택

두 안을 나란히 놓으면:

A. raw pointer + release (지금 base.h)B. Context 가 slot 을 들고 내준다
createnew (nothrow) Server 를 돌려준다Context 의 고정 slot (최대 N 개) 에 placement new. 가득 차면 NULL
destroydelete. 사용자가 잊으면 샌다slot 을 비운다. 사용자가 잊어도 releaseContext 와 프로세스 종료가 부순다
C++ RAIIOwnedHandle 이 destroy 를 부른다 (이미 있음)같다. 안이 바뀔 뿐 base.h 의 모양은 그대로다

추천: B. 이유는 두 가지다. 첫째, 의료기기 쪽의 "잊어도 샌 채로 남지 않는다". 둘째, 15-1 의 소유자 표가 Context 의 slot 으로 흡수되어 전역 표가 작아진다. 세 소유자의 크기 차이는 Holder<Owner> 로 흡수한다 (reference 의 Holder 가 이것이다). Connection[max_clients] 는 소유자 안이 아니라 create 때 따로 잡는 큰 덩어리라 slot 크기에 들어가지 않는다.

class Owner                                                   // Server, EventClient, StreamClient 의 공통 base. 가상 소멸자와 close 만
{
public:
    static const size_t HOLDER_SIZE  = 512;                   // 가장 큰 소유자. static_assert
    static const size_t HOLDER_ALIGN = 16;
    virtual ~Owner();
    virtual void shutdown() = 0;                              // close + run 의 return 대기. Context 소멸자가 부른다
};

class Context
{
public:
    static const size_t MAX_OWNERS = 16;

    Context(size_t tls_pool_bytes);                           // 플랫폼 초기화, TLS pool (15-4), slot
    ~Context();                                               // 남은 소유자 shutdown + 파괴

    template <typename T, typename... Args> T* create(Args&&...);   // 빈 slot 에 Holder<Owner>::make<T>. 없으면 nullptr
    void destroy(Owner* owner);
    Owner* find(uint32_t slot, uint32_t generation);          // handle 의 index 에서 온 값

private:
    Holder<Owner> _owners[MAX_OWNERS];
    uint32_t      _generations[MAX_OWNERS];
    Pool          _tls_pool;
    std::mutex    _mutex;
};

남는 문제 하나: C 의 KiottyNet_readConnection(handle) 은 context 를 받지 않는다. 그래서 handle 에서 Context 까지 가는 전역 길이 하나는 있어야 한다. 가장 작은 모양은 static Context* g_contexts[16] 과 handle index 의 상위 4 비트다. 이것은 15-1 과 함께 다음에 정한다. (Context 를 프로세스에 하나로 제한하면 이 배열도 사라진다. 그 선택지도 그때 같이.)

15-4. TLS pool 에 대한 보충

OpenSSL 이 메모리를 잡는 길은 CRYPTO_set_mem_functions(malloc, realloc, free) 하나이고 프로세스 전역 이다. "TlsProfile 을 초기화할 때 pool 을 받는다" 로는 OpenSSL 의 내부 할당 (handshake 중의 버퍼, 인증서 파싱) 을 그 pool 로 보낼 수 없다. 그래서 두 층으로 나눈다.

  • OpenSSL 내부 할당: 첫 Context 가 CRYPTO_set_mem_functions 로 전역 Pool 을 꽂는다. Pool 은 reference 의 BlockPool (크기 등급별 고정 블록, 가득 차면 heap fallback 과 카운터) 을 core/kiotty_pool.h 로 옮긴다. fallback 카운터가 0 인지가 "런타임 할당 없음" 의 검증 수단이 된다.
  • 우리가 잡는 것 (SSL 객체 자체, _cipher_recv / _cipher_send Stage): Connection 생성자에서 TlsCodec::open(profile, pool) 까지 해 두고 연결이 닫히면 SSL_clear 로 재사용한다. 이것이 TlsCodec::open 이 pool 을 받는 이유다. 둘 다 같은 Pool 이다.

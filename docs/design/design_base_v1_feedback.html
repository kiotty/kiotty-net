1. TLS 의 자리와 handshake 부분 동의

질문이 둘이다. "handshake 를 어떻게 구현하는가" 와 "socket 뒤에 TLS 가 가는 것이 맞지 않은가". 답은 데이터 흐름에서는 socket 뒤가 맞고, 코드 의존에서는 옆이 맞다 이고, 그 이유가 곧 handshake 의 구현 방식이다.

1.1 왜 TlsSocket 방식을 못 쓰는가

이전 라이브러리의 TLSSocket 은 OpenSSL 에 fd 를 주는 방식이다 (SSL_set_fd + SSL_connect). OpenSSL 이 직접 그 fd 에 recv / send 한다. 동기 socket 이나 reactor (readable 통지 뒤 내가 읽는 모델) 에서는 이것이 가장 편하다. 그런데 이 프로젝트는 15-3 에서 모든 backend 를 proactor 로 보이게 하기로 했다. proactor 에서는 소켓의 수신 길을 OS 요청 (IOCP 의 overlapped WSARecv) 이나 listener (epoll 흉내) 가 쥔다. 같은 소켓에 OpenSSL 이 또 recv 를 걸면:

  • IOCP : overlapped 요청이 걸려 있는 소켓에 동기 recv 를 섞으면 어느 쪽이 바이트를 가져갈지 정해지지 않는다. 쓸 수 없다.
  • epoll : listener 가 readable 을 받아 recv 해서 우리 버퍼에 넣기로 했는데, OpenSSL 도 같은 fd 에서 읽으려 한다. 둘 중 하나를 포기해야 한다.

그래서 TLS 는 socket 이 아니라 바이트 위에 얹는다. OpenSSL 의 memory BIO 가 그 길이다. socket 에서 받은 암호문을 OpenSSL 에 넣고 (rbio), OpenSSL 이 내놓은 암호문을 socket 으로 보낸다 (wbio). OpenSSL 은 fd 를 모른다.

1.2 두 그림

데이터 흐름 (받기)                                              코드 의존 (include)
socket ─ recv ─▶ cipher Stage ─▶ TlsCodec ─▶ plain Stage ─▶ onRead     connection ─┬─ socket   (socket 은 Stage 만 안다)
                                                                                    ├─ tls      (tls 는 Stage 만 안다)

"socket 뒤에 TLS" 는 왼쪽 그림이다. 오른쪽 그림에서 socket 과 tls 를 위아래로 그리면 tls 가 socket 헤더를 포함해야 하는데 포함할 이유가 없다. v0 의 "옆" 은 오른쪽 그림 이야기였다. 둘 다 맞다.

1.3 handshake 는 이렇게 돈다

handshake 도 같은 길을 쓴다. SSL_do_handshake 는 "더 받아야 한다" (WANT_READ) 를 돌려주고, 그 사이 wbio 에 보낼 바이트를 쌓는다. 그래서 handshake 는 "받기 완료 → 넣기 → do_handshake → 나온 것 보내기" 를 끝날 때까지 되풀이하는 것이다. 서버 (SSL_set_accept_state) 와 클라이언트 (SSL_set_connect_state + SNI) 가 같은 코드다.

// Connection 안. 평문이면 open 에서 바로 CONNECTED 가 되고 onConnected 가 나간다.
void Connection::open(ActiveSocket&& socket, TlsProfile* profile)
{
    _socket = std::move(socket);
    _phase  = profile ? HANDSHAKING : CONNECTED;           // onConnected 는 CONNECTED 가 된 뒤에만 나간다
}

Step Connection::stepHandshake()                           // IO Thread. 받기 완료마다, 그리고 open 직후 한 번
{
    KiottyNetCode code = _tls.handshake(cipherReceive(), cipherSend());   // rbio ← cipherReceive, cipherSend ← wbio
    // cipherSend 에 바이트가 생겼으면 IoLoop 가 submitSend 한다 (평소의 drain 과 같은 길)
    if (code == KIOTTY_SUCCESS) { _phase = CONNECTED; return Step::CONNECTED; }   // IoLoop 가 onConnected 를 낸다
    if (code == KIOTTY_BUSY)    { return Step::MORE; }                             // IoLoop 가 submitReceive 한다
    return Step::FAILED;                                                           // IoLoop 가 close(PROTOCOL_ERROR)
}
시점평문TLS
accept / connect 완료open → onConnectedopen → stepHandshake (클라이언트는 ClientHello 가 cipherSend 에 생긴다)
receive 완료 (HANDSHAKING)—cipherReceive.commit → stepHandshake → MORE 면 다시 submitReceive
send 완료 (HANDSHAKING)—cipherSend.consume. 남았으면 다시 submitSend
CONNECTEDonConnectedonConnected. 이때부터 receive 완료는 decode 로 plain Stage 를 채우고 pump
deadline—HANDSHAKING 에도 deadline 이 있다 (handshake_timeout_ms). 지나면 close(TIMEOUT). onTimeout 은 안 나간다

이것이 design_connection.md 의 "TLS 적용했을 경우 내부적으로 Handshake 까지 다 된 connection 을 수행한다" 와 같은 뜻이다. 사용자는 HANDSHAKING 을 보지 못한다. StreamClient 는 loop 가 없으니 같은 stepHandshake 를 while (MORE) { socket.send(cipherSend); socket.receive(cipherReceive); } 로 동기로 돌린다. 이전 라이브러리의 "connect 에서 handshake 까지" 가 StreamClient 에서는 그대로 성립하고, 코드는 한 벌이다.

1.4 cipher Stage 를 누가 드는가 선택

v0 설계는 Connection 이 _cipher_recv, _cipher_send 를 들었다. 그러면 Connection 의 receive / send 길마다 "TLS 면 cipher, 아니면 plain" 분기가 생긴다. 분기를 한 곳으로 모으는 안:

A. Connection 이 cipher Stage 를 든다 (v0)B. TlsCodec 이 cipher Stage 를 든다
Connection 이 받을 자리를 내줄 때tls ? _cipher_recv : _recv_stage 를 고른다_tls.valid() ? _tls.receiveProvider() : _recv_stage.provider(). 한 줄
receive 완료commit 뒤 tls 면 decode 를 돌린다같다. _tls.decode(_recv_stage)
TlsCodec::openopen(profile, pool, hostname)open(profile, pool, hostname, cipher_capacity). Stage 둘을 pool 에서 잡는다
StreamClientcipher Stage 둘을 또 가진다TlsCodec 하나만 가진다

추천: B. Connection 과 StreamClient 에서 cipher Stage 가 사라지고 TLS 를 아는 줄이 넷 (받을 자리, decode, encode, handshake) 으로 줄어든다. 이름은 B 로 가면 "Stage 둘을 가진 변환기" 라서 TlsCodec 이 여전히 맞는다고 본다. 더 "socket 뒤" 어감을 원하면 TlsChannel 도 된다.

2. IoAction 하나로 ReadRequest / FinishRequest 를 대신한다 부분 동의

제안의 핵심 "요청은 struct 하나를 만들어 넘기고, 알아야 할 타입을 줄인다" 에 동의한다. 다만 union 에 accept, connect 를 같이 넣는 것은 두 층을 섞는다. 층을 나누면 타입은 둘이고 각각 union 이 하나거나 없다.

층타입kind누가 만들어 누구에게
연결 (사용자가 시키는 것)IoActionNONE, READ, READ_UNTIL, WRITE, START_WORK, CLOSEhandler 의 return, finishWork, C 함수 → Connection
OS (loop 가 거는 것)submitAccept / submitReceive / submitSend 와 IoCompletionACCEPT, RECEIVE, SEND, WAKEIoLoop → EventListener → IoLoop

섞으면 안 되는 이유: READ 는 OS 요청이 아니다. recv 는 늘 걸려 있고 (구현 가이드 1.3) READ 는 "Stage 가 이 조건이 되면 onRead 한 번" 이라는 조건이다. 반대로 ACCEPT 는 사용자가 시킬 일이 없다. 한 union 에 두면 어느 자리에서든 kind 의 절반이 불법이다.

2.1 IoAction

그리고 이 struct 는 이미 있다. kiotty_net_statemachine.h 의 KiottyNetEntryAction 이 정확히 이 모양이다 (type + timeout_ms + union { read, read_until, write, close }). 내부 IoAction 은 그것의 C++ 판이고, 다른 점은 delimiter 를 복사해 소유 한다는 것뿐이다 (콜백이 돌아온 뒤에도 Connection 이 들고 있어야 하므로 사용자 메모리를 가리키면 안 된다).

enum class IoActionKind : uint8_t { NONE, READ, READ_UNTIL, WRITE, START_WORK, CLOSE };

struct IoAction
{
    IoActionKind kind;
    uint32_t     timeout_ms;                    // 0 이면 deadline 없음. READ / READ_UNTIL / START_WORK 에 쓴다
    union
    {
        struct { size_t exact; }                                      read;
        struct { char delimiter[4]; uint8_t length; size_t max; }     read_until;
        struct { KiottyNetSpan data; }                                write;        // 적용 시점에 lane 으로 복사된다
        struct { KiottyNetCode reason; }                              close;
    } as;

    static IoAction none();
    static IoAction read(size_t exact, uint32_t timeout_ms);
    static IoAction readUntil(KiottyNetSpan delimiter, size_t max, uint32_t timeout_ms);
    static IoAction write(KiottyNetSpan data);
    static IoAction startWork(uint32_t timeout_ms);
    static IoAction close(KiottyNetCode reason);
    static IoAction fromEntry(const KiottyNetEntryAction& entry);    // base.cpp 의 번역
};

이것으로 지워지는 것: ReadRequest / ReadCondition, FinishRequest / WorkOutcome, 그리고 v0 의 9번 이름 둘. Connection 이 드는 것은 IoAction _read (지금 걸린 read 조건. kind 가 NONE 이면 없음), IoAction _saved_read (Work 들어갈 때 보관), IoAction _work_outcome (worker 가 남긴 것), 그리고 READ_UNTIL 의 진행 위치 size_t _scanned 다. _scanned 는 IoAction 에 넣지 않는다. 사용자가 만드는 값이 아니기 때문이다.

2.2 finishWork 는 하나

KiottyNetCode IoLoop::startWork (PoolHandle handle, uint32_t timeout_ms);           // 아무 thread
KiottyNetCode IoLoop::finishWork(PoolHandle handle, IoAction outcome);              // 아무 thread. READ / READ_UNTIL / WRITE / CLOSE 만

// base.cpp 는 번역뿐이다
KiottyNetCode KiottyNet_finishWorkWithRead(KiottyNetWorkHandle work, size_t exact, uint32_t timeout_ms)
{
    return loopOf(work).finishWork(fromRaw(work), IoAction::read(exact, timeout_ms));
}

finishWorkWithRead / ReadUntil / Write / Close 넷으로 나누는 안도 나쁘지 않지만, 그러면 base.cpp 가 하는 번역을 IoLoop 가 한 번 더 한다. "알아듣기 쉬운 이름" 은 C 함수 넷이 이미 맡고 있으므로 안쪽은 하나로 둔다.

2.3 IoCompletion 에는 union 이 필요 없다

struct IoCompletion
{
    IoKind     kind;                            // ACCEPT, RECEIVE, SEND, WAKE
    int32_t    slot;                            // 연결 slot. ACCEPT 는 -1 (Acceptor 의 것)
    SocketCode code;
    size_t     length;                          // RECEIVE / SEND 가 옮긴 바이트. ACCEPT / WAKE 는 0
};

ACCEPT 완료에 실을 것이 없다. 새 소켓은 완료를 받은 뒤 Acceptor::accept() 로 꺼낸다 (IOCP 의 AcceptEx 뒤처리, epoll 의 accept 가 그 안이다). CONNECT 는 동기라서 없다. owner 를 void* 대신 int32_t slot 으로 둔 이유는 7절.

2.4 EventListener 의 submit 은 셋 그대로 선택

submit(event, IoCommand) 하나로 묶을 수도 있다 (union { accept { PassiveSocket* }, receive { buffer, length }, send { buffer, length } }). 그런데 셋의 인자가 다 달라서 union 이 "어느 kind 에 어느 필드가 유효한가" 를 숨길 뿐 줄여 주는 것이 없다. 추천: submitAccept / submitReceive / submitSend 셋 유지. 하나로 묶기를 원하면 그렇게 한다.

3. Acceptor 가 무엇인가 동의

v0 의 11번에서 "Server 의 loop 와 EventClient 의 loop 가 다른 것은 accept 한 줄" 이라고 했고, 그 한 줄을 IoLoop 밖으로 뺀 이름이 Acceptor 다. design_connection.md 의 host_socket + listener.submitAccept() + asAcceptor(owner) 가 바로 이것이다. 내용은 셋이다.

class Acceptor                                  // server/kiotty_acceptor.h. Server 만 만든다
{
public:
    Acceptor();
    ~Acceptor();

    KiottyNetCode                     open(const KiottyNetEndpoint& endpoint, int backlog);   // PassiveSocket::open. Unix domain 이면 unlink 뒤 bind
    void                              close();
    SocketCode                        submit(EventListener& listener);                        // 다음 accept 를 건다
    Result<SocketCode, ActiveSocket>  accept();                                               // ACCEPT 완료 뒤. 새 소켓을 꺼낸다
    bool                              valid() const;

private:
    PassiveSocket   _socket;
    Holder<IoEvent> _event;                     // 걸려 있는 accept 요청 하나
    SocketHandle    _pending;                   // IOCP 전용. AcceptEx 는 소켓을 미리 만들어 넘겨야 한다. epoll 은 INVALID
};

왜 클래스인가: IOCP 의 AcceptEx 는 받을 소켓을 미리 만들어 넘기고 주소 버퍼 (2 × (sizeof(sockaddr) + 16)) 도 넘겨야 한다. 그 상태가 어딘가에 살아야 하는데 PassiveSocket (OS 핸들) 도 IoLoop (backend 를 모름) 도 자리가 아니다. 그래서 "listen 소켓 + 걸린 accept 하나 + backend 가 필요로 하는 것" 을 묶은 것이 Acceptor 다. IoLoop 는 Acceptor* 를 받고 nullptr 이면 ACCEPT 완료가 올 일이 없다.

5. OpenSSL 없는 빌드 부분 동의

결정은 "빌드는 되고, TLS 설정을 받으면 KIOTTY_TLS_NOT_SUPPORTED" 로 읽었다 (OpenSSL 이 빌드 옵션에 안 들어간 경우를 말씀하신 것으로 이해했다). 구조는 v0 과 같다: tls/backend/kiotty_openssl_tls.cpp 와 kiotty_stub_tls.cpp 가 같은 선언을 구현하고 CMake 옵션 KIOTTY_NET_WITH_OPENSSL 이 하나를 고른다. stub 의 TlsProfile::open 이 KIOTTY_TLS_NOT_SUPPORTED 를 돌려준다. KiottyNetCode 에 값 하나가 는다.

남는 문제는 전달 경로 다. "초기화했을 때" 는 KiottyNet_createServer 인데 create 는 핸들만 돌려주고 코드를 돌려줄 자리가 없다.

장점단점
A. create 는 성공하고 코드를 기억한다. run 이 그 코드를 바로 돌려주고 await 도 같은 값을 본다base.h 가 안 바뀐다. 사용자는 run 의 반환값 하나만 보면 된다create 시점에는 모른다 (valid 는 true)
B. create 가 NULL 을 돌려준다가장 이르다왜 NULL 인지 알 길이 없다. 메모리 부족과 구분이 안 된다
C. config 검사 함수를 하나 더 둔다: KiottyNet_validateTlsServerConfig(config) 가 stub 빌드에서 KIOTTY_TLS_NOT_SUPPORTEDcreate 전에 안다C 함수가 는다. 사용자가 부르지 않으면 A 와 같다

추천: A. 필요하면 C 를 덧붙인다. v0 에서 걱정한 "조용한 평문" 은 이 결정으로 없어졌다. stub 은 평문을 보내지 않는다.

6. design_connection.md : Handler 변경 부분 동의

의도를 이렇게 읽었다. (1) 연결을 받을지 말지를 info 를 보고 먼저 정한다. (2) 콜백은 "다음에 할 IO 하나" 를 return 값으로 내고, 콜백 안에서 read / write 를 호출하는 길을 없앤다. (3) 그 action 은 2절의 IoAction 과 같은 것이다. 셋 다 방향에 동의한다. 특히 (2) 는 KiottyNet_moveToNextState(next, entry_action) 과 같은 모양이라서, base 와 stateful 계층이 같은 action 타입 을 쓰게 된다. 바꿀 점을 항목별로 적는다.

6.1 onAccept 와 accept / ignore

  • 시점: OS accept 뒤, TLS handshake 전. ignore 면 소켓을 바로 닫는다. handshake 비용을 쓰기 전에 거르므로 blacklist 의 목적에 맞다. 1절의 HANDSHAKING 은 accept 뒤에 온다.
  • slot 이 없으면 부르지 않는다: 맞다. 그런데 "부르지 않는다" 는 accept 를 안 건다는 뜻이어야 한다. OS 가 backlog 에 쌓아 두고, slot 이 생기면 (release 때) 다시 submitAccept 한다. 지금 v0 의 "가득 차면 accept 하고 바로 닫기" 보다 이것이 낫다. 반영한다.
  • handle 을 같이 준다: slot 을 잡아야 accept 가 걸리므로 onAccept 시점에 handle 이 이미 있다. 주면 KiottyNet_getConnectionInfo(handle) 로 info 를 다시 얻을 수 있어 info 를 값으로 넘길 필요도 없어진다. 다만 값 복사가 더 안전하다 는 지적 (4번) 은 맞으므로 info 는 그대로 값으로 넘기고, handle 은 stateful 계층의 createConnectionContext(app_context, handle) 이 쓰기 위해 넣는다.
  • return 은 값: typedef struct _X* KiottyNetConnectionHostAction 처럼 포인터를 돌려주면 그 포인터가 가리키는 메모리를 누군가 들어야 한다 (static 이면 thread 간에 깨지고, heap 이면 런타임 할당이다). 두 필드짜리 struct 를 값으로 돌려준다. C99 에서 struct 반환은 문제없다.
  • EventClient 도 부른다: 클라이언트는 accept 가 없지만 connection_context 는 있어야 한다 (onConnected 가 더 이상 return 하지 않으므로). connect 성공 뒤 같은 콜백을 한 번 부르고 거기서 context 를 받는다. 이름이 accept 라서 어색하면 onAdmit 으로 (선택).

6.2 콜백이 action 을 return 한다

동의한다. 얻는 것과 잃는 것을 적어 둔다.

얻는 것잃는 것
"한 콜백에 IO 하나" 가 타입으로 강제된다. 콜백 안에서 read 를 두 번 부르는 실수가 사라진다write 뒤 read 를 한 콜백에서 못 한다. 응답을 쓰고 다음 요청을 기다리려면 WRITE 를 return 하고 onWritten 에서 READ 를 return 한다. 콜백이 하나 는다
IoLoop 의 콜백 처리가 "return 값을 switch" 하나로 끝난다. 재진입이 없다 (구현 가이드 1.6 의 onWritten 재진입 문제가 구조로 사라진다)C++ KiottyNet_Connection::read() 같은 편의 메서드가 "부르면 된다" 에서 "만들어서 return 한다" 로 바뀐다
stateful 계층의 EntryAction 과 base 의 action 이 같은 타입이 된다. 번역이 사라진다base.h 가 바뀐다. websocket.h 는 영향 없다 (자기 handler 를 쓴다). http.h 는 아직 없다

"write 뒤 read" 는 구현 가이드의 HTTP 서버와 stateful 예제가 이미 Writing → onWritten → Reading 으로 가고 있어서 실제 비용은 작다고 본다.

세부에서 바꿀 것:

  1. KiottyNetConnectionAction 은 값이고, 모양은 KiottyNetEntryAction 그대로다. statemachine.h 의 그 struct 를 base.h 로 내리고 이름을 KiottyNetConnectionAction 으로 바꾸면 statemachine.h 는 entry_action 의 타입만 바꾸면 된다. 만드는 함수도 KiottyNet_make*EntryAction 여섯 개가 그대로 KiottyNet_readConnection(exact, timeout_ms) 등이 된다. 한 타입, 한 벌.
  2. setTimeout 은 action 이 아니라 action 의 필드다. 콜백이 action 하나만 return 하면 "READ 하면서 timeout 도" 를 표현할 길이 timeout 필드뿐이다. finishWorkWithRead(exact, timeout_ms) 와 KiottyNet_setEntryActionTimeout 이 이미 그 모양이다. KiottyNet_setConnectionTimeout 은 지운다. (design_connection.md 의 switch 에서 case TIMEOUT 에 break 가 없어 CLOSE 로 떨어지는 것도 이 통합으로 같이 없어진다.)
  3. onWorkStarted 는 void. IO Thread 가 Work 를 다른 thread 에 넘기는 자리라서 return 할 action 이 없고, 있으면 worker 의 finishWork 와 경쟁한다. 다음 action 은 finishWork 가 가져온다.
  4. NONE 이 필요하다. "지금은 아무것도 걸지 않는다 (push 나 timeout 만 기다린다)" 를 return 할 길. KiottyNet_holdConnection(void) 를 제안한다 (선택: hold / idle / wait).
  5. onError(code, const char*): 부분 동의. 문자열은 static literal 만 넘기고 (소유 문제), app_context 를 첫 인자로 넣는다. 나가는 경우는 세 가지로 한정한다: accept 실패 (EMFILE 등. run 을 끝낼 일은 아니지만 알려야 한다), handshake 실패 (onDisconnected 가 안 나가는 연결이라 다른 길이 없다), push slot 가득 참은 아니다 (notify 가 BUSY 를 돌려준다). 이 셋이 없으면 지운다.
  6. typedef int64_t KiottyNetConnectionHost 가 무엇을 위한 것인지 모르겠다. Server / EventClient 핸들이 이미 "연결들의 주인" 이라서 필요해 보이지 않는다. 의도가 있으면 알려 달라.

7. design_connection.md : IoCompletion, IoAction 부분 동의

  • IoKind 의 CONNECT 는 v0 의 7번으로 없다. 대신 WAKE (notify / startWork / finishWork / stop 이 IO Thread 를 깨우는 완료) 가 있다.
  • IOOwner = void* 와 asAcceptor / asConnection 의 reinterpret_cast 대신 int32_t slot 을 싣는다 (2.3). slot < 0 이면 Acceptor, 아니면 host.at(slot). cast 가 없고, 완료가 늦게 와서 slot 이 이미 재사용됐을 때도 포인터가 아니라 index 라서 안전하다 (IoEvent 가 slot 에 묶여 있으므로 재사용된 연결의 완료는 generation 으로 거른다).
  • IoAction::connection_handle 은 지운다 (6.2).
  • IoActionKind 의 TIMEOUT 은 timeout_ms 필드로 (6.2 의 2).

9.1 고쳐 쓴 한 바퀴

void IoLoop::runOnce()
{
    Result<SocketCode, Span<const IoCompletion>> waited = _listener.wait(nearestDeadline());   // (a)

    for (const IoCompletion& completion : waited.value())                                       // (b) 완료
    {
        if (completion.kind == IoKind::WAKE)   { drainSlots(); continue; }                       //     notify / broadcast → host.notify / broadcast
        if (completion.kind == IoKind::ACCEPT) { admit(); continue; }                            //     acceptor.accept → host.acquire → onAccept → open
        Connection& connection = *_host.at(completion.slot);
        if (completion.kind == IoKind::SEND)   { connection.onSent(completion.code, completion.length); continue; }
        apply(connection, connection.onReceived(completion.code, completion.length, *_handler));   // handshake 진행 또는 pump → onRead 의 action
    }

    uint64_t now = monotonicMs();                                                                // (c) scan. 32 개
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& connection = *_host.at(i);
        if (connection.workState() == WorkState::DONE)     { apply(connection, connection.takeWorkOutcome()); }
        if (connection.workState() == WorkState::DRAINING) { connection.tryStartWork(*_handler); }      // write lane 이 비었으면 WORKING + onWorkStarted
        if (connection.deadlineExpired(now))               { apply(connection, connection.expireDeadline(*_handler)); }   // RUNNING: onTimeout 의 action, DRAINING / HANDSHAKING: close
        if (connection.hasWritten())                       { apply(connection, connection.reportWritten(*_handler)); }    // (d) onWritten 의 action
    }

    if (_stop_when_empty && _host.empty()) { _stopped = true; }                                   // (e)
}

void IoLoop::apply(Connection& connection, IoAction action)                                     // 재귀 없이 loop
{
    for (;;)
    {
        switch (action.kind)
        {
        case IoActionKind::NONE:       return;
        case IoActionKind::READ:
        case IoActionKind::READ_UNTIL: connection.setRead(action); break;                        // 조건 등록. 아래 pump 가 바로 검사한다
        case IoActionKind::WRITE:      connection.write(action.as.write.data); submitSend(connection); return;
        case IoActionKind::START_WORK: connection.tryEnterWork(action.timeout_ms); return;
        case IoActionKind::CLOSE:      close(connection, action.as.close.reason); return;
        }
        action = connection.pump(*_handler);                                                     // 충족되면 onRead 한 번, 그 return 값. 아니면 NONE
    }
}

이 모양에서 Connection 의 public 은 "IoLoop 가 시키는 일" 로 줄어든다: open, close, receiveProvider, sendSegment, onReceived, onSent, setRead, write, pump, tryEnterWork, tryStartWork, takeWorkOutcome, expireDeadline, reportWritten, push, 그리고 아무 thread 의 startWork / finishWork 와 조회 몇 개. v0 의 9번 이름 둘 (resumeFromWork, completeWritten) 은 takeWorkOutcome + apply, reportWritten 이 된다.

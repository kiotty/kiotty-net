kiotty_net_websocket.h 설계 v0

2026-11-10. WebSocket (RFC 6455) 층의 첫 설계다. design_http_v0.html 과 같은 날의 짝이고, include/kiotty_net_websocket.h 의 지금 판 (2026-11-09, 공개 API v1) 을 HttpServer 위에 얹히도록 고친 판 v2 를 정한다. 사용 모델은 user_guide_websocket.md (2026-11-08) 가 기준이고 이 문서는 그 가이드가 미뤄 둔 것 (handle 의 모양, Upgrade 등록 자리, 표 바꿔 타기, 다른 thread 의 close) 을 닫는다. 공개 인터페이스가 중심이다.

표기: 유지 지금 헤더 그대로, 추가 이 판이 더하는 것, 제거 이 판이 빼는 것.

설계 방침

  1. WebSocket 은 HTTP 의 연장이다. 소유자 셋 (HttpServer 위의 Upgrade, WebSocketServer, WebSocketClient) 이 모두 같은 표의 WebSocket 행을 밟고 같은 Session 을 쓴다. WebSocketServer 는 Upgrade 경로 하나만 등록한 HttpServer 다 (requirement 10절). 새 Session 종류, 새 버퍼는 없다.
  2. 모든 송신은 push lane 이다. 사용자의 send, broadcast, 라이브러리의 pong / ping / close frame 전부 notify 의 길이다. 그래서 아무 thread 에서나 되고 완료 콜백이 없다 (user_guide 2절). write lane 은 핸드셰이크 (101 / Upgrade 요청) 에만 쓴다.
  3. handle 은 base 와 같은 모양이다. { owner, id }. 소유자를 handle 이 들고 전역 표가 없다 (설계 v5 3절, statemachine 설계 12.6 의 미결).
  4. http.h 와 websocket.h 는 서로 include 하지 않는다. Upgrade 등록은 websocket.h 에 있고 HttpServer handle 의 typedef 만 가드로 복사한다 (OwnedHandle 과 같은 방법).

1. 범위

이 판이 정하는 것: handle 의 모양, Upgrade 등록 함수와 두 헤더의 독립, 세 소유자가 한 표 / 한 Session 을 쓰는 방법, 다른 thread 의 send / close 가 IO thread 에 닿는 길, 메시지 버퍼와 HTTP body 버퍼의 공유. 사용자가 보는 흐름 (설정 → create → run → 콜백 넷 → send / close) 은 user_guide 그대로이고 여기서 다시 쓰지 않는다.

범위 밖 (user_guide 10절의 열린 질문 그대로): Work (backpressure), 조각 송신 (push_capacity 가 메시지 하나의 상한), 동기 WebSocketClient, permessage-deflate. MCP 는 WebSocket 을 쓰지 않는다. 이 층은 HTTP 가 돈 뒤에 온다 (9절).

2. 공개 API (C) 에서 바뀌는 것

2.1 handle 추가

typedef struct KiottyNetWebSocketOwner KiottyNetWebSocketOwner;              /* 불투명. HttpServer, WebSocketServer, WebSocketClient 가 안에서 이것이다 */

typedef struct KiottyNetWebSocketHandle {
    KiottyNetWebSocketOwner* owner;
    int64_t                  id;                                             /* generation + Session index. 0 은 무효 */
} KiottyNetWebSocketHandle;
  • base 의 KiottyNetConnectionHandle { KiottyNetEndpoint* owner; int64_t id; } 와 같은 모양이다. KiottyNetEndpoint 가 Server / StreamClient / EventClient 의 공통 base 이듯 KiottyNetWebSocketOwner 는 WebSocket 소켓을 가질 수 있는 셋의 공통 base 다. 안에서는 "WebSocket 행을 가진 표 + Session 배열을 든 것" 하나이고 (5절), 셋이 그것을 상속한다 (DV16 의 빈 struct 표지와 같은 패턴).
  • id 는 HTTP 의 response handle 과 같은 generation + index 다. 같은 Session 이므로 같은 값이다. Upgrade 뒤 onOpen 이 주는 WebSocket handle 과 그 전 HTTP 응답 handle 은 generation 이 다르다 (101 을 보낼 때 올린다). HTTP 쪽 handle 로 WebSocket 을 만질 수 없다.
  • 무효는 { NULL, 0 }. KiottyNet_getWebSocketClientSocket 이 onOpen 전에 돌려주는 값. 닫힌 handle 로 부른 함수는 PEER_CLOSED (user_guide 2절 그대로).
  • C++ 의 KiottyNet_WebSocket 에 operator== / != / < 를 둔다 (KiottyNet_Connection 과 같다). 앱이 handle 목록을 std::vector / std::set 에 들기 위해서다.

2.2 Upgrade 등록 추가

#ifndef KIOTTY_NET_HTTP_SERVER_HANDLE_DEFINED
#define KIOTTY_NET_HTTP_SERVER_HANDLE_DEFINED
typedef struct KiottyNetHttpServer* KiottyNetHttpServerHandle;                 /* http.h 와 글자까지 같은 한 줄. 먼저 include 된 쪽이 정의한다 */
#endif

KiottyNetCode KiottyNet_addWebSocketUpgrade(
    KiottyNetHttpServerHandle server,
    const KiottyNetWebSocketConfiguration* websocket,                        /* path 가 여기 있다. 라우트 표의 한 항목이 된다 */
    KiottyNetWebSocketHandler handler,                                       /* 값으로 복사. run 뒤 사용자 struct 는 버려도 된다 */
    KiottyNetAppContext app_context);                                        /* onUpgrade / onOpen / onClose 가 받는다 */
  • C99 는 같은 typedef 를 두 번 쓸 수 없어 (C11 부터 허용) 가드가 필요하다. OwnedHandle 의 KIOTTY_NET_OWNED_HANDLE_DEFINED 와 같은 규칙이다 (user_guide 헤더 구성: 두 정의는 글자까지 같아야 하고 고칠 때는 둘을 함께 고친다). http.h 도 같은 가드로 감싼다.
  • HttpServer 의 run 은 handler 를 받지 않는다 (라우트가 app_context 를 든다). 그래서 Upgrade 경로도 등록 때 handler 와 app_context 를 받아 라우트 표의 항목에 복사한다 (구현 가이드 4.1 의 RouteEntry::UPGRADE). WebSocketServer / Client 의 run(handler, app_context) 은 그대로다. 둘은 run 마다 handler 를 바꿀 수 있고 HttpServer 의 Upgrade 는 등록 때 고정된다는 차이가 있다.
  • 코드: run 뒤 BUSY, 표가 차면 TABLE_FULL, 같은 path 가 이미 (라우트든 Upgrade 든) 있으면 DUPLICATE_RULE, websocket 미초기화 / handler 의 onOpen 또는 onMessage 가 NULL / max_message_bytes > max_body_bytes 면 INVALID_ARGUMENT (statemachine 설계 14절 7. 메시지 버퍼가 HTTP body 의 Stage 라 create 뒤에는 키울 수 없다).
  • Upgrade 경로는 GET 만 받는다. 다른 메서드는 405. Upgrade 헤더가 없는 GET 은 426 (Upgrade: websocket 헤더와 함께) 으로 거절하고 onUpgrade 는 부르지 않는다.
  • C++ 의 KiottyNet_HttpServer 에 upgrade(...) 메서드는 두지 않는다. http.h 가 websocket.h 를 모르기 때문이다. C++ 사용자도 KiottyNet_addWebSocketUpgrade(server.handle(), ...) 를 부른다.

5. HttpServer 위의 Upgrade : 한 표, 한 Session

statemachine 설계 11절의 결정 (한 표, 한 Session, Session 의 Stage 하나를 body 와 메시지가 같이 쓴다) 을 소유자 셋에 펼친 것이다.

소유자base 의 소유자표Session
HttpServer (Upgrade 경로 있음)ServerHTTP 행 전부 + WebSocket 행 (서버 쪽, mask 검사)HttpSession. Upgrade 뒤 같은 Session 이 WebSocket 상태를 든다
WebSocketServerServer같은 표. 라우트 표에 UPGRADE 항목 하나 (path 는 설정의 것). 다른 path 는 404, 다른 메서드는 405HttpSession. limits 는 라이브러리가 정한다: max_routes 1, max_header_bytes 8 KiB, max_headers 32, max_body_bytes = max_message_bytes, response_bytes 1 KiB (101 / 403 / 404 / 426), header_timeout = handshake_timeout
WebSocketClientEventClientUpgrade 요청을 보내고 101 을 읽는 행 둘 + WebSocket 행 (클라이언트 쪽, mask 씌움)HttpSession 하나 (응답 헤더 파싱에 요청 버퍼를, 메시지에 Stage 를 쓴다)

셋 다 "HttpSession 배열 + 라우트 표 + HTTP_MACHINE 을 든 것" 이고 그것이 KiottyNetWebSocketOwner 다. HttpServer 가 그 자체이고, WebSocketServer 는 Upgrade 하나를 등록한 HttpServer 를 멤버로 들며, WebSocketClient 는 같은 Session 타입 하나와 EventClient 를 든다. 소유자 셋의 공통 base 를 어디에 두는지는 사이클 W1 의 코드 모양이고 공개 API 는 owner 포인터의 타입 하나다.

HttpServer 의 연결 하나 (Upgrade 경로 "/chat") [ReadingRequestLine] → [ReadingHeaderLine]... → afterHeaders : match 가 UPGRADE 항목 GET 이 아니면 405. Upgrade / Connection / Sec-WebSocket-Key / Version 13 이 없으면 426 onUpgrade(app_context, websocket handle, { path, query, host, origin, protocols }) → 0 (KiottyNetBool) 이면 403 (완성 응답, keep_alive 0) 1 이면 응답 버퍼에 101 + Sec-WebSocket-Accept + (고른) Sec-WebSocket-Protocol → { WebSocketOpening, thenWrite(101) } ← generation 을 올린다 [WebSocketOpening] WRITTEN → onOpen(app_context, websocket) → websocket_context 를 Session 에 → { WebSocketReadingHeader, thenRead(2, ping_interval) } [WebSocketReadingHeader] READ(2) → FIN / opcode / mask 비트 / 길이 7 비트 → 126 / 127 이면 [ReadingExtendedLength], mask 면 [ReadingMask], 아니면 [ReadingPayload] [WebSocketReadingPayload] READ(min(남은 길이, receive_capacity)) → unmask 하며 Stage 에 붙인다 → 남으면 같은 상태, 다 받으면 : control frame : ping → push lane 에 pong, pong → 타이머 리셋, close → [WebSocketClosing] (상대가 시작). 데이터 frame : FIN 이면 onMessage(websocket_context, websocket, { opcode, Stage }) → Stage 비움 → { WebSocketReadingHeader, thenRead(2, ping_interval) } TIMEOUT (어느 WebSocket 상태에서든) : ping 차례면 push lane 에 ping 하고 pong_timeout 으로 다시, pong 이 안 왔으면 close(TIMEOUT, 1001) [WebSocketClosing] 상대 close frame 을 받거나 close_timeout → thenClose(...) → CLOSED → onClose(app_context, websocket_context, websocket, { code, status, reason }) → release
  • HTTP body 와 WebSocket 메시지가 같은 Stage 를 쓴다. Upgrade 요청에는 body 가 없고 (있으면 400), 101 뒤에는 HTTP 가 없으므로 한 연결에서 둘이 겹치는 순간이 없다. max_message_bytes 를 넘는 메시지는 1009 로 닫는다.
  • 수신 frame 의 payload 는 receive_capacity 조각으로 읽어 Stage 에 붙인다 (user_guide 8절). 조각마다 unmask 의 key offset 을 Session 이 든다.
  • 송신 frame (pong / ping / close / 사용자 send) 은 전부 push lane 이고, frame 머리 (2 ~ 14 바이트) + payload 를 한 번에 넣는다. NotificationDesk 가 머리와 payload 를 한 lock 안에서 이어 복사하고, 전부 들어가지 않으면 하나도 넣지 않는다 (http 설계 2.1). 클라이언트는 mask key 4 바이트를 더하고 payload 를 씌워 넣는다 (복사하면서 XOR).
  • onMessage 의 data 는 Stage 를 가리키고 return 하면 무효다 (Stage 를 비운다). TEXT 는 UTF-8 검사를 지나지 않으면 1007.
  • HttpServer 의 close 는 WebSocket 연결도 close handshake 없이 끊는다 (onClose(CLOSED, 1001)). user_guide 5절 그대로.

6. 다른 thread 의 send 와 close

send 는 notify 라 끝이다 (push lane 에 복사, IO thread 의 drain 이 보낸다). close 는 close frame 을 보낸 뒤 "데이터 frame 거부 + close 타이머" 로 상태가 바뀌어야 하는데 notify 에는 이벤트가 없다. notify 에는 완료 이벤트가 없어서 상태를 옮길 자리가 따로 필요하다.

  1. closeWebSocket(handle, status, reason) (아무 thread): Session 의 닫힘 플래그 (std::atomic<uint16_t> 에 status, 0 이면 열림) 를 CAS 로 세운다. 이미 세워져 있으면 BUSY. 그 뒤 close frame 을 push lane 에 넣는다. 돌아온 뒤의 send 는 플래그를 보고 CLOSED.
  2. IO thread: drain 이 push lane 을 비운 뒤 플래그가 서 있고 상태가 아직 WebSocket 데이터 상태면 { WebSocketClosing, thenRead(2, close_timeout) } 로 옮긴다. "drain 뒤 플래그 검사" 는 IoLoop 의 한 줄이고 지금은 WebSocket 만 쓴다 (HTTP 는 push 스트림을 두지 않기로 했다, http 설계 1절 결정 4). 표의 행이 아니라 Handler 가 drain 뒤에 받는 작은 훅 하나다 (8절의 정할 것 2).
  3. 상대의 close frame 이 오면 (WebSocketClosing 의 READ) thenClose(SUCCESS), 안 오면 TIMEOUT 행이 thenClose(TIMEOUT). CLOSED 행이 onClose.

IO thread 콜백 안에서 부른 close 도 같은 길이다 (플래그 + notify). action 이 return 한 뒤 다음 drain 에서 전이된다. 콜백 안이라고 특별히 다루지 않는다.

8. 정할 것

  1. websocket.h 가 base.h 만 include 하는 것. 지금은 statemachine.h 다. 사용자 코드에서 표의 타입이 필요한 자리가 없다. 바꾸는 쪽을 추천한다. single header 에는 영향이 없다.
  2. "drain 뒤 플래그 검사" 를 어디에 둘지. 안쪽의 일이지만 Handler 인터페이스 (5 메서드) 에 하나를 더하는 것이라 적는다. 대안: (a) Handler::afterDrain(caller) 여섯째 메서드, (b) 플래그를 본 IoLoop 이 가짜 TIMEOUT 이벤트를 넣어 표의 TIMEOUT 행이 플래그를 보게 하는 것. (b) 는 표만으로 되지만 TIMEOUT 의 뜻이 흐려진다. (a) 를 추천한다. 지금은 WebSocket 의 close 만 쓴다.
  3. WebSocketServer 의 내부 limits. 5절의 값 (header 8 KiB / 32, response 1 KiB, body = max_message_bytes). 쿠키가 큰 브라우저 요청은 8 KiB 를 넘을 수 있다. 그런 앱은 HttpServer + Upgrade 로 가서 limits 를 직접 둔다. WebSocketServer 에 limits 인자를 더하지 않는다.
  4. Upgrade 경로의 handler 를 등록 때 값으로 복사하는 것. WebSocketServer / Client 는 run 마다 handler 를 받는데 HttpServer 의 Upgrade 는 등록 때 고정된다. 통일하려면 HttpServer 의 run 이 handler 를 받아야 하는데 라우트 모델과 맞지 않는다. 지금 모양을 추천한다.
  5. KiottyNetWebSocketUpgrade 의 필드. user_guide 10절 5 그대로 (path, query, host, origin, protocols). 나머지는 findWebSocketUpgradeHeader. 바꾸지 않는다.
  6. WebSocketClient 의 TLS hostname. Host 헤더와 SNI 는 KiottyNetClientConfiguration.address.host 에서 온다. 설정에 따로 두지 않는다.

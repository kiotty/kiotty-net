설계 방침

  1. WebSocket 은 HTTP 의 연장이다. 서버 쪽 입구는 HttpServer 의 Upgrade 경로 하나다. 따로 선 WebSocketServer 는 없다. 클라이언트 쪽은 WebSocketClient 하나다. 둘 다 같은 WebSocket 행과 같은 Session 을 쓴다. 새 Session 종류, 새 버퍼는 없다.
  2. 모든 송신은 push lane 이다. 사용자의 send, broadcast, 라이브러리의 pong / ping / close frame 전부 notify 의 길이다. 그래서 아무 thread 에서나 되고 완료 콜백이 없다 (user_guide 2절). write lane 은 핸드셰이크 (101 / Upgrade 요청) 에만 쓴다.
  3. handle 은 base 와 같은 모양이다. { owner, id }. owner 의 타입은 KiottyNetWebSocketEndpoint 이고, 소유자를 handle 이 들어 전역 표가 없다.
  4. websocket.h 가 http.h 를 include 한다. 서버 쪽 WebSocket 은 HttpServer 없이는 쓸 수 없으므로 의존 방향이 WebSocket → HTTP 하나다. http.h 는 websocket.h 를 모른다.

12subprotocol 은 서버만. WebSocketClient 는 보내지 않는다 (create 의 protocols 인자 없음). 서버는 onUpgrade 에서 KiottyNet_selectWebSocketProtocol 로 고를 수 있다 (3.2) (2026-11-11)일반 앱 (웹 UI, 게임, 채팅) 은 경로와 메시지 안의 형식으로 충분해 쓰지 않는다. 다만 MQTT, OCPP, GraphQL, STOMP 같은 외부 표준 클라이언트는 subprotocol 을 보내고 서버가 고르지 않으면 연결이 실패하므로, 그들을 받을 수 있게 서버 쪽 선택은 남긴다. 새 API 가 아니라 지금 헤더의 함수 하나다
13WebSocketClient 의 create 는 tls 를 받지 않고, run 이 주소와 tls 를 받는다. runWebSocketClient(client, address, tls, handler, app_context). tls 가 NULL 이면 ws, 아니면 wss (2026-11-11)base 의 결정 (design_http_v0.html 1절 결정 18, 2.3). 접속할 상대의 주소와 TLS 설정은 실행 중에 정해진다

2. 배경 : WebSocket 은 HTTP 연결에서 시작한다

그렇다. WebSocket 은 따로 여는 소켓이 아니라, HTTP 요청이 오가던 TCP 연결 하나를 그 자리에서 WebSocket 으로 바꿔 쓰는 것이다 (RFC 6455 1.3, 4절).

클라이언트 → 서버 GET /chat HTTP/1.1 Host: device.local:8080 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13 서버 → 클라이언트 HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= 이 줄부터 같은 TCP 연결 위로 HTTP 가 아니라 WebSocket frame 이 양쪽으로 오간다. 다시 HTTP 로 돌아가지 않는다.
  • 그래서 서버는 보통 한 포트에서 웹 페이지 (GET /index.html) 와 WebSocket (GET /chat + Upgrade) 을 같이 받는다. 브라우저의 new WebSocket("ws://device.local:8080/chat") 도 이 요청을 보낸다. TLS 면 wss:// 이고 TLS 위에서 같은 일이 일어난다.
  • 라이브러리 안에서는 HttpSession 의 상태가 HTTP 행 (ReadingRequestLine ...) 에서 WebSocket 행 (WebSocketReadingHeader ...) 으로 넘어간다. 연결도 Session 도 그대로다.
  • 경로가 진입점이다. RFC 6455 1.3: 핸드셰이크 GET 의 Request-URI 는 WebSocket 연결의 endpoint 를 가리키며, 한 서버가 여러 WebSocket endpoint 를 둘 수 있게 하려는 것이다. 그래서 한 HttpServer 에 /chat, /chat2 를 따로 두는 것은 규약 안이다. 경로마다 handler 를 따로 두는 방법은 규약이 정하지 않고 라이브러리마다 같은 모양이다 (경로 → handler 표). 한 경로 안에서 다시 나누는 표준 장치는 subprotocol (Sec-WebSocket-Protocol) 이다.
  • 클라이언트 쪽 (WebSocketClient) 은 연결한 뒤 위 GET 을 보내고 101 을 읽는 것부터 한다. HttpClient 가 아직 없으므로 이 두 단계는 WebSocketClient 의 행이 직접 한다.

3.1 handle 추가

typedef struct KiottyNetWebSocketEndpoint KiottyNetWebSocketEndpoint;        /* 불투명. HttpServer 와 WebSocketClient 가 안에서 이것이다 */

typedef struct KiottyNetWebSocketHandle {
    KiottyNetWebSocketEndpoint* owner;
    int64_t                     id;                                          /* generation + Session index. 0 은 무효 */
} KiottyNetWebSocketHandle;
  • base 의 KiottyNetConnectionHandle { KiottyNetEndpoint* owner; int64_t id; } 와 같은 모양이다. KiottyNetEndpoint 가 Server / StreamClient / EventClient 의 공통 base 이듯 KiottyNetWebSocketEndpoint 는 WebSocket 소켓을 가질 수 있는 둘 (HttpServer, WebSocketClient) 의 공통 base 다. 안에서는 "WebSocket 행을 가진 표 + Session 배열을 든 것" 하나이고 (6절), 둘이 그것을 상속한다 (DV16 의 빈 struct 표지와 같은 패턴).
  • id 는 HTTP 의 response handle 과 같은 generation + index 다. Upgrade 뒤 onOpen 이 주는 WebSocket handle 과 그 전 HTTP 응답 handle 은 generation 이 다르다 (101 을 보낼 때 올린다). HTTP 쪽 handle 로 WebSocket 을 만질 수 없다.
  • 무효는 { NULL, 0 }. KiottyNet_getWebSocketClientSocket 이 onOpen 전에 돌려주는 값. 닫힌 handle 로 부른 함수는 PEER_CLOSED (user_guide 2절 그대로).
  • C++ 의 KiottyNet_WebSocket 에 operator== / != / < 를 둔다 (KiottyNet_Connection 과 같다). 앱이 handle 목록을 std::vector / std::set 에 들기 위해서다.

  • 등록. run 전에 라우트처럼 부른다. 한 HttpServer 에 WebSocket 경로를 여럿 둘 수 있고 (/chat, /telemetry) 경로마다 handler 와 app_context 가 따로다. 설정 (메시지 상한, 타이머) 은 서버 하나에 한 벌이다 (결정 11).
  • 코드. run 뒤 BUSY, 표가 차면 TABLE_FULL (max_routes 에 들어간다), 같은 path 가 이미 (라우트든 WebSocket 이든) 있으면 DUPLICATE_RULE, path 가 NULL / / 로 시작하지 않음 / 상한 초과, handler 의 onOpen 또는 onMessage 가 NULL 이면 INVALID_ARGUMENT.
  • 메시지 상한. 메시지는 HTTP body 의 Stage 에 모이므로 상한이 max_body_bytes 다. 넘는 메시지는 1009 로 닫는다.
  • subprotocol (서버만, 결정 12). subprotocol 은 같은 경로 안에서 "메시지를 어떤 약속으로 주고받을지" 를 고르는 이름이다 (Sec-WebSocket-Protocol). 일반 앱은 쓰지 않지만 표준 프로토콜을 WebSocket 에 얹는 클라이언트는 반드시 보낸다: MQTT (mqtt), OCPP 충전기 (ocpp1.6, ocpp2.0.1), GraphQL 구독 (graphql-transport-ws), STOMP (v12.stomp), SIP (sip). 이런 클라이언트가 후보를 보냈는데 서버가 하나도 고르지 않으면 브라우저와 대부분의 라이브러리가 연결을 실패로 처리한다. 그래서 서버는 고를 수 있어야 한다.
    • 클라이언트가 보낸 후보는 onUpgrade 의 upgrade.protocols (쉼표로 이은 원문) 로 본다.
    • 고르는 일은 onUpgrade 안에서 KiottyNet_selectWebSocketProtocol(websocket, "mqtt") 한 번이다 (지금 헤더에 있는 함수, C++ KiottyNet_WebSocket::selectProtocol). 후보에 없는 값이면 INVALID_ARGUMENT, onUpgrade 밖이면 BUSY, 두 번째 호출은 앞의 것을 바꾼다.
    • 고른 값은 101 의 Sec-WebSocket-Protocol 로 나가고, 연결 뒤에는 KiottyNet_getWebSocketInfo 의 protocol 로 본다.
    • 쓰지 않는 앱은 아무것도 하지 않는다. onUpgrade 가 NULL 이거나 고르지 않으면 101 에 그 헤더가 없다.
    • 설정의 protocols 로 자동 선택하던 것 (지금 헤더) 은 설정 struct 와 함께 없앤다. 고르는 곳은 onUpgrade 하나다.
  • WebSocket 경로의 요청. GET 만 받는다. 다른 메서드는 405. Upgrade 헤더가 없는 GET 은 426 (Upgrade: websocket 헤더와 함께) 으로 거절하고 onUpgrade 는 부르지 않는다. 헤더 상한은 max_header_bytes, 시간 상한은 header_timeout 이다.
  • broadcast. 지금 헤더의 broadcastWebSocketServer 가 옮겨 온 것이다. 등록에 쓴 path 와 글자 그대로 비교한다. 소켓마다 push lane 에 복사하고, 자리가 없는 소켓은 건너뛴다 (지금 규칙 그대로). 아무 thread 에서나. 등록되지 않은 path 는 INVALID_ARGUMENT.
  • 서버의 close. HttpServer 의 close 는 WebSocket 연결도 close handshake 없이 끊는다 (onClose(CLOSED, 1001)). 연결이 끝나면 HttpServer 의 끊김 action 도 불린다 (WebSocket 이었던 연결도 연결이다).
  • C++ 의 KiottyNet_HttpServer 에는 메서드를 더하지 않는다 (http.h 는 websocket.h 를 모른다). C++ 사용자는 KiottyNet_addWebSocket(server.handle(), "/chat", handler, &app) 를 부른다.

base 판 v1, http 판 v2 와 같이 { code, handle } 을 돌려준다. create 의 인자는 넷, run 은 다섯이다 (공개 헤더는 사용자가 정한 모양, DV13). destroy / close / await / getWebSocketClientSocket / sendWebSocketClient 는 그대로다. 클라이언트는 subprotocol 을 보내지 않는다 (결정 12). Upgrade 요청에 Sec-WebSocket-Protocol 이 없고, 서버가 101 에 그 헤더를 담아 오면 RFC 6455 4.1 대로 PROTOCOL_ERROR 로 끝난다 (요청하지 않은 값). 필요해지면 그때 인자를 더한다.

6. 한 표, 한 Session

statemachine 설계 11절의 결정 (한 표, 한 Session, Session 의 Stage 하나를 body 와 메시지가 같이 쓴다) 을 Endpoint 둘에 펼친 것이다. WebSocket 행은 한 벌만 정의하고 두 표가 같이 쓴다 (결정 8).

HttpServerServerHTTP 요청 행 전부 + WebSocket 행HttpSession. Upgrade 뒤 같은 Session 이 WebSocket 상태를 든다. 역할 값 = 서버 (받은 frame 의 mask 를 검사하고 벗긴다, 보내는 frame 에 mask 없음)

  • HTTP body 와 WebSocket 메시지가 같은 Stage 를 쓴다. Upgrade 요청에는 body 가 없고 (있으면 400), 101 뒤에는 HTTP 가 없으므로 한 연결에서 둘이 겹치는 순간이 없다. max_body_bytes 를 넘는 메시지는 1009 로 닫는다.
  • 수신 frame 의 payload 는 receive_capacity 조각으로 읽어 Stage 에 붙인다 (user_guide 8절). 조각마다 unmask 의 key offset 을 Session 이 든다.
  • 송신 frame (pong / ping / closeWebSocket 과 pong 늦음의 close / 사용자 send) 은 push lane 이고, frame 머리 (2 ~ 14 바이트) + payload 를 한 번에 넣는다. NotificationDesk 가 머리와 payload 를 한 lock 안에서 이어 복사하고, 전부 들어가지 않으면 하나도 넣지 않는다 (http 설계 2.1). 클라이언트는 mask 를 desk 에 맡기지 않고 자기 push 에서 씌운다 (아래 W4).
  • 구현에서 정한 것 (W3, 2026-11-12). (1) 받은 frame 때문에 우리가 닫을 때 (1002 / 1007 / 1009, 상대 close 에 대한 답) 의 close frame 은 write lane 이다. close 를 하면 base 가 소켓을 바로 shutdown 하고 push lane 의 남은 것은 나가지 않으므로, Session 의 작은 버퍼 (131 바이트) 에서 write lane 으로 보내고 WRITTEN 뒤에 닫는다 (SocketClosing 상태). (2) pong 이 늦으면 1001 close frame 을 push lane 에 넣고 닫힘 플래그를 세운 뒤 같은 read 를 close_timeout 으로 다시 건다. TIMEOUT 행 안에서는 read 가 걸려 있어 write 를 걸 수 없다 (base 가 BUSY). 상대가 답하면 onClose(SUCCESS, 상대 status), 아니면 onClose(TIMEOUT, 1001). (3) 위 흐름의 WebSocketClosing 은 따로 된 상태가 아니다. 닫힘 플래그가 서 있으면 같은 frame 읽기 상태에서 read 의 timeout 만 close_timeout 이 된다. (4) 101 을 만들 때 generation 을 올리므로 onUpgrade 의 handle 과 onOpen 의 handle 은 다르다. (5) WebSocket 경로는 라우트 표에 GET 하나로 들어 OPTIONS 는 자동 204, GET / HEAD / OPTIONS 밖은 자동 405 (Allow: GET, HEAD, OPTIONS) 이고, HEAD 만 Upgrade 검사의 405 (Allow: GET) 다.
  • 구현에서 정한 것 (W4, 2026-11-13). (1) 클라이언트의 mask 는 push lane 안에서 씌운다. base 의 desk 는 조각을 그대로 복사하므로, WebSocketClient 가 push_capacity 크기의 scratch 버퍼 (initialize 때 한 번) 를 mutex 로 지키며 mask 한 frame 을 만들어 한 조각으로 notify 한다. base 는 바뀌지 않는다. (2) mask key 는 frame 마다 splitmix64 (std::random_device seed), write lane 의 close frame 은 시계에서 만든 key. Sec-WebSocket-Key 는 run 마다 std::random_device 16 바이트. (3) 역할 값은 Session 이 아니라 HttpSite::role 이다 (사이트 하나가 한 역할). (4) 클라이언트도 연결마다 generation 을 올린다. (5) await 는 onOpen 이 나가면 SUCCESS, 그 전에 run 이 끝나면 run 의 반환값. (6) run 의 반환값: 핸드셰이크 실패는 PROTOCOL_ERROR, 101 이 header_timeout 안에 없으면 TIMEOUT, close 는 CLOSED, 그 밖에 끊기면 PEER_CLOSED (close handshake 를 마친 정상 종료 포함).
  • onMessage 의 data 는 Stage 를 가리키고 return 하면 무효다 (Stage 를 비운다). TEXT 는 UTF-8 검사를 지나지 않으면 1007.

7. 다른 thread 의 send 와 close

send 는 notify 라 끝이다 (push lane 에 복사, IO thread 의 drain 이 보낸다).

close 를 다른 thread 에서 부르는 경우: 게임 서버의 로직 thread 가 한 플레이어를 내보낼 때, 인증 토큰이 만료되어 타이머 thread 가 끊을 때, 다른 세션의 로그아웃이나 관리자 명령으로 특정 소켓을 닫을 때. 서버 전체를 닫는 것 (closeHttpServer) 은 base 의 close 길이라 여기에 들지 않는다. WebSocket 에는 Work 가 없어서 "Work 를 돌려주며 닫기" 는 없다.

  1. closeWebSocket(handle, status, reason) (아무 thread): Session 의 닫힘 플래그 (std::atomic<uint16_t> 에 status, 0 이면 열림) 를 CAS 로 세운다. 이미 세워져 있으면 BUSY. 그 뒤 close frame 을 push lane 에 넣는다. 돌아온 뒤의 send 는 플래그를 보고 CLOSED.
  2. IO thread 는 따로 깨어나지 않는다. 다음에 그 연결의 행이 돌 때 플래그를 본다 (6절의 흐름):
    • 상대는 close frame 을 받으면 곧 close frame 으로 답한다 (RFC 6455 5.5.1). 그 READ 가 close frame 이고 플래그가 서 있으므로 "우리가 시작한 close 의 답" 이다 → thenClose(SUCCESS).
    • 그 사이에 온 데이터 frame 은 onMessage 로 넘기지 않고 버린다 (close 를 보낸 뒤라 앱은 더 받을 생각이 없다).
    • 상대가 답하지 않고 아무것도 보내지 않으면 걸려 있던 read 의 timeout (ping_interval) 이 와서 TIMEOUT 행이 플래그를 보고 close(TIMEOUT).
  3. CLOSED 행이 onClose.

IO thread 콜백 (onMessage) 안에서 부른 close 는 같은 플래그를 세우고, 콜백이 돌아온 뒤 행이 플래그를 보고 바로 { WebSocketClosing, thenRead(2, close_timeout) } 로 간다.

첫 판은 "drain 이 close frame 을 보낸 직후 상태를 Closing 으로 옮기는 훅" (Handler::afterDrain) 을 두려 했다. 상태를 바로 옮기지 않아도 위처럼 READ / TIMEOUT 행이 플래그를 보면 같은 결과가 나오므로 뺐다 (결정 3). 차이는 하나: 다른 thread 의 close 에서 상대가 끝까지 답하지 않으면 끊기기까지 close_timeout 이 아니라 걸려 있던 read 의 남은 시간 (최대 ping_interval) 이 걸린다 (결정 9).

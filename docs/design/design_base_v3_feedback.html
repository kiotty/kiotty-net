1. Codec 대신 TlsProfile + TlsPipe 동의

맞다. v2 의 Codec 은 "Connection 에 if (tls) 를 한 줄도 두지 않는다" 를 얻으려고 가상 인터페이스 + Holder + 구현 둘을 더했다. 분기 네 줄을 없애려고 클래스 셋을 더한 것이니 더 복잡해졌다는 지적이 맞다. 구체 클래스 둘로 간다.

TlsProfileTlsPipe
무엇SSL_CTX 하나. 인증서, key, 허용 버전, 검증 방식, handshake timeout연결 하나의 SSL + memory BIO 둘 + cipher Stage 둘
누가 몇 개소유자 (Server, EventClient, StreamClient) 가 하나Connection 과 StreamClient 가 하나씩. Connection 생성자에서 메모리를 잡는다

{
public:

enum class HandshakeStep : uint8_t { MORE, DONE, FAILED };

class TlsPipe                                   // tls/kiotty_tls_pipe.h
{
public:
    explicit TlsPipe(size_t cipher_capacity);  // 0 이면 평문 연결. Stage 를 잡지 않는다
    ~TlsPipe();

    KiottyNetCode open(TlsProfile& profile, const char* hostname);   // SSL_new (처음) 또는 SSL_clear (재사용). 서버는 accept state, 클라이언트는 connect state + SNI

    Stage&        cipherSend();                 // socket 으로 나갈 바이트. handshake 메시지와 암호문이 같은 Stage 에 쌓인다

    HandshakeStep handshake();                  // cipherReceive → rbio, SSL_do_handshake, wbio → cipherSend

    Result<KiottyNetCode, size_t> encode(Segment plain);   // SSL_write → cipherSend. 옮긴 plain 길이

private:
    void* _ssl;
    Stage _cipher_receive;
    Stage _cipher_send;
};

2. handshake 를 Phase 로 돈다 부분 동의

주신 흐름 일곱 줄을 하나씩 받았다. 여섯 줄은 그대로고, "handshake 용 read / write 를 다른 모양의 IoAction 으로 내보내고 IoCompletion 에서 식별한다" 한 줄만 다르게 하고 싶다.

주신 흐름답
onConnected 가 끝난 뒤 ActiveSocket 에 대해 Connection 을 생성한다 [공통]동의 Connection 객체는 pool 에 미리 있으므로 "생성" 은 connection.open(socket, context, profile) 이다. 서버는 ACCEPT 완료에서, 클라이언트는 동기 connect 뒤 run 안에서 같은 함수를 부른다
KIOTTY_NET_USE_TLS 면 Connection 이 handshake state 를 보관하는 context 를 가진다동의 그것이 TlsPipe 다. 다만 TLS 1.2 / 1.3 의 메시지 상태는 우리가 들지 않는다 (2.1)

IoAction 에 따라 다음 read / write 를 건다. handshake 용은 다른 구성의 IoAction 으로 내보내 IoCompletion 에서 구분한다부분 동의 구분은 하되 completion 이 아니라 Connection 의 phase 로 한다 (2.3)

handshake 중 오류면 onError부분 동의 onError 에 더해 onDisconnected 도 낸다 (2.4)
마지막 단계에 다다르면 onReady, 그 action 으로 정상 통신동의

2.2 stepHandshake 가 돌려주는 IoAction 은 기존 kind 셋이다

enum class Phase : uint8_t { FREE, HANDSHAKING, READY, CLOSING };   // CLOSING : 닫았지만 늦은 완료를 기다린다 (4절 Phase 6)

IoAction Connection::onOpened(const Handler& handler)                 // open 직후 한 번. IO Thread
{
    if (!_tls.active()) { _phase = Phase::READY; return handler.onReady(_context, handle()); }
    _phase = Phase::HANDSHAKING;
    return stepHandshake(handler);                                      // 클라이언트는 여기서 ClientHello 가 cipherSend 에 생긴다. 서버는 MORE
}

IoAction Connection::stepHandshake(const Handler& handler)            // HANDSHAKING 의 receive 완료마다
{
    switch (_tls.handshake())
    {
    case HandshakeStep::MORE:   return IoAction::hold(_tls_profile->handshakeTimeoutMs());   // 받기는 늘 걸려 있고, cipherSend 는 SUBMIT 이 보낸다
    case HandshakeStep::DONE:   _phase = Phase::READY; return handler.onReady(_context, handle());
    case HandshakeStep::FAILED: handler.onError(_app_context, KIOTTY_PROTOCOL_ERROR, "tls handshake failed");
                                return IoAction::close(KIOTTY_PROTOCOL_ERROR);
    }
}
  • MORE 가 HOLD 인 이유. "다음 바이트를 기다린다, 한도는 handshake_timeout" 이 HOLD 의 뜻 그대로다. HOLD 의 timeout 이 만료되면 SCAN 이 onDeadline 을 부르는데, HANDSHAKING 이면 onTimeout 대신 onError + close(KIOTTY_TIMEOUT) 다 (5절 표). handshake 전용 deadline 변수가 없어진다.
  • 보낼 것을 action 으로 표현하지 않는 이유. handshake 가 만든 바이트는 사용자의 WRITE 와 다르다. onWritten 이 나가면 안 되고, write lane 을 거치지도 않는다. cipherSend 에 쌓이고 SUBMIT 이 보내면 끝이라 action 이 필요 없다. 2.1 의 세 경우도 같은 길이다.
  • 그래서 IoActionKind 는 v2 의 여섯 개 (NONE, HOLD, READ, READ_UNTIL, WRITE, START_WORK, CLOSE 중 NONE 과 HOLD 는 timeout 0 / 양수의 차이라 하나로 봐도 된다) 그대로다. HANDSHAKE_READ / HANDSHAKE_WRITE 같은 kind 는 넣지 않는다.

2.3 식별은 completion 이 아니라 phase 로

"handshake 의 완료를 평소의 완료와 다른 로직으로 처리한다" 는 목표에 동의한다. 다른 점은 그 분기의 열쇠를 어디에 두느냐다.

A. IoCompletion 에 handshake 표시 (걸 때 kind 를 다르게)B. Connection 의 _phase (받을 때 지금 상태를 본다. 추천)
누가 TLS 를 알게 되나EventListener 와 IoEvent. "이 recv 는 handshake 용" 을 들어야 한다. event 층이 tls 를 안다Connection 만. event 층은 바이트만 옮긴다
늦게 온 완료IOCP 는 완료가 늦게 올 수 있다. HANDSHAKE kind 로 건 recv 가 DONE 뒤에 도착하면 그 바이트 (NewSessionTicket 또는 첫 application data) 를 어디로 보내나. kind 가 거짓말이 된다도착 시점의 phase 가 진실이다. READY 면 decode 로 간다
recv 를 거는 자리handshake 중과 뒤에 다른 함수로 건다하나. "receiveStage 에 자리가 있으면 건다"
결과같다. onReceived 안에서 HANDSHAKING 과 READY 가 다른 함수로 간다
IoAction Connection::onReceived(SocketCode code, size_t length, const Handler& handler)
{
    _receive_pending = false;
    if (_phase == Phase::CLOSING) return IoAction::none();                        // 닫은 뒤 늦게 온 완료. pending 만 끈다
    if (code != SocketCode::SUCCESS || length == 0) return onPeerGone(code);     // 2.5
    receiveStage().provider().commit(length);
    switch (_phase)
    {
    case Phase::HANDSHAKING: return stepHandshake(handler);                     // 2.2. 다른 함수
    case Phase::READY:       if (_tls.active()) _tls.decode(_recv_stage);        // 1.2 의 두 번째 줄. plain 이 0 바이트일 수 있다
                             return pump(handler);                              // 조건이 차면 onRead 한 번
    }
}

2.4 handshake 실패는 onError 와 onDisconnected 둘 다

onConnected 가 connection_context 를 만들어 줬으므로, 그 연결이 어떻게 끝나든 onDisconnected(app_context, connection_context, handle, reason) 이 한 번 나가야 사용자가 context 를 돌려받는다. handshake 실패도 예외가 아니다. onError 는 그 위에 이유를 더 주는 것이다.

실패onError 의 code, messageonDisconnected 의 reason
인증서 검증 실패, 버전 / cipher 불일치KIOTTY_PROTOCOL_ERROR, "tls handshake failed"KIOTTY_PROTOCOL_ERROR

3. WorkContext 동의

Work 의 상태와 결과를 Connection 안의 클래스 하나로 모은다. 세 단계가 세 메서드고 각각 부르는 thread 가 정해져 있다.

start() IO Thread IDLE ──▶ WORKING START_WORK action 이 apply 될 때. 그 뒤 onWorkStarted finish() worker WORKING ─▶ DONE IoAction 을 _outcome 에 넣고 CAS. 그 뒤 listener.wake() onFinished() IO Thread DONE ──▶ IDLE SCAN 이 DONE 을 보면 _outcome 을 꺼내 apply 로 넘긴다
class WorkContext                               // connection/kiotty_work_context.h. Connection 의 멤버
{
public:
    enum class State : uint8_t { IDLE, WORKING, DONE };

    WorkContext();

    // IO Thread
    void          start(int32_t generation);                 // IDLE → WORKING. generation 을 기억한다
    bool          finished() const;                          // SCAN 이 본다. _state.load(acquire) == DONE
    IoAction      onFinished();                              // DONE → IDLE. _outcome 을 돌려준다
    bool          working() const;                           // WORKING 또는 DONE. 콜백을 내면 안 되는 구간
    void          reset();                                   // close 때. IDLE 로

    // 아무 thread (worker)
    KiottyNetCode finish(int32_t generation, IoAction outcome);   // generation 이 다르면 KIOTTY_PEER_CLOSED. WORKING 이 아니면 KIOTTY_BUSY.
                                                                  // _outcome = outcome 뒤 CAS WORKING → DONE (release)
    bool          matches(int32_t generation) const;         // isWorkConnected 의 절반. 나머지 절반은 Connection::_peer_closed

private:
    std::atomic<State> _state;
    int32_t            _generation;
    IoAction           _outcome;
};
  • 메모리 순서. worker 는 _outcome 을 쓴 뒤 _state 를 release 로 DONE 으로 바꾼다. IO Thread 는 _state 를 acquire 로 읽어 DONE 을 본 뒤에만 _outcome 을 읽는다. 그래서 _outcome 자체는 atomic 이 아니다.
  • finish 가 WRITE 면 worker 가 write lane 에 복사하는 것은 v2 6절 그대로다. 그 복사는 Connection::finishWork 가 _work.finish 를 부르기 전에 한다. 순서: lane 복사 → _work.finish (release) → wake. IO Thread 가 DONE 을 본 시점에 lane 은 차 있다.
  • peer 가 Work 중에 끊으면 _peer_closed 만 세우고 콜백은 안 낸다. Connection::onWorkFinished 는 _peer_closed 면 outcome 을 버리고 IoAction::close(KIOTTY_PEER_CLOSED) 를 돌려준다. 그래서 SCAN 의 한 줄은 apply(c, c.onWorkFinished()) 다.
  • 소유자 close 는 WORKING 인 연결도 바로 닫고 generation 을 올린다. 늦게 온 finish 는 matches 가 거짓이라 PEER_CLOSED 로 끝난다. 이것은 progress 문서의 규칙 그대로다.

Connection 에서 지워지는 것: _work_state, _work_outcome, _saved_read, _saved_deadline, takeWorkOutcome, tryEnterWork, tryStartWork. 남는 것은 WorkContext _work 하나와 std::atomic<bool> _peer_closed 다.

4. IoLoop 한 바퀴 : 여섯 Phase 의 pipeline

한 바퀴를 여섯 phase 로 자른다. 각 phase 는 앞 phase 의 output 을 input 으로 받고, 자기 output 을 Connection 의 상태에 남긴다. 두 묶음이 서로를 모른다. 콜백이 나가는 phase (DISPATCH, SCAN, APPLY) 는 EventListener 를 부르지 않고, OS 에 거는 phase (WAIT, SUBMIT) 는 콜백을 내지 않는다. 둘 사이에 있는 것은 Connection 의 상태뿐이다.

큰 동작 ┌────────┐ ┌──────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │ 1 WAIT │───▶│2 DISPATCH│───▶│ 3 SCAN │───▶│5 SUBMIT│───▶│6 SETTLE│ └────────┘ └──────────┘ └────────┘ └────────┘ └────────┘ deadline completion connection connection host → completions → IoAction → IoAction → OS 요청 → slot 반납, stopped │ │ ▼ ▼ ┌──────────────────────┐ │ 4 APPLY │ (Connection, IoAction) → Connection 상태 └──────────────────────┘ 누가 무엇을 만지나 EventListener : 1, 5 만 handler 콜백 : 2, 3, 4 만 Connection : 2, 3, 4 가 쓰고 5, 6 이 읽는다
void IoLoop::runOnce()
{
    Span<const IoCompletion> completions = wait();                 // 1
    for (const IoCompletion& completion : completions)
        dispatch(completion);                                      // 2 (안에서 4)
    scan(monotonicMs());                                           // 3 (안에서 4)
    submit();                                                      // 5
    settle();                                                      // 6
}

Phase 1. WAIT

Span<const IoCompletion> IoLoop::wait()
{
    uint32_t timeout_ms = nearestDeadline(monotonicMs());          // READY / HANDSHAKING 연결의 _deadline 중 최소. 없으면 무한
    return _listener.wait(timeout_ms);                             // TIMEOUT 이면 빈 Span. 그래도 SCAN 은 돈다
}

작은 동작 하나다. 즉시 실패한 submit (5절) 도 EventListener 가 완료 하나로 바꿔 여기서 돌려주므로, 완료가 들어오는 길은 이 함수 하나다.

Phase 2. DISPATCH : completion → action

void IoLoop::dispatch(const IoCompletion& completion)
{
    switch (completion.kind)
    {
    case IoKind::WAKE:    drainPushSlots();                                                   return;   // 2a
    case IoKind::ACCEPT:  admit();                                                            return;   // 2b
    case IoKind::RECEIVE: { Connection& c = _host.at(completion.slot);
                            apply(c, c.onReceived(completion.code, completion.length, handler()));  return; }   // 2c
    case IoKind::SEND:    { Connection& c = _host.at(completion.slot);
                            apply(c, c.onSent(completion.code, completion.length));          return; }   // 2d
    }
}

2a. WAKE → push lane

void IoLoop::drainPushSlots()                                      // input: FILLED 인 PushSlot. output: push lane 에 복사, 호출자 풀어 줌
{
    for (PushSlot& slot : _slots)
    {
        if (slot.state.load() != PushSlot::FILLED) continue;
        slot.code = slot.broadcast ? _host.broadcast(slot.data) : _host.notify(slot.target, slot.data);
        slot.release();                                            // DONE + cv.notify. 호출자가 돌아간다
    }
}

WAKE 는 finishWork 와 close 도 보내지만 그 둘은 여기서 할 일이 없다. finishWork 의 결과는 SCAN 3a 가, close 는 run 의 while 조건이 본다. 깨우기만 하면 된다.

2b. ACCEPT → Connection 하나

void IoLoop::admit()                                               // input: 완료된 accept. output: 열린 Connection 또는 닫힌 socket
{
    Result<SocketCode, ActiveSocket> accepted = _acceptor->accept();
    if (!accepted) { handler().onError(_app_context, toNetCode(accepted.code()), "accept failed"); return; }

    Connection& c = *_host.acquire();                              // accept 는 빈 slot 이 있을 때만 걸었다 (5c). nullptr 이 아니다
    KiottyNetConnectionDecision decision = handler().onConnected(_app_context, c.handle(), accepted.value().peer());
    if (!decision.accepted) { accepted.value().close(); _host.release(c); return; }

    c.open(std::move(accepted.value()), decision.connection_context, _tls_profile);   // generation 증가. TLS 면 _tls.open
    apply(c, c.onOpened(handler()));                               // 2.2. 평문: onReady 의 action. TLS: HOLD (서버) 또는 HOLD + ClientHello (클라이언트)
}

EventClient 는 accept 가 없으므로 run 이 동기 connect 뒤에 같은 네 줄 (acquire → onConnected → open → apply(onOpened)) 을 loop 시작 전에 한 번 한다. 함수를 admit(ActiveSocket&&) 으로 두고 둘이 같이 쓴다.

2c, 2d. RECEIVE / SEND → Connection 의 hook

2c 의 onReceived 는 2.3 에 있다. 2d:

IoAction Connection::onSent(SocketCode code, size_t length)
{
    _send_pending = false;
    if (_phase == Phase::CLOSING) return IoAction::none();         // 닫은 뒤 늦게 온 완료. pending 만 끈다
    if (code != SocketCode::SUCCESS) return onPeerGone(code);
    advanceSend(length);                                           // 보내던 구간 전진. write lane 의 메시지가 다 나갔으면 _written = 길이, _sending = NONE
    return IoAction::none();                                       // onWritten 은 SCAN 3c 에서. 이 바퀴의 다른 콜백 뒤에 낸다
}

IoAction Connection::onPeerGone(SocketCode code)                   // RECEIVE 의 0 바이트 / 오류, SEND 의 오류
{
    if (_work.working()) { _peer_closed.store(true); return IoAction::none(); }   // Work 중엔 기록만. onWorkFinished 가 닫는다
    return IoAction::close(code == SocketCode::CLOSED ? KIOTTY_PEER_CLOSED : KIOTTY_SOCKET_ERROR);
}

Phase 3. SCAN : 완료 없이 생기는 세 가지

void IoLoop::scan(uint64_t now)
{
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& c = _host.at(i);
        if (!c.alive()) continue;                                  // FREE, CLOSING 은 건너뛴다
        if (c.workFinished())          apply(c, c.onWorkFinished());             // 3a  worker 가 남긴 outcome
        if (c.deadlineExpired(now))    apply(c, c.onDeadline(handler()));        // 3b  READY: onTimeout 의 action. HANDSHAKING: onError + CLOSE
        if (c.hasWritten())            apply(c, c.onWritten(handler()));         // 3c  onWritten 의 action
    }
}

세 가지가 한 phase 에 있는 이유는 셋 다 "completion 이 아닌 것에서 비롯되는 action" 이기 때문이다. 3a 는 다른 thread 의 CAS, 3b 는 시계, 3c 는 "이 바퀴의 콜백이 다 돌아온 뒤" 라는 순서 규칙 (구현 가이드 1.6). 셋 모두 Connection 의 플래그 하나를 읽고 hook 하나를 부른다. WORKING 인 연결은 3b, 3c 가 거짓이다 (deadline 멈춤, write lane 은 worker 것).

IoAction Connection::onWorkFinished()                              // 3a
{
    IoAction outcome = _work.onFinished();                         // DONE → IDLE
    if (_peer_closed.load()) return IoAction::close(KIOTTY_PEER_CLOSED);
    return outcome;                                                // READ / READ_UNTIL / WRITE / CLOSE. WRITE 면 lane 은 worker 가 이미 채웠다
}

IoAction Connection::onDeadline(const Handler& handler)            // 3b
{
    _deadline = 0;
    if (_phase == Phase::HANDSHAKING) { handler.onError(_app_context, KIOTTY_TIMEOUT, "tls handshake timeout"); return IoAction::close(KIOTTY_TIMEOUT); }
    return handler.onTimeout(_context, handle());
}

IoAction Connection::onWritten(const Handler& handler)             // 3c
{
    size_t length = _written; _written = 0;
    return handler.onWritten(_context, handle(), length);
}

Phase 4. APPLY : (Connection, IoAction) → Connection 상태

DISPATCH 와 SCAN 이 만든 action 이 Connection 에 들어가는 유일한 문 이다. 콜백의 return, worker 의 outcome, onTimeout 의 return 이 전부 여기를 지난다. 재귀가 아니라 loop 다. READ 가 이미 쌓인 데이터로 바로 충족되면 onRead 가 또 action 을 내므로, 그것을 같은 loop 의 다음 회차로 돈다.

void IoLoop::apply(Connection& c, IoAction action)
{
    for (;;)
    {
        switch (action.kind)
        {
        case IoActionKind::NONE:
        case IoActionKind::HOLD:       c.hold(action.timeout_ms);                      return;   // read 조건 없음. deadline 만 (0 이면 없음)
        case IoActionKind::READ:
        case IoActionKind::READ_UNTIL: c.setRead(action);                              break;    // 조건 + deadline 등록. 아래 pump 로
        case IoActionKind::WRITE:    { KiottyNetCode code = c.write(action.as.write.data, action.timeout_ms);   // write lane 에 복사
                                       if (code == KIOTTY_SUCCESS) return;             // 보내기는 SUBMIT 5b 가
                                       action = IoAction::close(code); continue; }     // BUSY (onWritten 전 write) / BUFFER_FULL
        case IoActionKind::START_WORK: c.startWork();                                  // _work.start(generation). 이 뒤 콜백 없음
                                       handler().onWorkStarted(c.context(), c.workHandle()); return;
        case IoActionKind::CLOSE:      close(c, action.as.close.reason);               return;
        }
        action = c.pump(handler());                                // 조건이 찼으면 onRead 한 번, 그 return. 아니면 NONE
    }
}

void IoLoop::close(Connection& c, KiottyNetCode reason)
{
    KiottyNetConnectionContext context = c.context();
    PoolHandle                 handle  = c.handle();
    c.close();                                                     // shutdown + close, _phase = CLOSING, _work.reset(). 걸린 IO 는 완료로 돌아와 pending 을 끈다
    handler().onDisconnected(_app_context, context, handle, reason);   // onConnected 가 accept 한 연결은 반드시 한 번
}

apply 가 EventListener 를 부르지 않는 것이 요점이다. WRITE 는 lane 에 복사만 하고, READ 는 조건만 걸고, CLOSE 는 socket 만 닫는다. "그래서 OS 에 무엇을 걸어야 하나" 는 다음 phase 가 Connection 의 상태를 읽어 결정한다. 그 덕에 apply 안에서 콜백이 또 콜백을 내는 재진입이 구조적으로 없다.

Phase 5. SUBMIT : Connection 상태 → OS 요청

void IoLoop::submit()
{
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& c = _host.at(i);
        if (!c.alive()) continue;

        Stage::Provider& space = c.receiveStage().provider();                               // 5a 받기. 1.2 의 첫 줄
        if (!c.receivePending() && space.writable() > 0)
            c.markReceivePending(_listener.submitReceive(receiveEvent(i), c.socket(), space));

        Segment segment = c.nextSendSegment();                                              // 5b 보내기. 1.2 의 셋째 줄. TLS 면 여기서 encode
        if (!c.sendPending() && !segment.empty())
            c.markSendPending(_listener.submitSend(sendEvent(i), c.socket(), segment));
    }
    if (_acceptor && !_acceptor->pending() && _host.hasFreeSlot())                           // 5c accept. slot 이 없으면 걸지 않는다 (backlog 가 받는다)
        _acceptor->submit(_listener);
}
  • 조건 셋뿐이다. "받을 자리가 있고 안 걸려 있으면 받는다", "보낼 것이 있고 안 걸려 있으면 보낸다", "빈 slot 이 있고 안 걸려 있으면 accept 한다". action 의 kind 를 보지 않는다. READ 가 걸렸는지, handshake 중인지, Work 중인지 (WORKING 중에도 recv 는 계속 걸고 push lane 은 보낸다) 를 몰라도 된다. 그 모든 것이 Connection 상태 (받을 자리, 보낼 구간) 로 환원돼 있기 때문이다.
  • 2.1 의 TLS 세 경우 가 자동으로 처리되는 자리다. handshake 가 끝나며 남긴 NewSessionTicket, decode 중 생긴 KeyUpdate 답장이 모두 cipherSend 에 있고, 5b 는 "비어 있지 않으면 보낸다" 만 한다.
  • 즉시 실패 (submit 이 PENDING 이 아닌 것) 는 EventListener 가 자기 완료 배열에 오류 완료 하나를 넣고 다음 wait 가 돌려준다. 그래서 SUBMIT 은 콜백을 내지 않고, pending 표시는 늘 true 로 끝난다.
Segment Connection::nextSendSegment()
{
    Segment plain = laneSegment();                                 // 구현 가이드 1.6 의 pickSegment. 보내던 lane 끝까지, 경계에서 교체, write 먼저, WORKING 이면 push 만
    if (!_tls.active()) return plain;
    if (!plain.empty()) advanceLane(_tls.encode(plain).value());   // plain → cipherSend. 자리가 없으면 0 바이트 옮긴다
    return _tls.cipherSend().consumer().segment();
}

Phase 6. SETTLE

void IoLoop::settle()
{
    for (size_t i = 0; i < _host.capacity(); ++i)
    {
        Connection& c = _host.at(i);
        if (c.phase() == Phase::CLOSING && !c.receivePending() && !c.sendPending())
            _host.release(c);                                      // CLOSING → FREE. 늦게 올 완료가 더 없을 때만 slot 을 돌려준다
    }
    if (_stop_when_empty && _host.empty()) _stopped = true;        // EventClient
}

slot 반납을 close 가 아니라 여기서 하는 이유는 IOCP 다. 닫은 socket 에 걸려 있던 receive / send 는 ERROR_OPERATION_ABORTED 완료로 돌아온다. slot 을 바로 재사용하면 그 늦은 완료가 새 연결의 것으로 보인다. "pending 이 0 이 될 때까지 CLOSING" 으로 두면 completion 에 generation 을 싣지 않아도 된다. epoll 은 늦은 완료가 없어 같은 바퀴에 FREE 가 된다.

5. Connection 의 hook 표

v2 7절의 규칙 1 "모든 hook 은 IoAction 을 돌려준다" 를 지킨 목록이다. 콜백이 안 나간 hook 은 NONE 을 돌려준다. 이 밖에 IoLoop 가 부르는 것은 상태 조회 (alive, phase, workFinished, deadlineExpired, hasWritten, receivePending, sendPending) 와 상태 변경 (open, close, hold, setRead, write, startWork, mark*Pending) 뿐이다.

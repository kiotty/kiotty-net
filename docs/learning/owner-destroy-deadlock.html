Owner destroy 의 교착 : 언제 멈추고 어떻게 풀까

2026-11-09. 7단계 (커밋 42e09a1) 의 Context::destroy 와 Context::release 가 멈출 수 있는 경우를 정리한 노트다. 1 ~ 2절은 지금 코드가 무엇을 기다리는지, 3절은 멈추는 경우 넷, 4절은 고칠 길, 5절은 추천이다.

1. destroy 가 기다리는 것

지금 destroy 는 세 단계를 Context mutex 를 쥔 채 한 번에 한다 (context/kiotty_context.cpp).

Context::destroy(server)
  lock(Context::_mutex)                    ← 여기서부터
    _servers.release(server)
      Server::reset()
        close()        : loop 에 stop 을 걸고 listener 를 깨운다
        _gate.join()   : run() 이 돌아올 때까지 잔다      ← 기다림
        _loop.reset(), _listener.close(), _profile.close()
  unlock                                   ← 여기까지

Context::release 도 같다. 풀 셋의 clear() 가 ACTIVE 인 Owner 마다 reset() 을 부르므로, 실행 중인 Owner 모두의 run 이 끝날 때까지 mutex 를 쥐고 잔다.

2. run 이 끝나려면 무엇이 필요한가

stop 이 걸린 IoLoop 은 바로 끝나지 않는다. IoLoop::shutdown 이 모든 연결에 close 를 건 다음, 풀이 빌 때까지 바퀴를 더 돈다 (kiotty_io_loop.cpp 의 while (!parts.host.empty() || ...)).

연결 칸은 두 조건이 모두 맞아야 비워진다.

  • OS 에 걸어 둔 읽기 / 쓰기가 모두 돌아왔다 (취소 완료 포함).
  • Work 로 worker 에 넘어간 연결이면, worker 가 KiottyNet_closeConnectionStream 을 불렀다. 테스트 ServerCloseWaitsForWorkerCloseStream 이 이 동작을 확인한다.

또 연결을 닫을 때 loop thread 가 사용자 콜백 (onDisconnected 등) 을 부른다. 콜백이 돌아와야 loop 가 다음 걸음으로 간다.

정리하면 destroy 를 부른 thread 는 Context mutex 를 쥔 채 아래 둘을 기다린다.
  1. loop thread 가 부르는 콜백이 모두 돌아오는 것
  2. Work 를 받은 worker 모두가 closeConnectionStream 을 부르는 것
둘 중 누구라도 Context mutex 를 원하거나 destroy 하는 thread 자신이면 영원히 멈춘다.

3. 멈추는 경우 넷

3.1 worker 가 closeStream 전에 Context 를 부른다 (thread 둘)

thread A                               worker W (Server S 의 연결 하나를 Work 로 받음)
────────                               ────────
destroy(S)
  lock(mutex)  ✔
  S.reset → join … W 의 closeStream 을 기다림
                                       createEventClient(...)   // 받은 요청을 다른 서버로 전달하려고
                                         lock(mutex) … A 를 기다림
                                       closeConnectionStream(...)  // 여기까지 못 감

A 는 W 를, W 는 A 를 기다린다. W 가 부르는 것이 create 든 다른 Owner 의 destroy 든 Context mutex 를 쓰면 같다.

3.2 loop thread 의 콜백이 Context 를 부른다 (thread 둘, Work 없이도)

thread A                               loop thread of S
────────                               ────────────────
destroy(S)
  lock(mutex)  ✔
  S.reset → join … run 이 끝나기를 기다림
                                       shutdown 중 onDisconnected 콜백
                                         destroy(어떤 EventClient)   // 연결이 끊기면 짝 클라이언트도 정리
                                           lock(mutex) … A 를 기다림

Work 를 쓰지 않는 사용자도 걸린다. 콜백 안에서 다른 Owner 를 만들거나 지우는 것은 흔한 사용법이라 3.1 보다 더 자주 생길 수 있다.

3.3 자기 자신을 destroy 한다 (thread 하나)

  • 콜백 안에서 자기 Server 를 destroy: loop thread 가 join 으로 자기 run 이 끝나기를 기다린다. run 은 이 콜백이 돌아와야 끝난다.
  • worker 가 closeStream 전에 그 Server 를 destroy: join 이 worker 자신의 closeStream 을 기다린다.

이 경우는 mutex 와 상관없다. mutex 밖에서 join 해도 멈춘다.

3.4 release 가 위 셋을 모두 가진다

KiottyNet_releaseContext 는 실행 중인 Owner 모두를 차례로 reset 한다. 위 세 경우가 Owner 어느 하나에서라도 생기면 멈춘다. 프로그램 끝에서 부르는 함수라 종료가 멈춘 채로 남는다.

3.5 정리

경우필요한 것mutex 를 join 밖으로 빼면
3.1 worker 가 Context 호출Work, 다른 thread 의 destroy풀린다
3.2 콜백이 Context 호출다른 thread 의 destroy풀린다
3.3 자기 destroy (콜백)콜백 안의 destroy(자기)안 풀린다
3.3 자기 destroy (worker)closeStream 전의 destroy(자기)안 풀린다
3.4 release위 어느 것이든3.1, 3.2 몫은 풀린다

4. 고칠 길

4.1 destroy 를 두 번에 나눈다 (join 을 mutex 밖으로)

destroy(S)
  lock    : 칸 상태 ACTIVE → CLOSING   (create 가 이 칸을 못 잡는다)
  unlock
  S.close(); S.join()                  (mutex 없이 기다린다)
  lock    : S.reset(), 칸 상태 CLOSING → RETIRED
  unlock
  • 3.1, 3.2 가 풀린다. 기다리는 동안 다른 thread 가 Context 를 자유롭게 쓴다.
  • 같은 Owner 를 두 thread 가 동시에 destroy 하면, 두 번째는 CLOSING 을 보고 바로 돌아간다 (assert 로 잡는다).
  • 바뀌는 곳: LazyReusablePool 에 SlotState::CLOSING 과 retire / finish 두 단계, Context::destroy 셋, release. release 는 "모두 CLOSING 으로, unlock, 모두 close, 모두 join, lock, clear" 로 바뀐다. 모두에 먼저 close 를 걸고 join 하므로 Owner 여럿을 차례로 기다리던 지금보다 빨리 끝난다.

4.2 loop thread 의 자기 destroy 는 미룬다

IoLoop::isIoThread() 가 이미 있다. destroy 를 부른 thread 가 그 Owner 의 loop thread 면 join 하지 않고 "run 이 끝나면 칸을 돌려준다" 표시만 하고 돌아간다. run 의 마지막 (leave) 이 표시를 보고 칸을 RETIRED 로 돌린다.

  • libuv 의 uv_close 도 같은 모양이다. 닫기를 요청만 하고, 실제 정리는 loop 가 다음 바퀴에 끝낸 뒤 close callback 으로 알린다.
  • 사용자 입장에서는 destroy 가 바로 돌아오고, 그 뒤 handle 을 쓰지 않으면 된다. 지금도 같은 약속이다.

4.3 worker 의 자기 destroy 는 규칙으로 막는다

worker thread 는 사용자의 thread 라 라이브러리가 알아볼 수 없다. 두 길이 있다.

길좋은 점나쁜 점
A. 문서로 금지: "Work 로 받은 stream 을 closeConnectionStream 하기 전에 그 Owner 를 destroy 하지 않는다"코드가 바뀌지 않는다어기면 멈춘다. 사용자가 원인을 찾기 어렵다
B. stop 때 stream 을 강제로 끊는다: shutdown 이 Work 연결도 socket 을 닫고 칸을 돌려준다. worker 의 다음 read / write / closeStream 은 연결 id 의 generation 이 맞지 않아 실패 code 를 받는다어떤 순서로 불러도 멈추지 않는다. 3.1 의 남은 가능성도 사라진다worker 가 socket 을 쓰는 중에 IO thread 가 닫는다. 지금 Work 의 약속 ("worker 가 돌려줄 때까지 IO thread 는 socket 을 만지지 않는다") 을 깬다. 칸이 다른 연결에 다시 쓰이는 경쟁을 따로 막아야 한다

4.4 destroy 에 timeout 을 둔다 (추천하지 않음)

join 을 일정 시간만 기다리고 실패를 돌려주는 길이다. C API 의 destroy 는 void 라 실패를 알릴 곳이 없고, 기다림을 포기하면 실행 중인 Owner 의 칸을 다시 쓸 수 없어 결국 누수다.

5. 추천

4.1 + 4.2 + 4.3 A.
  • 4.1 로 thread 둘 사이의 교착 (3.1, 3.2) 을 없앤다. 사용자가 실수하지 않아도 생기던 경우다.
  • 4.2 로 콜백 안의 자기 destroy (3.3 첫째) 를 안전하게 만든다. libuv 와 같은 모양이다.
  • worker 의 자기 destroy (3.3 둘째) 는 문서로 금지하고 debug 빌드에서 assert 로 알린다. 강제 끊기 (4.3 B) 는 Work 의 약속을 바꾸는 일이라 따로 정한다.
바뀌는 범위는 LazyReusablePool, Context, Owner 셋의 reset / leave 와 테스트 셋 (3.1, 3.2, 3.3 첫째의 재현) 이다. 8단계 (base.cpp) 전에 넣는 것이 좋다. base.cpp 의 KiottyNet_destroy* 가 이 동작을 그대로 내보내기 때문이다.

2. worker 의 자기 destroy 는 문서 금지 (A) 로 둘까, stop 때 강제로 끊을까 (B)?

6. 정한 것과 넣은 모양 (2026-11-09)

4.1 + 4.2 + 4.3 A 로 정했다.
  • RunGate 가 run 하는 thread 의 id (runner()) 를 들고, RunLifetime (Owner 의 lifetime()) 이 그것을 읽는다: isRunner / abandon / isReleasable / join.
  • Context::destroy (Server, EventClient): close() 를 mutex 없이 부른다. 부른 thread 가 그 Owner 의 loop thread 면 abandon() 만 하고 돌아간다 (칸은 ACTIVE 로 남는다). 아니면 mutex 없이 join() 한 뒤 mutex 를 잡고 칸을 돌려준다.
  • 버려진 칸은 다음 create* 가 mutex 안에서 쓸어 담는다 (forEachActive 로 isReleasable() 인 것을 release). run 이 이미 끝났으므로 reset 의 join 은 바로 돌아온다.
  • release: phase 를 RELEASING 으로 바꾸고 mutex 를 놓은 채 모든 Server / EventClient 를 close, join 한다. 그 사이의 create* 와 open 은 INVALID_ARGUMENT, destroy 는 close / join 만 하고 칸은 건드리지 않는다. 마지막에 mutex 안에서 풀을 비우고 CLOSED 로 둔다.
  • StreamClient 는 loop 가 없어 reset 이 짧으므로 mutex 안에서 그대로 돌려준다.
사용자가 하면 안 되는 것
  • worker 가 자기 Stream 의 closeStream 전에 그 Stream 의 Owner 를 destroy 한다 (3.3 둘째). destroy 가 그 closeStream 을 기다리므로 영원히 멈춘다.
  • 콜백 (loop thread) 이나 worker 에서 release 를 부른다. release 는 모든 run 의 끝을 기다린다. debug 빌드는 loop thread 에서 부르면 assert 로 알린다.

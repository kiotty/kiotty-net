1. 라이브러리들을 관통하는 7가지 핵심 아이디어

라이브러리마다 이름은 다르지만, 결국 모두 같은 일곱 가지 질문에 답하고 있습니다. kiotty-net의 인터페이스도 결국 이 일곱 질문에 대한 답의 조합이 됩니다.

1.1 Readiness(준비됨) vs Completion(완료됨)

OS 비동기 I/O는 두 가족으로 나뉩니다. 준비 통지(reactor)는 "지금 읽으면 블록되지 않는다"만 알려 주고 실제 recv는 앱이 합니다. 완료 통지(proactor)는 앱이 버퍼와 함께 작업을 먼저 제출하고, 커널이 버퍼를 채운 뒤 "몇 바이트 끝났다"를 알려 줍니다.

플랫폼기본 메커니즘모델비고

Linuxio_uring (SQ/CQ 링)완료커널 5.1+. Android는 seccomp 정책으로 대부분의 앱에서 io_uring 시스템콜이 차단되므로 epoll 폴백이 필수

통일 전략. 크로스플랫폼 라이브러리는 둘 중 하나를 외부 인터페이스로 고르고 나머지를 에뮬레이션합니다.

  • 완료 인터페이스로 통일 (libuv, Asio, .NET, Java NIO.2). 준비 통지 백엔드 위에서는 "준비되면 라이브러리가 대신 recv를 호출하고 완료 콜백을 부른다"로 에뮬레이션합니다. IOCP 위에서 자연스럽고 io_uring과도 모양이 같습니다.
  • 준비 인터페이스로 통일 (Rust mio/tokio, libevent의 저수준 event). IOCP 위에서는 반대로 "0바이트 읽기로 준비 신호를 흉내" 내거나 내부 버퍼를 두어야 해 복잡하고 비효율적입니다. mio는 결국 Windows에서 AFD 드라이버를 직접 호출하는 길을 택했습니다.
결론IOCP와 io_uring을 1급 백엔드로 삼는 kiotty-net은 완료 인터페이스가 자연스럽습니다. 즉 "버퍼를 주면서 읽기를 요청하고, 콜백으로 (코드, 바이트 수)를 받는다"가 모든 플랫폼에서 같은 모양이 됩니다. 현재 초안의 EventClient::onRead(ctx, buffer, capacity, cb)와 NetConnection::readAsync는 이미 이 모양입니다.

1.2 이벤트 루프의 소유권: 누가 run을 도는가

모든 라이브러리는 "루프를 돌리는 함수"를 사용자에게 노출하되, 얼마나 돌고 돌아올지를 선택하게 합니다. GUI 메인 루프나 의료기기 제어 루프가 이미 있는 앱에 끼워 넣으려면 이 선택지가 반드시 필요합니다.

1.3 객체 수명과 메모리 소유권

동적 할당 제약과 dangling 방지라는 요구사항에 가장 직접 닿는 질문입니다. 네 라이브러리가 네 가지 다른 답을 냅니다.

연결 객체를 누가 할당하나1회성 작업 상태는 어디에닫기와 해제
libuv호출자. uv_tcp_t를 사용자가 스택·정적·풀 어디에든 두고 uv_tcp_init으로 초기화. 라이브러리는 핸들을 malloc하지 않음호출자가 uv_write_t 같은 요청(req) 객체를 제공. 완료 콜백 후 재사용 가능uv_close(h, cb)는 비동기. cb가 불린 뒤에야 메모리를 재사용할 수 있고, 진행 중 요청은 UV_ECANCELED로 모두 완료됨
Asio호출자(tcp::socket 객체). 다만 비동기 연산 중 살아 있어야 하므로 관용적으로 shared_ptr + shared_from_this를 씀라이브러리가 연산마다 내부 op 객체를 만들되, 핸들러에 연결된 allocator로 할당. 사용자가 완전히 통제 가능close()는 동기지만 진행 중 연산은 operation_aborted로 나중에 완료됨. 그래서 핸들러가 소켓 수명을 잡아야 함
Mongoose라이브러리가 calloc(매크로로 교체 가능). 사용자는 수명을 신경 쓰지 않음연결마다 내부 recv/send 버퍼에 누적. 요청 객체 없음c->is_closing = 1 표시 → 다음 폴링에서 MG_EV_CLOSE 이벤트 후 해제
lwIP컴파일 타임 고정 풀(memp). MEMP_NUM_TCP_PCB로 개수 확정패킷 버퍼도 고정 풀(pbuf)콜백 안에서 tcp_close, 실패 시 재시도 규약
공통 규약 하나모든 라이브러리가 "진행 중인 비동기 작업이 있는 객체를 해제하면 안 되며, 라이브러리는 취소된 작업도 반드시 완료 콜백으로 끝내 준다"를 지킵니다. dangling pointer 방지의 핵심은 이 규약을 인터페이스에 명시하고(예: 닫기를 비동기로 만들거나, onDisconnected 이후에만 해제 가능하다고 못 박기) 라이브러리가 예외 없이 지키는 것입니다.

1.4 콜백 + void* 컨텍스트

C ABI를 갖는 라이브러리는 모두 "함수 포인터 + 불투명 사용자 포인터" 패턴입니다. libuv는 handle->data와 req->data, Mongoose는 c->fn_data와 연결당 32바이트 스크래치 c->data[], libevent는 콜백 등록 시 ctx 인자입니다. C++ 래퍼는 정적 thunk에서 this를 복원하는 한 줄로 끝납니다.

이보다 중요한 것은 콜백 호출 시점 규약입니다. libuv와 Asio는 모두 "비동기 함수 안에서 콜백을 직접(동기적으로) 부르지 않는다"를 보장합니다. 데이터가 이미 도착해 있어도 콜백은 루프의 다음 단계에서 불립니다. 이 규약이 없으면 사용자 코드가 재진입(reentrancy)을 항상 방어해야 하고, 그게 가장 흔한 버그 원인입니다.

1.6 스레딩 모델

네 라이브러리 모두 기본은 "루프 하나 = 스레드 하나, 객체는 그 스레드에서만 만진다"입니다. 다른 스레드에서 할 수 있는 일은 단 하나, 루프를 깨우는 것입니다 (uv_async_send, asio::post, mg_wakeup, event_active). Asio만 여러 스레드가 같은 io_context를 run할 수 있고 그 경우 strand로 직렬화합니다. 32 클라이언트 전제에서는 단일 루프 스레드가 충분하고, 외부 스레드(예: UI, 장비 제어)가 데이터를 보내고 싶을 때 쓰는 "깨우기 + 큐" 하나만 있으면 됩니다.

1.7 프로토콜 계층화: TCP → TLS → HTTP → WebSocket

세 가지 방식이 있습니다.

  1. 타입 합성 (Asio): ssl::stream<tcp::socket>처럼 아래 계층을 템플릿 인자로 감싸고, 위 계층(Beast의 HTTP/WS)은 "async_read_some/async_write_some이 있는 아무 스트림"을 요구합니다. 컴파일 타임에 결정되고 가상 호출이 없지만 C 인터페이스로 내보낼 수 없습니다.
  2. 필터 체인 (libevent filter bufferevent, Netty ChannelPipeline): 바이트가 핸들러 목록을 순서대로 통과합니다. TLS는 "암호문 ↔ 평문" 필터, HTTP 파서는 "바이트 → 메시지" 디코더. 런타임에 끼우고 뺄 수 있어 커스텀 프로토콜에 가장 유연합니다.
  3. 연결 상태 플래그 + 이벤트 분기 (Mongoose): 연결 구조체에 is_tls, is_websocket 같은 비트가 있고, 라이브러리가 MG_EV_READ 바이트를 보고 현재 상태에 맞는 상위 이벤트(MG_EV_HTTP_MSG, MG_EV_WS_MSG)로 바꿔 올려 줍니다. 가장 단순하고 C에 잘 맞습니다.

어느 방식이든 요청/응답 모델과 이벤트 모델의 차이는 계층의 맨 위에서만 나타납니다. 아래 계층(TCP, TLS)은 항상 양방향 바이트 스트림이고, HTTP는 그 위에 "요청 하나에 응답 하나"라는 규칙을 얹은 것이며, WebSocket과 커스텀 이벤트 프로토콜은 "메시지가 아무 때나 양방향으로 온다"는 규칙을 얹은 것입니다. 따라서 기반 인터페이스는 이벤트(메시지 도착 콜백) 모델 하나면 되고, 요청/응답은 그 위에서 "보낸 뒤 다음 메시지를 기다린다"로 만들 수 있습니다. Mongoose가 정확히 이렇게 되어 있습니다.

2.3 루프 한 바퀴

uv_run 한 바퀴는 고정된 순서로 돕니다. 모든 콜백은 이 단계 중 하나에서만 불립니다.

  1. timers: 만료된 uv_timer_t 콜백
  2. pending callbacks: 직전 바퀴에서 미뤄 둔 I/O 콜백(예: 즉시 완료된 write의 콜백)
  3. idle, prepare 핸들
  4. poll: 백엔드에 블로킹 대기. 대기 시간은 가장 가까운 타이머까지. 여기서 읽기/쓰기/accept/connect 콜백이 불림
  5. check 핸들
  6. closing callbacks: uv_close로 닫은 핸들의 close_cb

루프는 "살아 있는(active) 핸들이나 진행 중 요청"이 하나도 없으면 uv_run에서 돌아옵니다. uv_unref(handle)로 특정 핸들(예: 주기 타이머)을 종료 조건 계산에서 빼는 장치가 있습니다. 즉 루프의 종료 조건을 객체 참조 수로 정의하는 것인데, 사용자가 "언제 끝났는지"를 따로 관리하지 않아도 되는 대신 왜 안 끝나는지 디버깅하기 어렵다는 단점도 있습니다.

2.5 최소 예제: 고정 슬롯 에코 서버

libuv 공식 예제는 콜백마다 malloc을 쓰지만, 호출자 소유 설계 덕분에 아래처럼 malloc 없이 쓸 수 있습니다. kiotty-net의 32 슬롯 모델과 거의 같은 모양이 됩니다.

#include <uv.h>
#include <stdio.h>
#include <string.h>

enum { MAX_CONN = 32, BUF = 4096 };

typedef struct {
    uv_tcp_t   handle;       /* 반드시 첫 멤버: (conn_t*)stream 캐스팅을 위해 */
    uv_write_t wreq;         /* 연결당 쓰기 요청 객체 1개 (동시 쓰기 1개 정책) */
    char       rbuf[BUF];    /* 고정 읽기 버퍼 */
    char       wbuf[BUF];    /* 고정 쓰기 버퍼: write_cb까지 건드리면 안 됨 */
    int        in_use;
    int        writing;
} conn_t;

static conn_t   slots[MAX_CONN];   /* 시작 시점에 전부 확보 */
static uv_tcp_t server;

static conn_t* take_slot(void) {
    for (int i = 0; i < MAX_CONN; i++) if (!slots[i].in_use) { slots[i].in_use = 1; return &slots[i]; }
    return NULL;
}

static void on_close(uv_handle_t* h) {
    conn_t* c = (conn_t*)h;
    c->in_use = 0;           /* close_cb 이후에만 슬롯 재사용 가능 */
}

static void on_alloc(uv_handle_t* h, size_t suggested, uv_buf_t* buf) {
    conn_t* c = (conn_t*)h;
    *buf = uv_buf_init(c->rbuf, BUF);        /* malloc 대신 고정 버퍼 */
}

static void on_write(uv_write_t* req, int status) {
    conn_t* c = (conn_t*)req->handle;
    c->writing = 0;                          /* 여기서부터 wreq, wbuf 재사용 가능 */
    if (status < 0) uv_close((uv_handle_t*)&c->handle, on_close);
}

static void on_read(uv_stream_t* s, ssize_t nread, const uv_buf_t* buf) {
    conn_t* c = (conn_t*)s;
    if (nread > 0) {
        if (c->writing) return;              /* 단순화: 진행 중 쓰기가 있으면 버림 (실제론 큐잉/백프레셔) */
        memcpy(c->wbuf, buf->base, (size_t)nread);
        uv_buf_t out = uv_buf_init(c->wbuf, (unsigned)nread);
        c->writing = 1;
        uv_write(&c->wreq, s, &out, 1, on_write);
    } else if (nread < 0) {                  /* UV_EOF 포함. 콜백은 항상 루프에서 호출됨 */
        if (nread != UV_EOF) fprintf(stderr, "read: %s\n", uv_err_name((int)nread));
        uv_close((uv_handle_t*)s, on_close);
    }
    /* nread == 0 : 아무 일도 안 함 */
}

static void on_connection(uv_stream_t* srv, int status) {
    if (status < 0) return;
    conn_t* c = take_slot();
    if (!c) return;                          /* 가득 참: accept 안 하면 백로그에 남음 (정책 결정 필요) */
    uv_tcp_init(srv->loop, &c->handle);
    c->handle.data = c;                      /* 사용자 포인터 */
    if (uv_accept(srv, (uv_stream_t*)&c->handle) == 0)
        uv_read_start((uv_stream_t*)&c->handle, on_alloc, on_read);
    else
        uv_close((uv_handle_t*)&c->handle, on_close);
}

int main(void) {
    uv_loop_t* loop = uv_default_loop();
    struct sockaddr_in addr;
    uv_ip4_addr("0.0.0.0", 7000, &addr);
    uv_tcp_init(loop, &server);
    uv_tcp_bind(&server, (const struct sockaddr*)&addr, 0);
    int r = uv_listen((uv_stream_t*)&server, MAX_CONN, on_connection);
    if (r) { fprintf(stderr, "listen: %s\n", uv_strerror(r)); return 1; }
    return uv_run(loop, UV_RUN_DEFAULT);
}

클라이언트 쪽은 요청 객체 하나가 더 등장합니다.

static uv_tcp_t     sock;

2.6 메모리·수명 규칙 (문서에 명시된 것들)

  • 핸들과 요청은 호출자가 할당하고 라이브러리는 포인터만 보관합니다. 핸들은 close_cb가 불릴 때까지, 요청은 완료 콜백이 불릴 때까지 이동·해제 금지.
  • 읽기 버퍼는 alloc_cb가 줍니다. read_cb가 끝나면 라이브러리는 그 버퍼를 다시 참조하지 않으므로, 정리(또는 재사용) 책임은 사용자에게 있습니다. nread < 0인 경우에도 buf는 전달되고 사용자가 정리해야 합니다.
  • 쓰기 버퍼(uv_buf_t가 가리키는 메모리)는 write_cb까지 유효해야 합니다. uv_buf_t 배열 자체는 복사되므로 스택에 있어도 됩니다.
  • 쓰기는 큐잉됩니다. 여러 uv_write를 연달아 호출해도 순서대로 나가며, stream->write_queue_size로 밀린 바이트 수를 볼 수 있습니다. 이 값이 커지면 사용자가 uv_read_stop 등으로 백프레셔를 걸어야 합니다. 라이브러리는 한도를 두지 않습니다.
  • uv_close는 비동기입니다. 호출 즉시 fd는 닫히지만 close_cb는 다음 바퀴의 closing 단계에서 불리고, 진행 중이던 요청들은 그 전에 UV_ECANCELED로 콜백이 호출됩니다. 그래서 "요청 콜백이 모두 끝난 뒤 close_cb가 온다"는 순서를 믿고 정리할 수 있습니다.
  • 콜백은 동기적으로 호출되지 않습니다. 예를 들어 Unix에서 uv_write는 즉시 writev를 시도해 전부 보냈더라도 write_cb는 pending 큐에 넣어 다음 단계에서 부릅니다.
  • 스레드 안전한 함수는 uv_async_send뿐입니다. 나머지는 루프 스레드에서만.

2.7 Unix Domain / Named Pipe: uv_pipe_t

libuv는 로컬 IPC를 uv_pipe_t 하나로 추상화합니다. Unix에서는 AF_UNIX 소켓이고, Windows에서는 \\.\pipe\이름 형식의 Named Pipe입니다. 둘 다 uv_stream_t이므로 read/write 코드는 TCP와 완전히 같습니다. ipc=1로 만들면 fd(소켓 핸들)를 넘길 수도 있습니다.

kiotty-net 요구사항 13과의 관계Windows 10 1803부터는 Winsock이 AF_UNIX 스트림 소켓을 직접 지원하고, 이 소켓은 보통의 소켓이므로 IOCP·WSARecv·AcceptEx 경로를 TCP와 그대로 공유합니다. libuv처럼 Named Pipe용 코드를 따로 두지 않아도 됩니다. 제약은 (1) 파일 시스템 경로만 가능(추상 네임스페이스 없음), (2) SOCK_STREAM만, (3) bind 전에 기존 소켓 파일을 지워야 함, (4) socketpair 없음 정도입니다. Asio도 최근 버전에서 같은 방식으로 Windows를 지원하기 시작했습니다.

가져올 것

  • 콜백은 절대 동기 호출하지 않음
  • run 모드 3종과 uv_stop
  • 핸들의 data 필드 하나로 끝나는 사용자 컨텍스트
  • 스트림 추상 하나로 TCP와 로컬 소켓을 같은 코드로 다루기
  • uv_accept를 사용자가 호출하게 해서 "가득 찼을 때" 정책을 사용자에게 맡기기
피하거나 단순화할 것

  • 범위(fs, dns, process, 스레드풀)는 kiotty-net 목표 밖
  • HTTP/TLS 없음: 별도 설계 필요

3.3 최소 예제: 에코 세션 (C++11)

#include <asio.hpp>
#include <memory>
using asio::ip::tcp;

class session : public std::enable_shared_from_this<session> {
public:
    explicit session(tcp::socket s) : socket_(std::move(s)) {}
    void start() { do_read(); }
private:
    void do_read() {
        auto self = shared_from_this();                        // 핸들러가 살아 있는 동안 세션 유지
        socket_.async_read_some(asio::buffer(data_),           // 1회성 읽기: 한 번 완료되면 끝
            [this, self](std::error_code ec, std::size_t n) {  // (오류, 바이트 수)
                if (ec) return;                                // eof, operation_aborted 포함 → 세션 소멸
                do_write(n);
            });
    }
    void do_write(std::size_t n) {
        auto self = shared_from_this();
        asio::async_write(socket_, asio::buffer(data_, n),     // 조합 연산: n바이트 전부 나갈 때까지
            [this, self](std::error_code ec, std::size_t) {
                if (!ec) do_read();
            });
    }
    tcp::socket socket_;
    char data_[4096];
};

class server {
public:
    server(asio::io_context& io, unsigned short port)
      : acceptor_(io, tcp::endpoint(tcp::v4(), port)) { do_accept(); }
private:
    void do_accept() {
        acceptor_.async_accept([this](std::error_code ec, tcp::socket s) {
            if (!ec) std::make_shared<session>(std::move(s))->start();
            do_accept();                                       // 다음 접속을 다시 건다
        });
    }
    tcp::acceptor acceptor_;
};

int main() {
    asio::io_context io;
    server srv(io, 7000);
    io.run();                                                  // 블로킹. poll()/run_one()/run_for()도 있음
}

계층화는 타입으로. TLS를 얹어도 읽기/쓰기 호출은 그대로입니다. 위 계층(Beast의 HTTP/WS)은 async_read_some/async_write_some만 있으면 되는 스트림 템플릿 인자를 받습니다.

타임아웃은 타이머와 취소의 조합. Asio에는 "읽기 타임아웃" 같은 옵션이 없고, 타이머를 따로 걸고 만료 시 socket.cancel()을 부르면 진행 중 읽기가 operation_aborted로 완료됩니다. 단순하지만 매번 두 개의 비동기 연산을 짝지어야 해서, 초보자가 가장 자주 틀리는 부분입니다. kiotty-net이 "이해하기 쉬움"을 노린다면 연결 단위 타임아웃을 내장 옵션으로 두는 편이 낫습니다(Mongoose와 libevent는 내장).

3.5 메모리 모델: 핸들러 할당 훅

Asio는 비동기 연산마다 내부 상태(op 객체)를 하나 만들어야 하는데, 이를 핸들러에 연결된 allocator(associated_allocator)로 할당합니다. 그리고 중요한 보장이 하나 있습니다. "연산을 위해 할당된 메모리는 핸들러를 호출하기 직전에 해제된다." 그래서 핸들러 안에서 다음 연산을 시작하면 방금 해제된 같은 블록을 재사용할 수 있고, 결과적으로 연결당 고정 블록 1~2개로 모든 연산을 처리할 수 있습니다. 공식 예제 allocation/server.cpp의 handler_memory가 정확히 이것이고, asio::recycling_allocator는 이를 스레드 로컬 캐시로 일반화한 것입니다.

// 연결당 고정 블록 하나로 모든 비동기 연산의 내부 상태를 처리하는 패턴 (Asio 예제 축약)
class handler_memory {
public:
    void* allocate(std::size_t size) {
        if (!in_use_ && size < sizeof(storage_)) { in_use_ = true; return &storage_; }
        return ::operator new(size);                 // 넘치면 폴백 (크기를 미리 재서 없애는 게 목표)
    }
    void deallocate(void* p) {
        if (p == &storage_) in_use_ = false; else ::operator delete(p);
    }
private:
    typename std::aligned_storage<1024>::type storage_;
    bool in_use_ = false;
};
// 이 메모리를 가리키는 allocator를 핸들러에 "associated" 시키면 Asio가 op 객체를 여기서 꺼내 쓴다.

반면 소켓 객체의 수명은 Asio가 전혀 관리하지 않습니다. 진행 중 연산이 있는 소켓이 파괴되면 미정의 동작이므로, 관용구는 세션을 shared_ptr로 만들고 모든 핸들러가 self를 캡처하는 것입니다. 이것이 Asio 코드가 동적 할당을 피하기 어려운 이유입니다. 풀에 둔 세션 객체 + "진행 중 연산 수" 카운터로 대체할 수 있지만 라이브러리가 도와주지는 않습니다.

3.6 Beast가 보여 주는 HTTP 계층의 모양

Boost.Beast는 HTTP/WebSocket을 Asio 위에 얹되, HTTP 계층이 스트림을 소유하지 않습니다. http::async_read(stream, buffer, message, handler)처럼 스트림·누적 버퍼·메시지 컨테이너를 인자로 받는 자유 함수입니다. WebSocket만 상태(핸드셰이크 여부, 프레임 마스킹)가 있어서 websocket::stream<next_layer>라는 래퍼 타입이 됩니다. "요청/응답은 함수, 이벤트 스트림은 상태를 가진 객체"라는 구분은 kiotty-net의 Stream/Event 두 모델과 잘 맞습니다.

  • 버퍼를 뷰로 받고 소유권은 사용자에게: 복사가 없고 규칙이 단순
  • "시작 함수 안에서 핸들러를 호출하지 않는다" 규칙

4.3 최소 예제: HTTP + WebSocket + 메모리 상주 정적 파일

#include "mongoose.h"

static void fn(struct mg_connection *c, int ev, void *ev_data) {
  if (ev == MG_EV_HTTP_MSG) {                              /* 요청/응답 모델 */
    struct mg_http_message *hm = (struct mg_http_message *) ev_data;
    if (mg_match(hm->uri, mg_str("/ws"), NULL)) {
      mg_ws_upgrade(c, hm, NULL);                          /* 이후 이 연결은 WS 이벤트를 받음 */
    } else if (mg_match(hm->uri, mg_str("/api/status"), NULL)) {
      mg_http_reply(c, 200, "Content-Type: application/json\r\n", "{%m:%d}\n", MG_ESC("ok"), 1);
    } else {
      struct mg_http_serve_opts opts = { .root_dir = "/web_root", .fs = &mg_fs_packed };
      mg_http_serve_dir(c, hm, &opts);                     /* 바이너리에 패킹된 파일을 서빙 */
    }
  } else if (ev == MG_EV_WS_MSG) {                         /* 이벤트 모델 */
    struct mg_ws_message *wm = (struct mg_ws_message *) ev_data;
    mg_ws_send(c, wm->data.buf, wm->data.len, WEBSOCKET_OP_TEXT);
  } else if (ev == MG_EV_CLOSE) {
    /* 연결별 정리. c->data[32] 또는 c->fn_data 사용 */
  }
}

int main(void) {
  struct mg_mgr mgr;
  mg_mgr_init(&mgr);
  mg_http_listen(&mgr, "http://0.0.0.0:8000", fn, NULL);   /* fn_data = NULL */
  for (;;) mg_mgr_poll(&mgr, 1000);                        /* 루프는 사용자가 돈다 */
  mg_mgr_free(&mgr);
}

정적 파일과 메모리 상주 파일(요구사항 9). mg_http_serve_dir / mg_http_serve_file은 Range 요청, ETag/If-Modified-Since, 디렉터리 목록, MIME 매핑, 사전 압축된 .gz 서빙을 처리합니다. 파일 시스템은 struct mg_fs(open/read/seek/stat/list 함수 포인터 묶음)로 추상화되어 있어 mg_fs_posix, mg_fs_fat, 그리고 pack 도구로 파일들을 C 배열로 바꿔 넣은 mg_fs_packed를 같은 코드로 씁니다. 즉 "메모리에 올라온 바이너리를 정적 파일처럼 제공"은 파일 시스템 인터페이스를 함수 포인터 5개로 추상화하는 것으로 해결됩니다.

4.4 프로토콜 계층화: 연결에 꽂힌 내부 핸들러

Mongoose의 계층화는 놀랄 만큼 단순합니다. mg_http_listen은 mg_listen을 부른 뒤 c->pfn = http_cb를 설정할 뿐입니다. 폴링 중 바이트가 c->recv에 쌓이면 MG_EV_READ가 먼저 pfn(내부 핸들러)에 전달되고, 내부 핸들러가 메시지를 완성하면 MG_EV_HTTP_MSG로 바꿔 사용자 fn에 넘긴 뒤 mg_iobuf_del로 소비합니다. WebSocket으로 업그레이드하면 pfn이 ws_cb로 바뀌고 is_websocket 비트가 켜집니다. TLS는 is_tls 비트와 송수신 직전의 암복호화 단계로 처리됩니다.

/* 커스텀 프로토콜: raw TCP 리스너 + MG_EV_READ에서 직접 프레이밍 (예: DICOM PDU 6바이트 헤더) */
static void pdu_fn(struct mg_connection *c, int ev, void *ev_data) {
  if (ev == MG_EV_READ) {
    struct mg_iobuf *r = &c->recv;
    while (r->len >= 6) {                                  /* 헤더가 모였는가 */
      uint32_t body;
      memcpy(&body, r->buf + 2, 4); body = mg_ntohl(body); /* type(1) reserved(1) length(4 BE) */
      if (r->len < 6 + body) break;                        /* 바디가 덜 왔다 → 다음 READ에서 재시도 */
      handle_pdu(c, r->buf, 6 + body);
      mg_iobuf_del(r, 0, 6 + body);                        /* 소비 */
    }
    if (r->len > MAX_PDU) c->is_closing = 1;               /* 프레임이 버퍼 한도를 넘으면 끊기 */
  }
}
mg_listen(&mgr, "tcp://0.0.0.0:104", pdu_fn, NULL);

4.5 수명과 메모리

  • 연결 구조체는 라이브러리가 calloc으로 만들고 MG_EV_CLOSE 후 free합니다. MG_ENABLE_CUSTOM_CALLOC으로 mg_calloc/mg_free를 풀 할당자로 바꿀 수 있습니다.
  • 닫기는 플래그입니다. c->is_closing = 1은 다음 폴링에서 즉시 닫기, c->is_draining = 1은 send 버퍼를 비운 뒤 닫기. 사용자가 핸들러 안에서 free를 직접 부를 일이 없으므로 재진입·dangling 문제가 구조적으로 줄어듭니다.
  • 연결 포인터를 보관하지 말고 c->id를 보관하라고 문서가 권장합니다. mg_wakeup도 id로 연결을 지정합니다. id는 단조 증가하므로 재사용된 슬롯을 옛 id로 건드리는 일이 없습니다. 이것이 7장에서 다루는 세대 번호 핸들의 가장 단순한 형태입니다.
  • 수신·송신 버퍼는 MG_IO_SIZE 단위로 realloc 성장합니다. 고정 메모리 요구에는 맞지 않지만, is_full 비트로 "수신 버퍼가 한도에 닿았으니 읽기를 멈춘다"는 백프레셔 개념은 있습니다.
  • 쓰기는 항상 c->send에 복사됩니다. 사용자 버퍼는 mg_send가 돌아오면 즉시 재사용 가능합니다. 복사 비용 대신 "쓰기 버퍼 수명" 규칙이 아예 사라집니다. 32 클라이언트 규모에서는 매우 합리적인 교환입니다.
  • 타임아웃은 MG_EV_POLL에서 c->data에 저장한 마지막 활동 시각과 비교하는 식으로 사용자가 구현하거나 mg_timer_add를 씁니다.

5.3 가져올 만한 아이디어

  • 워터마크 = 백프레셔를 인터페이스 1급으로. 읽기 high watermark를 넘으면 라이브러리가 읽기를 멈추고, low 아래로 내려오면 재개합니다. 쓰기 low watermark에 닿으면 writecb가 "더 넣어도 된다"고 알립니다. 고정 메모리 환경에서는 사실상 필수 개념인데, libuv와 Asio는 사용자에게 맡깁니다.
  • evbuffer_add_reference(buf, data, len, cleanup_cb, arg). 메모리에 이미 있는 데이터를 복사 없이 송신 큐에 넣고, 다 나가면 cleanup_cb가 불립니다. 메모리 상주 바이너리를 HTTP 응답 본문으로 보내는 데 필요한 정확한 프리미티브입니다. evbuffer_add_file은 디스크 파일 버전(sendfile/mmap)입니다.
  • 필터 bufferevent. TLS를 "바이트 변환 계층"으로 끼우는 방식은, kiotty-net의 "TLS 적용 여부" 계층을 런타임 스위치로 만들 때의 모델이 됩니다.
  • bufferevent_pair_new. 소켓 없이 메모리로 연결된 bufferevent 쌍. 프로토콜 코드를 네트워크 없이 단위 테스트하는 데 쓰입니다. kiotty-net에서도 "루프백 메모리 커넥션"을 테스트용으로 제공하면 프로토콜 계층 테스트가 쉬워집니다.
  • 읽기/쓰기 타임아웃이 연결 객체의 속성입니다.
주의IOCP 지원은 bufferevent_async에 한정된 부분 지원이고, 내부에서 malloc을 많이 쓰며, 저수준 event API와 고수준 bufferevent API가 섞여 있어 배우는 비용이 큽니다. 백엔드 통합의 참고로는 부적합하고, 버퍼드 스트림 추상의 참고로만 보는 것이 좋습니다.

6. 프로토콜 파서와 프레이머

HTTP, WebSocket, 그리고 커스텀 프로토콜(DICOM 포함)은 결국 "바이트 스트림에서 메시지 경계를 찾는 일"입니다. 이 일을 하는 코드의 인터페이스에는 두 가지 전통이 있습니다.

6.1 Push 파서: llhttp

Node.js가 쓰는 HTTP 파서. 상태 기계가 파서 객체(수십 바이트)에만 상태를 두고, 입력 조각이 어디서 끊기든 상관없이 콜백을 호출합니다. 메모리 할당이 전혀 없고, 데이터 콜백은 입력 버퍼 내부를 가리키는 포인터(제로카피)를 줍니다. 대신 한 헤더 값이 여러 조각으로 나뉘어 여러 번 콜백될 수 있어 사용자가 누적해야 합니다.

static int on_url(llhttp_t* p, const char* at, size_t len) {
    conn_t* c = (conn_t*)p->data;
    return append_bounded(&c->url, at, len) ? 0 : -1;        /* 조각일 수 있음: 고정 버퍼에 누적 */
}
static int on_headers_complete(llhttp_t* p) { return 0; }    /* 1을 돌려주면 바디 생략, 2면 업그레이드 */
static int on_body(llhttp_t* p, const char* at, size_t len) { return 0; }
static int on_message_complete(llhttp_t* p) { /* 요청 1개 완성 */ return 0; }

llhttp_settings_t st; llhttp_settings_init(&st);
st.on_url = on_url; st.on_headers_complete = on_headers_complete;
st.on_body = on_body; st.on_message_complete = on_message_complete;

llhttp_t parser; llhttp_init(&parser, HTTP_REQUEST, &st);
parser.data = conn;

/* 들어온 조각마다: */
llhttp_errno_t err = llhttp_execute(&parser, data, len);
if (err == HPE_PAUSED_UPGRADE) { /* 헤더 끝 이후 바이트는 WebSocket 등 다른 프로토콜로 */ }
else if (err != HPE_OK) { /* llhttp_errno_name(err), llhttp_get_error_reason(&parser) */ }

llhttp_pause/llhttp_resume으로 "지금은 더 처리하지 말라"는 백프레셔를 걸 수 있고, 업그레이드(WebSocket) 지점에서 HPE_PAUSED_UPGRADE로 멈춰 나머지 바이트를 다음 프로토콜에 넘기는 규약이 깔끔합니다.

6.2 Pull 파서: picohttpparser

H2O 서버의 파서. "완성된 요청 헤더가 버퍼에 다 있으면 파싱하고, 아니면 -2를 돌려준다"는 단순한 함수 하나입니다. 헤더 배열을 호출자가 넘기므로 완전 무할당이고, 조각 누적은 호출자 버퍼에서 자연스럽게 이뤄집니다.

const char *method, *path; size_t method_len, path_len; int minor;
struct phr_header headers[32]; size_t nh = 32;                /* 호출자 제공 → 무할당 */

int n = phr_parse_request(buf, len, &method, &method_len, &path, &path_len,
                          &minor, headers, &nh, prev_len);    /* prev_len: 지난번까지 본 길이(재스캔 최소화) */
if (n > 0)       { /* 헤더 끝까지 n바이트 소비. 포인터들은 buf 내부 */ }
else if (n == -2){ /* 더 받아야 함. 버퍼가 가득 찼다면 431/413 후 끊기 */ }
else             { /* -1 파싱 오류 */ }

32 클라이언트에 요청 크기가 작은 환경이라면 pull 방식이 더 단순합니다. 요청 헤더 상한(예: 8KB)을 고정 버퍼로 두고, 넘치면 오류로 끊으면 됩니다. 바디(청크 포함)는 phr_decode_chunked처럼 별도 단계로 처리합니다.

6.3 Netty의 파이프라인과 프레임 디코더

Java 라이브러리지만 "커스텀 프로토콜을 가장 적은 코드로 지원하는 인터페이스"의 사실상 표준이므로 짚고 갑니다. 연결(Channel)마다 핸들러 목록(ChannelPipeline)이 있고, 바이트는 목록을 순서대로 통과하며 변환됩니다. 핵심은 ByteToMessageDecoder의 규약 하나입니다.

// 규약: in(누적 버퍼)에서 메시지를 만들 수 있으면 out에 추가하고 소비한다.
//       아무것도 추가하지 않고 돌아오면 "더 받을 때까지 기다리겠다"는 뜻. 누적은 프레임워크가 한다.
protected abstract void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out);

// 길이 프리픽스 프로토콜은 디코더를 쓰지 않고 매개변수 5개로 끝난다.
new LengthFieldBasedFrameDecoder(
    maxFrameLength,      // 이보다 큰 프레임은 오류 (메모리 상한)
    lengthFieldOffset,   // 길이 필드가 시작되는 오프셋
    lengthFieldLength,   // 길이 필드 크기 (1, 2, 3, 4, 8)
    lengthAdjustment,    // 길이 값이 가리키는 범위 보정

);
프로토콜프레임 구조길이 필드 디코더로 표현

WebSocket 프레임길이 필드가 7/16/64비트로 가변, 마스킹 키 선택적표현 불가 → 전용 디코더 필요

따라서 "서버 개발자가 프로토콜 정의만 하면 되게" 하려면 일반적인 디코더 규약이 필요하고, 길이 프리픽스는 그 위의 편의 기능입니다.

6.4 kiotty-net용 프레이머 인터페이스 스케치

위 세 전통을 C로 가장 작게 줄이면 함수 하나가 남습니다. 라이브러리가 수신 버퍼에 누적하고, 매번 이 함수에 "여기 메시지 하나가 완성됐나?"를 묻습니다.

typedef struct KiottyFramer {
    void* ctx;
    /* 누적 버퍼 [data, data+len) 를 보고 메시지 1개의 경계를 판단한다.
       반환 > 0 : 첫 메시지의 전체 길이(바이트). 라이브러리가 onMessage(data, 반환값)를 부르고 그만큼 소비한다.
       반환 = 0 : 아직 모자람. 더 받은 뒤 다시 묻는다. need_hint 에 최소 몇 바이트가 더 필요한지 적어도 된다.
       반환 < 0 : 프로토콜 오류 코드(NetCode). 라이브러리가 연결을 끊는다.                                */
    int32_t (*frame)(void* ctx, const uint8_t* data, size_t len, size_t* need_hint);
} KiottyFramer;

/* DICOM PDU 프레이머는 이게 전부다 */
static int32_t dicom_frame(void* ctx, const uint8_t* d, size_t len, size_t* need) {
    if (len < 6) { *need = 6 - len; return 0; }
    uint32_t body = ((uint32_t)d[2] << 24) | ((uint32_t)d[3] << 16) | ((uint32_t)d[4] << 8) | d[5];
    if (body > ((dicom_ctx*)ctx)->max_pdu) return NET_PROTOCOL_ERROR;
    if (len < 6 + body) { *need = 6 + body - len; return 0; }
    return (int32_t)(6 + body);
}
  • 사용자는 상태 없는 함수 하나만 씁니다. 누적·분할·호출 순서는 라이브러리 책임입니다.
  • 수신 버퍼가 고정 크기이므로 "버퍼가 꽉 찼는데 아직 0을 돌려준다"면 라이브러리가 NET_FRAME_TOO_LARGE로 끊습니다. 메모리 상한이 자동으로 프로토콜 상한이 됩니다.
  • HTTP처럼 경계가 파싱에 달린 프로토콜은 frame() 안에서 picohttpparser를 호출하면 됩니다(-2 → 0). 바디가 버퍼보다 큰 경우를 지원하려면 push 스타일 스트리밍 콜백이 추가로 필요한데, 이것은 설계 결정 사항입니다.
  • Mongoose의 pfn처럼 연결마다 프레이머를 바꿔 끼울 수 있게 하면 HTTP → WebSocket 업그레이드가 "프레이머 교체"가 됩니다.

7. 고정 메모리 설계 참고

7.1 lwIP: 모든 상한을 컴파일 타임에

lwipopts.h에서 MEMP_NUM_TCP_PCB(연결 수), MEMP_NUM_TCP_SEG, PBUF_POOL_SIZE, TCP_SND_BUF, TCP_WND 등을 정하면 memp(타입별 고정 풀)와 pbuf(패킷 버퍼 풀)가 정적으로 잡힙니다. 런타임에는 풀에서 꺼내고 돌려줄 뿐이며, 풀이 비면 ERR_MEM을 돌려주고 호출자가 나중에 재시도합니다. raw API는 콜백 기반입니다.

tcp_recv(pcb, recv_cb);            /* err_t recv_cb(void* arg, struct tcp_pcb*, struct pbuf* p, err_t) */
tcp_sent(pcb, sent_cb);            /* 상대가 ACK한 바이트 수를 알려 줌 = 송신 버퍼 공간이 생겼다는 신호 */
tcp_err(pcb, err_cb);              /* pcb가 이미 해제된 뒤 불림: 포인터를 쓰지 말라는 규약 */
tcp_write(pcb, data, len, TCP_WRITE_FLAG_COPY);   /* COPY 없이 쓰면 ACK될 때까지 data 유효해야 함 */
tcp_recved(pcb, len);              /* 앱이 처리한 만큼 수신 윈도우를 다시 열어 줌 = 명시적 백프레셔 */

눈여겨볼 점은 (1) 송신 버퍼의 소유권 규칙이 libuv와 같다는 것(복사 플래그로 선택 가능), (2) 수신 윈도우를 앱이 tcp_recved로 직접 연다는 것, (3) 오류 콜백이 "이미 해제됨"을 뜻한다는 규약입니다. Zephyr의 net_buf도 같은 철학으로, NET_BUF_POOL_DEFINE(name, count, size, user_data, destroy) 매크로로 정적 풀을 선언하고 참조 카운트로 돌려줍니다.

7.2 포인터 대신 세대 번호 핸들

dangling pointer를 "오류 코드"로 바꾸는 가장 확실한 방법은 외부에 포인터 대신 (슬롯 인덱스, 세대 번호)를 주는 것입니다. 슬롯이 재사용될 때마다 세대가 1 증가하므로, 옛 핸들로 접근하면 세대가 맞지 않아 NET_STALE_HANDLE이 반환됩니다. Mongoose의 c->id, Vulkan 핸들, 게임 엔진의 ECS, Rust의 slotmap이 모두 이 기법입니다.

typedef struct { uint16_t index; uint16_t gen; } NetHandle;      /* 값 타입, 32비트 */

typedef struct { uint16_t gen; int in_use; /* ...연결 상태... */ } Slot;
static Slot slots[32];

static Slot* resolve(NetHandle h) {
    if (h.index >= 32) return NULL;
    Slot* s = &slots[h.index];
    return (s->in_use && s->gen == h.gen) ? s : NULL;          /* 세대 불일치 = 이미 닫힌 연결 */
}
static void release(Slot* s) { s->in_use = 0; s->gen++; }       /* 다음 사용자는 새 세대 */

비용은 C++ 인터페이스에서 NetConnection* 같은 포인터 대신 값 핸들을 들고 다녀야 한다는 점입니다. 절충안은 내부 콜백 인자로는 포인터를 주고(콜백 동안은 유효가 보장됨), 콜백 밖에서 보관할 때만 핸들을 쓰게 하는 것입니다. libuv도 핸들 포인터를 그대로 쓰지만 비동기 close 규약으로 같은 안전성을 얻는다는 점에서, 두 방식 중 하나는 반드시 있어야 합니다.

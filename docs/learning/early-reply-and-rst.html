0. 한 줄 요약

올리기 (begin → write 여러 번 → finish) 도중에 서버가 413 / 401 같은 응답을 먼저 보내고 연결을 끊으면, 그 응답 바이트는 운영체제의 수신 버퍼에 와 있지만 kiotty 는 올리는 동안 읽지 않으므로 우리 수신 Stage 에는 아직 없다. 서버의 끊음이 RST 로 오면 Linux 는 그 바이트를 남겨 두고 Windows 는 버린다. 그래서 같은 코드가 Linux 에서는 finish 로 413 을 돌려주고, Windows 에서는 SOCKET_ERROR 를 돌려준다. 고치려면 RST 가 오기 전에 그 바이트를 우리 Stage 로 옮겨야 한다.

1. 장면

설계 6.1 의 "펌웨어 / 로그 파일 올리기" 를 그대로 쓴다.

begin(client, { PUT, "/devices/7/logs/today.log", OCTET_STREAM }, [], 4 MiB, 5000)   /* 머리만 */
loop : write(client, piece, 64 KiB, 10000)                                           /* 64 번 */
reply = finish(client, 30000)

서버는 body 를 256 KiB 까지만 받는다 (우리 HttpServer 의 KiottyNet_configureHttpBodyCapacity, nginx 의 client_max_body_size 와 같은 것). 서버는 머리의 Content-Length: 4194304 를 보자마자 받을 수 없다는 것을 안다. 그래서 body 를 기다리지 않고

  1. HTTP/1.1 413 Content Too Large 를 보내고
  2. 연결을 닫는다. 이 연결의 뒤에 오는 바이트는 4 MiB 짜리 body 이므로 다음 요청으로 읽을 수 없기 때문이다.

앱이 기대하는 것: finish 가 { SUCCESS, status 413 } 을 돌려주고, 앱은 "파일이 너무 크다" 를 알고 나누어 올리거나 포기한다. 401 이면 토큰을 새로 받고 다시 한다. 이것이 설계의 정할 것 1 "보여준다" 다.

2. 바이트가 머무는 자리

TCP 바이트는 상대 앱에 닿기까지 여러 버퍼를 지난다. 이 문제는 "응답 바이트가 지금 어느 칸에 있느냐" 의 문제다.

 서버 앱                                                      클라이언트 (kiotty)
 ───────                                                      ───────────────────
 "413 ..." ─▶ [서버 커널 송신 버퍼] ─▶ 네트워크 ─▶ [클라이언트 커널 수신 버퍼] ─▶ [수신 Stage] ─▶ HttpReplyStore
                                                     (A)                      (B)
                                                 운영체제가 가진 칸         kiotty 가 가진 칸
칸누가 가지나언제 채워지나언제 비워지나
(A) 커널 수신 버퍼운영체제패킷이 오면 운영체제가 알아서앱이 recv 를 부르면 앱으로. RST 가 오면 운영체제 마음대로 (5절)
(B) 수신 Stagekiotty (StreamClient::_receive)kiotty 가 recv 를 불렀을 때 (ConnectionStream::peek / fillStage)응답 머리 / body 를 읽어 consume 할 때, 또는 disconnect

핵심: 올리는 동안 kiotty 는 recv 를 부르지 않는다. begin / write 는 보내기만 한다 (writeAll → ConnectionStream::write). 그래서 서버가 먼저 보낸 413 은 (A) 에 쌓여 있고 (B) 는 비어 있다. (A) 에 있는 동안은 운영체제의 규칙을 따른다.

3. FIN 과 RST

TCP 연결을 끝내는 방법은 둘이다.

FIN (정상 종료)RST (강제 종료)
뜻"나는 더 보낼 것이 없다". 반대 방향은 아직 열려 있다"이 연결은 없다". 양쪽 모두 끝
받는 쪽의 읽기와 있는 바이트를 다 읽은 뒤 EOF (recv 가 0) → kiotty 의 PEER_CLOSED오류 (ECONNRESET / WSAECONNRESET) → kiotty 의 SOCKET_ERROR
받는 쪽의 쓰기보낼 수는 있다 (상대가 이미 닫았으면 상대가 RST 로 답한다)오류 (EPIPE / ECONNRESET)
읽지 않은 바이트가 있는 채로 닫으면 RST 가 나간다앱이 close 를 부를 때 자기 커널 수신 버퍼에 아직 읽지 않은 바이트가 있으면, 운영체제는 FIN 대신 RST 를 보낸다 (RFC 1122 4.2.2.13, RFC 2525 2.17). "상대가 보낸 것을 아무도 읽지 않았다" 를 상대에게 알리는 것이다. 위 장면의 서버가 바로 이 경우다: 클라이언트가 보낸 body 가 서버의 수신 버퍼에 남아 있는 채로 닫는다. 서버가 413 뒤에 shutdown(SHUT_WR) 로 FIN 을 먼저 보냈더라도, 그 뒤 소켓을 닫는 순간 남은 body 때문에 RST 가 나간다. 이미 닫힌 소켓으로 클라이언트의 body 가 더 도착해도 서버 운영체제는 RST 로 답한다.

우리 HttpServer 도 같다. 연결을 닫을 때 IoLoop::submit 의 CLOSE 가 shutdownWrite (FIN) 를 한 뒤 소켓을 놓는다. 남은 body 를 끝까지 읽어 주는 "lingering close" (8절) 는 하지 않는다.

4. 시간 순서로 보기

#클라이언트 앱 / kiotty클라이언트 커널 수신 버퍼 (A)수신 Stage (B)서버
1begin: 머리를 보냄비어 있음비어 있음
2write 1 번째 64 KiB 보냄머리를 읽음. 4 MiB > 256 KiB
3write 2 번째 ..."HTTP/1.1 413 ..." 도착비어 있음 (읽지 않으므로)413 을 보냄, FIN
4write 3 번째 ...413 + FIN비어 있음소켓을 닫음. 읽지 않은 body 가 있어 RST
5RST 도착 → 운영체제가 처리 (5절)비어 있음
6write n 번째: SOCKET_ERROR (또는 PEER_CLOSED)Linux: 413 이 남아 있음 / Windows: 버려짐비어 있음
7finish: 응답 머리를 읽음 (receiveReply → recv)Linux: 413 을 내줌 / Windows: WSAECONNRESETLinux: 413 이 들어옴
8Linux: { SUCCESS, 413 } / Windows: { SOCKET_ERROR }

3 과 5 사이는 루프백에서 수 마이크로초, 실제 네트워크에서도 왕복 한 번 안쪽이다. 그 사이에 kiotty 가 (A) 를 (B) 로 옮기지 않으면 5 에서 운영체제의 규칙이 결과를 정한다.

5. Linux 와 Windows 의 차이

LinuxRST 를 받으면 소켓에 오류 (ECONNRESET) 를 표시하고 연결을 닫힌 상태로 둔다. 그러나 이미 수신 큐에 들어와 있던 바이트는 지우지 않는다. recv 는 큐에 바이트가 있으면 먼저 그것을 돌려주고, 큐가 비었을 때 오류를 돌려준다. 그래서 7 의 finish 가 413 을 읽는다.
Windows (Winsock)RST 를 받으면 연결을 끊고 아직 앱이 읽지 않은 수신 바이트를 버린다. 다음 recv 는 바로 WSAECONNRESET 이다. 그래서 7 의 finish 는 아무것도 읽지 못하고 SOCKET_ERROR 를 돌려준다.

이것은 kiotty 가 고를 수 있는 동작이 아니라 운영체제 TCP 구현의 차이다. 우리가 확인한 것은 다음과 같다 (2026-11-18).

테스트WSL Ubuntu (gcc / clang, TLS 켬 / 끔, asan, tsan, release)Windows MSVC
FinishShowsTheReplyOfAServerThatRefusedTheBodyEarly (우리 HttpServer, 256 KiB 상한에 4 MiB)통과: finish 가 413실패: finish 가 SOCKET_ERROR (code 2)
FinishAfterAWriteThePeerCutOffShowsTheReplyItSentFirst (raw peer 가 401 을 보내고 FIN 뒤 닫음)통과: finish 가 401 과 body nope실패: finish 가 SOCKET_ERROR

macOS / iOS (BSD 계열), Android (Linux 커널) 은 따로 확인하지 않았다. Android 는 Linux 와 같을 것으로 보지만 확인 전에는 기대지 않는다.

6. 지금 kiotty 가 하는 일 (U2 구현)

write(piece)
  sendPiece → writeAll → ConnectionStream::write          (보내기만, recv 없음)
  실패 code 가 PEER_CLOSED / SOCKET_ERROR 면
      stopUpload: 연결을 닫지 않고 upload.mode = REFUSED   (수신 Stage 와 소켓을 남김)
  그 밖의 실패 (TIMEOUT, CLOSED) 면 연결을 닫고 IDLE

finish()
  mode 가 REFUSED 면 끝 표시를 보내지 않고 refusedReply:
      receiveReply → readLine → ConnectionStream::peek → recv   (여기서 처음으로 (A) 를 읽는다)
      성공하면 응답을 돌려주고 persistence = CLOSE (body 뒤에 닫음)

U2 는 "연결이 끊겨도 (B) 와 소켓을 지우지 않는다" 까지 했다. U1 에서는 write 실패 때 바로 disconnect 해서 (B) 와 소켓을 모두 지웠으므로 Linux 에서도 응답을 볼 수 없었다. 남은 문제는 (A) 에 있는 동안 RST 가 오는 경우다. 그때 Windows 의 운영체제가 (A) 를 지운다.

7. 왜 문제인가

  • 이유를 잃는다. 앱은 413 (너무 큼), 401 (토큰 만료), 403 (권한 없음), 507 (저장소 가득) 을 네트워크 장애 (SOCKET_ERROR) 와 구별하지 못한다.
  • 헛된 재시도. 네트워크 장애로 보이면 보통 앱은 같은 올리기를 다시 한다. 413 이나 401 이면 몇 번을 해도 같은 결과다. 장비에서는 그만큼 회선과 전력을 쓰고, 로그 올리기가 밀린다.
  • 플랫폼마다 결과가 다르다. 같은 앱 코드가 Linux 장비에서는 413 을 보고 Windows 의 시험 도구 / PC 앱에서는 SOCKET_ERROR 를 본다. 테스트와 현장이 갈린다.

8. 언제 일어나고 언제 숨는가

이 문제가 드러나려면 세 가지가 모두 맞아야 한다.

  1. 서버가 body 를 다 받기 전에 응답한다 (413, 401, 403, 507, 혹은 라우트가 없음 404).
  2. 서버가 남은 body 를 읽지 않고 닫는다 → RST.
  3. 클라이언트가 그 응답을 RST 가 오기 전에 자기 쪽으로 읽어 두지 않는다.
lingering close 가 문제를 숨긴다HTTP/1.1 (RFC 9112 9.6) 은 서버가 응답 뒤에 바로 닫지 말고 쓰기 쪽만 닫은 다음 (FIN) 상대가 보내는 것을 잠시 읽어 버리라고 권한다. nginx 는 이것을 기본으로 한다 (lingering_close, lingering_time 30 초, lingering_timeout 5 초). 이런 서버를 만나면 2 가 일어나지 않는다. 클라이언트의 write 는 계속 성공하고 (서버가 읽어 버리므로), finish 가 413 을 읽는다. 그러나 lingering 에도 시간 한도가 있어서 느린 회선에서 큰 파일을 올리면 한도가 지나 RST 가 나간다. 또 kiotty 의 HttpServer, 작은 임베디드 서버, 일부 proxy / gateway 는 lingering 을 하지 않는다. 클라이언트는 서버를 고를 수 없으므로 2 가 일어난다고 보아야 한다.

9. write 가 막혀 있는 동안 온 응답

4절의 장면은 write 가 짧게 끝나는 경우다. 큰 조각을 느린 회선으로 보내면 write 는 대부분의 시간을 "송신 버퍼에 자리가 날 때까지 기다림" 에서 보낸다.

ConnectionStream::write → send → sendAll
    send() 가 WOULD_BLOCK  →  awaitWritable → waitWritable (poll POLLOUT / select write)
                                  ↑ 여기서 몇 초씩 잠들어 있다
    이 사이에 413 이 (A) 에 도착하고, 이어서 RST 가 도착한다
    poll 이 오류로 깨어남 → write 가 SOCKET_ERROR

서버는 머리를 보자마자 413 을 보내므로, 413 이 도착하는 때는 거의 언제나 클라이언트가 write 안에서 기다리고 있을 때다. 이 기다림은 "쓸 수 있게 됨" 만 보고 "읽을 것이 옴" 은 보지 않는다. 그래서 "write 를 부르기 전에 한 번 확인" 하는 방법 (10절의 길 2) 은 이 경우를 놓친다.

10. 고치는 세 길

목표는 하나다: RST 가 오기 전에 (A) 의 바이트를 (B) 로 옮긴다. (B) 에 들어온 바이트는 kiotty 의 메모리이므로 운영체제가 지울 수 없다. 그 뒤의 finish 는 지금 코드 그대로 (B) 에서 413 을 읽는다.

길 1. write 의 기다림이 읽을 것도 본다 (추천)

ConnectionStream 송신의 기다림
    지금 : poll(POLLOUT)
    바꿈 : poll(POLLOUT | POLLIN)
        POLLOUT 이면 → 지금처럼 이어서 보냄
        POLLIN  이면 → recv 로 (A) 를 수신 Stage (B) 로 옮김 (Stage 가 차면 그만 옮김)
                       그리고 다시 기다림 (보내기는 계속)
    송신이 끝내 실패하면 → write 는 SOCKET_ERROR / PEER_CLOSED,
                          그러나 413 은 이미 (B) 에 있으므로 finish 가 읽는다
  • 되는 것: 9절의 "막혀 있는 동안 온 응답" 까지 잡는다. Windows / Linux 모두. 바이트가 오는 즉시 옮기므로 RST 와의 경주에서 거의 언제나 먼저다 (같은 poll 이 둘을 함께 보고하면 recv 를 먼저 한다).
  • 고치는 자리: base 의 ConnectionStream 송신 경로 (awaitWritable, 소켓 backend 의 waitWritable 옆에 "둘 다 기다림" 하나). 이 경로는 HttpClient 뿐 아니라 StreamClient 의 writeStream 과 서버의 work stream (worker thread 가 ConnectionStream 으로 직접 보냄) 도 쓴다. 이벤트 루프가 보내는 서버의 보통 응답은 이 경로를 쓰지 않는다.
  • 값: 수신 Stage 를 넘치게 받지 않도록 Stage 의 남은 자리만큼만 옮긴다. Stage 가 차면 POLLIN 을 그만 보고 지금처럼 POLLOUT 만 기다린다 (응답 머리는 Stage 하나에 들어가므로 413 의 머리는 잡힌다).
  • 조심할 것: 보내는 중에 들어온 바이트가 "응답" 인지 아닌지는 base 가 판단하지 않는다. 옮기기만 하고, 읽는 것은 지금처럼 http 의 finish 가 한다. 올리기가 아닌 보통 송신에서도 와 있는 바이트를 조금 일찍 Stage 로 옮길 뿐이라 뜻이 바뀌지 않는다.
  • 크기: base 의 소켓 backend (POSIX 의 waitFor, Windows 의 waitReady 에 "읽기 또는 쓰기" 방향 하나) 와 ConnectionStream, 그리고 테스트. 별도의 작은 사이클로 하는 것이 맞다.

길 2. write 를 부를 때마다 한 번 확인

HttpClientExchange::write
    조각을 보내기 전에: 소켓에 읽을 것이 있는지 기다림 없이 한 번 본다
        있으면 → (B) 로 옮기고, upload.mode = REFUSED, write 는 오류를 돌려줌 (어떤 code 인지 새로 정해야 함)
        없으면 → 지금처럼 보냄
  • 되는 것: write 와 write 사이에 도착한 응답. http 쪽만 바뀐다.
  • 안 되는 것: 9절의 경우 (write 안에서 기다리는 동안 응답과 RST 가 함께 옴). Windows 에서 가장 흔한 경우를 놓친다.
  • 값: write 마다 시스템 호출 하나. kiotty 의 peek 는 0 ms 를 "끝없이" 로 보므로 (Deadline(0)) 기다림 없는 확인은 새 함수가 필요하다. 그리고 "서버가 아직 열려 있는데 응답을 먼저 보냈다" 를 write 가 어떤 code 로 알릴지 정해야 한다 (설계 4절의 표에 없는 경우).

11. TLS 에서는

  • (A) 에 오는 것은 암호문 레코드다. 길 1 은 그것을 TLS 의 수신 Stage (TlsEngine::stages().receive) 로 옮기면 된다. 풀기 (decode) 는 지금처럼 finish 의 읽기가 한다.
  • 지금 코드에는 TLS 만의 걸림이 하나 더 있다. 송신이 깨지면 보내지 못한 암호문이 송신 Stage 에 남을 수 있고, ConnectionStream 의 읽기는 시작할 때 송신 Stage 를 먼저 비우려 한다 (flush). 연결이 이미 끊겼으므로 그 flush 가 실패하고, finish 는 Linux 에서도 응답 대신 연결 잃음 code 를 돌려줄 수 있다. 길 1 을 하면 REFUSED 뒤의 읽기는 보내지 못한 것을 버리고 읽도록 함께 고친다. 길 2 / 3 에서도 이것은 따로 남는다 (U2 progress 의 "설계와 다른 것" 3).
  • TLS 1.3 의 NewSessionTicket 처럼 응답이 아닌 레코드도 (A) 에 온다. 길 1 은 옮기기만 하므로 상관없다. 풀어 보면 평문이 없을 뿐이다.

13. 정해야 할 것

질문Windows (와 확인하지 않은 BSD 계열) 에서 "서버가 먼저 보낸 응답" 을 지킬 것인가.
  • 지킨다 → 길 1. U2 는 지금 상태 (Linux 에서 됨) 로 끝내고, 길 1 을 별도 사이클 (예: U2b) 로 base 송신 경로에 넣는다. 그 사이클이 끝나기 전에는 두 테스트를 Windows 에서 길 3 처럼 받아들이게 해 두어야 U2 를 commit 할 수 있다.
  • 일부만 → 길 2. 9절의 경우를 놓친다는 것을 받아들일 때. 새 write code 의 뜻을 정해야 한다.
  • 지키지 않는다 → 길 3. 대상 장비가 Linux / Android 뿐이고 Windows 는 개발용일 때.

추천은 길 1 이다. 413 / 401 은 올리기에서 가장 흔한 거절이고, 그것은 9절처럼 write 가 막혀 있을 때 오기 때문이다. 길 2 는 고치는 양에 비해 가장 흔한 경우를 놓친다.

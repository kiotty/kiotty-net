IoLoop 을 만들기 전에 정할 세 가지 : 배경 설명

2026-11-07. 5b 를 마치며 "6 (io_loop) 에서 정할 것" 으로 적은 세 질문이 무슨 뜻인지 풀어 쓴 노트다. 앞부분 (1 ~ 2절) 은 세 질문 모두에 필요한 배경이고, 3 ~ 5절이 질문 하나씩이다. 각 질문 끝에 고를 수 있는 길과 추천을 적었다.

1. IoLoop 이 무엇을 하나

Server 하나는 연결 (Connection) 을 최대 128 개 담는 풀을 가진다. 풀은 칸 (slot) 128 개짜리 고정 배열이다. 연결이 들어오면 빈 칸 하나를 켜고 (acquire), 연결이 끝나면 그 칸을 끈다 (release). 칸은 다시 쓰인다. 실행 중에 메모리를 새로 잡지 않기 위해서다 (수칙 1.1, 1.3).

IoLoop 은 IO thread 하나가 도는 무한 반복이다. 한 바퀴는 다섯 걸음이다 (설계 v5 10절):

걸음하는 일비유
drain연결마다 "보낼 것이 쌓여 있으면 OS 에 보내기를 건다"우체통을 비운다
settle끝난 연결의 칸을 풀에 돌려주고, 새 연결을 받는 요청 (accept) 을 다시 건다, 멈출지 본다퇴실한 방을 청소하고 "빈 방 있음" 간판을 건다
collectIoEventsOS 가 "끝났다" 고 알려 준 것 (완료) 이 올 때까지 잔다초인종이 울릴 때까지 기다린다
step완료 하나마다 해당 연결의 사용자 콜백을 부르고, 다음에 할 일 (읽기 등) 을 OS 에 건다온 손님을 응대한다
stepLocalEventstimeout 이 지난 연결, Work 를 시작 / 끝낼 연결을 찾아 처리한다예약 시간이 지난 방을 확인한다

세 질문은 모두 settle 걸음에서 나온다. IoLoop 을 아직 만들지 않았으므로, 지금 코드의 부품 (Connection, ConnectionHost, Acceptor) 이 settle 에 필요한 정보를 다 내주는지가 문제다.

2. 꼭 알아야 할 낱말 넷

2.1 "걸려 있는 요청" (pending)

Windows IOCP 와 Linux epoll 은 "읽기를 걸어 두면 나중에 완료를 알려 준다" 는 방식이다. 걸어 둔 순간부터 완료가 돌아올 때까지 그 요청은 pending 이다. Connection 은 방향마다 요청 하나를 담는 그릇 (IoEvent) 둘을 가진다: 읽기용 _read_event, 쓰기용 _write_event. 각 그릇에 pending 이라는 bool 이 있다.

중요한 성질. pending 인 동안 OS (특히 Windows) 는 그 Connection 안의 버퍼 주소를 들고 있다. 그 사이에 칸을 풀에 돌려주고 다른 연결이 그 칸을 쓰면, 늦게 도착한 OS 의 데이터가 새 연결의 버퍼를 덮어쓴다. 그래서 요청이 걸려 있는 칸은 돌려주면 안 된다.

2.2 Phase (연결의 일생)

IDLE ──accept──▶ HANDSHAKING ──TLS 끝──▶ READY ──닫기──▶ CLOSING ──settle 이 돌려줌──▶ IDLE

닫기를 결정하면 바로 IDLE 로 가지 않고 CLOSING 에 머문다. OS 에 걸어 둔 요청을 취소하면 "취소됨 (CANCELLED)" 완료가 나중에 돌아오기 때문이다. 그 완료를 다 받은 뒤에야 칸을 돌려줄 수 있다 (2.1).

2.3 Work

사용자가 thenWork() 를 돌려주면 그 연결은 잠시 다른 thread (worker) 의 것이 된다. worker 가 closeConnectionStream 을 부를 때까지 IO thread 는 그 연결의 socket 을 만지지 않는다. 이 동안 연결이 닫혀도 worker 가 아직 socket 을 쓰고 있을 수 있으므로 역시 칸을 돌려주면 안 된다.

2.4 public 메서드 7 개 한계

개발 수칙 4.1 은 클래스의 public 메서드를 7 개 이하로 정한다. 리팩터링 6단계에서 Connection 을 이 한계에 맞추느라 메서드를 덜어 냈다. 그리고 수칙 4.16 ("부르는 곳이 없는 메서드를 만들지 않는다") 때문에, 당시 테스트만 부르던 메서드도 지웠다. 그때 지운 것 가운데 IoLoop 이 나중에 부를 것이 있었다. 질문 1 과 2 는 이것 때문에 생겼다.

3. 질문 1 : settle 이 "이 칸을 돌려줘도 되나" 를 어디에 묻나

원래 질문: "settle 이 묻는 '반납해도 되나' 의 자리"

3.1 settle 이 알아야 하는 것

2절에서 본 대로, 칸을 돌려줘도 되는 조건은 넷이 모두 참일 때다.

phase 가 CLOSING           (닫기로 정했고)
그리고 읽기 요청이 pending 아님   (OS 가 읽기 버퍼를 들고 있지 않고)
그리고 쓰기 요청이 pending 아님   (OS 가 쓰기 버퍼를 들고 있지 않고)
그리고 Work 중이 아님            (worker 가 socket 을 쓰고 있지 않다)

3.2 v4 에서는 어떻게 물었나

if (c.phase() != Phase::CLOSING) continue;
if (c.readEvent().pending() || c.writeEvent().pending() || c.working()) continue;
host.release(c);

Connection 에 phase(), readEvent(), writeEvent(), working() 이 있었다.

3.3 지금은 왜 못 묻나

v4 의 것지금
phase()state().phase 로 읽을 수 있다 ✔
working()flows().work.isWorking() 로 읽을 수 있다 ✔
readEvent(), writeEvent()지웠다. Connection 의 public 이 7 개로 꽉 차 있고, 당시 부르는 곳이 테스트뿐이었다 ✘

즉 "요청이 걸려 있나" 를 IoLoop 이 물을 길이 지금 없다. 이 정보는 Connection 안에 있으니 어딘가에 묻는 함수 하나가 필요하다. 그 함수를 어느 클래스에 둘지가 질문이다.

3.4 고를 수 있는 길

길모양좋은 점걸리는 점
A. Connection 에 8 번째 메서드c.isReleasable()가장 읽기 쉽다. 수명 판단이 수명 클래스에 있다public 8 개로 수칙 4.1 을 넘는다. deviations.md 에 편차를 하나 더 적어야 한다
B. ConnectionState 값에 필드 추가c.state().has_pending_io메서드 수가 늘지 않는다state() 는 다른 thread (notify, info) 도 lock 안에서 부른다. pending 은 IO thread 만 쓰는 atomic 아닌 bool 이라, 다른 thread 가 그것을 복사하면 data race 다 (TSan 이 잡는다)
C. WorkFlow 의 isWorking() 을 isSettled() 로 바꾼다c.flows().work.isSettled() = 두 요청이 비었고 Work 중이 아님WorkFlow 는 이미 두 IoEvent 를 참조로 들고 있고 (isReady() 가 같은 것을 본다), 메서드 수가 7 그대로다. isWorking() 은 지금 테스트만 부른다"Work 맥락" 클래스가 "반납 가능" 이라는 수명 판단을 하게 된다. 이름으로 그 뜻을 분명히 해야 한다
추천: C. 편차를 늘리지 않고, thread 문제도 없고, 이미 같은 재료 (두 IoEvent + Work 상태) 로 isReady() 를 계산하는 클래스에 형제 함수 하나를 두는 것이라 코드가 가장 작다. settle 은 state().phase == CLOSING && flows().work.isSettled() 가 된다.

4. 질문 2 : ConnectionHost 가 풀의 "몇 칸 찼나" 를 알려 줄지

원래 질문: "host 의 count 노출"

4.1 settle 이 알아야 하는 것

settle 은 칸의 개수에 대해서도 두 가지를 묻는다.

  1. 꽉 찼나? 꽉 찼으면 새 연결을 받는 요청 (accept) 을 걸지 않는다. 받아도 넣을 칸이 없기 때문이다.
  2. 비었나? EventClient 는 "연결이 모두 끝나면 run 을 끝낸다" (StopPolicy::WHEN_EMPTY). 비었는지 알아야 멈춘다. 종료 (shutdown) 때도 "모든 칸이 돌아올 때까지" 바퀴를 돈다.

4.2 v4 와 지금

v4 의 ConnectionHost 에는 full() 과 empty() 가 있었다. 리팩터링 6단계에서 host 가 template 이 아니게 바뀌면서, 부르는 곳이 테스트뿐이던 이 둘을 지웠다 (수칙 4.16). 테스트는 풀을 직접 보도록 바꿨다 (pool.count()).

지금 구조:

Owner (Server) 가 가진 것
 ├── ReusablePool<Connection, 128> _connections   ← 칸 수 (count / capacity) 는 여기에 있다
 ├── ConnectionHost _host(_connections)            ← IoLoop 이 받는 것. 풀을 참조로 들고 있지만 count 를 내주지 않는다
 └── NotificationDesk _desk(_connections, ...)

IoLoop 은 ConnectionHost& 를 받는데, host 에는 capacity() 만 있고 "몇 칸이 켜져 있나" 가 없다.

4.3 고를 수 있는 길

길모양좋은 점걸리는 점
A. host 에 full(), empty() 를 되살린다host.full()v4 와 같아 읽기 쉽다host 의 public 이 6 → 8 개로 한계를 넘는다
B. host 에 count() 하나host.count() == host.capacity(), host.count() == 0public 7 개로 한계 안. 풀의 이름 (count / capacity) 과 같다full / empty 의 비교식을 IoLoop 이 직접 쓴다 (두 줄)
C. LoopParts 에 풀 참조를 하나 더 넣는다parts.connections.count()host 를 고치지 않는다같은 풀로 가는 길이 둘 (host 와 직접) 이 되어, "풀은 host 를 거쳐 만진다" 는 규칙이 흐려진다
추천: B. 메서드 하나로 두 질문에 답하고 한계 안에 들어간다. 이번에는 IoLoop 이 부르므로 수칙 4.16 에도 맞다.

5. 질문 3 : Windows 에서 accept 준비가 실패하면 IoLoop 은 무엇을 하나

원래 질문: "Windows 에서 Acceptor 의 accept socket 준비가 실패해 submit 이 INVALID_ARGUMENT 를 돌려줄 때 IoLoop 이 어떻게 할지"

5.1 Windows 의 accept 는 socket 을 미리 만들어 둬야 한다

Linux 의 epoll 에서 새 연결을 받는 순서는 이렇다: "새 연결이 왔다" 는 알림을 받은 뒤 accept() 를 부르면, OS 가 그 자리에서 새 socket 을 만들어 준다.

Windows IOCP 의 AcceptEx 는 다르다. 연결이 오기 전에 빈 socket 을 하나 만들어서 "연결이 오면 이 socket 에 붙여 줘" 하고 건다. 그래서 accept 를 걸 때마다 빈 socket 을 하나씩 만들어야 한다. 5b 에서 이 일을 Acceptor::resolve 가 한다 (PassiveSocket::prepare).

Linux:    [accept 를 건다] → (연결 옴) → 알림 → accept() 가 socket 을 만든다
Windows:  socket 을 만든다 → [AcceptEx(그 socket) 를 건다] → (연결 옴) → 완료 → 그 socket 이 연결이 된다
                ↑ 여기서 실패할 수 있다 (socket 핸들이 바닥났을 때 등)

5.2 실패하면 지금 무슨 일이 일어나나

  1. 빈 socket 을 못 만들면 AcceptBuffer 에 "무효 socket" 이 들어간다.
  2. IOCP backend 의 submit 은 무효 socket 을 보면 요청을 걸지 않고 그 자리에서 INVALID_ARGUMENT 를 반환값으로 돌려준다.
  3. 그런데 v4 설계의 IoLoop::submit 은 listener 의 반환값을 보지 않는다. 다른 실패는 전부 "오류가 담긴 완료" 로 나중에 돌아오기 때문이다 (테스트 ImmediateFailureIsDeliveredAsAnErrorCompletionNotAReturnCode).

결과: accept 요청이 걸리지 않았는데 완료도 오지 않는다. settle 은 다음 바퀴에 "accept 가 pending 이 아니네" 를 보고 다시 시도하지만, 그 바퀴는 다른 연결의 완료나 timeout 이 와야 돈다. 그 사이 서버는 조용히 새 연결을 받지 않고, 사용자는 아무 오류도 듣지 못한다. 연결이 하나도 없는 서버라면 다음 바퀴가 오지 않아 영영 멈출 수도 있다.

Linux 에서는 이 문제가 없다. epoll 은 미리 만들 socket 이 없고, accept() 의 실패는 완료가 온 뒤 Acceptor::accept 의 반환값으로 IoLoop 의 access 가 받는다.

5.3 고를 수 있는 길

길모양좋은 점걸리는 점
A. 지금대로 둔다반환값을 무시, 다음 바퀴에 다시코드 0 줄5.2 의 조용한 멈춤. 의료기기 수준 라이브러리에서 오류를 삼키는 것은 받아들이기 어렵다
B. 실패를 "오류가 담긴 ACCEPT 완료" 로 바꾼다listener 가 무효 socket 도 즉시 실패 완료로 돌려준다 (다른 즉시 실패와 같은 길)IoLoop 의 길이 하나다. accept 실패는 언제나 완료로 온다. 다음 wait 가 바로 깨어난다event backend (IOCP 쪽) 를 고친다. 지금은 "인자 검사 실패는 반환값" 이라는 구분이 있어 그 규칙을 바꾸는 것이다
C. IoLoop 이 ACCEPT 의 submit 반환값만 본다실패면 사용자 onError 를 한 번 부르고, 다음 바퀴에 다시 건다backend 를 고치지 않는다"반환값을 보는 자리" 가 IoLoop 에 하나 생긴다. 다음 바퀴가 오지 않는 문제 (연결 0 개인 서버) 는 따로 짧은 wait timeout 이 필요하다
추천: B. "OS 에 무엇을 걸든, 결과는 완료로 돌아온다" 는 규칙 하나로 IoLoop 이 단순해지고 (설계 방침 2: 엣지 케이스는 프로세스가 삼킨다), 완료가 즉시 와서 wait 가 깨어나므로 "다음 바퀴가 오지 않는" 문제도 함께 없어진다. IoLoop 의 access 는 오류 완료를 받으면 사용자에게 onError 를 알리고 settle 이 다시 건다. 다만 socket 이 계속 바닥난 상태면 바퀴마다 실패가 반복되므로, onError 를 매번 부를지 (로그 폭주) 상태가 바뀔 때만 부를지는 함께 정해야 한다.

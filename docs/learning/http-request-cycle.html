HTTP 요청 하나의 일생 : kiotty-net HttpServer

2026-11-11 (같은 날 정할 것 4, 5 결정 반영). docs/design/design_http_v0.html (HTTP 설계 v0) 의 "정할 것" 4, 5 가 무슨 뜻인지 알려면 요청 하나가 들어와서 나갈 때까지의 전체 흐름이 필요하다. 1 ~ 6절이 그 흐름이고, 7절과 8절이 정할 것 4, 5 의 풀이다. 아직 코드는 없다. 설계 v0 와 구현 가이드 4절의 모양으로 적었다.

1. 등장인물

이름무엇
IO threadKiottyNet_runHttpServer 를 부른 thread 하나. 모든 소켓의 읽기 / 쓰기 완료를 받아 상태를 옮긴다. 여기서 오래 걸리는 일을 하면 다른 연결이 전부 멈춘다
worker앱이 가진 thread (thread pool 등). Work 를 넘겨받으면 그 연결 하나를 혼자 쓴다. 라이브러리는 worker 를 만들지 않는다
ConnectionTCP (또는 pipe, TLS) 연결 하나. base 층의 것. 받은 바이트를 담는 수신 Stage, 보낼 바이트를 담는 send Stage, 다른 thread 가 넣는 notify Stage 를 가진다
HttpSession연결 하나에 붙는 HTTP 의 기억. 요청 줄, 헤더, body, 응답 버퍼, 지금 상태를 든다. 연결이 끝나면 다음 연결이 다시 쓴다
라우트(method, path) 마다 앱이 등록한 { app_context, onRequest, onWorkStarted }
response / work handle{ server, id }. 요청 하나 동안만 유효한 손잡이. 요청이 끝나면 generation 이 올라가 옛 handle 은 PEER_CLOSED 만 돌려받는다

2. 연결 하나의 전체 그림

연결은 아래 상태를 돈다. 상태 이름은 구현 가이드 4.3 의 HTTP 표다. 한 연결에서 요청을 여러 개 받는 것 (keep-alive) 이 HTTP/1.1 의 기본이라 그림이 고리 모양이다.

accept (TLS 면 handshake)
   │
   ▼
[ReadingRequestLine] ── "GET /mcp HTTP/1.1"         timeout: 첫 요청은 header_timeout, 다음 요청부터는 keep_alive_timeout
   │
   ▼
[ReadingHeaderLine] ×N ── "Accept: text/event-stream" ... 빈 줄          timeout: header_timeout 이 계속 흐른다
   │
   ▼
[ReadingBody] 또는 [ReadingChunk*] ── Content-Length 만큼, 또는 chunked 를 합쳐서
   │
   ▼
라우트 찾기 → onRequest(app_context, request, response)      ← IO thread 에서 불린다
   │
   ├── (A) 그냥 return ──────────────────────────────▶ [Sending] 완성 응답 ─┐
   │                                                                            │
   └── startHttpWork 후 return ─▶ [Working] ─▶ onWorkStarted ─▶ worker         │
              (B) worker 가 응답을 채우고 finishHttpWorkWithResponse ─▶ [Sending] ┤
              (C) worker 가 chunk 를 계속 쓰다가 finishHttpWorkWithResponse ──────┤
                                                                                │
   ┌────────────────────────────────────────────────────────────────────────────┘
   ▼
keep-alive 면 [ReadingRequestLine] 으로 (다음 요청), 아니면 close
worker 는 읽지 않는다. 요청 body 는 onRequest 가 불리기 전에 라이브러리가 끝까지 읽어 request->body 에 담아 둔다. worker 는 그 요청을 보고 응답을 쓰기만 한다. Work 중에는 IO thread 도 그 연결을 읽지 않는다 (다음 요청은 응답이 끝난 뒤에 읽는다).

3. 모양 A : 완성 응답 (IO thread 에서 끝)

가장 흔한 모양이다. 정적 파일, 작은 JSON, 오류 응답 (404, 405, 406), MCP 의 202 가 여기다.

IO thread
  onRequest {
      setHttpStatus(response, KIOTTY_NET_HTTP_STATUS_OK)
      setHttpBody(response, KIOTTY_NET_HTTP_CONTENT_TYPE_JSON, data)     ← 응답 버퍼에 복사
  } return
  라이브러리: 상태줄 + 헤더 (Content-Length, Content-Type, Date, Connection) + body 를 send Stage 로
  [Sending] WRITE → WRITTEN → 남았으면 다음 조각 WRITE → ... → 다 보냄
  keep-alive 면 [ReadingRequestLine]
  • body 가 크면 (큰 파일) 응답 버퍼 크기의 조각으로 나눠 WRITE 를 여러 번 건다. 조각 하나를 상대가 받아 가야 다음 조각을 건다.
  • 여기서 상대가 읽지 않으면 WRITE 하나가 끝나지 않는다. 그 시간이 send_timeout (기본 30000 ms) 을 넘으면 base 가 연결을 끊고 사유를 KIOTTY_NET_CODE_PEER_NOT_READING 으로 남긴다. 7절이 이 사유가 앱까지 가는지의 문제다.

4. 모양 B : Work 뒤 완성 응답

답을 만드는 데 시간이 걸릴 때다 (DB 조회, DICOM 파일 읽어 base64, MCP 의 tool 실행). IO thread 를 붙잡지 않으려고 worker 에 넘긴다.

IO thread   onRequest { startHttpWork(response) } return
            [Working] ── 이 연결은 IO thread 가 손대지 않는다
            onWorkStarted(app_context, request, response, work) → 앱이 worker 에 넘기고 바로 return
worker      ... 오래 걸리는 일 ...
            setHttpStatus / setHttpBody(...)
            finishHttpWorkWithResponse(work)        ← 여기서 연결이 IO thread 로 돌아간다
IO thread   [Sending] 모양 A 와 같다 → keep-alive

5. 모양 C : Work 스트림 (SSE)

끝이 정해지지 않은 응답이다. MCP 의 POST 에 대한 SSE 응답, GET 으로 여는 긴 알림 스트림이 여기다. worker 가 동기 write 로 바로 보낸다.

IO thread   onRequest { startHttpWork(response) } return → [Working] → onWorkStarted → worker 에 넘김
worker      setHttpStatus(response, OK)
            setHttpBodyStream(response, KIOTTY_NET_HTTP_CONTENT_TYPE_EVENT_STREAM)
            writeHttpWorkChunk(work, "data: ...\n\n", 5000)   ← 첫 write 가 상태줄 + 헤더 (Transfer-Encoding: chunked) + chunk
            loop {
                이벤트를 기다린다 (15 초 동안 없으면 ": ping\n\n" 을 쓴다)
                writeHttpWorkChunk(work, 이벤트, 5000)
                PEER_CLOSED / TIMEOUT / CLOSED 가 오면 finishHttpWorkWithClose(work) 하고 끝
            }
            finishHttpWorkWithResponse(work)          ← 끝 chunk "0\r\n\r\n"
IO thread   keep-alive 면 [ReadingRequestLine]
  • write 하나가 돌아오면 그 이벤트는 이미 소켓에 넘어갔다 (반응성). 상대가 끊었는지는 다음 write 의 반환값이 바로 알려 준다.
  • worker 의 write 는 호출마다 자기 timeout 을 받는다. 상대가 읽지 않으면 TIMEOUT 이 worker 에게 돌아온다. 그래서 모양 C 의 "읽지 않는 상대" 는 앱이 안다.
  • 스트림이 이어지는 동안 worker 하나가 그 연결에 묶인다. MCP 의 GET 스트림은 클라이언트 (session) 마다 하나라서 클라이언트 수만큼 worker 가 든다 (설계 1절 결정 11).

7. 정할 것 4 풀이 : "모름" 칸을 어떻게 할까

결정 (2026-11-11). HttpServer 도 onDisconnected 와 onError 를 둔다. KiottyNetHttpServerHandler 를 runHttpServer(server, handler, app_context) 로 받는다 (설계 4.9, 결정 15). 6절 표의 "모름" 은 전부 onDisconnected 의 reason 이나 onError 로 온다. 아래는 정하기 전의 풀이다.

base 층과 StateMachine 층에는 연결 단위 콜백이 있다. 연결이 끝나면 onDisconnected(..., reason) 이 불리고, 오류는 onError(app_context, info, code, message) 로 온다. 그런데 HttpServer 의 공개 API 에는 라우트 콜백 (onRequest, onWorkStarted) 만 있다. 라이브러리 안에서는 위 표의 사유를 전부 알지만, 앱에 건네줄 구멍이 없다. 그래서 6절 표의 "모름" 은 조용히 사라진다.

왜 문제가 되나. 의료 장비에서는 "누가 언제 접속했고 왜 끊겼나" 가 감사 로그 (audit log) 와 장애 분석에 필요하다. 예: 원격 뷰어가 큰 DICOM 파일을 받다가 30 초 동안 읽지 않아 끊겼는데 장비 로그에는 아무것도 없다. TLS 인증서가 만료되어 모든 클라이언트가 handshake 에서 떨어지는데 앱은 "요청이 안 온다" 고만 본다.

고를 길:

  • (a) 서버 단위 onError 하나를 둔다. createHttpServer 나 runHttpServer 에 onError(app_context, info, code, message) 를 받는다. base 와 StateMachine 의 onError 와 같은 시그니처다. info 에 상대 주소가 있어 로그 한 줄이 된다. 정상 종료 (SUCCESS, keep-alive timeout) 는 부르지 않는다. NULL 이면 지금처럼 조용하다. 추천.
  • (b) 두지 않는다. 앱은 라우트에서 보는 것만 안다. 로그가 필요하면 base 의 Server 로 직접 HTTP 를 짜야 한다.

8. 정할 것 5 풀이 : HEAD

결정 (2026-11-11). 라이브러리가 처리한다 (설계 4.9, 결정 16). onRequest 에서 스트림 body 를 정하고 startHttpWork 를 부른 라우트는 HEAD 면 Work 를 열지 않고 헤더만 보낸 뒤 다음 요청으로 간다. body 종류를 worker 가 정하는 라우트는 Work 를 열고, 스트림이면 첫 write 가 헤더만 보내고 CLOSED 를 돌려준다. 앱이 request->method 를 보고 직접 처리해도 된다. 아래는 정하기 전의 풀이다.

8.1 HEAD 가 뭔가

HTTP 메서드의 하나다. 뜻은 "GET 을 보냈을 때 받을 헤더만 달라. body 는 빼라" 이다. 파일을 받지 않고 크기 (Content-Length), 종류 (Content-Type), 있는지 (200 / 404) 만 보고 싶을 때 쓴다.

누가 보내나: curl -I, 링크 검사기, 모니터링 (장비가 살아 있나 확인), 일부 프록시와 다운로드 관리자. 브라우저는 보통 보내지 않는다. 그래서 흔하지 않지만 장비가 네트워크에 노출되면 언젠가는 온다.

8.2 모양 A 에서는 쉽다

HEAD /index.html
  라이브러리: GET 라우트 (또는 정적 경로) 를 그대로 실행한다
  onRequest 가 setHttpBody(HTML, data) 를 한다
  라이브러리: Content-Length 는 body 길이로 적고, body 바이트는 보내지 않는다

응답이 IO thread 에서 다 정해지므로 라이브러리가 마지막에 body 만 떼면 된다. 설계 v0 의 H3 사이클이 이것이다.

8.3 모양 C 에서는 꼬인다

HEAD /mcp            (GET /mcp 는 Work 스트림 라우트)
  라이브러리가 GET 처럼 onRequest 를 부르면 → startHttpWork → worker 가 스트림을 연다
  worker 는 이벤트를 계속 쓴다 (끝이 없다)
  그런데 HEAD 라 body 를 보내면 안 된다 → 라이브러리가 chunk 를 전부 버려야 한다
  → worker 하나가 아무것도 보내지 않는 스트림을 끝없이 돈다

문제의 뿌리는 "헤더를 정하는 것이 worker" 라는 점이다. 모양 A 는 onRequest 가 끝나면 헤더가 정해지지만, 모양 C 는 worker 가 첫 write 를 할 때 정해진다. 라이브러리는 그 전에 헤더를 알 수 없다.

8.4 고를 길

(a) 앱이 직접 답한다 추천(b) 라이브러리가 Work 를 막는다
방법라이브러리는 HEAD 를 GET 라우트로 부르기만 한다. onRequest 가 request->method == HEAD 를 보고 status 와 헤더만 놓고 return (Work 를 시작하지 않는다)HEAD 에서 startHttpWork 가 불리면 라이브러리가 Work 를 열지 않고 200 + Transfer-Encoding: chunked + 지금까지 놓인 헤더만 보낸다
좋은 점라이브러리 규칙이 하나 (HEAD = GET 라우트, body 는 뗀다). 앱이 정확한 헤더를 고를 수 있다앱이 HEAD 를 몰라도 된다
나쁜 점스트림 라우트를 짜는 앱이 HEAD 를 잊으면 위 8.3 이 그대로 생긴다 (worker 하나가 헛돈다. 단, 상대가 끊으면 write 가 PEER_CLOSED 로 끝난다)헤더를 worker 가 정하는 라우트는 HEAD 의 헤더가 GET 과 달라진다 (Content-Type 이 빠진다). 규칙이 하나 더 는다

(a) 로 정하면 MCP 예제 (설계 6절) 의 GET 라우트에 if (request->method == KIOTTY_NET_HTTP_METHOD_HEAD) { 200 + Content-Type 만; return; } 한 줄이 들어간다.

9. MCP 클라이언트 하나의 한 바퀴

위 모양들이 실제로 어떻게 섞이는지 MCP (Streamable HTTP) 로 본다. 클라이언트는 연결을 둘 이상 연다 (GET 스트림 하나, 요청 하나 이상).

#클라이언트가 보냄서버의 모양응답
1POST /mcp initializeA200 JSON + Mcp-Session-Id 헤더
2POST /mcp notifications/initializedA202, body 없음
3GET /mcp (연결 ②)CSSE 스트림이 열린 채로 남는다. 서버가 보낼 알림 (tools/list_changed 등) 을 앱이 이 session 의 큐에 넣으면 worker 가 쓴다. 15 초마다 : ping
4POST /mcp tools/call (짧은 일)B200 JSON
5POST /mcp tools/call (긴 일, 진행률 보고)CSSE: progress 알림 몇 개 뒤 결과 하나, 끝 chunk. keep-alive 로 연결 ① 이 다음 요청을 받는다
6연결 ② 가 끊김 (네트워크)C 의 worker다음 write 가 PEER_CLOSED → worker 가 finishHttpWorkWithClose. 클라이언트는 Last-Event-ID 와 같은 session id 로 GET 을 다시 연다. 놓친 이벤트를 다시 보내는 일은 앱이다
7DELETE /mcpA204. 앱이 session 을 지운다. 그 session 의 GET worker 는 큐에서 "끝" 을 받고 finish 한다

10. 한 줄 요약

  • 요청은 라이브러리가 끝까지 읽고, 앱은 onRequest 에서 답하거나 (A) worker 에 넘긴다 (B, C). worker 는 쓰기만 한다.
  • 모양 C 의 문제는 worker 의 write 반환값이 다 알려 준다. 모양 A / B 와 연결 단계의 문제는 서버 handler 의 onDisconnected / onError 로 온다 (결정 15).
  • HEAD 는 모양 A 에서는 라이브러리가 body 만 떼면 끝이다. 모양 C 는 스트림의 헤더를 onRequest 에서 정해 두면 라이브러리가 Work 없이 헤더만 보낸다 (결정 16).

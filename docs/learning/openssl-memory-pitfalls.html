OpenSSL 메모리를 고정 arena 에 가둘 때의 함정

R8 (TlsMemory) 에서 실제로 부딪힌 것과 그 진단 방법

작성일 2026-11-05 · OpenSSL 3.6.1 (정적 링크, KIOTTY_NET_USES_TLS_STATIC_LIBRARY) · 관련 문서: docs/design/design_base_v5.html 19절 (v4 의 19.5 ~ 19.7), docs/progress/261105_progress_base_r8.md · 코드: src/implementation/base/tls/kiotty_tls_memory.*, backend/kiotty_openssl_tls.cpp

이 방식은 버렸다 (2026-11-05)아래의 TlsMemory (hook, 전역 arena, Owner 서브풀, 예열, Scope 의 attach / detach) 는 R8 에서 만들고 보정까지 한 뒤 뺐다. OpenSSL 의 lazy 할당을 수명이 맞는 arena 로 보내는 규칙이 OpenSSL 내부 동작 (파일 이름, ERR 칸의 표시, provider 키 캐시) 에 기대며 계속 늘었기 때문이다. 지금 kiotty 는 OpenSSL 의 기본 malloc 을 쓴다 (설계 v4 19.5). 이 노트는 다시 hook 을 검토할 때 같은 함정을 다시 밟지 않도록 남긴다.

0. 한 줄 요약

핵심OpenSSL 은 메모리를 그 메모리가 쓰일 객체가 생길 때가 아니라, 처음 필요해진 순간에 잡는다. 할당을 "그 순간 이 thread 의 current arena" 로 보내는 설계에서는, 처음 필요해진 순간이 다른 수명의 arena 의 Scope 안이면 수명이 어긋난다. 어긋나면 crash 가 아니라 나중에, 다른 곳에서 지워진 메모리를 읽거나 쓴다.

kiotty 의 TLS 메모리는 두 층이다. process 에 하나인 전역 arena (.bss 의 GlobalPool) 와 Owner 마다 하나인 서브풀 (MemberPool) 이다. TlsMemory::Scope 가 "지금 이 thread 의 할당은 이 Owner 로" 를 정하고, 해제는 주소로 arena 를 찾는다. 아래 함정은 전부 "할당한 순간의 arena" 와 "그 메모리를 쥐고 있는 객체의 수명" 이 다른 경우다.

3. 함정 1: error queue 의 data 버퍼

증상: 한 Owner 의 Scope 안에서 profile 과 연결을 열고 전부 닫았는데, 그 서브풀에 블록이 남았다. 할당 자리를 찍어 보니 이것이었다.

TRACE ..\..\external\openssl\crypto\err\err.c:846 81        x5
TRACE ..\..\external\openssl\crypto\err\err_blocks.c:84 1024 x1

thread 의 ERR_STATE 에는 오류 칸이 16 개 있고, 칸마다 data 문자열 버퍼가 있다. OpenSSL 은 이 버퍼를 오류가 날 때 처음 잡고, 그 뒤로는 지우지 않고 재사용한다.

  • ERR_vset_error (err_blocks.c): 칸의 버퍼를 OPENSSL_realloc(buf, 1024) 으로 키워 쓰고 길이만큼 줄인다. 버퍼가 없으면 realloc(nullptr) = 새 할당이다.
  • ERR_add_error_vdata (err.c): 칸의 표시가 MALLOCED | STRING 둘 다일 때만 재사용하고, 아니면 81 B 를 새로 잡는다.
  • ERR_clear_error 는 버퍼를 놓지 않는다. 칸을 비우고 표시를 MALLOCED 로만 남긴다. 버퍼를 놓는 것은 OPENSSL_thread_stop 뿐이다.
왜 위험한가이 버퍼가 Owner A 의 Scope 안에서 처음 잡히면 A 의 서브풀에 있다. 그런데 그것을 쥔 것은 thread 다. A 가 지워진 뒤 그 thread 에서 오류가 나면 OpenSSL 은 지워진 A 의 메모리에 문자열을 쓴다. 메모리 오염이고, crash 는 엉뚱한 곳에서 난다.
미리 채우기로는 안 된다attach 때 16 칸을 전부 전역 버퍼로 채워도, 평범한 ERR_raise (data 없음) 가 한 번 지나가면 그 칸의 표시가 MALLOCED 만 남는다. 그 칸에 다음 ERR_add_error_data 가 오면 81 B 를 current 에서 새로 잡는다.
해법hook 이 받는 file 이 crypto/err/ 이면 current 가 아니라 thread().state (그 thread 상태가 있는 arena) 에서 준다. 파일 이름에 기대는 방법이지만, OpenSSL 은 kiotty 가 혼자 쓰는 고정 사본이고 회귀는 격리 테스트가 잡는다 (8절).

4. 함정 2: 인증서 객체 안의 키 사본

증상: 서브풀 바닥 테스트가 끝날 때 0xc0000005. cdb 로 본 스택:

kiotty::net::TlsProfile::~TlsProfile
  SSL_CTX_free
    X509_STORE_free → X509_OBJECT_free → X509_free
      ASN1_item_free → ... → EVP_PKEY_free
        evp_pkey_export_to_provider → evp_keymgmt_freedata   ← 지워진 메모리

테스트가 profile 은 전역에서 열고, handshake 는 작은 Owner 의 Scope 안에서 돌렸다. handshake 중에 OpenSSL 이 CA 인증서의 공개키를 처음으로 provider 쪽으로 내보내면서 그 사본을 X509 객체 안에 캐시했다. 그 할당은 그때의 current, 즉 작은 Owner 로 갔다. 작은 Owner 가 profile 보다 먼저 지워졌고, profile 의 SSL_CTX_free 가 그 사본을 놓으려다 죽었다.

규칙profile 은 Owner 를 넘어 나누지 않는다. 설계 19.3 의 흐름이 원래 그렇다: Owner 의 initialize 가 자기 Scope 안에서 _profile 을 열고, run 의 같은 Owner Scope 안에서 연결이 그것을 참조로 쓰고, reset 이 같은 Scope 안에서 닫는다. 이 사고는 테스트가 그 흐름을 어긴 데서 났다.

5. 함정 3: 아직 만들어지지 않은 멤버를 base 로 묶기

처음 (UB) 
template <class Layout>
class OwnerTlsMemory : public TlsMemory
{
public:
    OwnerTlsMemory()
        : TlsMemory(_pool)   // ① base 가 먼저
        , _pool() {}         // ② 멤버는 나중
private:
    MemberPool<Layout> _pool;
};
① 에서 MemberPool& 를 PoolBase& 로 바꾼다. 생성이 시작되지 않은 객체를 base 로 변환하면 묶기만 해도 UB 다 ([class.cdtor]/3).
바꾼 것 (base-from-member) 
template <class Layout>
struct OwnerTlsPool { MemberPool<Layout> pool; };

template <class Layout>
class OwnerTlsMemory
    : private OwnerTlsPool<Layout>   // ① 먼저
    , public TlsMemory               // ② 다 만들어진 pool 을 받는다
{
public:
    OwnerTlsMemory()
        : OwnerTlsPool<Layout>()
        , TlsMemory(this->pool, this->pool.arena(),
                    MemberPool<Layout>::ARENA_BYTES) {}
};
base 는 선언 순서대로 만들어진다. 그래서 TlsMemory 생성자 안에서 바로 등록표에 발행해도 된다.

6. 함정 4: thread 개수를 셀 수 없다

처음에는 thread 상태를 전역 arena 에 두고 크기를 global + thread × OWNERS 로 잡았다. 그러나 StreamClient 를 부르는 사용자 thread 는 라이브러리가 셀 수 없다. Windows 정적 링크에서는 끝난 thread 의 상태가 놓이지도 않는다.

검토한 안문제
전역 arena 에 thread 몫 × 상수상수가 가정이다. 넘으면 전역 arena 가 바닥나고 모든 Owner 가 영향을 받는다
thread_local 마다 작은 GlobalPoolstatic TLS 는 OpenSSL 을 쓰지 않는 thread 까지 모두가 크기를 낸다. 다른 thread 에서 오는 free 가 어느 arena 인지 찾으려면 개수를 모르는 표가 또 필요하다
넘치면 시스템 malloc"실행 중 heap 할당 없음" 원칙이 깨진다
attach 한 Owner 가 thread 상태를 갖고, 그 Scope 가 끝날 때 detach채택. 아래
Scope(owner) 생성:  이 thread 가 attach 되어 있지 않으면
                       state = current = owner 의 서브풀, attachTlsThread()  (ERR 상태, thread DRBG)
                       attacher = this
                    current = owner 의 서브풀
allocate(file):     crypto/err/ 면 state, 아니면 current
~Scope():           attacher == this 면 OPENSSL_thread_stop, state = 전역
                    current = 이전 것
  • Scope 는 Owner 의 함수 안에서만 산다. 그래서 thread 상태가 Owner 보다 오래 남지 않는다.
  • 안쪽 Scope (IO Thread 의 콜백 안에서 부른 StreamClient) 는 attach 도 detach 도 하지 않는다. 그 사이의 ERR 버퍼는 바깥 Owner 로 간다.
  • Owner Layout 마다 thread 하나 몫 (약 31 KB) 을 더하고, 전역 arena 에서는 thread 몫을 뺐다.
  • 값: StreamClient 호출마다 attach + detach 한 번. Linux clang Release 9.4 µs, MSVC Debug 38 µs. thread DRBG 는 process 안의 primary DRBG 에서 seed 를 받으므로 OS 를 부르지 않는다.

7. 진단 방법

할당 자리 추적

hook 이 file / line 을 받으므로, 임시로 "current 가 전역이 아닐 때의 할당" 을 (주소, file, line, 크기) 표에 넣고 free 에서 지운다. 테스트 끝에 그 Owner 의 주소 범위에 남은 것을 찍으면 무엇이 새는지 바로 보인다. 3절의 출력이 이것이다. 추적 코드는 확인 뒤 지웠다.

Windows 에서 접근 위반의 스택

MSYS_NO_PATHCONV=1 "/c/Program Files (x86)/Windows Kits/10/Debuggers/x64/cdb.exe" \
    -g -G -c "kn 30; q" "D:\repo\kiotty-net\build\msvc\tests\unit\kiotty_net_tls_pool_tests.exe" \
    --gtest_filter=*Exhaustion* --gtest_catch_exceptions=0

--gtest_catch_exceptions=0 이 없으면 gtest 가 SEH 를 삼켜 "SEH exception 0xc0000005" 한 줄만 남는다.

등급 계측

tests/measure/kiotty_measure_tls_memory.cpp 는 할당마다 꼬리표 (global / warm / thread / profile / connection) 를 붙여 등급별 동시 최대를 잰다. 인증서는 tests/measure/generate_certs.sh (Git Bash 에서는 MSYS_NO_PATHCONV=1. 아니면 /CN= 이 경로로 바뀐다). 출력의 Blocks::count(global, thread, profile, connection) 줄을 MSVC 와 gcc 둘 다 돌려 항목별 최대로 kiotty_memory_layout.h 에 넣는다.

8. OpenSSL 을 올릴 때의 점검표

  1. 계측 도구를 Windows 와 Linux 에서 다시 돌리고 TlsLayoutOf 를 갱신한다.
  2. kiotty_net_tls_pool_tests 를 돌린다. 특히 이 셋이 새 lazy 할당을 잡는다:
    • HandshakeInsideAScopeTakesBlocksFromThatOwnersSubpoolOnly (Scope 를 닫으면 서브풀 0)
    • ThreadStateLivesInTheOwnerWhoseScopeAttachedItAndLeavesWithThatScope (thread 상태가 그 Scope 와 같이 끝난다)
    • LateFreesAreZeroAfterEveryObjectIsClosed
  3. 실패하면 7절의 할당 자리 추적으로 file / line 을 본다. 새 thread 상태 파일이면 tlsThreadStateFile 에 더하고, 새 전역 캐시면 warmTlsMemory 가 그 경로를 지나가게 한다.
  4. ERR 의 파일 경로 (crypto/err/) 가 그대로인지 확인한다.
OpenSSL 의 내부 동작 (ERR 칸의 표시, provider 키 캐시) 은 3.6.1 에서 관찰한 것이다. 버전이 바뀌면 8절의 점검표로 다시 확인한다.
